V3 실시간 아키텍처: 상태 계산은 Flink, ClickHouse는 적재와 조회

브라우저 행동 이벤트로 세션을 만드는 분석 플랫폼입니다. late event와 재전송 이벤트를 다루는 stateful 계산을 ClickHouse에서 꺼내 Flink로 옮겼습니다. Kafka를 원본 로그로 두어, 같은 입력이면 같은 결과가 나오는 구조로 다시 설계했습니다. 운영 트래픽을 끊지 않고 새 경로로 전환했습니다.

01상황과 역할

2026년 9월 말, 사람 방문 세션 중 집계가 끝난 비율이 사흘 사이 약 60%에서 30%로 떨어졌습니다. 원본 이벤트는 남아 있었고, 세션 집계만 빠졌습니다.

세션 집계는 ClickHouse 안에서 SQL로 정의한 Refreshable Materialized View 여러 개가 줄줄이 이어진 MV chain이 맡고 있었습니다. SQL은 약 2만 줄이었습니다. queue, rate limit, 처리 기록, checkpoint를 모두 SQL로 만든 셈이었습니다. 사실상 SQL로 만든 stream processor였습니다. 그중 한 MV가 queue에서 후보를 일부만 고르고 offset을 넘겼습니다. 후보가 되지 못한 세션은 처리되지 않고 지나갔습니다.

부하 기록을 보면 CPU의 절반 이상을 수집 쪽이 썼습니다. 몇 행짜리 INSERT 하나가 Materialized View(MV) 십여 개로 퍼져, 입력보다 수백 배 많은 병합이 일어났습니다. 메모리 한도 사고도 대부분 Refreshable MV에서 났습니다. 대시보드 읽기는 CPU의 1%도 쓰지 않았습니다.

관리형 ClickHouse를 해지하고 자체 운영 클러스터로 옮기는 일정도 정해져 있었습니다. 새 클러스터로는 이 MV chain을 옮기지 않기로 했습니다. 그래서 세션 집계를 맡을 곳이 따로 필요했습니다.

설계 제약은 그보다 앞서 바꾼 세션 정의에서 왔습니다. 30분 동안 움직임이 없으면 세션을 끊던 방식을 탭 수명으로 바꿨습니다. 이어서 같은 브라우저의 탭들이 함께 쓰는 장기 세션을 두고, 유입은 따로 기록하게 했습니다. 세션이 며칠씩 열리자, 세션은 언젠가 닫히는 창이 아니라 계속 고쳐 쓰는 키가 됐습니다. 게다가 SDK는 최대 7일까지 이벤트를 다시 보냅니다.

그래서 과제는 세 가지였습니다.

  • 이벤트가 늦게 오거나 같은 이벤트가 다시 와도, 세션 집계 결과에는 한 번만 반영되어야 했습니다.
  • 장애가 나면 원본 이벤트부터 다시 읽어 결과를 다시 계산할 수 있어야 했습니다.
  • 관리형 ClickHouse 해지 일정 안에, 운영 트래픽을 끊지 않고 새 경로로 옮겨야 했습니다.
맡은 일
세션과 키, dedup 경계를 정하고, Go receiver, Flink 세션 집계 job, Go sinker, 전환 절차를 설계하고 구현했습니다. 전환 판단도 맡았습니다.

방문자 신원 계산은 별도 배치로 설계했습니다. 자세한 내용은 CDP 방문자 신원 페이지에 적었습니다.

02해결 과정

1. Kafka와 Flink를 고른 기준

브라우저가 이벤트를 다시 보내는 것, queue가 메시지를 다시 전달하는 것, Kafka에서 같은 구간을 다시 읽는 것은 모두 at-least-once 방식, 곧 적어도 한 번은 전달하는 방식입니다. 그래서 같은 이벤트가 두 번 이상 오는 일은 반드시 생깁니다. 이 전제에서 기준을 둘로 정했습니다. 첫째, 세션 집계에 들어갈 dedup은 Flink의 세션 state 한 곳에서만 합니다. 둘째, 같은 입력을 다시 돌리면 같은 결과가 나와야 합니다.

  • Kafka는 버퍼이면서, 다시 계산할 때 읽을 원본 로그입니다. 원본 topic은 30일 동안 보관하고, replication factor는 3으로 두었습니다. queue만 쓰는 안은 메시지를 한 번 읽으면 사라져 다시 계산할 수 없어서 쓰지 않았습니다.
  • Go consumer가 세션을 직접 계산하는 안도 비교했습니다. 비용은 쌌지만 keyed state와 timer, checkpoint를 직접 다시 만들어야 했습니다. 기존 MV chain이 바로 그렇게 2만 줄이 됐습니다.
  • 이벤트가 들어와 세션 집계에 반영되기까지의 목표는 약 15분이었습니다. 이 정도 속도는 Flink가 아니어도 낼 수 있었습니다. Flink를 고른 이유는 속도가 아니라, 늦게 오거나 다시 오는 데이터를 다루는 기능이었습니다.

2. 트래픽 수용 설계

평균 트래픽은 크지 않습니다. 그래서 처리량보다, 순간적으로 몰릴 때 버티는 방식과 나중에 바꾸기 어려운 값을 먼저 정했습니다.

  • 브라우저 이벤트를 처음 받는 곳은 Cloudflare Workers에서 도는 수집 Worker입니다. Kafka는 사설망 안에 있고 클라우드 IAM 인증을 거쳐야 해서 Worker가 직접 붙을 수 없습니다. 그래서 둘 사이에 Go receiver를 두었습니다.
  • receiver는 요청에 담긴 모든 레코드를 Kafka replica 모두가 기록했다고 확인한 뒤에만(acks=all) 성공 응답인 HTTP 200을 돌려줍니다. 레코드가 하나라도 기록에 실패하면 요청 전체를 실패로 돌려보냅니다.
  • receiver에는 자체 버퍼를 두지 않았습니다. 버퍼가 receiver와 Kafka 클라이언트 두 곳에 있으면, 성공이라고 답한 이벤트가 어디까지 실제로 기록됐는지 흐려지기 때문입니다.
  • Kafka 클라이언트의 버퍼가 차면 기다리지 않고 바로 실패를 돌려주는 전송 함수(TryProduce)를 썼습니다. 버퍼가 가득 찼거나 약 1.2초 안에 기록을 끝내지 못하면, receiver는 "지금은 처리할 수 없다"는 HTTP 503을 돌려줍니다. Worker는 503을 받으면 그 요청을 fallback queue로 보냅니다.
  • fallback queue에는 평소에도 전체 트래픽의 1%를 흘려 보냅니다. 장애 때만 쓰는 경로는 정작 필요할 때 고장 나 있기 쉽기 때문입니다.
  • receiver 대수는 Kubernetes HPA가 CPU 사용률 60%를 threshold로 2대에서 8대까지 늘립니다.
  • Kafka는 topic을 여러 partition으로 나눠 저장하고, 레코드에 붙은 key로 어느 partition에 넣을지 정합니다. 이 partition key는 고객사와 세션의 조합으로 정했고, partition 수는 12개로 고정했습니다. 이렇게 정한 이유는 아래 설계 결정 D-05에 적었습니다.

3. Flink 세션 집계와 idempotent 적재

  • Flink job은 기능별로 나누지 않고 하나로 두었고, 고객과 세션의 조합을 key로 삼아 세션마다 keyed state를 따로 듭니다. 이 state 안에 이미 받은 이벤트 ID를 7일 동안 보관합니다. SDK가 이벤트를 다시 보낼 수 있는 기간과 같습니다.
  • 같은 이벤트가 다시 오면 버립니다. ID는 같은데 내용이 다르면 한쪽을 고르지 않고 따로 빼서 알림을 보냅니다.
  • Flink가 내는 세션 결과마다 버전을 붙입니다. 재처리 회차, 반영한 이벤트 수, 결과 상태를 이 순서로 비교해 큰 쪽을 최신으로 봅니다. 결과 상태는 진행 중, 마감, 삭제 순으로 큽니다. 결과를 낸 횟수나 현재 시각은 버전에 쓰지 않습니다. 그래야 같은 입력을 다시 돌렸을 때 같은 버전이 나옵니다.
  • Flink가 장애 뒤 이어서 시작할 수 있도록, RocksDB state backend에서 바뀐 부분만 담은 incremental checkpoint를 60초마다 GCS에 남깁니다.
  • 원본 이벤트는 Flink를 거치지 않습니다. 원본 sinker가 Kafka에서 바로 읽어 원본 표에 넣습니다. 그래서 Flink가 멈춰도 원문 저장은 멈추지 않습니다.
  • Go sinker는 Kafka에서 읽은 레코드를 구간 단위로 묶어, 구간마다 다음 순서로 ClickHouse에 넣습니다.
    1. 이번에 넣을 offset 구간을 sink ledger에 적습니다. sink ledger는 어느 구간을 넣기 시작했는지 따로 남겨 두는 기록입니다.
    2. 데이터를 넣습니다.
    3. 두 replica가 모두 받았는지 확인합니다.
    4. Kafka에 offset을 확정합니다.
  • sinker가 중간에 죽으면 같은 구간을 같은 dedup token(insert_deduplication_token)을 붙여 다시 넣습니다. ClickHouse는 같은 token으로 들어온 데이터를 한 번만 받습니다. token은 topic, partition, offset 구간, 대상 테이블을 묶어 계산하므로 같은 구간이면 늘 같은 값이 나옵니다. 그래서 같은 구간을 두 번 넣어도 중복이 생기지 않습니다. 몇 번을 넣어도 한 번 넣은 것과 결과가 같은 이 성질을 idempotent하다고 합니다.
  • 두 replica가 모두 받아야 쓰기가 성공하도록 설정(insert_quorum=2)해서, replica 하나가 내려가면 쓰기가 멈춥니다. 그동안 밀린 데이터는 Kafka에 남아 있습니다. 쓰기가 멈추는 쪽이 두 replica 내용이 서로 갈라지는 쪽보다 복구가 쉽다고 판단했습니다.
  • 새 클러스터에는 MV와 Refreshable MV를 하나도 두지 않았습니다. 스키마 lint가 이런 MV를 만들려고 하면 실패하도록 해서 막았습니다.

4. 전환

전환은 수집 Worker의 설정값 하나로 했습니다. 이 값은 꺼짐, mirror, 주 경로 세 가지입니다. 꺼짐은 새 경로로 아무것도 보내지 않는 상태입니다. mirror는 기존 경로를 그대로 쓰면서 같은 이벤트의 복사본을 새 경로에도 보내는 상태이고, 이렇게 두 경로를 나란히 돌리는 것을 mirroring이라고 불렀습니다. 주 경로는 새 경로가 실제 서비스를 맡는 상태입니다. 스테이징 환경에서 먼저 mirroring을 해 보고, 운영 환경에서 mirroring한 뒤, 주 경로로 바꿨습니다. 운영 mirroring을 시작하기 전에는 스테이징에서 replica를 일부러 멈추고 sinker를 강제로 종료해 봤고, runbook대로 움직이는 훈련도 했습니다.

mirroring 동안에는 건수가 아니라, 두 경로에 들어온 이벤트 키의 목록과 partition별 offset을 맞춰 봤습니다. 건수는 일부가 빠지고 다른 일부가 더 들어가도 우연히 맞을 수 있기 때문입니다. 이 대조로 mirroring 첫날 새 경로로 가는 복사본 중 약 0.2%가 빠진 것을 찾았습니다. 자세한 내용은 트러블슈팅 T-01에 적었습니다.

해결 과정의 방향을 정한 판단 여덟 가지입니다. 고민, 선택지, 결정과 이유, 대가 순서로 적었습니다.

D-01

원본의 중복 0을 포기하고, 결과에 한 번만 반영하기

고민
브라우저 재전송, queue 재전달, Kafka 재소비는 모두 at-least-once 전달입니다. 기존 경로는 dedup을 네 겹으로 두었습니다. 그래도 30분 넘게 늦게 다시 보낸 이벤트는 모두 이 거르기를 통과해 집계 숫자를 부풀린 적이 있었습니다. 저장소가 나중에 병합하며 중복 행을 접어도, 이미 MV에 더해진 숫자는 되돌아가지 않습니다.
선택지
① 중복을 거르는 층을 더 촘촘하게 만드는 안
② Kafka의 exactly-once 기능이나 저장소의 병합에 dedup을 맡기는 안
③ 원본은 중복이 섞인 채 도착한 그대로 기록하고, 결과를 되돌릴 수 없게 되는 첫 계산 바로 앞에서 한 번만 반영하는 안
결정과 이유
③을 골랐습니다. 원본 표가 병합하며 중복을 지우는 것은 꼭 지켜야 할 조건에서 뺐습니다. 대신 세션 집계와 적재는 같은 데이터가 여러 번 들어와도 한 번 넣은 것과 결과가 같아야 한다는 조건, 곧 idempotent만 반드시 지키게 했습니다. 두 이벤트가 같은지 가리는 키는 고객, 세션, 이벤트 ID의 조합으로 정했습니다. 중복이 정상인 시스템에서는 중복을 없앨 곳보다, 되돌릴 수 없는 연산 앞에서 한 번만 반영할 곳을 정해야 한다고 봤습니다. 저장 전에 거르다 잘못 판정하면 정상 이벤트를 버립니다. 그 판단은 되돌릴 수 없습니다.
대가
원본 표의 행 수가 서로 다른 이벤트의 수보다 많습니다. 원본 표를 직접 읽는 화면은 중복된 행 가운데 최신본 하나만 골라 읽어야 집계와 같은 수가 나옵니다.
D-02

상태 계산은 Flink, ClickHouse는 적재와 조회만

고민
Refreshable MV를 고치면 누락은 막을 수 있었습니다. 하지만 저장소가 상태 계산과 작업 관리를 계속 떠안습니다. 새 클러스터로 MV chain도 옮겨야 했습니다.
선택지
① Refreshable MV의 queue를 보강해 누락만 막는 안
② Go consumer가 바뀐 세션만 골라 직접 계산하는 안
③ 배치 처리부터 먼저 만드는 안
④ 저장소 엔진을 바꾸는 안
⑤ 상태 계산을 Flink로 옮기고, 저장소에는 적재와 조회만 맡기는 안
결정과 이유
⑤를 골랐습니다. MV는 데이터의 현재 상태를 보고 계산하지 않고, 새 행이 들어오는 순간(INSERT)마다 들어온 행만 보고 계산합니다. 그래서 같은 행이 다시 들어오거나, 지난 데이터를 거슬러 고치거나 빠진 기간을 나중에 채워 넣는 backfill 데이터와는 맞지 않습니다. ②는 월 비용이 훨씬 쌌지만, keyed state, 시간이 지나면 동작하는 timer, 장애 복구용 checkpoint를 직접 다시 만들어야 했습니다. ④는 버렸습니다. 문제는 엔진보다, 원본 보관과 해석, 세션 계산, 조회가 한 체인에 섞인 데 있었습니다. 몇 분 안에 결과를 보여 주는 것은 Flink 없이도 할 수 있었습니다. 필요한 것은 7일 늦게 온 이벤트를 반영할 때도, 이미 낸 결과를 고칠 때도, 처음부터 다시 처리할 때도 모두 같은 결과를 내는 기능이었습니다. 자주 바뀌는 해석은 조회할 때 계산하게 두었습니다. 전환을 어느 유입의 몫으로 볼지 정하는 attribution, 유입을 어느 채널로 묶을지, 방문자가 누구인지가 여기에 해당합니다. 거의 바뀌지 않는 "무엇이 세션이고, late event를 어떻게 고치는가"만 Flink에 두었습니다.
대가
Kafka, Flink, sinker로 움직이는 부품이 늘었습니다. 작은 규모로 운영하는 시스템에 JVM 도구가 더해졌습니다. 범위를 넓힌 채 일정을 지켜야 해서 마지막 몇 주가 빠듯했습니다.
D-03

Kafka를 원본 로그로 두고, 두 경로는 입구에서 나누기

고민
재처리하려면 원본이 저장소와 떨어진 곳에 남아 있어야 했습니다. 기존 queue는 한 번 읽으면 사라지고 보관 기간도 14일이라 다시 읽을 수 없었습니다. 관리형 ClickHouse를 해지하면 그 안의 기존 원본도 되살릴 수 없었습니다.
선택지
① 기존 경로에서 적재에 성공한 이벤트를 새 경로로 복사하는 안
② 새 경로 전용 queue를 따로 두고 bridge로 이어 붙이는 안
③ 수집 Worker에서 이벤트를 두 경로로 나누고, 새 경로는 Kafka로 바로 보내는 안
결정과 이유
③을 골랐습니다. 원본 로그가 기준이고, 저장소의 모든 표는 로그를 다시 읽어 만들 수 있어야 합니다. 기존 경로의 성공분을 복사하면 새 경로가 기존 경로에 기대게 됩니다. 복사에서 빠진 것은 영구 누락이 됩니다. 같은 입구에서 나눠야 두 경로를 서로 독립으로 비교할 수 있습니다. 같은 이유로 fingerprint 조회처럼 바깥 서비스를 부르는 일은 Flink 밖에 두었습니다. Flink는 Kafka에 있는 것만 replay해 같은 결과를 내는 계층이어야 하기 때문입니다.
대가
두 경로를 함께 돌린 기간에는 비용도 두 경로 몫을 함께 냈습니다. Kafka에는 SDK가 다시 보낸 이벤트가 중복된 채 그대로 쌓입니다.
D-04

세션은 닫히는 창이 아니라 버전을 고쳐 쓰는 키로

고민
같은 브라우저의 탭들이 함께 쓰는 장기 세션에는 "세션이 끝났다"는 신호가 없습니다. 그래서 한 세션의 결과를 여러 번 고쳐 내야 합니다. 다시 처리해도 같은 결과가 나와야, 같은 결과를 여러 번 넣어도 한 번 넣은 것과 같아집니다.
선택지
① 일정 시간 이벤트가 없으면 세션을 닫는 session window를 쓰는 안
② 기능마다 Flink job을 따로 나누는 안
③ 결과의 버전을 결과를 낸 횟수, Kafka offset, 현재 시각으로 정하는 안
④ 고객과 세션을 key로 하는 job 하나에 모으고, 버전은 입력만으로 정해지는 규칙으로 매기는 안
결정과 이유
④를 골랐습니다. 한 번 닫은 세션은 late event가 오면 다시 열어야 합니다. 버전은 재처리 회차, 반영한 이벤트 수, 상태 순위를 앞에서부터 차례로 비교합니다. 반영한 이벤트 수는 줄어들지 않으므로, 새 이벤트를 반영한 결과가 옛 버전에 가려 조용히 사라지지 않습니다. 같은 입력이면 같은 버전이 나옵니다. 그래서 exactly-once 반영을 Flink checkpoint 기능에 기대지 않고, 결과가 입력만으로 정해지는 성질로 얻었습니다. 같은 이벤트가 두 번 처리되어도 같은 버전이 나오므로, checkpoint는 at-least-once 모드로 충분합니다. state를 들고 있는 기간도 둘로 나눴습니다. 받은 이벤트 ID를 기억하는 기간은 SDK가 다시 보낼 수 있는 7일에 맞췄고, 집계 state는 결과가 확정될 때까지 두었습니다.
대가
한 세션에 버전이 다른 행이 여러 개 쌓이므로, 읽는 쪽이 세션마다 가장 큰 버전 하나만 골라야 합니다. 트래픽이 끊긴 환경에서는 다음 이벤트가 올 때까지 Flink가 결과를 내보내지 않습니다.
D-05

수신, Kafka key, 적재를 한 계약으로 맞추기

고민
receiver가 성공(200)이라고 답한 이벤트를 잃어버리는 일이 없어야 했습니다. 한 세션 안의 이벤트 순서를 지키면서도, 트래픽이 한 고객사에 몰릴 때 한 partition에만 쏠리지 않아야 했습니다. Flink가 결과를 냈다고 해서 저장소에 한 번만 들어간다는 보장이 생기지는 않아서, 이것도 따로 풀어야 했습니다.
선택지
① receiver에 자체 버퍼를 두고, 고객사만 키로 쓰고, partition은 적게 시작해 나중에 늘리는 안
② Flink가 공식 connector로 ClickHouse에 직접 넣는 안
③ receiver에는 버퍼를 두지 않고, 고객사와 세션의 조합을 키로 쓰고, partition을 처음부터 12개로 고정하는 안. 적재는 Go sinker 하나가 맡아 sink ledger, dedup token, 두 replica 쓰기로 한 번만 넣습니다.
결정과 이유
③을 골랐습니다. SDK는 200을 받으면 그 이벤트를 다시 보내지 않습니다. 그래서 200 응답은 곧 "더 보내지 않아도 된다"는 약속이고, 이 응답은 Kafka replica 모두가 기록을 확인했을 때(acks=all)만 주게 했습니다. partition key를 Flink가 쓰는 key와 같게 두어, 한 세션의 이벤트는 늘 같은 partition에 들어가 순서가 지켜집니다. partition 수를 나중에 바꾸면 같은 세션이 다른 partition으로 가게 됩니다. 그래서 지금 트래픽의 100배가 들어와도 partition마다 감당할 수 있다고 계산한 12개로 처음부터 고정했습니다. Go 코드와 Java 코드가 같은 키를 같은 partition으로 보내는지는, 정해 둔 입력을 양쪽에 똑같이 넣어 결과를 비교하는 시험으로 묶어 두었습니다. 공식 connector는 at-least-once만 보장하고, retry를 다 하고도 실패하면 레코드를 버리기 때문에 쓰지 않았습니다. sink ledger와 Kafka offset을 서로 다른 시스템에 기록해 두면, 둘을 맞춰 보는 것만으로 "건수는 맞는데 일부가 빠진" 누락도 잡을 수 있습니다.
대가
12개는 load test로 확인한 값이 아니라 계산으로 정한 값이라, 설정에 "잠정"이라고 적어 두었습니다. replica 한 대가 빠지면 쓰기가 멈춥니다. 의도한 동작이고, 그동안 밀린 데이터는 Kafka가 30일 동안 들고 있습니다. Go와 Java 두 언어의 코드가 같은 출력 규칙을 지켜야 해서, 양쪽 결과를 맞대 보는 교차 시험이 계속 필요합니다.
D-06

늦게 와서 바뀌는 세션 시작도 Flink가 확정하기

고민
처음에는 Flink가 세션과 유입의 시작 이벤트를 후보로만 쌓아 두었습니다. 그리고 화면에서 조회할 때마다 그 고객의 과거 후보 전체에서 시작을 다시 골랐습니다. 세션이 며칠씩 이어지다 보니 7일치만 조회해도 이력 전체를 정렬해야 했고, 90일치를 조회하면 메모리 한도를 넘었습니다. 세션 ID로 정렬해도 시간 순서가 되지 않았습니다. 세션 ID는 앞부분에 만든 시각이 들어가는 UUIDv7인데, ClickHouse는 UUID를 비교할 때 뒤쪽 64비트를 먼저 보기 때문에 시간순으로 놓이지 않습니다.
선택지
① 마감된 날의 세션 시작은 더 바뀌지 않는다고 규칙을 정하고, 조회 기간을 나눠 처리하는 안
② 조회 기간 앞뒤에 여유를 두고 그 범위만 잘라 읽는 안
③ Flink가 후보를 state로 들고 있다가 시작을 확정하고, 저장소에는 세션마다 현재 값 한 줄만 두는 안
결정과 이유
처음에는 ①을 검토했습니다. 그런데 "늦게 와서 과거 결과를 바꾸는 이벤트도 Flink에서 다 받을 수 있지 않나"를 다시 물어 보니, ①은 조회할 때 시작을 고르는 구조를 그대로 둔 채 덧댄 땜질이었습니다. 그래서 ③으로 바꿨습니다. late event로 결과가 바뀌는 것은 state가 할 일이고, state는 이미 Flink로 옮겼습니다. ClickHouse sort key 맨 앞에는 세션 ID(UUIDv7)에서 꺼낸 날짜를 두었습니다. 그래서 세션 ID 하나로 세션을 구별하면서 시간 순서로도 정렬할 수 있게 됐습니다. 이후로는 조회 때 이력 전체에서 현재값을 고르는 설계를 보면, 읽기 최적화보다 먼저 Flink state로 옮길 수 있는지 묻습니다.
대가
Flink state가 더 오래 남습니다. 세션 시작을 정하는 state는 60일 동안 보존합니다. 세션 ID로 바로 찾는 조회는 따로 빠르게 만들어야 합니다. 대신 화면 조회는 조회 기간 안에 있는 세션만큼만 읽게 됐습니다.
D-07

재전송 폭주는 저장 구조가 아니라 원인에서 막기

고민
운영 mirroring 중 Kafka에 쌓인 레코드 수가 서로 다른 이벤트 수의 약 4.5배였습니다. 업로드 완료를 알리는 이벤트 한 종류는 약 28배였습니다. 배포된 SDK에서 탭끼리 함께 쓰는 공유 세션을 항상 켜면서, 모든 이벤트가 바로 보내지 않고 버퍼에 넣었다가 나중에 보내는 방식으로 바뀌었습니다. 그런데 이 이벤트를 보내는 업로더는 "받아들여졌다"는 확인을 받을 때까지 60초마다 다시 보내도록 만들어져 있었습니다. "나중에 보낸다"는 약속과 "받아들여질 때까지 다시 보낸다"는 약속은 뜻이 달랐고, 둘이 만나 같은 이벤트를 끝없이 다시 내보내게 됐습니다.
선택지
① receiver에 TTL이 짧은 cache를 두어 같은 이벤트가 들어오는 횟수에 상한을 거는 안
② 브라우저와 가까운 edge에서 고객사별, 세션별로 rate limit을 거는 안
③ 원본 이벤트도 Flink를 거쳐 중복을 거른 뒤 저장하는 안
④ 원본은 모두 저장하고 입구에서 막지 않되, 배수를 재고 경보만 걸어 둔 채 원인인 SDK의 전송 약속을 고치는 안
결정과 이유
④를 골랐습니다. 기존 경로에서 저장 전에 중복을 거른 것은 결과를 정확하게 하려는 장치가 아니었습니다. INSERT 하나가 MV 여러 개로 번지며 부하가 불어나는 것과, 유료 API 비용을 막는 방패였습니다. 새 구조는 그런 비용이 생기지 않게 만들었으니 방패를 다시 들일 이유가 없었습니다. 실제로 새 저장소의 부하도 CPU 평균 약 3%로 작았습니다. 원본까지 Flink를 거치게 하면 Flink가 멈출 때 원문 저장도 함께 멈춥니다. 대신 SDK 안에 "이벤트가 실제로 전송 단계에 넘겨졌다"는 내부 알림을 따로 두고, 그 알림이 온 뒤에만 이벤트를 지우게 했습니다. 또 만든 지 7일이 지난 이벤트는 더 보내지 않게 했습니다. 서버가 받은 이벤트를 기억하는 기간이 모두 7일이라, 그보다 늦게 다시 보낸 이벤트는 처음 보는 이벤트로 들어오기 때문입니다.
대가
옛 SDK가 이미 떠 있는 브라우저 탭은 고친 SDK를 받기 전까지 계속 다시 보냅니다. 이런 옛 탭에서 온 몫을 빼고 보면, 레코드 수는 서로 다른 이벤트 수의 약 1.2배로 내려갔습니다.
D-08

전환 판정에서 기존 경로를 정답지로 쓰지 않기

고민
기존 경로는 세션 집계가 끝난 비율 자체가 30%까지 떨어져 있었습니다. 기존 경로를 정답으로 놓고 대조하면, 기존 경로에서 빠진 것을 새 경로의 오류로 세게 됩니다.
선택지
① 기존 경로의 결과를 정답으로 놓고 대조하는 안
② 건수만 비교해 보고 전환하는 안
③ 원본이 빠짐없이 들어왔는지, 대표 사례가 맞게 계산되는지, 늘 성립해야 하는 invariant가 지켜지는지로 판정하고, 원본이 새 경로에 도달하지 못한 누락만 엄격하게 보는 안
결정과 이유
③을 골랐습니다. 비교 기준이 틀리면 대조가 오히려 판단을 흐립니다. 집계는 원본만 있으면 다시 계산할 수 있습니다. 반면 새 경로에 도달하지 못한 원본은 해지 뒤 되살릴 수 없어서, 그것만 엄격하게 봤습니다. 운영 mirroring을 시작하려면 replica 장애 시험, sinker 강제 종료 시험, runbook 훈련을 먼저 통과하도록 정했습니다. 7일 동안 지켜보는 단계와 트래픽 비율을 조금씩 올리는 단계는, 관리형 클러스터 비용을 먼저 끊으려고 생략했습니다. 대신 해지 직전에 새 경로에는 없고 다시 계산할 수도 없는 원천 데이터만 골라 따로 보관하고, 원본과 대조했습니다.
대가
해지 시점에는 매일 도는 대조, 경보 채널, 운영 Flink 복구 리허설 같은 공식 안정 판정 장치 대신, 운영 중에 바로 볼 수 있는 지표로 판단했습니다. sink ledger와 Kafka offset 사이에 차이가 없었고, 재시작이 없었고, 빠진 이벤트 키도 없었습니다.

04결과

  • 운영 환경에서 24시간 동안 두 경로를 나란히 돌리며, 양쪽에 들어온 이벤트 키를 하나하나 맞춰 봤습니다. 한쪽에만 있는 이벤트는 약 0.06%였고, 고객사별로 나눠 봐도 ±0.2% 안이었습니다. Kafka 12개 partition의 offset을 대조해도 모두 맞았습니다.
  • mirroring 첫날에는 새 경로로 보내는 복사본이 약 0.2% 빠졌습니다. 수집 Worker가 복사본 전송을 거는 순서를 고친 뒤 다시 대조했을 때는 빠진 이벤트가 없었습니다. 이미 빠진 이벤트도 기존 경로의 원본에서 되살려 새 원본 표에 다시 넣었고, 대조해 보니 남은 누락은 없었습니다.
  • replica 한 대를 일부러 멈춘 시험에서는, 멈춘 동안 쓰기가 바로 거부됐고 잃어버린 데이터는 없었습니다. replica가 돌아오고 약 2분 뒤 그동안 밀린 데이터를 모두 넣었습니다.
  • 적재 도중 sinker를 강제로 종료하거나 동시에 다시 띄운 시험에서도, 두 번 들어간 데이터는 없었고 두 replica의 내용은 같았습니다.
  • 운영 환경에서 sink ledger에 적힌 구간과 Kafka에 확정된 offset을 대조했더니 12개 partition 모두 일치했습니다. 약 1주 뒤 다시 대조했을 때도 차이가 없었습니다.
  • Flink 세션 집계 job은 10월 중순까지 약 8일 동안 한 번도 재시작하지 않고 돌고 있습니다.
  • 새 클러스터에는 MV와 Refreshable MV가 하나도 없습니다. 2026년 10월 16일 새 경로를 주 경로로 전환하고 관리형 ClickHouse를 해지했습니다.

이벤트 한 건이 receiver에 들어와 원본 표에 저장되기까지 약 33초, 세션 집계 표에 반영되기까지 약 65초 걸렸습니다. 스테이징 환경에서 시험용으로 만든 이벤트로, 쉬고 있던 구성 요소가 다시 켜진 상태에서 한 번 잰 값입니다.

05트러블슈팅

T-01

실패 기록이 없는데 복사본 약 0.2%가 빠진 문제

문제
운영 mirroring을 켠 첫날, 두 경로의 이벤트 키를 맞춰 보니 기존 경로에는 있고 새 경로에는 없는 이벤트가 약 0.2% 나왔습니다. 실패 로그, fallback queue, DLQ에는 아무것도 없었습니다.
원인
크기 초과와 형식 오류를 먼저 의심했지만 둘 다 아니었습니다. 빠진 이벤트는 모두 페이지를 떠날 때 나가는 이벤트였습니다. 같은 시간대 Worker 호출의 약 4%는 클라이언트가 먼저 연결을 끊은 호출이었습니다. waitUntil은 응답을 마친 뒤에도 끝까지 처리할 일을 Cloudflare에 맡기는 함수입니다. 그런데 Worker 코드는 기존 경로 전송을 await로 기다린 뒤에야 복사본 전송을 waitUntil에 걸었습니다. Cloudflare는 클라이언트가 먼저 연결을 끊으면, 그때까지 waitUntil에 걸려 있던 일만 이어서 처리합니다. 그래서 기존 경로를 기다리는 사이 연결이 끊기면 복사본 전송은 아예 시작되지 않았습니다.
해결
기존 경로를 기다리기 전에 복사본 전송을 waitUntil에 거는 순서로 바꿨습니다. 끊김을 흉내 낸 unit test로, 고치기 전에는 복사본 전송이 아예 걸리지 않는 것을 먼저 확인했습니다. 끊긴 뒤 실제로 전송되는지는 배포 뒤 키 대조로 확인했습니다.
결과
배포 뒤 키 대조에서 누락은 0이었습니다. 이미 빠진 이벤트는 기존 경로 원본에서 되살려 원본 표에 다시 넣었고, 대조에서 누락 0을 확인했습니다. 건수만 비교했다면 찾지 못했을 누락입니다.

06배운 점

  • sort key, partition, dedup은 따로 고르는 설정이 아니었습니다. 세션을 무엇으로 볼지가 바뀌자 셋이 함께 바뀌었습니다. 결국 state를 어디에 둘지까지 정했습니다.
  • 경로를 바꿀 때는 이벤트 종류마다 언제 보내고 언제 다시 보내는지부터 표로 맞춰 봐야 합니다. 저장 전에 중복을 거르는 단계를 없애면서, 그 단계가 의도하지 않게 해 주던 일, 곧 재전송이 불어나도 일정 수준에서 끊어 주던 역할을 놓쳤습니다(D-07).
  • 경로를 바꿀 때 건수만 비교하면 일부가 빠져도 알아채지 못합니다. 이벤트 키 집합과 offset처럼 서로 다른 기록이 맞는지를 전환 조건으로 걸어야 합니다.
