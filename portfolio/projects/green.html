Kafka + Flink 스트림 처리 아키텍처 재설계와 무중단 전환

01요약과 역할

세션 계산을 ClickHouse의 SQL에서 Flink로 옮기고, Kafka를 유일한 원본 로그로 두는 구조로 실시간 계층을 다시 설계했습니다. 이 구조에서는 모든 상태를 원본 이벤트를 다시 읽어 만들 수 있어서, 늦게 온 이벤트와 다시 온 이벤트, 과거 데이터 재처리를 같은 방식으로 다룹니다.

문제
세션 약 88만 개가 오류 없이 집계에서 빠졌습니다. 세션 계산이 ClickHouse의 insert trigger 방식 MV에 묶여 있어서, 늦게 온 이벤트가 들어와도 이미 낸 결과를 고칠 수 없었고 처음부터 다시 계산할 수도 없었습니다.
결정
기준은 속도가 아니라 의미론이었습니다. 7일 늦게 온 이벤트를 반영할 때도, 이미 낸 결과를 고칠 때도, 처음부터 다시 계산할 때도 같은 결과가 나오도록 Flink와 Kafka 원본 로그를 골랐습니다. 이어지는 02부터 04에서 이유를 설명합니다.
결과
운영 중에 cutover를 마쳤습니다. 운영 환경에서 24시간 대조한 결과 한쪽에만 있는 이벤트는 약 0.06%였고 partition 12개의 offset이 모두 일치했습니다. 약 6,800만 행의 과거분도 같은 코드로 재생해 채웠습니다. 안전하게 옮긴 방법은 05에 있습니다.
맡은 일
세션 정의, partition key, dedup 위치를 정했습니다. Go receiver, Flink 세션 집계 job, Go sinker와 전환 절차를 설계하고 구현했고, 각 단계로 넘어가는 시점도 직접 판단했습니다.
범위 밖
방문자를 한 사람으로 잇는 신원 모델은 CDP Identity Resolution 페이지에 적었습니다. 이 계층의 Flink는 연락처 쪽 신원 계산만 함께 맡습니다.

02전환 전 구조와 문제

전환 전에는 ClickHouse 한 곳이 저장, 세션 계산, queue 관리, 조회를 모두 맡고 있었습니다. 수집 Worker가 받은 이벤트는 queue와 consumer를 거쳐 관리형 ClickHouse에 들어갔습니다. 세션 계산은 Materialized View(MV)와 Refreshable MV를 줄줄이 이어 붙인 chain이 했습니다. SQL은 약 2만 줄이었고, queue, rate limit, 처리 기록, checkpoint까지 SQL로 구현한 사실상의 stream processor였습니다.

한 곳이 너무 많은 일을 맡은 이 구조에서 실제로 무엇이 깨졌는지 먼저 보겠습니다. 구조 전체를 전과 후로 비교한 그림은 03의 끝에 두었습니다.

문제는 네 가지로 드러났습니다

1. 세션이 조용히 빠졌습니다. 2026년 9월 말, 봇을 제외한 방문 세션 중 집계가 끝난 비율이 30% 수준까지 떨어졌고, 누적으로 약 88만 개 세션이 집계에서 빠졌습니다. 원본 이벤트는 남아 있었고 집계만 빠졌습니다. 원인은 처리 대기 목록의 고르는 방식에 있었습니다. 대기 목록 창은 최대 1만 건인데, 그중 도착이 가장 새로운 800건만 후보로 고르고 읽은 위치를 창 끝까지 넘겼습니다. 고르지 못한 오래된 건은 한 번도 처리되지 않았고, 건너뛴 세션은 아무 기록 없이 8일 뒤 사라졌습니다. 누락이 오류로 드러나지 않는다는 점이 가장 나빴습니다.

2. 결과를 되돌릴 수 없었습니다. ClickHouse의 MV는 테이블의 현재 상태를 보고 계산하지 않고, INSERT가 일어날 때 새로 들어온 행만 보고 계산하는 insert trigger입니다. 이미 더해진 숫자는 나중에 중복 행이 병합돼도 돌아가지 않습니다. SDK는 최대 7일까지 이벤트를 다시 보내는데, 기존 경로의 dedup은 30분 안쪽만 막아서 그보다 늦은 재전송이 집계를 부풀린 적이 있었습니다.

3. 다시 계산할 수 없었습니다. queue는 한 번 읽으면 사라지고 보관 기간도 14일이었습니다. 관리형 ClickHouse를 해지하면 그 안의 원본도 함께 사라지는 상황이었습니다. 부하 면에서도, 몇 행짜리 INSERT 하나가 MV 십여 개로 퍼져, 적재가 대시보드 조회보다 훨씬 많은 자원을 썼습니다.

4. 세션 정의가 바뀌어 window 모델이 맞지 않았습니다. 30분 inactivity timeout으로 세션을 끊던 방식을 탭 수명 기준으로 바꾸고, 같은 브라우저의 탭들이 함께 쓰는 장기 세션과 세션과 따로 기록하는 유입을 도입했습니다. 세션이 며칠씩 열려 있게 되자, 세션은 언젠가 닫히는 window가 아니라 결과를 계속 고쳐 내는 key가 됐습니다.

그래서 과제는 세 가지였습니다. 이벤트가 늦게 오거나 다시 와도 결과에는 한 번만 반영되어야 했습니다. 장애가 나면 원본부터 다시 읽어 같은 결과를 다시 만들 수 있어야 했습니다. 그리고 관리형 ClickHouse를 해지하기 전에 운영 트래픽을 끊지 않고 옮겨야 했습니다.

03선택지와 기준

Flink를 고른 기준은 속도가 아니라 의미론이었습니다. 이벤트가 들어와 세션 집계에 반영되기까지의 목표는 약 15분이었고, 이 정도는 Flink 없이도 낼 수 있었습니다. 필요한 것은 7일 늦게 온 이벤트를 반영할 때도, 이미 낸 결과를 고칠 때도, 처음부터 다시 처리할 때도 모두 같은 결과를 내는 성질이었습니다.

이 기준으로 아래 선택지를 비교했습니다. 비용은 결정을 좌우할 만큼 크지 않았고, 실제로 갈린 것은 운영해야 할 구성 요소와 직접 만들어야 할 기능이었습니다.

표 2. 선택지와 trade-off
선택지얻는 것포기하는 것결과
Refreshable MV의 queue를 보강해 누락만 막기변경이 가장 작습니다.저장소가 상태 계산을 계속 떠안고, 새 클러스터로 SQL 2만 줄을 그대로 옮겨야 합니다. insert trigger 구조라 재전송, late event, backfill과 맞지 않습니다.채택하지 않았습니다. 세션이 며칠씩 열려 있는 새 세션 정의에서는 누락을 막아도 늦은 이벤트를 고칠 수 없어서, 문제의 원인이 그대로 남습니다.

수신 경로도 한 번 고쳤습니다

처음 수신 설계는 Cloudflare queue에 이벤트를 넣고 GKE 쪽 bridge가 당겨 오는 방식이었습니다. 이 queue를 거치지 않고 수집 Worker가 Go receiver를 통해 Kafka에 직접 쓰고, Kafka 자체를 buffer로 쓰도록 바꿨고 bridge는 없앴습니다. 구성 요소가 하나 줄고, 성공 응답의 의미도 "Kafka가 기록을 확인했다"는 하나로 단순해집니다.

04event sourcing 원칙

원본 이벤트만 사실로 두고, 나머지 상태는 모두 원본을 다시 읽어 계산합니다. 원본은 Kafka에 30일 동안, ClickHouse의 원본 테이블에 그보다 오래 남습니다. 세션 결과, 중복 판정, 세션 시작 같은 값은 여기서 파생된 값일 뿐이라 잃어도 다시 만들 수 있습니다. 30일 안은 Kafka를 다시 읽고, 30일 밖은 원본 테이블을 같은 코드로 BATCH 재생합니다.

  • 원본 로그는 Kafka입니다. 원본 topic은 partition 12개, replication factor 3, 보존 30일로 두었고, key는 고객사와 세션의 조합입니다. 같은 세션의 이벤트는 늘 같은 partition에 순서대로 쌓입니다.
  • 상태는 재생으로 계산합니다. Flink의 keyed state는 로그에서 파생된 값입니다. 장애가 나면 마지막 checkpoint에서 복원해 로그를 이어 읽고, 버전을 올리거나 되돌릴 때는 savepoint를 씁니다.
  • 결과의 버전은 입력만으로 결정됩니다. 재처리 회차, 반영한 이벤트 수, 상태를 차례로 비교하고, 결과를 낸 횟수나 현재 시각은 쓰지 않습니다. 그래서 같은 입력을 다시 돌리면 같은 버전이 나옵니다.

Flink로 옮긴 상태 계산

세션 계산은 기능별로 나누지 않고 Flink job 하나에 두었습니다. 고객사와 세션의 조합을 key로 삼아 세션마다 keyed state를 따로 들고, 아래 일을 모두 이 state 위에서 합니다. key가 다른 연락처 신원 계산만 별도 job으로 분리했습니다.

표 3. 상태 계산은 Flink, 적재와 조회는 ClickHouse
계산어디서 하는가내용
중복 제거Flink받은 이벤트 ID를 7일 동안 기억합니다. SDK가 이벤트를 다시 보낼 수 있는 기간과 같습니다. ID는 같은데 내용이 다르면 한쪽을 고르지 않고 따로 빼서 알립니다.
세션 조각과 마감Flink세션을 하루 단위 조각으로 나눠 계산하고, 날짜가 끝나고 7일이 지나면 마감합니다. late event가 오면 조각의 버전을 올려 다시 냅니다.
세션 시작 확정Flink시작 표식이 있는 이벤트를 우선하고, 없으면 가장 이른 시각의 이벤트를 시작으로 삼습니다. 이 state는 60일 동안 보존합니다.
클라이언트 시각 보정Flink브라우저가 보낸 시각이 과거 7일보다 오래됐거나 미래 24시간보다 멀면 서버에서 범위 안으로 자릅니다.
구매 관측, 결제 시도 후보, 방문 키Flink세션 계산과 같은 입력에서 곁가지 출력으로 따로 내보냅니다.
연락처 신원 계산Flink의 별도 job같은 Kafka 로그를 읽어 연락처 단위 신원과 귀속을 계산합니다. 자세한 내용은 CDP 페이지에 적었습니다.
원본 이벤트 저장ClickHouseFlink를 거치지 않고 sinker가 Kafka에서 바로 읽어 넣습니다. Flink가 멈춰도 원본 저장은 멈추지 않습니다.
채널 분류와 어트리뷰션ClickHouse의 view자주 바뀌는 해석 규칙은 조회 시점에 계산합니다. 거의 바뀌지 않는 "무엇이 세션이고 late event를 어떻게 고치는가"만 Flink에 둡니다.

Flink가 하지 않는 일도 정해 두었습니다. fingerprint 조회처럼 외부 서비스를 부르는 일은 Flink 밖에 둡니다. Flink는 Kafka에 있는 입력만 replay해도 같은 결과를 내야 하기 때문입니다. ClickHouse에는 MV와 Refreshable MV를 하나도 두지 않았고, schema lint가 MV를 만드는 구문을 막습니다. 법적 의무로 삭제해야 하는 개인정보만 DELETE 예외를 한 가지 두었고, 재생과 복구 때도 삭제 목록으로 걸러냅니다.

이 원칙은 세션 계산 경로에는 끝까지 적용했습니다. 연락처 신원은 계산을 Flink가 하지만 결과의 기준 저장소는 PostgreSQL입니다. 그래서 세션 계산은 결과까지 로그에서 다시 만들 수 있고, 연락처 신원은 계산 상태만 로그에서 다시 만들 수 있습니다.

05안전한 전환

수집 Worker의 설정값 하나로 단계를 나눠, 기존 경로를 끄기 전까지는 매 단계마다 되돌리는 방법이 있는 상태에서 옮겼습니다. 설정값은 꺼짐, mirror, primary 세 가지입니다.

1. mirroring으로 나란히 비교하기

mirror 단계는 기존 경로로 서비스를 계속하면서 같은 이벤트의 복사본을 새 경로에도 보내 두 경로를 나란히 돌립니다. 비교는 건수가 아니라 이벤트 키 집합과 partition별 offset으로 했습니다. 건수는 일부가 빠지고 다른 일부가 더 들어가도 우연히 맞을 수 있기 때문입니다. 이렇게 비교해서 mirror 첫날 복사본이 약 0.2% 빠진 것을 찾았고, 원인은 트러블슈팅 T-01에 적었습니다. 고친 뒤 운영 환경에서 24시간 동안 대조한 결과, 한쪽에만 있는 이벤트는 약 0.06%였고 12개 partition의 offset은 모두 맞았습니다.

2. idempotent 적재

Go sinker는 Kafka에서 읽은 레코드를 구간 단위로 묶어 다음 순서로 ClickHouse에 넣습니다.

  1. 이번에 넣을 offset 구간을 sink ledger에 먼저 적습니다. sink ledger는 어느 구간을 넣기 시작했는지 따로 남겨 두는 기록입니다.
  2. 데이터를 넣습니다.
  3. replica 두 대가 모두 받았는지 확인합니다.
  4. Kafka에 offset을 확정합니다.

sinker가 중간에 죽으면 같은 구간을 같은 dedup token으로 다시 넣습니다. token은 topic, partition, offset 구간, 대상 테이블을 묶어 계산하므로 같은 구간이면 늘 같은 값이 나오고, ClickHouse는 같은 token으로 들어온 데이터를 한 번만 받습니다. replica 두 대가 모두 받아야 쓰기가 성공하도록 설정해서, replica 하나가 내려가면 쓰기가 멈춥니다. 그동안 밀린 데이터는 Kafka에 남아 있습니다. 두 replica 내용이 서로 갈라지는 쪽보다 쓰기가 멈추는 쪽이 복구하기 쉽다고 판단했습니다.

3. checkpoint와 savepoint

Flink는 RocksDB state backend의 incremental checkpoint를 60초마다 남깁니다. checkpoint 모드는 at-least-once입니다. checkpoint 이후 구간을 다시 처리하면 같은 버전의 행이 한 번 더 들어가지만, 결과가 입력만으로 정해지고 읽는 쪽이 세션마다 가장 큰 버전 하나만 고르므로 화면 결과는 같습니다. 장애에서는 checkpoint로 자동 복구하고, 새 버전을 올리거나 되돌릴 때는 savepoint를 씁니다. 새 버전을 올리기 전에는 savepoint를 먼저 만들고, operator ID를 고정해 두어 state가 복원되지 않는 사고를 사전에 점검 도구로 막습니다. 병렬도를 나중에 올릴 수 있도록 key group 상한도 미리 넉넉하게 잡았습니다.

4. backfill과 replay

Kafka 보존은 30일이므로, 전환 이전의 과거분은 로그만으로 다시 만들 수 없습니다. 그래서 세 갈래로 나눠 채웠습니다.

  • mirror를 켠 뒤 빠진 이벤트는 원래 수신 시각 그대로 보충용 topic에 다시 넣어 같은 경로로 흘렸습니다.
  • mirror 이전의 과거 원본은 기존 클러스터에서 새 클러스터로 복사했습니다.
  • 과거분의 세션 결과는 복사한 원본을 Flink BATCH 모드로 처음부터 다시 읽어 만들었습니다. 스트리밍과 같은 계산 코드를 쓰므로, 과거분을 위한 코드를 따로 만들지 않았습니다.

스트리밍 결과와 재생 결과는 마감된 버전끼리만 비교하고, 아직 늦은 이벤트가 올 수 있는 최신 날은 제외했습니다. 경계가 되는 하루를 비교하니 스트리밍 쪽이 18,212건, 재생 쪽이 18,215건이었습니다. 차이 3건은 스트리밍이 내보내지 못했던 것이었습니다. 합격선을 숫자로 정해 두지 않고, 차이가 나면 그 사유를 설명할 수 있는지로 판단했습니다. 판단이 끝난 뒤 읽기 상한 값을 0에서 1로 바꿔 화면이 재생 결과를 읽게 했습니다. 이 값은 언제든 0으로 되돌릴 수 있습니다.

5. cutover와 rollback

primary 단계에서는 receiver가 Kafka에 쓰고 성공을 확인한 뒤에만 200을 돌려줍니다. 실패하면 예비 queue에 넣고, 예비 queue에도 못 넣으면 503을 돌려줍니다. 장애 때만 쓰는 경로는 정작 필요할 때 고장 나 있기 쉬워서, 평소에도 트래픽의 1%를 예비 queue로 흘려 검증합니다.

rollback은 단계마다 방법이 다릅니다. mirror 단계에서 문제가 있으면 설정값을 끄면 끝입니다. primary 단계에서는 기존 경로에 먼저 동기로 쓰는 방식으로 돌아가고, 이때 유실은 없습니다. 기존 경로의 적재를 끈 뒤에는 되돌릴 기존 경로가 없어서, 예비 queue 14일과 SDK의 재전송이 마지막 안전망입니다. 이 단계는 각 화살표마다 go/no-go를 직접 판단했습니다. 넘어가는 조건은 다음과 같았습니다.

  • 리허설에서 mirror로: staging에서 replica 정지와 sinker 강제 종료 훈련을 runbook대로 마쳤을 때.
  • mirror에서 primary로: 두 경로의 이벤트 키 집합 차이를 원인까지 설명할 수 있고, 12개 partition의 offset이 모두 맞을 때.
  • 기존 경로를 끄고 해지로: 새 경로에 없고 다시 계산할 수도 없는 원천 데이터를 snapshot으로 보관하고 원본과 대조해 확인했을 때.

다만 7일 관찰 단계와 트래픽 비율을 조금씩 올리는 canary 단계는 생략했습니다. 관리형 클러스터 비용을 먼저 끊으려는 선택이었고, 위험의 크기를 따져 본 결과이기도 합니다. 계산 결과는 원본만 있으면 재생으로 고칠 수 있으니 관찰 기간을 줄여도 되돌릴 수 있는 위험이었습니다. 되돌릴 수 없는 위험은 원본이 새 경로에 도달하지 못하는 누락뿐이어서, 그것만 키 대조와 원천 snapshot 대조로 엄격하게 막았습니다(D-06). 그 대신 운영 mirroring을 시작하기 전에 staging에서 replica를 일부러 멈추고 sinker를 강제로 종료하는 훈련을 runbook대로 해 보았습니다. 해지 직전에는 새 경로에 없고 다시 계산할 수도 없는 원천 데이터만 골라 snapshot으로 보관하고 원본과 대조했습니다.

06설계 결정과 트러블슈팅

앞 절의 흐름 속에서 방향을 갈랐던 판단 여섯 가지와, 전환 중 찾은 문제 하나입니다. 고민, 선택지, 결정과 이유, 대가 순서로 적었습니다.

D-01

중복 제거는 저장 전이 아니라 되돌릴 수 없는 계산 바로 앞에서 하기

고민
브라우저 재전송, queue 재전달, Kafka에서 다시 읽기는 모두 적어도 한 번은 전달하는 at-least-once 방식입니다. 그래서 같은 이벤트가 두 번 이상 오는 일은 반드시 생깁니다. 기존 경로는 dedup을 네 겹으로 두었는데도 30분보다 늦게 다시 온 이벤트는 모두 빠져나갔습니다.
선택지
① 중복을 거르는 층을 더 촘촘하게 만드는 안
② Kafka의 exactly-once 기능이나 저장소의 병합에 dedup을 맡기는 안
③ 원본은 중복이 섞인 채 도착한 그대로 기록하고, 결과를 되돌릴 수 없게 되는 첫 계산 바로 앞에서 한 번만 반영하는 안
결정과 이유
③을 골랐습니다. 저장소가 병합하며 중복을 지우는 일은 꼭 지켜야 할 조건에서 뺐습니다. 대신 세션 집계와 적재는 같은 데이터가 여러 번 들어와도 한 번 넣은 것과 결과가 같아야 한다는 idempotent 조건만 반드시 지키게 했습니다. 두 이벤트가 같은지 가리는 키는 고객사, 세션, 이벤트 ID의 조합입니다. 중복이 정상인 시스템에서는 중복을 없앨 곳보다 되돌릴 수 없는 연산 앞에서 한 번만 반영할 곳을 정해야 한다고 봤습니다. 저장 전에 거르다 잘못 판정하면 정상 이벤트를 버리게 되고, 그 판단은 되돌릴 수 없습니다.
대가
원본 테이블의 행 수가 서로 다른 이벤트의 수보다 많습니다. 원본 테이블을 직접 읽는 화면은 중복된 행 가운데 최신본 하나만 골라 읽어야 집계와 같은 수가 나옵니다.
D-02

세션은 닫히는 window가 아니라 버전을 올려 고쳐 쓰는 key로 다루기

고민
같은 브라우저의 탭들이 함께 쓰는 장기 세션에는 "세션이 끝났다"는 신호가 없습니다. 그래서 한 세션의 결과를 여러 번 고쳐 내야 하고, 그 결과를 여러 번 넣어도 한 번 넣은 것과 같아야 했습니다.
선택지
① 일정 시간 이벤트가 없으면 세션을 닫는 session window를 쓰는 안
② 세션 계산 기능마다 Flink job을 따로 나누는 안
③ 결과의 버전을 결과를 낸 횟수, Kafka offset, 현재 시각으로 정하는 안
④ 고객사와 세션을 key로 하는 job 하나에 세션 계산을 모으고, 버전은 입력만으로 정해지는 규칙으로 매기는 안
결정과 이유
④를 골랐습니다. ①처럼 세션을 닫으면 late event가 올 때마다 다시 열어야 합니다. 버전은 재처리 회차, 반영한 이벤트 수, 상태 순위를 앞에서부터 차례로 비교합니다. 반영한 이벤트 수는 줄어들지 않으므로, 새 이벤트를 반영한 결과가 옛 버전에 가려 조용히 사라지지 않습니다. 같은 입력이면 같은 버전이 나옵니다. 그래서 한 번만 반영되는 효과를 Flink의 exactly-once checkpoint에 기대지 않고, 결과가 입력만으로 정해지는 deterministic 처리로 얻었습니다. state TTL도 둘로 나눴습니다. 받은 이벤트 ID는 SDK가 다시 보낼 수 있는 7일 동안 기억하고, 집계 state는 결과가 확정될 때까지 둡니다.
대가
한 세션에 버전이 다른 행이 여러 개 쌓이므로 읽는 쪽이 세션마다 가장 큰 버전 하나만 골라야 합니다. 트래픽이 끊긴 환경에서는 다음 이벤트가 올 때까지 Flink가 결과를 내보내지 않습니다.
D-03

수신 응답, partition key, 적재 방식을 하나의 규칙으로 맞추기

고민
receiver가 성공(200)이라고 답한 이벤트를 잃어버리는 일이 없어야 했습니다. 한 세션 안의 이벤트 순서를 지키면서도 한 고객사에 트래픽이 몰릴 때 한 partition에만 쏠리지 않아야 했습니다. Flink가 결과를 냈다고 해서 저장소에 한 번만 들어간다는 보장이 생기지는 않아서, 이것도 따로 풀어야 했습니다.
선택지
① receiver에 자체 버퍼를 두고, 고객사만 키로 쓰고, partition은 적게 시작해 나중에 늘리는 안
② Flink가 공식 connector로 ClickHouse에 직접 넣는 안
③ receiver에는 버퍼를 두지 않고, 고객사와 세션의 조합을 키로 쓰고, partition을 처음부터 12개로 고정하는 안. 적재는 Go sinker 하나가 sink ledger, dedup token, 두 replica 쓰기로 한 번만 넣습니다.
결정과 이유
③을 골랐습니다. SDK는 200을 받으면 그 이벤트를 다시 보내지 않으므로, 200은 "더 보내지 않아도 된다"는 약속입니다. 그래서 Kafka replica 모두가 기록을 확인했을 때만 200을 주게 했습니다. partition key를 Flink가 쓰는 key와 같게 두어 한 세션의 이벤트는 늘 같은 partition에 순서대로 들어갑니다. partition 수를 나중에 바꾸면 같은 세션이 다른 partition으로 가게 되므로, 평소 트래픽보다 훨씬 큰 부하도 감당하도록 계산한 12개로 처음부터 고정했습니다. Go 코드와 Java 코드가 같은 키를 같은 partition으로 보내는지는, 고정된 입력을 양쪽에 똑같이 넣어 결과를 비교하는 교차 테스트로 확인합니다. 공식 connector는 at-least-once만 보장하고, retry를 다 하고도 실패하면 레코드를 버리기 때문에 쓰지 않았습니다.
대가
12개는 load test로 확인한 값이 아니라 계산으로 정한 값입니다. replica 한 대가 빠지면 쓰기가 멈추는데, 의도한 동작이고 밀린 데이터는 Kafka가 30일 동안 들고 있습니다. Go와 Java 두 언어가 같은 규칙을 지켜야 해서 교차 테스트를 계속 유지합니다.
D-04

늦게 와서 바뀌는 세션 시작도 Flink가 확정하기

고민
처음에는 Flink가 세션 시작 이벤트를 후보로만 쌓아 두고, 화면에서 조회할 때마다 그 고객의 과거 후보 전체에서 시작을 다시 골랐습니다. 세션이 며칠씩 이어지다 보니 7일치만 조회해도 이력 전체를 정렬해야 했고, 더 긴 기간을 조회하면 메모리 한도를 넘었습니다.
선택지
① 마감된 날의 세션 시작은 더 바뀌지 않는다고 규칙을 정하고 조회 기간을 나눠 처리하는 안
② 조회 기간 앞뒤에 여유를 두고 그 범위만 잘라 읽는 안
③ Flink가 후보를 state로 들고 있다가 시작을 확정하고, 저장소에는 세션마다 현재 값 한 줄만 두는 안
결정과 이유
처음에는 ①을 검토했지만, 조회할 때 시작을 고르는 구조를 그대로 둔 채 규칙을 덧대는 우회책이었습니다. late event로 과거 결과가 바뀌는 일은 state가 다룰 문제이고, state는 이미 Flink로 옮겼습니다. 그래서 ③으로 바꿨습니다. 세션 ID는 앞부분에 만든 시각이 들어가는 UUIDv7인데 ClickHouse는 UUID를 비교할 때 뒤쪽 비트를 먼저 보기 때문에 시간순으로 놓이지 않습니다. 그래서 sort key 맨 앞에 세션 ID에서 꺼낸 날짜를 두어, 세션 ID 하나로 세션을 구별하면서 시간 순서로도 정렬하게 했습니다. 이후로는 조회할 때 이력 전체에서 현재 값을 고르는 설계를 보면, 읽기 최적화보다 먼저 Flink state로 옮길 수 있는지부터 따집니다.
대가
Flink state가 더 오래 남습니다. 세션 시작을 정하는 state는 60일 동안 보존합니다. 대신 화면 조회는 조회 기간 안에 있는 세션만큼만 읽게 됐습니다.
D-05

재전송 폭주는 서버에서 거르지 않고 원인인 SDK에서 막기

고민
운영 mirroring 중 Kafka에 쌓인 레코드 수가 서로 다른 이벤트 수의 약 4.5배였습니다. 평소에는 1.2배에서 1.3배 수준입니다. 배포된 SDK가 탭끼리 함께 쓰는 공유 세션을 항상 켜면서 모든 이벤트를 버퍼에 넣었다가 나중에 보내게 바뀌었는데, 일부 이벤트의 업로더는 "받아들여졌다"는 확인을 받을 때까지 60초마다 다시 보내도록 만들어져 있었습니다. 버퍼의 "나중에 보낸다"와 업로더의 "받아들여질 때까지 다시 보낸다"가 맞물려 같은 이벤트를 끝없이 다시 내보냈습니다.
선택지
① receiver에 TTL이 짧은 cache를 두어 같은 이벤트가 들어오는 횟수에 상한을 거는 안
② 브라우저와 가까운 edge에서 고객사별, 세션별로 rate limit을 거는 안
③ 원본 이벤트도 Flink를 거쳐 중복을 거른 뒤 저장하는 안
④ 원본은 수집 단계에서 막지 않고 모두 저장하되, 중복 배수를 측정해 경보를 걸고, 원인인 SDK의 재전송 규칙을 고치는 안
결정과 이유
④를 골랐습니다. 기존 경로에서 저장 전에 중복을 거른 것은 결과를 정확하게 하려는 장치가 아니라, INSERT 하나가 MV 여러 개로 번지며 불어나는 부하와 유료 API 비용을 막는 장치였습니다. 새 구조에는 그런 비용이 생기지 않으므로 그 장치를 다시 들일 이유가 없었습니다. ③은 Flink가 멈출 때 원본 저장까지 함께 멈추게 되어 쓰지 않았습니다. 대신 SDK 안에 이벤트가 실제로 전송 단계에 넘어갔다는 신호를 따로 두고, 그 신호를 받은 뒤에만 이벤트를 지우게 했습니다. 또 만든 지 7일이 지난 이벤트는 더 보내지 않게 했습니다. 서버가 받은 이벤트를 기억하는 기간이 7일이라, 그보다 늦게 다시 보낸 이벤트는 처음 보는 이벤트로 들어오기 때문입니다.
대가
이미 떠 있는 브라우저 탭은 고친 SDK를 받기 전까지 계속 다시 보냅니다.
D-06

cutover 판정에서 기존 경로를 정답으로 쓰지 않기

고민
기존 경로는 세션 집계가 끝난 비율 자체가 30% 수준까지 떨어져 있었습니다. 기존 경로를 정답으로 놓고 대조하면, 기존 경로에서 빠진 것을 새 경로의 오류로 세게 됩니다.
선택지
① 기존 경로의 결과를 정답으로 놓고 대조하는 안
② 건수만 비교해 보고 전환하는 안
③ 원본이 빠짐없이 들어왔는지, 대표 사례가 맞게 계산되는지, 늘 성립해야 하는 invariant가 지켜지는지로 판정하고, 원본이 새 경로에 도달하지 못한 누락만 엄격하게 보는 안
결정과 이유
③을 골랐습니다. 비교 기준이 틀리면 대조가 오히려 판단을 흐립니다. 집계는 원본만 있으면 다시 계산할 수 있습니다. 반면 새 경로에 도달하지 못한 원본은 해지 뒤 되살릴 수 없어서, 그것만 엄격하게 봤습니다.
대가
해지 시점의 판단은 매일 도는 대조나 경보 채널 같은 별도 안정성 장치 대신, 운영 중 바로 확인할 수 있는 지표로 내렸습니다.
T-01

실패 기록이 없는데 복사본 약 0.2%가 빠진 문제

문제
운영 mirroring을 켠 첫날, 두 경로의 이벤트 키를 맞춰 보니 기존 경로에는 있고 새 경로에는 없는 이벤트가 약 0.2% 나왔습니다. 실패 로그, 예비 queue, dead letter queue에는 아무것도 없었습니다.
원인
payload 크기 초과와 형식 오류를 먼저 의심했지만 둘 다 아니었습니다. 빠진 이벤트는 모두 페이지를 떠날 때 나가는 이벤트였습니다. 같은 시간대 Worker 호출 가운데 상당수는 클라이언트가 먼저 연결을 끊은 호출이었습니다. waitUntil은 응답을 마친 뒤에도 끝까지 처리할 일을 Cloudflare에 맡기는 함수입니다. 그런데 Worker 코드는 기존 경로 전송을 await로 기다린 뒤에야 복사본 전송을 waitUntil에 걸었습니다. Cloudflare는 클라이언트가 먼저 연결을 끊으면 그때까지 waitUntil에 걸려 있던 일만 이어서 처리합니다. 그래서 기존 경로를 기다리는 사이 연결이 끊기면 복사본 전송은 시작되지 않았습니다.
해결
기존 경로를 기다리기 전에 복사본 전송을 waitUntil에 거는 순서로 바꿨습니다. 끊김을 흉내 낸 unit test로, 고치기 전에는 복사본 전송이 걸리지 않는 것을 먼저 확인했습니다. 끊긴 뒤 실제로 전송되는지는 배포 뒤 키 대조로 확인했습니다.
결과
배포 뒤 키 대조에서 누락은 없었습니다. 이미 빠진 이벤트는 기존 경로 원본에서 되살려 새 원본 테이블에 다시 넣었고, 다시 대조해 남은 누락이 없음을 확인했습니다. 건수만 비교했다면 찾지 못했을 누락입니다.

07지금의 운영 상태

지금은 새 실시간 계층이 운영 트래픽을 처리하고 있고, 관리형 ClickHouse는 해지했습니다. 세션 집계 job과 연락처 신원 job이 모두 운영 환경에서 실행 중이며, 새 클러스터에는 MV와 Refreshable MV가 하나도 없습니다.

  1. 10월 7일, 모든 고객 트래픽에 mirror 가동

    기존 경로로 서비스를 하면서 같은 이벤트를 새 경로에도 보내 비교를 시작했습니다. 다음 날 복사본 누락의 원인을 찾아 고쳤습니다.

  2. 10월 16일, 읽기 전환과 관리형 ClickHouse 해지

    화면이 새 계층을 읽도록 바꾸고, 기존 경로의 적재를 끄고, 관리형 ClickHouse를 해지했습니다. 당초에는 해지를 더 늦추는 일정이었는데, 비용 때문에 먼저 끄고 천천히 옮기는 쪽으로 바꿨습니다.

  3. 10월 18일, 연락처 신원 계산을 Flink로 이관

    Go로 돌던 연락처 신원 계산과 복구를 Flink의 별도 job으로 옮겼고, 지금 운영 환경에서 실행 중입니다.

  4. 10월 19일, 대시보드 화면 전환과 과거분 재생

    대시보드 화면을 새 호스팅으로 옮기고 예전 화면 앱을 제거했습니다. 같은 날 운영 환경에서 과거분 재생을 한 번 실행했습니다. 약 6,800만 행의 과거 원본을 읽어 하루 단위 세션 조각 약 248만 개를 만들었고, 작업은 약 157분 걸렸습니다.

운영 환경에서는 세션 집계 job이 병렬도 2로 실행 중이고, checkpoint는 60초마다 남습니다. 평소 트래픽은 하루 40만에서 60만 건 수준이라 처리량보다 정확성과 복구 가능성에 설계 비용을 썼습니다.

08배운 점

  • sort key, partition, dedup은 따로 고르는 설정이 아니었습니다. 세션을 무엇으로 볼지가 바뀌자 셋이 함께 바뀌었고, state를 어디에 둘지까지 세션 정의가 정했습니다.
  • 경로를 바꿀 때는 이벤트 종류마다 언제 보내고 언제 다시 보내는지부터 표로 맞춰 봐야 합니다. 저장 전에 중복을 거르는 단계를 없애면서, 그 단계가 의도치 않게 해 주던 일, 곧 재전송이 불어나도 일정 수준에서 끊어 주던 역할을 놓쳤고, 이것이 D-05의 재전송 폭주로 드러났습니다.
  • 건수만 비교하면 일부가 빠져도 알아채지 못합니다. 이벤트 키 집합과 offset처럼 서로 다른 기록이 맞는지를 전환 조건으로 걸어야 합니다. 비교 기준 자체가 이미 틀어져 있다면 기준부터 바꿔야 합니다.
  • 스트리밍과 BATCH가 같은 계산 코드를 쓰면, 과거 데이터를 채우는 일이 별도 이전 작업이 아니라 같은 로직의 재실행이 됩니다. 계산을 재생 가능하게 만든 값을 가장 크게 느낀 부분입니다.
