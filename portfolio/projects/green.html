V3 실시간 아키텍처: 상태 계산은 Flink, ClickHouse는 적재와 조회

브라우저 행동 이벤트로 세션을 만드는 분석 플랫폼입니다. 늦게 오고 다시 오는 이벤트를 다루는 상태 계산을 ClickHouse에서 꺼내 Flink로 옮겼습니다. Kafka를 원본 로그로 두어, 같은 입력이면 같은 결과가 나오는 구조로 다시 설계했습니다. 운영 트래픽을 끊지 않고 새 경로로 전환했습니다.

01상황과 역할

2026년 9월 말, 사람 방문 세션 중 집계가 끝난 비율이 사흘 사이 약 60%에서 30%로 떨어졌습니다. 원본 이벤트는 남아 있었고, 세션 집계만 빠졌습니다.

세션 집계는 ClickHouse 안의 SQL 갱신 뷰 체인이 맡고 있었습니다. SQL은 약 2만 줄이었습니다. 처리 대기 목록, 처리량 상한, 처리 기록, 체크포인트를 모두 SQL로 만든 셈이었습니다. 사실상 SQL로 만든 스트림 처리기였습니다. 그중 한 뷰가 대기 목록에서 후보를 일부만 고르고 읽은 위치를 넘겼습니다. 후보가 되지 못한 세션은 처리되지 않고 지나갔습니다.

부하 기록을 보면 CPU의 절반 이상을 수집 쪽이 썼습니다. 몇 행짜리 INSERT 하나가 집계 뷰 십여 개로 퍼져, 입력보다 수백 배 많은 병합이 일어났습니다. 메모리 한도 사고도 대부분 갱신 뷰에서 났습니다. 대시보드 읽기는 CPU의 1%도 쓰지 않았습니다.

관리형 ClickHouse를 해지하고 자체 운영 클러스터로 옮기는 일정도 정해져 있었습니다. 새 클러스터로는 이 뷰 체인을 옮기지 않기로 했습니다. 그래서 세션 집계를 맡을 곳이 따로 필요했습니다.

설계 제약은 그보다 앞서 바꾼 세션 정의에서 왔습니다. 30분 동안 움직임이 없으면 세션을 끊던 방식을 탭 수명으로 바꿨습니다. 이어서 같은 브라우저의 탭들이 함께 쓰는 장기 세션을 두고, 유입은 따로 기록하게 했습니다. 세션이 며칠씩 열리자, 세션은 언젠가 닫히는 창이 아니라 계속 고쳐 쓰는 키가 됐습니다. 게다가 SDK는 최대 7일까지 이벤트를 다시 보냅니다.

그래서 과제는 세 가지였습니다.

  • 늦게 오고 다시 오는 이벤트가 결과에 한 번만 반영되는 세션 집계
  • 장애가 나면 원본부터 다시 계산할 수 있는 구조
  • 해지 일정 안에, 운영 트래픽을 끊지 않고 새 경로로 전환
맡은 일
세션과 키, 중복 제거 경계를 정하고, Go 수신 서버, Flink 세션 집계 잡, Go 적재기, 전환 절차를 설계하고 구현했습니다. 전환 판단도 맡았습니다.
범위 밖
방문자 신원 계산은 별도 배치로 설계했습니다(CDP 방문자 신원 페이지).

같은 내용을 책임별로 다시 적으면 아래와 같습니다.

02해결 과정

1. Kafka와 Flink를 고른 기준

브라우저 재전송, 큐 재전달, Kafka 재소비는 모두 최소 한 번 전달(at-least-once)입니다. 중복은 반드시 생깁니다. 그래서 기준을 둘로 정했습니다. 세션 집계의 중복은 Flink 세션 상태 한 곳에서 지웁니다. 같은 입력을 다시 돌리면 같은 결과가 나와야 합니다.

  • Kafka는 버퍼이면서, 다시 계산할 때 읽을 원본 로그입니다. 원본 토픽은 30일 보관, 복제 3으로 두었습니다. 큐만 쓰는 안은 메시지를 한 번 읽으면 사라져 다시 계산할 수 없어서 쓰지 않았습니다.
  • Go 소비자가 세션을 직접 계산하는 안도 비교했습니다. 비용은 쌌지만 키 상태와 타이머, 체크포인트를 직접 다시 만들어야 했습니다. 기존 뷰 체인이 바로 그렇게 2만 줄이 됐습니다.
  • 집계 반영 목표는 약 15분이었습니다. Flink를 고른 이유는 지연 시간보다, 늦게 오거나 다시 오는 데이터를 다루는 기능이었습니다.

2. 트래픽 수용 설계

평균 트래픽은 크지 않습니다. 그래서 처리량보다, 순간적으로 몰릴 때 버티는 방식과 나중에 바꾸기 어려운 값을 먼저 정했습니다.

  • Kafka는 사설망과 클라우드 IAM 인증 뒤에 있어 Worker가 직접 붙을 수 없습니다. 그래서 사이에 Go 수신 서버를 두었습니다.
  • 수신 서버는 모든 레코드가 acks=all로 확인된 뒤에만 200을 돌려줍니다. 1건이라도 실패하면 요청 전체를 실패로 봅니다.
  • 수신 서버에는 자체 버퍼를 두지 않았습니다. 버퍼가 둘이면 어디까지 확정됐는지 흐려지기 때문입니다.
  • Kafka 클라이언트 버퍼가 차면 기다리지 않고 바로 실패하는 TryProduce를 썼습니다. 버퍼가 가득 찼거나 약 1.2초 안에 끝내지 못하면 503을 돌려줍니다. Worker는 503을 받으면 요청을 예비 큐로 보냅니다.
  • 예비 큐에는 평소에도 트래픽 1%를 흘립니다. 장애 때만 쓰는 경로는 정작 필요할 때 고장 나 있기 쉽기 때문입니다.
  • 수신 서버는 CPU 60%를 기준으로 HPA가 2대에서 8대까지 늘립니다.
  • 파티션 키는 (고객사, 세션)이고 파티션은 12개로 고정했습니다. 이유는 설계 결정 D-05에 적었습니다.

3. Flink 세션 집계와 멱등 적재

  • 키 (고객, 세션) 하나에 잡 하나입니다. 세션 상태 안에 이미 받은 이벤트 ID를 7일 동안 보관합니다. SDK가 다시 보낼 수 있는 기간과 같습니다.
  • 같은 이벤트가 다시 오면 버립니다. ID는 같은데 내용이 다르면 한쪽을 고르지 않고 따로 빼서 알림을 보냅니다.
  • 결과마다 버전을 붙입니다. 재처리 회차, 반영한 이벤트 수, 결과 상태(진행 중 < 마감 < 삭제)를 이 순서로 비교해 큰 쪽이 최신입니다. 결과를 낸 횟수나 현재 시각은 쓰지 않습니다.
  • RocksDB 증분 체크포인트를 60초마다 GCS에 남깁니다.
  • 원본 이벤트는 Flink를 거치지 않습니다. 원본 적재기가 Kafka에서 바로 읽어 원본 표에 넣습니다. 그래서 Flink가 멈춰도 원문 저장은 멈추지 않습니다.
  • Go 적재기는 구간마다 다음 순서로 일합니다.
    1. 적재할 오프셋 구간을 적재 원장에 적습니다.
    2. 데이터를 넣습니다.
    3. 두 레플리카가 모두 받았는지 확인합니다.
    4. Kafka에 읽은 위치를 확정합니다.
  • 적재기가 중간에 죽으면 같은 구간을 같은 insert_deduplication_token으로 다시 넣습니다. 토큰은 (토픽, 파티션, 오프셋 구간, 테이블)에서 계산합니다. 그래서 같은 구간을 두 번 넣어도 중복이 생기지 않습니다.
  • insert_quorum=2라 레플리카 하나가 내려가면 쓰기가 멈춥니다. 밀린 분량은 Kafka가 들고 있습니다. 쓰기가 멈추는 쪽이 두 레플리카 내용이 갈라지는 쪽보다 복구가 쉽다고 판단했습니다.
  • 새 클러스터에는 집계 뷰와 갱신 뷰를 하나도 두지 않았습니다. 스키마 lint로 만들지 못하게 막았습니다.

4. 전환

전환은 Worker 설정값 하나로 했습니다. 이 값은 꺼짐, 미러, 주 경로 세 가지입니다. 순서는 스테이징 미러링, 운영 미러링, 주 경로였습니다. 운영 미러링 전에는 스테이징에서 레플리카 중단과 적재기 강제 종료를 일부러 일으켜 봤고, 런북 훈련도 했습니다.

미러링 동안에는 건수가 아니라 이벤트 키 집합과 파티션별 오프셋을 대조했습니다. 건수는 일부가 빠지고 일부가 더 들어가도 맞을 수 있기 때문입니다. 이 대조로 첫날 복사본 누락 약 0.2%를 찾았습니다(T-01).

03설계 결정

해결 과정의 방향을 정한 판단 여덟 가지입니다. 고민, 선택지, 결정과 이유, 대가 순서로 적었습니다.

D-01

원본의 중복 0을 포기하고, 결과에 한 번만 반영하기

고민
브라우저 재전송, 큐 재전달, Kafka 재소비는 모두 최소 한 번 전달입니다. 기존 경로는 중복 거르기를 네 겹으로 두었습니다. 그래도 30분 넘게 늦은 재전송이 모두 통과해 집계를 부풀린 적이 있었습니다. 저장소 병합은 이미 집계 뷰에 들어간 중복을 거꾸로 빼 주지 않습니다.
선택지
① 거르는 층을 더 촘촘히
② Kafka의 정확히 한 번 기능이나 저장소 병합에 맡김
③ 원본은 중복을 허용하는 도착 기록으로 두고, 되돌릴 수 없는 첫 연산 앞에서 한 번만 반영
결정과 이유
③을 골랐습니다. 원본 표의 병합 중복 제거는 필수 조건에서 내리고, 세션 집계와 적재의 멱등만 필수로 두었습니다. 논리 키는 (고객, 세션, 이벤트)로 정했습니다. 중복이 정상인 시스템에서는 중복을 없앨 곳보다, 되돌릴 수 없는 연산 앞에서 한 번만 반영할 곳을 정해야 한다고 봤습니다. 저장 전에 거르다 잘못 판정하면 정상 이벤트를 버립니다. 그 판단은 되돌릴 수 없습니다.
대가
원본 행 수가 고유 이벤트 수보다 많습니다. 원본을 직접 읽는 화면은 최신본을 골라야 같은 수가 나옵니다.
D-02

상태 계산은 Flink, ClickHouse는 적재와 조회만

고민
갱신 뷰를 고치면 누락은 막을 수 있었습니다. 하지만 저장소가 상태 계산과 작업 관리를 계속 떠안습니다. 새 클러스터로 뷰 체인도 옮겨야 했습니다.
선택지
① 갱신 뷰 대기 목록 보강
② Go 소비자가 바뀐 키만 직접 계산
③ 배치 처리 먼저
④ 저장소 엔진 교체
⑤ 상태 계산을 Flink로 옮기고, 저장소는 적재와 조회만
결정과 이유
⑤를 골랐습니다. 집계 뷰는 데이터의 현재 상태가 아니라 INSERT라는 사건에 반응합니다. 중복, 소급, 백필이 있는 데이터와는 맞지 않습니다. ②는 월 비용이 훨씬 쌌지만, 키 상태와 타이머, 체크포인트를 다시 만들어야 했습니다. ④는 버렸습니다. 문제는 엔진보다, 원본 보관과 해석, 세션 계산, 조회가 한 체인에 섞인 데 있었습니다. 분 단위 신선도는 Flink 없이도 낼 수 있었습니다. 필요한 것은 7일 늦게 온 이벤트, 결과 정정, 재처리가 모두 같은 결과를 내는 기능이었습니다. 자주 바뀌는 해석(귀인, 채널 매핑, 신원)은 조회 시점에 두었습니다. 거의 바뀌지 않는 "무엇이 세션이고, 늦은 이벤트를 어떻게 고치는가"만 Flink에 두었습니다.
대가
Kafka, Flink, 적재기로 움직이는 부품이 늘었습니다. 소규모 운영에 JVM 도구가 더해졌습니다. 범위를 넓힌 채 일정을 지켜야 해서 마지막 몇 주가 빠듯했습니다.
D-03

Kafka를 원본 로그로 두고, 두 경로는 입구에서 나누기

고민
재처리하려면 원본이 저장소와 떨어진 곳에 남아 있어야 했습니다. 기존 큐는 읽으면 사라지고 보존이 14일이라 다시 읽을 수 없었습니다. 해지 뒤에는 기존 원본을 되살릴 수도 없었습니다.
선택지
① 기존 경로에서 적재에 성공한 것을 새 경로로 복사
② 새 경로 전용 큐와 브리지
③ 수집 Worker에서 둘로 나누고, 새 경로는 Kafka로 바로
결정과 이유
③을 골랐습니다. 원본 로그가 기준이고, 저장소의 모든 표는 로그를 다시 읽어 만들 수 있어야 합니다. 기존 경로의 성공분을 복사하면 새 경로가 기존 경로에 기대게 됩니다. 복사에서 빠진 것은 영구 누락이 됩니다. 같은 입구에서 나눠야 두 경로를 서로 독립으로 비교할 수 있습니다. 같은 이유로 핑거프린트 조회 같은 외부 호출은 Flink 밖에 두었습니다. Flink는 Kafka에 있는 것을 다시 재생해 같은 결과를 내는 계층이기 때문입니다.
대가
병행 기간에는 두 경로 비용을 함께 냈습니다. Kafka에는 SDK 재전송 중복이 그대로 쌓입니다.
D-04

세션은 닫히는 창이 아니라 버전을 고쳐 쓰는 키로

고민
공유 장기 세션에는 끝 신호가 없습니다. 한 세션의 결과를 여러 번 고쳐 내야 합니다. 재처리해도 같은 결과가 나와야 적재가 멱등해집니다.
선택지
① 세션 윈도우로 닫음
② 기능별로 잡을 나눔
③ 버전을 결과 낸 횟수, 오프셋, 현재 시각으로 정함
④ 키 (고객, 세션) 하나에 잡 하나, 버전은 입력만으로 정해지는 규칙으로
결정과 이유
④를 골랐습니다. 닫힌 창은 늦은 이벤트가 오면 다시 열어야 합니다. 버전은 (재처리 회차, 반영한 이벤트 수, 상태 순위)를 앞에서부터 비교합니다. 반영 수는 줄지 않아서, 새 이벤트가 옛 버전에 가려 조용히 사라지지 않습니다. 같은 입력이면 같은 버전이 나옵니다. 그래서 정확히 한 번을 엔진 체크포인트로 얻지 않고, 결과가 입력만으로 정해지는 성질로 얻었습니다. 체크포인트 모드는 최소 한 번으로 충분합니다. 상태 수명도 둘로 나눴습니다. 중복 기억은 재전송 기간(7일)에, 집계 상태는 결과가 확정되는 기간에 맞췄습니다.
대가
버전 행이 여러 개 쌓여, 읽는 쪽이 가장 큰 버전으로 접어야 합니다. 트래픽이 끊긴 환경에서는 다음 이벤트가 올 때까지 결과 방출이 멈춥니다.
D-05

수신, Kafka 키, 적재를 한 계약으로 맞추기

고민
"200을 줬는데 잃었다"가 없어야 했습니다. 한 세션의 순서를 지키면서, 트래픽이 한 고객사에 몰려도 한 파티션에 쏠리지 않아야 했습니다. Flink가 결과를 내도 저장소에 한 번만 들어간다는 보장은 별개였습니다.
선택지
① 수신 서버 자체 버퍼, 고객사 키, 작게 시작해 나중에 파티션 증설
② Flink가 공식 커넥터로 ClickHouse에 직접 적재
③ 버퍼 없는 수신 서버, (고객사, 세션) 키와 파티션 12개 고정, Go 적재기 하나가 원장과 토큰, 두 레플리카 쓰기로 적재
결정과 이유
③을 골랐습니다. SDK는 200을 받으면 다시 보내지 않습니다. 그래서 200의 뜻이 곧 재전송 계약이고, 200은 "Kafka에 acks=all로 기록됨"만 뜻하게 했습니다. 파티션 키를 Flink 키와 같게 두어 한 세션은 한 파티션에서 순서를 지킵니다. 파티션 수를 나중에 바꾸면 같은 세션이 다른 파티션으로 갑니다. 그래서 지금 트래픽의 100배에서도 파티션 하나가 감당한다고 계산한 12개로 처음부터 고정했습니다. Go와 Java가 같은 키를 같은 파티션에 보내는지는 고정 입력 시험으로 묶었습니다. 공식 커넥터는 최소 한 번 전달이고, 재시도 뒤 레코드를 버려서 쓰지 않았습니다. 원장과 오프셋을 서로 다른 시스템에 두면 "건수는 맞는데 일부가 빠진" 누락도 대조로 잡을 수 있습니다.
대가
12는 부하 시험 결과가 아니라 계산값이라 설정에 "잠정"으로 적어 두었습니다. 레플리카 한 대가 빠지면 쓰기가 멈춥니다(의도한 동작, 밀린 분량은 Kafka가 30일 보관). 두 언어가 같은 출력 계약을 알아야 해서 교차 시험이 필요합니다.
D-06

늦게 와서 바뀌는 세션 시작도 Flink가 확정하기

고민
세션과 유입의 시작 이벤트를 Flink는 후보로만 쌓았습니다. 조회할 때마다 그 고객의 과거 후보 전체에서 다시 골랐습니다. 세션이 길어서 7일만 조회해도 이력 전체를 정렬했고, 90일 조회는 메모리 한도를 넘었습니다. 세션 ID 정렬에도 시간 순서가 없었습니다. ClickHouse의 UUID 비교는 뒤쪽 64비트를 먼저 봐서, UUIDv7을 넣어도 시간순으로 놓이지 않습니다.
선택지
① 마감된 날의 시작은 바뀌지 않는다는 규칙과 기간 분할
② 조회 기간 앞뒤에 여유폭을 두고 자르기
③ Flink가 후보를 상태로 들고 시작을 확정하고, 저장소에는 세션당 현재 한 줄
결정과 이유
처음에는 ①을 검토했습니다. "소급을 Flink에서 다 받을 수 있지 않나"를 다시 물어 보니, ①은 조회 때 고르는 구조를 남긴 땜질이었습니다. 그래서 ③으로 바꿨습니다. 늦게 온 이벤트로 결과가 바뀌는 것은 상태의 일이고, 상태는 이미 Flink로 옮겼습니다. 정렬키 앞에는 UUIDv7에서 꺼낸 날짜를 두었습니다. 같은 키 체계 안에서 시간 순서와 세션 정체성을 함께 얻었습니다. 이후로는 조회 때 이력 전체에서 현재값을 고르는 설계를 보면, 읽기 최적화보다 먼저 Flink 상태로 옮길 수 있는지 묻습니다.
대가
Flink 상태가 더 오래 남습니다(시작 상태 보존 60일). 세션 ID로 바로 찾는 조회는 따로 빠르게 만들어야 합니다. 조회는 조회 창 안의 세션만큼만 읽게 됐습니다.
D-07

재전송 폭주는 저장 구조가 아니라 원인에서 막기

고민
운영 미러링 중 Kafka 레코드 수가 고유 이벤트의 약 4.5배였습니다. 업로드 완료를 알리는 이벤트 한 종류는 약 28배였습니다. 배포 SDK에서 공유 세션을 항상 켜면서, 모든 이벤트가 "버퍼에 넣고 나중에 보냄"으로 바뀌었습니다. 그 업로더는 "받아들여짐"을 확인할 때까지 60초마다 다시 보내도록 만들어져 있었습니다. 뜻이 다른 두 약속이 만나 끝나지 않는 재발행이 됐습니다.
선택지
① 수신 서버에 짧은 시간 캐시 상한
② 엣지에 고객사, 세션별 속도 제한
③ 원본도 Flink를 거쳐 걸러서 저장
④ 원본은 모두 두고 입구 상한 없이 계측과 경보만, 원인인 SDK 계약을 고침
결정과 이유
④를 골랐습니다. 기존 경로의 저장 전 거르기는 정확성 장치가 아니었습니다. 집계 뷰 연쇄 증폭과 유료 API 비용을 막는 방패였습니다. 새 구조는 그 비용을 구조로 없앴으니 방패를 다시 들일 이유가 없었습니다. 실제 새 저장소 부하도 CPU 평균 약 3%로 작았습니다. 원본까지 Flink를 거치면 Flink가 멈출 때 원문 저장도 멈춥니다. 대신 SDK에 "실제로 전송 단계에 넘겨졌다"는 내부 알림을 따로 두고, 그 알림 뒤에만 지우게 했습니다. 만든 지 7일이 지난 이벤트는 더 보내지 않습니다. 서버의 중복 기억이 모두 7일이라, 그보다 늦은 재전송은 새 이벤트로 들어오기 때문입니다.
대가
이미 퍼진 옛 SDK 탭은 고친 SDK가 닿을 때까지 계속 다시 보냅니다. 옛 탭 몫을 빼면 배수는 약 1.2배로 내려갔습니다.
D-08

전환 판정에서 기존 경로를 정답지로 쓰지 않기

고민
기존 경로의 세션 집계 자체가 30%까지 떨어져 있었습니다. 기존 경로를 정답으로 놓고 대조하면, 기존 경로의 결손을 새 경로의 오류로 세게 됩니다.
선택지
① 기존 경로를 정답지로 대조
② 건수만 비교하고 전환
③ 원본 완결성, 대표 사례, 불변식으로 판정하고, 원본 도달 누락만 엄격하게
결정과 이유
③을 골랐습니다. 비교 기준이 틀리면 대조가 판단을 흐립니다. 집계는 원본에서 다시 계산할 수 있습니다. 원본 도달은 해지 뒤 되살릴 수 없어서 그것만 엄격하게 봤습니다. 운영 미러링 전에는 레플리카 장애 시험, 적재기 강제 종료 시험, 런북 훈련을 입장 조건으로 두었습니다. 7일 관찰과 비율 램프는 관리형 클러스터 비용을 먼저 끊으려고 생략했습니다. 대신 해지 직전, 새 경로에 없고 다시 계산할 수 없는 원천만 골라 보관하고 원본과 대조했습니다.
대가
해지 시점에는 공식 안정 판정 장치(매일 대조, 경보 채널, 운영 Flink 복구 리허설) 대신 런타임 지표(원장과 오프셋 차이 0, 재시작 없음, 키 누락 0)로 판단했습니다.

04결과

  • 운영 미러링 24시간, 두 경로의 이벤트 키 집합 차이 약 0.06% (고객사별 ±0.2% 안), 12개 파티션 오프셋 모두 일치
  • 미러링 첫날 복사본 누락 약 0.2% → 순서 수정 뒤 0. 이미 빠진 분량은 보충 경로로 원본에 되살려 누락 0
  • 레플리카 1대 정지 동안 쓰기 즉시 거부, 유실 0. 복귀 약 2분 뒤 밀린 분량 처리 완료
  • 적재 중 강제 종료와 동시 재시작에서 중복 0, 두 레플리카 내용 동일
  • 적재 원장과 Kafka 오프셋 12개 파티션 모두 일치, 약 1주 뒤 다시 대조해도 차이 0 (운영)
  • Flink 세션 집계 잡 약 8일 재시작 없이 운영 (10월 중순 기준)
  • 새 클러스터의 집계 뷰와 갱신 뷰 0개. 2026.10.16 주 경로 전환과 관리형 ClickHouse 해지

측정: 수신 → 원본 표 약 33초, 세션 집계까지 약 65초 (스테이징 합성 이벤트, 휴면 뒤 기동 상태에서 1회).

05트러블슈팅

T-01

실패 기록이 없는데 복사본 약 0.2%가 빠진 문제

문제
운영 미러링을 켠 첫날, 기존 경로에는 있고 새 경로에는 없는 이벤트가 키 기준 약 0.2% 나왔습니다. 실패 로그, 예비 큐, 실패 메시지 보관 큐(DLQ)에는 아무것도 없었습니다.
원인
크기 초과와 형식 오류를 먼저 의심했지만 둘 다 아니었습니다. 빠진 이벤트는 모두 페이지를 떠날 때 나가는 이벤트였습니다. 같은 시간대 Worker 호출의 약 4%는 클라이언트가 먼저 연결을 끊은 호출이었습니다. 코드는 기존 경로 전송을 await로 기다린 뒤에야 복사본 전송을 waitUntil에 걸었습니다. Cloudflare는 클라이언트가 먼저 끊으면, 그때까지 waitUntil에 걸린 일만 이어서 처리합니다.
해결
기존 경로를 기다리기 전에 복사본 전송을 waitUntil에 거는 순서로 바꿨습니다. 끊김을 흉내 낸 단위 테스트로, 고치기 전에는 복사본 전송이 아예 걸리지 않는 것을 먼저 확인했습니다. 끊긴 뒤 실제로 전송되는지는 배포 뒤 키 대조로 확인했습니다.
결과
배포 뒤 키 대조에서 누락은 0이었습니다. 이미 빠진 이벤트는 기존 경로 원본에서 되살려 원본 표에 다시 넣었고, 대조에서 누락 0을 확인했습니다. 건수만 비교했다면 찾지 못했을 누락입니다.

06배운 점

  • 정렬키, 파티션, 중복 제거는 따로 고르는 설정이 아니었습니다. 세션을 무엇으로 볼지가 바뀌자 셋이 함께 바뀌었습니다. 결국 상태를 어디에 둘지까지 정했습니다.
  • 경로를 바꿀 때는 이벤트 종류별 전송 약속부터 표로 맞춰야 합니다. 저장 전 거르기를 없애면서, 기존 거르기가 우연히 하던 상한 역할을 놓쳤습니다.
  • 경로를 바꿀 때 건수만 비교하면 일부가 빠져도 알아채지 못합니다. 이벤트 키 집합과 오프셋처럼 서로 다른 기록이 맞는지를 전환 조건으로 걸어야 합니다.
