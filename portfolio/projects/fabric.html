Scholarly Chain, Hyperledger Fabric 학생회 장부

학생이 낸 회비는 학생회가 승인하고, 학생회가 쓴 돈은 학생이 투표로 허가하는 블록체인 장부 서비스입니다. 그중 Hyperledger Fabric 네트워크를 AWS EKS에 배포해 운영하고, 서비스 서버와 블록체인을 잇는 NestJS 서버를 만들었습니다.

기간
2025.03 – 2025.06
구분
학과 캡스톤디자인 과제입니다. 4명이 기획과 디자인, 프론트엔드, 백엔드, 블록체인과 인프라를 한 명씩 나눠 맡았습니다.
역할
블록체인과 인프라를 맡았습니다. Fabric 네트워크와, 서비스 서버의 요청을 블록체인으로 전달하는 NestJS 연동 서버를 직접 설계하고 개발했습니다. chaincode 배포도 제가 했습니다.

01상황: 어떤 프로젝트이고 무엇을 해결하는가

학과 캡스톤디자인에서 4명이 만든 학생회비 장부 서비스입니다. 주제는 "학생회비 장부를 학과 구성원들과 투명하게 공개하는 블록체인 기반 클라우드 네이티브 웹 서비스"입니다.

학생회비는 학생이 내고 학생회가 씁니다. 그런데 장부는 학생회만 기록합니다. 학생은 기록이 맞는지 확인할 방법이 없습니다. 목표는 학생회 공금 횡령 문제를 예방하는 것입니다.

해결하려는 문제
학생회만 기록하는 학생회비 장부를 학생이 확인할 수 없습니다.
해결 방식
입금은 학생회가 승인하고, 출금은 학생이 투표로 허가합니다. 승인된 기록은 블록체인 ledger에 남깁니다.

서비스 기능

  • 입금: 학생이 행사명, 연도, 학기, 금액, 증빙 자료로 입금 내역을 올립니다. 학생회가 승인하거나 거절합니다.
  • 출금: 학생회가 같은 항목으로 출금 내역을 올립니다. 학생이 1시간 동안 투표해 허가 여부를 정합니다.
  • 가입: 학생과 학생회 소속을 인증합니다. 가입 요청은 학생회 구성원이 승인합니다.

블록체인을 쓴 이유는 승인된 기록을 학생회도 나중에 고칠 수 없게 하려는 것이었습니다. 블록체인은 기록이 hash로 이어져 있어 하나를 고치면 드러납니다.

용어

  • ledger: 블록체인에 남는 거래 기록입니다.
  • chaincode: ledger에 무엇을 어떻게 기록할지 정한 프로그램입니다.
  • peer: 거래를 실행해 결과에 서명(endorsement)하고 ledger를 보관하는 node입니다.
  • orderer: endorse된 거래를 순서대로 모아 블록으로 묶는 node입니다.
  • CA: 사용자와 node에 인증서를 발급하는 서버입니다.

02과제와 역할

팀 목표는 가입, 입금 승인, 출금 투표를 ledger에 남기는 서비스를 한 학기 안에 만드는 것이었습니다. 팀은 기획과 디자인, 프론트엔드, 백엔드, 블록체인과 인프라 각 1명입니다. 저는 블록체인과 인프라를 맡았습니다.

직접 설계하고 개발
Fabric 네트워크를 구성했습니다. 거래를 블록으로 묶는 orderer 3대, 학생과 학생회 두 조직의 peer와 peer가 상태 데이터를 두는 CouchDB, 인증서를 발급하는 CA 3대로 이루어져 있습니다. 네트워크 설정 파일은 44개이고, 그중 27개가 Kubernetes에 올리는 리소스 정의입니다. chaincode는 이미지로 만들어 peer 밖의 별도 Deployment로 띄우고, peer가 여기에 접속해 실행을 맡기는 외부 서비스 방식으로 배포했습니다. NestJS 연동 서버는 CA에서 사용자 인증서를 발급받고, chaincode를 호출하고, 실행 결과를 Spring 서버에 돌려줍니다. 서버끼리 주고받는 메시지 형식은 백엔드 담당 팀원과 함께 정했고, 그중 NestJS 쪽 구현을 맡았습니다.
팀원이 맡은 부분
로그인, 학번 검증, MySQL 저장, Firebase 푸시 알림(FCM), 증빙 이미지 업로드를 맡는 Spring Boot API 서버는 팀원이 만들었습니다. Next.js 화면과 Vercel 배포, 서비스 기획과 디자인도 팀원들이 맡았습니다.

03해결 과정

1. 아키텍처

초기 구조에서는 Spring 서버가 Fabric과 직접 통신했습니다. 최종 구조에서는 블록체인 통신을 NestJS 서버로 떼어 냈습니다. 두 서버 사이에는 Redis Streams를 두었습니다.

  • 화면은 팀원이 Next.js로 만들었습니다. 학생과 학생회가 입출금 내역을 올리고, 승인하고, 투표하고, 조회하는 곳입니다.
  • API 서버는 팀원이 Spring Boot로 만들었습니다. 로그인과 학번 검증을 하고, 블록체인이 필요한 요청은 요청 스트림에 넣은 뒤 응답 스트림에서 결과를 기다립니다. 사용자에게 가는 푸시 알림(FCM)도 이 서버가 보냅니다.
  • 두 서버 사이의 메시지는 Redis Streams로 주고받습니다. Spring 서버가 요청을 넣는 요청 스트림과, NestJS 서버가 결과를 돌려주는 응답 스트림 두 개를 두었습니다.
  • 연동 서버는 제가 NestJS와 Fabric SDK로 만들었습니다. 요청 스트림에서 읽은 메시지를 chaincode 호출로 바꾸고, 실행 결과를 응답 스트림으로 돌려줍니다.
  • key store로는 Firebase를 썼습니다. 사용자마다 발급한 인증서와 개인키를 여기에 보관합니다.
  • ledger는 Fabric 2.3 네트워크에 남습니다. 네트워크는 Raft consensus를 쓰는 orderer 3대, 학생 조직과 학생회 조직의 peer와 CouchDB, CA 3대로 이루어져 있고, ledger를 함께 쓰는 단위인 채널은 하나만 두었습니다.
  • 배포와 운영은 AWS EKS에서 했습니다. 서울 리전 가용영역 2개에 worker node를 두고, orderer와 peer의 데이터는 EFS로 공유하는 PV에 두었습니다. 개발할 때는 같은 매니페스트를 로컬 Kubernetes에 띄웠습니다. 처음에는 k3s, 이후에는 minikube를 썼습니다.

2. 주요 흐름

흐름 1. 가입과 인증서 발급

  1. 팀원이 만든 Spring 서버가 가입하려는 사람이 실제 학생인지 확인하고, 요청 스트림에 가입 메시지를 넣습니다.
  2. NestJS 서버가 요청 스트림에서 메시지를 읽습니다.
  3. NestJS 서버가 사용자가 속한 조직의 CA에 사용자를 등록하고, 인증서와 개인키를 발급받습니다.
  4. 받은 인증서와 개인키를 Firebase에 저장합니다.
  5. 그 인증서로 가입 요청 chaincode를 실행합니다. ledger에는 대기(PENDING) 상태가 남습니다.
  6. chaincode 실행이 끝나면 응답 스트림에 결과를 넣습니다.
  7. 가입 요청은 학생회 구성원이 승인 chaincode를 실행해야 승인(APPROVED) 상태가 됩니다.

최종 구현에서는 인증서와 개인키를 Firebase에 두었습니다. ledger에는 가입 요청과 승인 상태만 남겼습니다.

흐름 2. 입금과 학생회 승인

  1. 학생이 입금 내역을 올립니다.
  2. NestJS 서버가 Firebase에서 그 학생의 인증서를 꺼내 입금 chaincode를 실행합니다.
  3. chaincode가 요청자가 학생 조직원인지 검사하고 대기 항목을 만듭니다.
  4. 학생회 구성원이 승인하면 chaincode가 승인자의 소속을 검사합니다.
  5. 검사를 통과하면 항목이 승인(APPROVED) 상태가 됩니다.

흐름 3. 출금과 학생 투표

  1. 학생회가 출금 내역을 올리면 chaincode가 1시간짜리 투표를 엽니다.
  2. 출금 chaincode 실행이 끝나면 NestJS 서버가 결과를 응답 스트림에 넣습니다.
  3. 팀원이 만든 Spring 서버가 이 응답을 받아 학생들에게 투표 알림을 보냅니다.
  4. 학생이 투표하면 투표 chaincode가 집계를 바꿉니다.
  5. 투표 마감은 마감 확인 chaincode로 처리합니다. 1시간이 지난 투표는 찬반 비율로 결과가 정해져 ledger에 남습니다.
  6. 마감 확인 chaincode는 NestJS 서버 안에 등록한 작업이 10분마다 호출합니다.
  7. 마감 확인은 NestJS 서버에 HTTP 요청을 보내 실행할 수도 있습니다.

3. 설계 고민과 결정

계좌 자동 연동인가, 직접 입력과 상호 확인인가

  • 고민: 처음에는 학생회 계좌 거래 내역을 API로 받아 블록체인에 넣으려 했습니다. 계좌 조회 API는 마이데이터 사업자만 쓸 수 있었습니다.
  • 선택지: 두 가지였습니다. 모의 데이터를 계속 넣어 실시간으로 연동되는 것처럼 보이게 하는 방법과, 학생과 학생회가 직접 입력하고 상대가 확인하는 방법입니다.
  • 결정: 팀 회의에서 직접 입력 방식으로 정했습니다. 모의 데이터 방식은 사용자가 할 일이 없었습니다. 이에 따라 입금은 학생회가, 출금은 학생이 확인하는 구조가 됐습니다.

퍼블릭 체인인가, 허가형 Fabric인가

  • 고민: 학과 밖 사람은 장부를 볼 수 없어야 했습니다. 학생과 학생회 소속도 구분해야 했습니다.
  • 선택지: 누구나 참여할 수 있는 퍼블릭 체인과, 미리 허가된 참여자만 들어올 수 있는 Hyperledger Fabric을 비교했습니다.
  • 결정: Fabric을 골랐습니다. chaincode는 Go로, 연동 서버는 TypeScript로 쓸 수 있어 새 언어를 배울 부담이 적었습니다.
  • 구성: 학생 조직과 학생회 조직을 나누었습니다. Fabric이 조직 구성원의 신원을 확인할 때 쓰는 조직 식별자(MSP)는 각각 StudentMSP와 Student-councilMSP입니다. 조직마다 인증서를 발급하는 CA를 따로 두었습니다.
  • endorsement policy: 거래 하나를 ledger에 남기려면 몇 개 조직의 endorsement(서명)를 받아야 하는지 정하는 규칙입니다. Fabric default인 과반(MAJORITY)을 그대로 썼습니다. 조직이 2개뿐이라 과반을 넘으려면 두 조직이 모두 endorse해야 기록이 남습니다.

chaincode 이벤트를 누가 받을 것인가

  • 고민: 가입 요청이 ledger에 남으면 학생회 구성원에게 알려야 했습니다.
  • 선택지: 세 가지 안을 비교했습니다. 1안은 각 클라이언트가 chaincode 이벤트를 감지해 API 서버에 다시 알리는 구조라, 클라이언트가 1,000개면 이벤트 하나에 API 서버로 요청이 1,000개 들어옵니다. 2안은 WebSocket 연결을 계속 유지하는 구조라 연결이 늘수록 서버 부담이 커집니다. 3안은 로그인 상태를 Redis에 두고, 로그인한 클라이언트만 알림 채널을 구독하게 합니다.
  • 결정: 당시 블로그 글에서는 3안을 절충안으로 적어 두고, 최종안은 팀원과 함께 정하기로 했습니다.
  • 최종 구조: 블록체인과 통신하는 서버를 NestJS 서버 한 곳으로 모았습니다. 사용자 알림은 팀원이 만든 Spring 서버가 FCM 푸시로 보냅니다.

Redis Pub/Sub인가, Redis Streams인가

  • 고민: 요청 하나가 여러 서버를 거칩니다. 중간에 NestJS 서버가 멈추면 Pub/Sub 메시지는 사라집니다.
  • 선택지: Redis Pub/Sub, Redis Streams, Kafka 세 가지를 비교했습니다.
  • 결정: Redis Streams를 골랐습니다. 메시지가 스트림에 남아 있어, 받는 서버가 잠시 멈춰도 사라지지 않습니다.
  • 지연: 블록체인에 기록 한 건을 남기는 데 수백 밀리초에서 몇 초가 걸립니다. 그래서 Streams를 한 번 거치며 생기는 지연은 이에 비해 작아 문제가 되지 않는다고 봤습니다.
  • 제외: Kafka는 운영 부담이 커서 뺐습니다.

사용자 키를 어디에 둘 것인가

  • 고민: Fabric SDK의 default wallet은 키를 서버 디스크 파일로 둡니다. NestJS Pod가 여러 개면 한 Pod에서 가입한 사용자의 키가 다른 Pod에는 없습니다.
  • 선택지: 키를 서버 디스크에 두는 파일 wallet, CouchDB에 두는 CouchDB wallet, Firebase에 두는 방법을 비교했습니다.
  • 결정: Firebase를 골랐습니다. CouchDB wallet은 별도 인프라가 필요했습니다. Firebase는 알림 때문에 이미 쓰고 있었습니다.
  • 구현: 요청이 올 때마다 Firebase에서 해당 사용자의 인증서와 개인키를 꺼내, 메모리에만 두는 wallet에 넣고 그 사용자의 신원으로 chaincode를 실행합니다.

4. 구현 상세

Fabric 네트워크를 Kubernetes에 올리기

  • orderer는 Raft consensus 방식으로 3대를 두었습니다. Fabric 설정에서는 이 방식을 etcdraft라고 부릅니다. 3대 중 2대만 살아 있어도 거래 순서를 정하는 consensus가 계속 이루어집니다.
  • 블록은 2초가 지나거나 거래가 10건 모이면 만들어집니다. Fabric 샘플 설정의 default를 그대로 썼습니다.
  • peer와 CouchDB를 한 Pod에 두었습니다.
  • peer는 Prometheus가 지표를 읽어 갈 수 있게 9443 포트를 열었습니다.
  • 네트워크는 다음 순서로 띄웁니다. 먼저 데이터를 보관할 PV를 만들고 CA 3대를 띄웁니다. 이어서 한 번 실행하고 끝나는 Kubernetes 작업(Job)으로 인증서를 발급하고, 또 다른 Job으로 첫 블록과 채널 설정 파일을 만듭니다. 그다음 orderer와 peer를 띄워 peer를 채널에 가입시키고, 마지막으로 chaincode를 설치해 조직마다 승인합니다.

chaincode를 peer 밖에서 실행하기

  • chaincode를 이미지로 만들어 조직마다 별도 Deployment로 띄웠습니다.
  • peer에는 external builder 스크립트를 넣었습니다. 그래서 peer는 chaincode를 직접 빌드하지 않고, 따로 떠 있는 chaincode 서버에 접속해 실행을 맡깁니다.
  • chaincode 소스는 공개 저장소에 올라가 있지 않습니다. 배포에 쓴 이미지는 제 Docker Hub 계정에 있습니다.
  • NestJS 서버가 호출하는 chaincode 함수는 22개입니다. ledger에 기록을 남기는 함수가 11개, 조회만 하는 함수가 11개입니다.

NestJS 연동 서버

  • 요청 스트림에서 메시지를 한 번에 10개씩 읽습니다. 가입, 입금, 투표처럼 요청 종류가 17가지이고, 종류마다 맡는 handler로 나눠 넘깁니다.
  • 메시지를 handler에 넘긴 뒤 Redis에 ACK를 남겨 처리를 마쳤다고 표시합니다.
  • chaincode 실행이 실패하면 오류 응답을 응답 스트림에 넣어 Spring 서버에 알립니다.
  • 응답에 원래 요청의 ID를 넣어 Spring 서버가 요청과 응답을 짝짓게 했습니다.
  • chaincode가 보내는 이벤트를 받는 handler와, 10분마다 투표 마감을 확인하는 작업을 서버에 등록했습니다.

04트러블슈팅

T-01

CA 인증서에 Pod 이름이 들어가 접속에 실패한 문제

문제
인증서 발급 스크립트가 CA에 접속하면 x509: certificate is valid for ca-orderer-549bd75db5-xxg95, localhost, not ca-orderer 오류가 났습니다. 12시간 넘게 막혀 있었습니다.
원인
CA는 처음 뜰 때 TLS 인증서를 만들면서 인증서의 이름(CN)에 자기 Pod 이름을 넣었습니다. Pod 이름은 Kubernetes가 붙이는 이름이라 ca-orderer-549bd75db5-xxg95처럼 뒤에 무작위 문자가 붙습니다. 클라이언트는 고정된 Service 이름인 ca-orderer로 접속했기 때문에, 접속한 주소와 인증서에 적힌 이름이 달라 hostname verification에서 실패했습니다.
해결
CA 3대의 설정 파일에 인증서에 넣을 이름으로 Service 이름을 적어 두고, CA가 처음 뜨기 전에 이 설정이 적용되게 했습니다. peer 인증서도 Service 이름으로 발급했습니다.
결과
인증서에 적힌 이름과 접속하는 Service 이름이 같아지면서, CA와 orderer와 peer가 서로 Service 이름으로 접속해 TLS 연결을 맺었습니다.
T-02

WSL2 위 k3s에서 CA에 닿지 않던 문제

문제
k3s에 띄운 CA에 localhost:10054로 접속하면, 그 주소에서 응답하는 프로세스를 찾지 못했습니다.
원인
k3s가 쓰는 네트워크와 WSL2의 네트워크가 분리돼 있어 localhost로는 CA에 닿지 않았습니다. port forwarding으로 우회할 수는 있었지만, WSL2의 IP 주소가 실행할 때마다 바뀌어 쓰기 번거로웠습니다.
해결
클러스터를 별도 가상 머신(VM)에 만드는 minikube로 옮겼습니다. minikube의 VM은 Windows와 같은 호스트 네트워크를 씁니다.
결과
minikube로 옮기면서 orderer와 peer가 데이터를 저장하는 볼륨 설정을 minikube 환경에 맞게 고쳤습니다.

05결과

  • 거래 순서를 정하는 orderer 3대, 학생과 학생회 두 조직, 인증서를 발급하는 CA 3대로 이루어진 Fabric 네트워크를 AWS EKS에 배포해 운영했습니다. 개발 단계에서는 같은 구성을 로컬 Kubernetes에 띄워 검증했습니다.
  • 가입, 입금 승인, 출금 투표에 쓰는 chaincode 함수 22개를 NestJS 서버에서 호출할 수 있게 만들었습니다. ledger에 기록을 남기는 함수와 조회만 하는 함수가 11개씩입니다.
  • 구성과 문제 해결 과정은 블로그로 남겼습니다.

한계

  • 개인키를 Firebase에 암호화하지 않고 저장했습니다.
  • 서버가 모든 사용자의 키를 대신 보관했습니다. 그래서 서버를 운영하는 사람은 누구의 이름으로도 서명할 수 있었습니다.
  • NestJS 서버는 메시지를 handler에 넘기자마자 ACK를 남깁니다. 그래서 chaincode를 실행하는 도중에 서버가 멈추면, 그 요청은 이미 끝난 것으로 표시돼 있어 다시 처리되지 않습니다.

06배운 점

인증서에 적힌 이름이 접속에 쓰는 Service 이름과 다르면 TLS 연결이 맺어지지 않았습니다. node를 띄우기 전에 인증서 이름과 Service 이름이 같은지 먼저 확인해야 합니다.
