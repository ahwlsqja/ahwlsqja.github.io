01상황과 역할

수파리드는 광고 클릭부터 자사몰, 매장, 외부몰 구매까지 고객 여정을 하나의 어트리뷰션으로 잇는 옴니채널 고객 인텔리전스 플랫폼입니다. 행동 이벤트는 고객사 웹사이트에 심은 브라우저 SDK로 모읍니다. 수집 Worker와 SDK는 Cloudflare에서, API와 인증 서비스는 GCP에서 돌고, 이벤트는 ClickHouse에 쌓입니다. 개발은 AI 네이티브 방식이라 작은 변경이 빠르게 많이 들어왔고, 배포 파이프라인은 하루 30건 안팎의 변경을 가정하고 설계했습니다.

처음에는 변경이 반영되면 사람이 스키마 적용과 배포 명령을 순서대로 손으로 실행했습니다. 하루에 두 번 사고가 났습니다. 새 컬럼을 쓰는 수집 Worker가 운영 ClickHouse에 그 컬럼이 생기기 전에 배포돼 약 9시간 동안 이벤트 적재가 거부됐고, 약 9,200건을 잃었습니다. 수집 응답은 정상이라 경보도 울리지 않았습니다. 같은 날 API도 마이그레이션 없이 코드만 올라가 오류를 냈습니다.

저는 두 사고가 사람의 부주의보다 "스키마를 먼저 적용하고 배포한다"는 순서를 지키게 하는 장치가 없어서 생겼다고 판단했습니다. 변경이 빨라질수록 배포는 더 자주 깨지기 때문에, 검증과 rollback 장치가 변경 속도보다 앞서야 한다고 생각했습니다. 그래서 첫 배포 경로 설계부터 구현과 운영, GitOps 전환까지 직접 맡았습니다.

이 일을 하며 풀어야 했던 과제는 세 가지였습니다.

  • 스키마 적용, 인프라 적용, 배포가 사람의 기억이 아니라 파이프라인 안에서 정해진 순서로만 돌아야 했습니다.
  • staging에서 검증한 것과 운영에 올라가는 것이 같은 이미지라는 것을 기록으로 보일 수 있어야 했습니다.
  • 운영에 무엇이 떠 있는지 언제든 Git으로 설명할 수 있어야 했습니다.
맡은 일
배포 순서를 지키게 하는 첫 배포 경로, 반영 전 검사와 deploy queue, 같은 digest로 올리는 운영 promotion과 canary, 스키마와 인프라 변경 게이트를 설계하고 구현해 운영했습니다. 이어서 Argo CD와 Kargo 기반 GitOps 전환을 결정하고 진행했습니다.
범위 밖
API를 Cloud Run에서 GKE로 옮긴 이관 자체는 무중단 인프라 이관 페이지에 적었습니다. 이 페이지는 그 위에서 변경 하나가 운영까지 가는 길을 다룹니다.

02해결 과정

그림 1은 한 번 빌드한 이미지가 staging 검증을 거쳐 같은 digest로 운영까지 가는 흐름입니다. 탭에서 staging 검증이 실패할 때와 운영에서 이상이 보일 때의 경로도 볼 수 있습니다. 아래에는 이 흐름을 만든 순서대로 적었습니다.

1. 첫 배포 경로: 순서를 파이프라인이 지키게

운영 배포는 명시적으로 실행해야만 도는 별도 경로로 바꾸고, staging 배포가 성공해도 운영 배포가 자동으로 이어지지 않게 했습니다. 배포 스크립트는 ClickHouse 스키마가 준비됐는지와 schema drift를 먼저 검사하게 했고, 스크립트를 거치지 않은 직접 배포 명령은 일부러 실패하게 막았습니다.

도구도 이때 골랐습니다.

  • 스키마는 ClickHouse까지 선언형으로 다루고 파괴적 변경을 CI에서 정책으로 막을 수 있는 Atlas Pro를 썼습니다. 문서로만 적은 규칙은 권고에 그치고, 변경이 빠르게 들어오는 개발에서는 도구가 막아야 한다고 봤습니다.
  • 인프라는 Terraform으로 선언했습니다. 처음에는 라이선스 때문에 OpenTofu를 먼저 검토했습니다. 그런데 사내 인프라 관리 용도로는 Terraform 라이선스로도 비용 없이 쓸 수 있었고, 같은 구성을 그대로 옮길 수 있어서 Terraform을 골랐습니다.
  • GitHub Actions는 실행 트리거로만 쓰고 실제 로직은 CLI와 배포 스크립트에 뒀습니다. CI가 흔들려도 같은 스크립트를 다시 돌리면 되게 하려는 선택이었고, 이 선택 덕분에 CI가 멈췄을 때도 배포 경로가 살아 있었습니다.

2. 반영 전 검사, 자격 증명 분리, deploy queue

반영 전 검사는 "반영해도 되는가"만 판단하는 읽기 전용 단계로 두었습니다. 타입 검사와 테스트, Atlas의 파괴적 스키마 변경 검사, Terraform plan, SDK 이벤트와 ClickHouse 컬럼이 맞는지 보는 contract test가 여기서 돕니다. 이 단계는 시크릿을 쓰지 않습니다.

자격 증명은 Infisical에 모으고, 단계마다 GitHub OIDC로 short-lived credential만 발급받게 했습니다. 반영 전 단계는 staging과 운영 자격을 받을 수 없고, 자격을 발급받는 단계에서는 저장소의 스크립트를 실행하지 않습니다. 검사 전 코드가 운영 자격에 닿는 길을 규칙이 아니라 구조로 없앤 것입니다.

반영된 변경은 한 번만 빌드하고, 이미지 digest와 스키마 계획, 인프라 계획, 테스트 결과를 하나로 묶은 배포 후보 기록을 만들어 deploy queue에 넣었습니다. staging을 바꿀 수 있는 것은 이 queue 하나뿐입니다. queue는 한 번에 한 후보씩 staging에 마이그레이션과 배포를 적용하고, 실제 랜딩 페이지에서 SDK가 보낸 이벤트가 ClickHouse에 쌓여 대시보드에서 조회되기까지 전체 수집 경로를 E2E로 확인합니다. 이 검증을 통과한 후보만 운영 후보가 됩니다. 첫 후보가 이 검증을 통과했습니다.

3. 같은 digest로 운영 promotion

운영 promotion은 staging을 통과한 후보만 입력으로 받습니다. 운영 직전에 스키마와 인프라 계획을 다시 뽑아 그사이 바뀐 것이 없는지 보고, 이미지는 다시 빌드하지 않고 배포 후보 기록에 적힌 digest를 그대로 올립니다. 배포 뒤에는 10분 동안 데이터 신호를 보고 유지, 보류, rollback을 판정합니다.

한 번도 끝까지 돌아 본 적 없는 파이프라인이라 첫 운영 promotion은 범위를 좁혔습니다. 스키마와 인프라 변경이 없는 코드 변경만 올렸고, 자동 rollback은 staging에서 먼저 연습했습니다. 이 연습에서 rollback에 쓸 토큰이 비어 있는 결함을 찾아 고쳤습니다. 열세 번째 시도에서 첫 운영 promotion을 끝까지 마쳤습니다. 그 전의 실패는 모두 판정 단계에서 멈춰 운영을 바꾸지 않았습니다.

운영 promotion을 돌리면서 ClickHouse 마이그레이션이 배포마다 51개 파일을 처음부터 다시 실행하고 있다는 것도 드러났습니다. promotion을 하는 동안 집계 뷰가 지워졌다가 다시 만들어졌고, 운영이 몇 번째 마이그레이션까지 적용됐는지 시스템이 알려 주지 못했습니다. Atlas의 versioned migration 방식으로 바꿔, 적용 이력을 담은 ledger를 보고 아직 적용하지 않은 파일만 한 번 적용하게 했습니다.

4. 병목과 우회를 걷어 낸 과정

그 뒤에는 배포 경로 자체가 병목이 됐습니다. 스키마 사전 점검이 과거 데이터 backfill까지 떠안아 무거워졌고, Atlas가 적용하는 마이그레이션을 사전 점검이 한 번 더 적용하면서 queue가 하루 동안 멈췄습니다. 되돌릴 수 없는 스키마 적용은 정확히 한 번만 하고, backfill은 배포와 떼어 백그라운드로 보내는 구조로 나눴습니다.

한 대상의 실패가 무관한 대상의 배포까지 막는 문제도 있었습니다. Terraform plan에 삭제가 한 건 잡히면 그 실패가 API 배포까지 열흘 넘게 붙잡는 식이었습니다. 배포를 대상별 경로로 나누고, 각 경로는 그 대상이 실제로 쓰는 스키마와 기능이 준비됐는지만 기다리게 했습니다. 실행 이력 검사는 배포를 막지 않고 기록만 남기게 바꿨습니다. 배포를 멈추는 게이트는 데이터 손실과 직결되는 스키마 검사, staging 동시 배포를 막는 lock, 인프라 삭제와 교체의 자동 적용 금지 셋만 남겼습니다.

queue가 일곱 번 연속 실패하는 동안 경보가 한 건도 없었던 일도 있었습니다. queue 정지, 운영에 나가지 못하고 쌓인 변경, 인프라 drift 감시 job 자체의 고장을 각각 따로 감시하게 했습니다. 로컬에서 배포 명령을 직접 실행하는 것은 실행 전에 막고, 긴급 배포도 검증된 후보만 올리게 했습니다.

5. Argo CD와 Kargo 기반 GitOps 전환

API를 Cloud Run에서 GKE로 옮긴 뒤, deploy queue는 한 번도 성공하지 못했고 운영 promotion은 11일 동안 멈췄습니다. 그사이 운영은 사람이 직접 바꿨습니다. 조사해 보니 운영 클러스터를 바꾼 작업의 약 90%가 사람 손이었고, 운영 API는 반영된 적 없는 중간 버전으로 떠 있었습니다. 운영에 무엇이 떠 있는지 Git으로 설명할 수 없는 상태였습니다.

하루 동안 조사와 결정, 전환을 진행했습니다. 배포 상태만 담는 별도 GitOps 저장소를 만들고, 운영 중인 리소스를 지금 상태 그대로 Git으로 가져왔습니다. server-side diff로 차이가 0인 것을 확인한 뒤에 Argo CD가 넘겨받게 했고, 옛 배포 경로의 클러스터 쓰기 권한을 끈 다음에야 staging 자동 동기화를 켰습니다.

역할은 셋으로 나눴습니다. CI는 빌드와 테스트만 하고, Kargo는 새 이미지를 promotion 후보로 기록해 staging에 자동으로 올리고 검증하며, Argo CD는 Git에 적힌 상태를 클러스터에 반영합니다. 운영에는 staging에서 검증된 digest만 올라가고, 승인 한 번이 마지막 사람 판단입니다. DB 마이그레이션은 Argo CD의 PreSync Job으로 옮겨 앱 반영 직전에 같은 이미지로 한 번 돌게 했습니다. 시크릿은 External Secrets Operator가 키 파일 없이 GCP Secret Manager에서 읽게 했고, CI 계정의 클러스터 권한은 읽기 전용으로 줄였습니다. Argo CD는 GKE에서 도는 앱만 맡고, Cloudflare에서 도는 수집 Worker와 SDK, Terraform으로 다루는 인프라는 각자의 경로로 배포합니다.

같은 내용을 책임별로 다시 적으면 아래와 같습니다.

03설계 결정

해결 과정의 방향을 정한 판단 여덟 가지입니다. 고민, 선택지, 결정과 이유, 대가 순서로 적었습니다.

D-01

배포 단위: 시간 묶음 대신 후보 하나씩 통과시키는 deploy queue

고민
여러 변경이 같은 staging에 쌓였습니다. 변경마다 따로 배포하면 늦게 끝난 검증이 다른 변경이 덮어쓴 staging을 통과할 수 있어, 어느 변경의 성공인지 알 수 없었습니다.
선택지
① GitHub이 제공하는 기본 queue 기능을 쓰는 안
② 정해진 시간에 여러 변경을 묶어 배포하는 release train
③ 변경마다 병렬로 staging에 배포하는 안
④ 반영된 후보를 한 줄로 staging에 통과시키는 자체 deploy queue
결정과 이유
④를 골랐습니다. ①은 private 저장소에서 상위 요금제가 필요했고, 코드를 합치기 전 단계의 도구라 배포 순서를 관리하는 용도와 맞지 않았습니다. ②는 실패가 어느 변경 때문인지 흐려지고, 빠르게 들어오는 변경을 시간 단위로 끊어 지연이 생겼습니다. 후보를 한 줄로 직렬화하면 staging 상태가 항상 한 후보에만 대응해, 무엇이 깨뜨렸는지 바로 짚을 수 있습니다. 아직 시작하지 않은 오래된 후보만 새 후보로 대체하고, 실패한 후보의 기록은 남기되 뒤 후보를 막지 않게 했습니다. release train은 후보 이력과 audit log만 남기는 역할로 줄였습니다.
대가
처리량이 직렬로 묶이고 queue가 single point of failure가 됐습니다. ledger와 lock을 모두 직접 구현해 워크플로 정의가 4천 줄을 넘었고, 이 유지 부담이 나중에 GitOps로 옮긴 이유 중 하나가 됐습니다.
D-02

운영 후보 자격: 가벼운 smoke가 아니라 전체 수집 경로 E2E

고민
E2E가 느리고 불안정해서 5분 안쪽의 API smoke test로 줄이는 방법도 검토했습니다. 하지만 이 서비스의 핵심은 SDK가 보낸 이벤트가 ClickHouse까지 쌓이는 수집 경로 자체였고, 수집은 비동기라 응답 코드만으로는 성공을 알 수 없었습니다.
선택지
① smoke로 막고 전체 E2E는 야간에만 돌리는 안
② 변경마다 전체 E2E를 돌리는 안
③ 반영 뒤 staging에 실제로 배포하고, 전체 경로 E2E를 통과한 후보만 운영 후보로 삼는 안
결정과 이유
③을 골랐습니다. 반영 전 검사는 반영 가능성을, queue는 운영 후보 자격을, canary는 운영 배포 뒤 위험을 보도록 역할을 나눴습니다. 불안정성은 E2E를 줄여서가 아니라 원인을 분류해 다뤘습니다. 고정 대기 시간 대신 이벤트 ID로 정해진 시간 안에서만 조회하고, 테스트 인프라 실패만 제한적으로 retry하며 제품 로직 실패는 retry로 덮지 않습니다. 스키마가 안전한지와 데이터 의미가 맞는지는 서로 다른 검사 항목으로 나눠, 스키마 검사를 통과했다고 데이터까지 안전하다고 읽지 않게 했습니다.
대가
게이트가 무거워져 후보 하나를 판정하는 시간이 늘었습니다.
D-03

단계마다 할 일을 나누고, 환경을 바꾸는 주체는 하나만

고민
기존 자동 배포는 API 코드가 바뀌면 PostgreSQL과 ClickHouse 마이그레이션, 설정 동기화, 배포를 한 번에 돌렸고, ClickHouse만 바뀌면 아무것도 돌지 않았습니다. queue를 더하면서 이 경로를 남기면 같은 staging을 두 곳이 바꾸게 됩니다.
선택지
① 기존 자동 배포를 두고 queue만 추가하는 안
② 반영 전 검사를 단위 테스트로만 줄이는 안
③ 단계마다 할 일과 하지 않을 일을 정하고, staging 변경 권한은 queue에만 주는 안
결정과 이유
③을 골랐습니다. 반영 전 검사는 읽기 전용이고 시크릿을 쓰지 않습니다. 반영 뒤 빌드 단계는 이미지와 배포 후보 기록만 만들고 staging을 건드리지 않습니다. queue만 staging을 바꾸고, 운영 promotion은 통과한 후보만 받습니다. 기존 자동 배포는 명시적으로 끄고 지웠습니다. 반영 전에 만든 인프라 계획은 그사이 운영 상태가 바뀌면 낡기 때문에, 운영 직전에 plan을 다시 만드는 배포 게이트를 따로 뒀습니다.
대가
단계 사이에 후보를 넘기는 지점이 새 실패 지점이 됐습니다. 빌드가 끝나기 전에 후보가 queue에 등록되는 race condition이 있어, 빌드가 성공으로 끝난 이벤트에서만 등록하게 고쳤습니다.
D-04

한 번 빌드하고 같은 digest로 promotion

고민
운영 배포 때 다시 빌드하거나 태그로 이미지를 다시 찾으면, staging에서 검증한 것과 다른 바이트가 운영에 갈 수 있습니다. 실제로 같은 소스를 한 실행 안에서 두 번 빌드해 digest가 갈린 일이 있었습니다.
선택지
① 태그를 아무도 덮어쓰지 않는다는 규율에 기대는 안
② 운영 배포 때 다시 빌드하는 안
③ 한 번만 발행하고, 운영은 기록된 digest를 그대로 쓰는 안
결정과 이유
③을 골랐습니다. 검증한 대상과 배포한 대상이 같다는 것은 내용으로 정해지는 digest로만 보장됩니다. 레지스트리에 같은 소스의 이미지가 있으면 재사용하고 태그는 덮어쓰지 않으며, 운영은 태그를 다시 찾지 않고 배포 후보 기록의 digest를 씁니다. 수집 SDK와 Worker의 릴리스 이름도 같은 후보 식별자로 맞춰, canary에서 어떤 빌드가 떠 있는지 구분할 수 있게 했습니다. GitOps로 옮긴 뒤에도 이미지는 digest로만 고정하고 태그만 적으면 검사에서 실패하게 했습니다.
대가
같은 소스가 다른 후보로 다시 들어오면 처음 빌드한 이미지가 계속 쓰여, 후보 식별자와 실행 중인 버전이 맞는지는 경고로만 남습니다.
D-05

되돌릴 수 없는 것만 막고, backfill은 배포에서 떼기

고민
ClickHouse 마이그레이션이 배포마다 전체 파일을 다시 실행해 집계 뷰를 지웠다가 다시 만들었습니다. 사전 점검은 과거 데이터 backfill까지 떠안아, 한 고객의 세션 수십만 개를 다시 훑는 동안 배포가 멈췄습니다.
선택지
① 모든 데이터가 맞을 때까지 마이그레이션을 기다리는 안
② 검증을 생략하거나 준비 상태를 그냥 통과로 기록하는 안
③ 스키마 적용, 적용 뒤 쓰기 확인, backfill을 서로 다른 단계로 나누는 안
결정과 이유
③을 골랐습니다. DDL은 되돌릴 수 없어서 Atlas가 ledger를 보고 아직 적용하지 않은 파일만 한 번 적용하게 했고, 일부만 적용되면 되돌리지 않고 다음 마이그레이션으로 고칩니다. 적용 뒤 확인은 정상 표본으로 쓰기와 자원 한도만 짧게 보는 hard gate로 두고, backfill은 배포와 떼어 백그라운드로 보내며, 아직 채우지 못한 구간은 불완전하다고 표시합니다. 파괴적 스키마 변경은 반영 전 단계에서 모든 변경에 대해 10초대에 막고, 정당한 예외는 마이그레이션 파일 안에 이유를 적어야만 통과합니다. 검증의 강도는 되돌릴 수 있는지에 맞췄습니다.
대가
데이터가 완전히 맞지 않은 상태로 운영하는 기간이 생기고, 그 상태를 따로 감시해야 합니다.
D-06

사람 판단은 한 번, canary는 데이터 신호로

고민
운영 promotion 한 번에 사람 승인이 두세 번 필요했고, 승인을 기다리는 실행이 배포 lock을 붙잡아 다른 후보가 10시간 동안 시작하지 못했습니다. canary는 오류 추적 도구에 남은 오래된 오류 때문에 정상 후보를 계속 막거나, 이전 버전의 실패를 보고 새 배포를 rollback하려 했습니다.
선택지
① 승인과 canary 게이트를 모두 그대로 두는 안
② 모두 없애는 안
③ 승인은 운영 첫 배포 한 번, lock은 실제로 운영을 바꾸는 구간에만 걸고, canary는 데이터 신호만 차단하는 안
결정과 이유
③을 골랐습니다. 승인을 기다리는 동안 운영은 바뀌지 않으므로, lock은 운영을 바꾸거나 관측하는 구간에만 걸었습니다. 더 새 후보가 있다고 오래된 실행을 자동으로 취소하지 않고, 배포 대상 집합을 비교해 새 후보가 모두 포함할 때만 멈추게 했습니다. canary는 배포 뒤 10분 동안 보고, 신호가 비면 rollback이 아니라 보류합니다. 오류 추적 도구의 신호는 기록만 하고, 실패 이벤트가 쌓이는 queue나 데이터 신선도 같은 데이터 유실 신호는 계속 배포를 멈춥니다. 관측 구간은 새 버전이 배포된 시점부터 계산하게 했습니다.
대가
운영 반영 속도는 여전히 사람 승인에 묶입니다. 오류 추적 도구의 신호는 사람이 따로 봐야 합니다.
D-07

운영 상태를 그대로 Git으로 옮긴 뒤 넘겨받기

고민
운영은 반영된 적 없는 버전과 수동 변경으로 떠 있었고, 저장소의 매니페스트에는 placeholder 이미지가 남아 있었습니다. 그대로 GitOps 도구를 붙이면 운영을 덮어써 장애가 납니다.
선택지
① staging이나 앱 하나부터 시범 적용하는 안
② 저장소의 매니페스트를 정답으로 보고 바로 동기화하는 안
③ 처음부터 자동 동기화와 삭제까지 켜는 안
④ 운영 상태를 그대로 Git으로 가져와 차이 0을 확인한 뒤 넘겨받고, 옛 경로를 끈 다음 자동 반영을 켜는 안
결정과 이유
④를 골랐습니다. GitOps의 전제는 Git이 원하는 상태의 유일한 원천이라는 것입니다. 넘겨받는 순간 Git과 운영이 다르면 넘겨받기가 곧 운영 변경이 되므로, 옮기는 단계와 바꾸는 단계를 섞지 않았습니다. 차이가 남으면 운영이 아니라 Git을 고쳤고, 동기화해도 되는지는 차이를 분류하는 스크립트로 판정했습니다. 같은 필드를 두 주체가 바꾸면 서로 덮어쓰기 때문에, 옛 경로를 끄기 전에는 자동 동기화를 켜지 않았습니다. Git에서 빠뜨린 리소스가 지워지지 않도록 자동 삭제는 끄고, 디스크와 namespace에는 삭제 방지 설정을 걸었습니다.
대가
손으로 server-side apply한 객체에는 다른 field manager가 소유한 필드가 남아 diff에는 드러나지 않는 잔재가 생겨, managedFields를 따로 확인해 정리해야 했습니다.
D-08

빌드는 CI, promotion은 Kargo, 반영은 Argo CD, 마이그레이션도 같은 흐름 안에

고민
처음 계획은 CI가 빌드 뒤 GitOps 저장소에 이미지 digest를 직접 쓰고 나중에 promotion 도구로 넘기는 것이었습니다. DB 마이그레이션은 별도 Job을 사람이 로컬에서 실행하고 있었습니다.
선택지
promotion: ① CI가 GitOps 저장소에 직접 쓰는 안 ② 이미지 갱신 도구에 맡기는 안 ③ promotion 전용 도구 Kargo에 맡기는 안
마이그레이션: ① 별도 Job을 그대로 두는 안 ② 마이그레이션 도구를 바꿔 Kubernetes operator로 관리하는 안 ③ 같은 이미지와 ledger를 쓰는 Argo CD PreSync Job으로 옮기는 안
결정과 이유
promotion은 처음부터 Kargo에 맡겼습니다. CI가 저장소에 쓰면 CI에 쓰기 권한이 남고, 어떤 이미지가 어느 단계까지 검증됐는지가 사람 기억에 남습니다. Kargo는 새 이미지를 promotion 후보 객체로 기록하고, staging에는 한 번에 하나씩 올려 검증이 끝나기 전에는 다음 이미지를 올리지 않습니다. 곧 버릴 쓰기 경로를 하나 더 만들지 않는 편이, 같은 필드는 한 주체만 바꾼다는 원칙과도 맞았습니다. 마이그레이션은 앱 반영 직전의 PreSync Job으로 옮겨, 실패하면 앱이 바뀌지 않게 했습니다. 앱 rollback과 DB 되돌리기는 묶지 않고, DB는 다음 마이그레이션으로 앞으로 고칩니다.
대가
운영해야 할 도구가 늘었습니다. 일부 리소스만 골라 동기화하면 마이그레이션 hook이 건너뛰어져, 이미지 변경은 전체 동기화만 하도록 절차로 막아야 했습니다.

04결과

  • 반영된 변경은 한 번만 빌드되고, staging에서 전체 수집 경로를 통과한 이미지만 운영 후보가 되는 경로가 생겼습니다. 처음으로 운영 promotion을 끝까지 마쳤습니다.
  • 운영 promotion 한 번에 두세 번 필요하던 사람 승인을 한 번으로 줄였고, 승인 대기는 배포 lock 밖에서 기다리게 됐습니다.
  • ClickHouse 마이그레이션은 배포마다 51개 파일을 전부 다시 실행하던 방식에서, 아직 적용하지 않은 파일만 한 번 적용하는 방식으로 바뀌었습니다. 운영에 어디까지 적용됐는지도 ledger로 바로 알 수 있게 됐습니다.
  • GitOps 전환은 조사와 결정부터 저장소 생성, Argo CD와 Kargo 설치, 운영 리소스 넘겨받기, 옛 배포 경로 차단까지 하루에 마쳤습니다. 전환 뒤에는 Argo CD가 관리하는 애플리케이션 25개가 모두 Git과 차이 없이 동기화됐습니다.
  • 새 이미지는 빌드 뒤 약 5분 만에 사람 손을 거치지 않고 staging에 반영되고 검증됩니다. 2주 남짓 동안 staging 자동 promotion이 24번 이뤄졌고, 운영에는 staging에서 검증한 이미지를 승인 한 번으로 11번 올렸습니다.
  • 권한을 회수한 뒤 CI 계정이 클러스터를 직접 바꾼 기록은 한 건도 없습니다. 더는 쓰지 않는 옛 클러스터 배포 코드 약 2만 줄을 지웠습니다.
  • CI 실행이 결제 문제로 멈춘 기간에도 promotion과 반영, 검증은 그대로 동작했습니다.

05트러블슈팅

T-01

같은 소스를 두 번 빌드해 digest가 갈린 문제

문제
staging 사전 검사를 통과한 API 이미지와 실제로 배포된 이미지의 digest가 서로 달랐습니다. 검증한 바이트가 staging에도 운영에도 올라가지 않은 상태였습니다. 태그는 같아서 겉으로는 같은 이미지처럼 보였습니다.
원인
queue가 같은 배포 단계를 한 실행 안에서 두 번 불렀는데, 빌드 단계에 이미 있는 이미지를 확인하는 가드가 없었습니다. Go 빌드는 bit 단위로 재현되지 않아서 같은 소스라도 두 번 빌드하면 digest가 달라졌습니다. 운영 배포는 태그로 이미지를 다시 찾고 있어서 나중에 덮어쓴 이미지를 가져갔습니다.
해결
빌드 전에 레지스트리를 먼저 조회해 같은 소스의 이미지가 있으면 재사용하고 태그는 덮어쓰지 않게 했습니다. "태그가 없다"는 응답일 때만 새로 빌드하고, 다른 조회 실패는 retry한 뒤 멈추게 했습니다. 운영 promotion은 태그를 다시 찾지 않고 배포 후보 기록에 적힌 digest를 그대로 쓰게 바꿨고, build provenance attestation을 이미지에 붙였습니다.
결과
운영에 올라가는 이미지가 staging에서 검증한 digest와 같은지 기록으로 바로 확인할 수 있게 됐습니다. 이 규칙은 GitOps로 옮긴 뒤 이미지를 digest로만 고정하는 검사로 이어졌습니다.
T-02

승인 대기 하나가 배포를 약 10시간 막고, 취소하자 API 배포가 빠진 문제

문제
운영 승인을 기다리던 promotion 실행이 concurrency group을 약 10시간 붙잡아 새로 통과한 후보가 시작조차 못 했습니다. 더 새 후보가 있으니 오래된 실행이라고 보고 취소했는데, 새 후보는 수집 Worker만 바꾼 후보여서 API 배포가 조용히 빠졌습니다.
원인
concurrency 제어를 워크플로 전체에 걸어, 운영을 바꾸지 않는 승인 대기까지 lock 안에 들어가 있었습니다. 또 "더 새 코드는 배포 대상도 더 많다"는 가정이 틀렸습니다. 새 후보가 더 최신 코드여도 배포할 대상은 더 적을 수 있었습니다.
해결
운영을 실제로 바꾸거나 관측하는 단계만 별도 reusable workflow로 떼어, 그 호출 하나에만 concurrency 제어를 걸었습니다. 승인 대기와 판정 근거를 모으는 단계는 lock 밖에 뒀습니다. 운영을 바꾸기 직전에는 코드의 선후가 아니라 배포 대상 집합을 비교해, 새 후보가 모두 포함하면 멈추고 겹치지 않으면 진행하며 일부만 겹치면 사람이 판단하게 했습니다. 승인 재알림에는 실행을 취소할 권한을 주지 않았습니다.
결과
빠진 API 배포는 다시 실행해 복구했습니다. 이후 승인 대기는 배포 lock 밖에서 기다리고, 오래된 실행인지는 사람의 짐작이 아니라 배포 대상 비교로 판정합니다.

06배운 점

  • 검증한 것과 배포한 것이 같다는 보장은 사람의 규율로는 오래가지 않았습니다. 내용으로 정해지는 digest와 한 번만 빌드하는 규칙처럼 구조로 만들어야 지켜졌습니다.
  • 파이프라인이 막히면 사람은 우회하고, 우회는 다음 배포가 모르는 상태를 만듭니다. 경로를 더 정교하게 만드는 것보다 운영 상태를 바꾸는 주체를 하나로 모으고, 한 대상의 실패가 다른 대상의 배포를 붙잡지 않게 하는 쪽이 오래간다고 생각합니다.
  • 검증 강도는 되돌릴 수 있는지에 맞춰야 했습니다. staging처럼 되돌릴 수 있는 곳은 자동으로 빠르게 흘리고, 스키마 삭제나 운영 반영처럼 되돌리기 어려운 지점에 사람의 판단을 한 번 모았습니다.

07관련 링크

사내 작업이라 코드와 운영 기록은 공개하지 않았습니다.
