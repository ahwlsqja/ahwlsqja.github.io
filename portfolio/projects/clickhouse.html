01상황과 역할

수파리드는 광고 클릭부터 자사몰, 매장, 외부몰 구매까지 고객 여정을 하나의 어트리뷰션으로 잇는 옴니채널 고객 인텔리전스 플랫폼입니다. 이 프로젝트는 수집한 행동 데이터를 세션과 유입 채널로 묶어 대시보드에 보여 주는 ClickHouse 저장 구조와 조회 경로를 다룹니다. 데이터가 늘자 쓰기가 느려지고, 저장된 데이터 조각을 뒤에서 합치는 병합 작업의 부담도 커졌습니다. 요약 화면은 결과를 미리 계산해 두는 갱신 작업이 메모리 부족으로 거듭 실패했습니다. 유입 채널 화면은 조회 한 번에 읽을 수 있는 한도를 넘겨 실패했습니다. 실행 시간만 봐서는 읽기가 문제인지 쓰기가 문제인지 나눌 수 없었습니다.

02해결 과정

그림 1은 파티션을 나눈 때와 없앤 때, part가 쌓이고 병합되는 과정을 나란히 놓은 것입니다. 그림 2는 이 구조를 포함해 화면별 조회 경로까지 그린 것입니다.

  1. hash 파티션이 쓰기를 무겁게 만드는 이유 확인

    ClickHouse의 기본 저장 방식인 MergeTree는 한 번에 들어온 쓰기(INSERT)를 파티션 값별로 나누고, 파티션마다 part라는 데이터 조각을 따로 만듭니다. part는 뒤에서 조금씩 병합되는데, 병합도 파티션 경계를 넘지 않습니다. 그래서 행을 64개 파티션에 고르게 흩어 놓는 hash 파티션은 INSERT batch 하나를 최대 64개 part로 쪼갰습니다. 조회에 FINAL을 붙이면 아직 병합되지 않은 같은 키의 행을 조회 시점에 하나로 합쳐 돌려줍니다. 이때 이 part들을 모두 읽어 맞춰 보기 때문에, part가 많을수록 메모리를 많이 썼습니다.

    조회가 실제로 어떤 파티션을 읽는지는 실행 계획을 보여 주는 EXPLAIN indexes=1로 확인했습니다. 실제 화면 조회의 필터 조건을 테이블의 파티션 식과 하나씩 맞춰 봤습니다. 조회 조건이 파티션을 나눈 hash 식과 똑같을 때만 64개 파티션 중 1개를 골라 읽었습니다. 조건이 조금이라도 다르면 건너뛴 파티션이 하나도 없었습니다. 쓰기 쪽은 part의 생성과 병합을 기록하는 system.part_log에서 새로 생긴 part 수와 병합 횟수를 봤습니다. 읽기 쪽은 쿼리마다 실행 기록을 남기는 system.query_log에서 읽은 행 수와 메모리 사용량을 봤습니다. 두 기록은 같은 시간대로 맞춰 비교했습니다.

  2. 테이블마다 파티션을 반대로 선택

    원본 이벤트 테이블은 파티션을 아예 없앴습니다(D-01). 원본 신호 테이블은 반대로 월 단위로 파티션을 나누고, (고객, 시각, 이벤트) 순서로 정렬하도록 했습니다. 이 테이블은 주로 시간 범위를 정해 읽고, 보존 기간이 지나면 지우기 때문입니다. 월 파티션이면 partition pruning이 작동해, 조회한 시간 범위 밖의 파티션은 읽지 않고 건너뜁니다. 보존 기간이 지난 데이터도 만료된 데이터를 자동으로 지우는 TTL 설정으로 정리하기 쉽습니다.

    두 테이블 모두 서비스를 멈추지 않고 교체했습니다. 무파티션이 낫다는 것을 어떤 실험으로 확인했는지, 그리고 테이블 이름을 맞바꾸는 EXCHANGE TABLES로 어떻게 교체하고 rollback 경로를 남겼는지는 03 실험 설계와 무중단 전환에 따로 적었습니다.

  3. 이벤트 키로 정렬하고, 화면마다 조회 경로를 따로 설계

    원본 이벤트 테이블의 sort key를 (고객, 이벤트)에서 (고객, 세션, 이벤트)로 바꿨습니다(D-04). 이 키 변경은 운영 테이블 7개에 걸쳐 있었고, 이 테이블들에 연결된 파생 집계 19개가 전환하는 동안에도 끊기지 않게 했습니다.

    요약 화면은 결과를 미리 계산해 두던 갱신 작업이 메모리 부족으로 계속 실패하고 있었습니다. 이 갱신을 멈추고 화면이 원본 테이블을 직접 읽게 했습니다. 대신 원본에 projection을 붙였습니다. projection은 같은 테이블 안에 데이터를 다른 정렬 순서로 한 벌 더 저장해 두는 기능입니다. 여기에는 이 화면이 읽는 열 7개만 (고객, 시각) 순서로 담았습니다(D-05).

    projection을 붙이면서 행을 지운 뒤의 결과도 확인했습니다. DELETE로 행을 지운 뒤 원본에는 8건이 남았는데 projection에는 9건이 남는 경우를 재현했습니다. 그래서 lightweight_mutation_projection_mode='drop' 설정을 걸어, 삭제가 적용된 part에서는 projection을 쓰지 않고 원본에서 읽게 했습니다. 과거 데이터에는 MATERIALIZE PROJECTION으로 projection을 따로 만들어, projection이 전체 기간을 덮게 했습니다.

    유입 채널 화면은 조회 기간 안의 이벤트를 읽은 뒤에도, 기간과 상관없이 고객 전체의 세션 지표와 채널 정보를 붙이고 있었습니다. 순서를 바꿔, 기간 안의 최신 이벤트를 먼저 고르고 세션마다 한 줄로 줄인 다음 채널 정보를 붙이게 했습니다. 운영 환경에서 같은 고객의 7일치 조회를 3번 실행해 비교했고, 읽은 행이 약 80% 줄었습니다.

  4. AI 유입 화면이 조회용 테이블을 읽게 하고, 늘어난 갱신 비용까지 계산

    AI 유입 화면은 요청이 올 때마다 원본 이벤트에 세션 지표와 채널 정보를 붙여 계산했습니다. 그중 일별 조회는 날짜 조건 때문에 고객 필터가 테이블을 읽는 단계까지 push down되지 않아, 모든 고객의 데이터를 읽었습니다. 관측 기간 동안 일별 조회 37번이 모두 실패했습니다.

    채널 분류를 미리 끝내 둔 채널 snapshot 테이블이 이미 주기적으로 갱신되고 있었습니다. 이 snapshot에서 AI 유입 세션만 골라 15분마다 집계해 두는 조회용 테이블을 만들었습니다. 정해진 주기마다 쿼리를 다시 실행해 결과를 테이블에 저장하는 Refreshable Materialized View 기능을 썼습니다. 화면은 이 테이블의 마지막 refresh가 끝난 시각이 1시간 이내일 때만 이 테이블을 읽고, 그보다 오래됐으면 원래 방식의 조회로 fallback하게 했습니다. 다만 권한 오류나 통신 오류가 나면 원래 조회로 넘기지 않고 오류를 그대로 돌려줬습니다.

    전환한 뒤에는 15분마다 도는 이 갱신 작업의 비용을 따로 계산했습니다. 화면 요청에서 줄어든 읽기를 빼고도, 갱신 때문에 하루 약 200GiB를 더 읽는 셈이었습니다. 이 값은 읽기량으로 추정한 것입니다. 채널 snapshot의 (고객, 시각) 순 정렬은 유입 채널 화면이 쓰고 있어 그대로 두고, snapshot을 AI 유입인지 아닌지에 따라 파티션 2개로만 나눴습니다. 로컬 실험에서 갱신이 읽는 행이 99% 넘게 줄었고, 대신 snapshot을 만드는 시간은 약 1.4배로 늘었습니다. 다른 방법도 비교했습니다. 조건에 맞지 않는 데이터 블록을 건너뛰게 하는 skip index는 건너뛸 수 있는 양이 약 8%뿐이어서 쓰지 않았습니다. 파티션을 16개로 나누는 방법은 읽기가 줄어드는 정도는 같은데 생성 시간만 약 1.8배로 늘어 고르지 않았습니다. 파티션 2개 구성은 운영 환경에 적용했습니다.

03실험 설계와 무중단 전환

EXPLAIN과 시스템 테이블로 hash 파티션이 조회를 거르지 못한다는 것은 확인했습니다. 하지만 파티션을 없앴을 때 쓰기가 얼마나 가벼워지는지, 그리고 dedup 결과가 그대로인지는 직접 재 봐야 알 수 있었습니다. 원본 이벤트 테이블은 모든 화면이 읽는 곳이라, 바꾼 뒤에 틀린 것을 알면 rollback도 어렵습니다. rollback이 어려운 곳일수록 검증을 두껍게 해야 한다고 생각해, 운영을 바꾸기 전에 실험으로 먼저 답을 내기로 했습니다.

가설은 한 문장이었습니다. 엔진, sort key, 열, 입력을 모두 같게 두고 파티션 절 하나만 없애면, dedup 결과는 같으면서 쓰기와 병합 비용은 줄어든다는 것입니다. 실험은 로컬 재생, 운영 입력을 mirroring해 받는 Shadow 비교, 운영 화면 쿼리로 새 테이블 후보를 번갈아 실행하는 비교의 세 단계로 쌓았고, 결과가 나온 뒤 기존 테이블과 새 테이블을 나란히 두는 Blue/Green 방식으로 운영 테이블을 교체했습니다.

실험 설계를 변인별로 나누면 아래와 같습니다.

표 1. 실험 설계
항목설계
가설파티션 절 하나만 없애도 dedup 결과는 그대로입니다. 같은 키의 행이 같은 파티션에 모여야 병합 때 합쳐지는데, 파티션이 하나뿐이면 이 조건이 저절로 지켜지기 때문입니다. 대신 INSERT 한 번이 64개 part로 쪼개지지 않으니 INSERT 지연과 part 수, 병합 횟수가 줄어듭니다. sort key가 같으므로 날짜 범위로 읽는 조회는 좋아지지 않는다고 예측했습니다.
조작 변인PARTITION BY 절 하나입니다. A는 고객 ID와 이벤트 ID를 이어 붙인 값의 hash로 나눈 파티션 64개, B는 파티션 없음입니다. sort key나 엔진을 함께 바꾸는 안과 월 파티션 안은 어느 쪽의 효과인지 나눌 수 없어 이 비교에서 뺐습니다.
통제 변인: 구조엔진(ReplacingMergeTree)과 버전 열, sort key를 같게 두고, TTL, 압축 codec, skip index, 테이블 설정도 똑같이 맞췄습니다. 원본 정의를 통째로 복사하지 않고 이벤트 본문 61개 열로 두 테이블을 다시 만들어, retry 때마다 바뀌는 처리 정보가 비교에 끼어들지 않게 했습니다.
통제 변인: 입력로컬에서는 기본 21,000행에 정확한 중복 1,910행과 높은 버전 수정 3,000행을 더하고, 수정 뒤 늦게 도착한 낮은 버전 retry 3,000행까지 섞은 합성 입력 28,911행을 썼습니다. 같은 버전에 본문이 다른 충돌 행도 일부러 넣었고, 29개 배치로 나눠 양쪽에 같은 순서로 넣었습니다. 운영 입력은 운영 queue 발행이 성공한 배치만, 같은 메시지 배열 그대로 Shadow queue에 넘겼습니다.
통제 변인: 처리Shadow 쪽 consumer도 운영과 같은 정규화 코드와 같은 async insert 설정을 썼습니다. 운영 테이블을 다시 읽거나 부가 분석을 다시 호출하지 않아, A의 조회 비용이 B의 측정값에 섞이지 않습니다.
통제 변인: 측정A와 B를 같은 시간 구간에서 같은 집계 쿼리로 쟀고, 쿼리마다 20초, 2,500만 행, 2GiB 상한을 똑같이 걸었습니다. 약 9시간 누적 구간과, 그와 따로 잡은 최근 30분 구간을 각각 봤습니다.
통제하지 못한 것Shadow의 A는 replica 2대에서 파생 집계 19개와 과거 데이터를 함께 처리했고, B는 replica 1대의 최소 구성이었습니다. 두 서비스는 저장소와 Keeper를 공유했고, B가 받은 행은 구간에 따라 A의 약 90%와 약 122%였습니다. 그래서 Shadow 수치는 방향의 근거로만 쓰고, 파티션 하나로 몇 배 좋아졌다는 주장에는 쓰지 않았습니다.
종속 변인쓰기는 INSERT 지연의 p50, p95, 최대와 예외 수를 system.query_log와 system.asynchronous_insert_log에서 쟀습니다. 병합 부담은 system.part_log의 새 part 생성 수와 병합 횟수, system.parts의 활성 part 수로 봤습니다. 자원은 쿼리당 최고 메모리와 새 part 한 행당 CPU 시간을, 읽기는 읽은 행과 바이트를 쟀고, 실제로 건너뛴 part는 EXPLAIN indexes=1로 확인했습니다.
결과가 같은지 먼저 본 방법기대값은 후보 테이블의 결과를 복사하지 않고, 별도 JavaScript 계산으로 키마다 남아야 할 행을 구해 만들었습니다. A와 B 각각의 FINAL 결과와 argMax 결과의 digest가 이 값과 모두 같은지 본 뒤에야 성능을 봤습니다. Shadow 쪽은 본문 61개 필드와 수집기 버전으로 만든 SHA-256 hash로 B에 들어간 행을 하나씩 다시 읽어 대조했습니다.
운영과의 격리B는 별도 ClickHouse 서비스에 두고, 실험용 database 안에서만 테이블을 만들고 지울 수 있는 전용 계정과 별도 queue 3개, 별도 worker를 붙였습니다. mirroring은 운영 queue 발행이 성공한 뒤에만 일어나고, 전송은 최초 1회와 50ms 뒤 retry 1회까지만 합니다. 실패해도 운영 응답과 ACK, retry는 바뀌지 않는 fail-open입니다. 시작과 종료 시각, 최대 7일 조건 중 하나라도 어긋나면 mirroring만 꺼지고, 운영 쪽 측정은 system 테이블 집계 SELECT만 썼습니다.
판정 기준같은 이벤트, 같은 버전에 본문이 다른 묶음이 하나라도 나오면 성능 비교를 멈춥니다. 결과 불일치, 시간 초과, 빠진 지표는 통과로 치지 않았습니다. 성능은 가장 좋은 한 번이 아니라 중앙값, 분산, 최악값으로 비교했고, 근거가 모자라면 채택하지 않고 보류했습니다.

세 단계로 쌓은 실험

비용이 싸고 통제하기 쉬운 곳에서 시작해 운영에 가까운 곳으로 옮겨 갔습니다. 앞 단계를 통과해야 다음 단계로 넘어가게 했고, 어느 단계에서나 결과가 같은지를 먼저 확인한 뒤 속도를 봤습니다.

  1. 로컬 재생 A/B: 파티션 하나가 쓰기 비용을 바꾸는지

    로컬 ClickHouse 26.3에서 파티션 절만 다른 두 테이블을 만들고, 표 1의 합성 입력을 같은 순서로 재생했습니다. 목적은 파티션 하나가 쓰기 비용을 바꾸는지와 결과가 그대로인지를 가장 싼 환경에서 확인하는 것이었습니다. 강제 병합은 하지 않고 자연스럽게 병합되는 상태에서, 조회 형태 11개를 A와 B에 똑같이 돌려 지표 22개를 모았습니다.

    먼저 두 테이블의 FINAL 결과와 argMax 결과가 따로 계산한 기대값과 모두 같다는 것을 확인했습니다. 같은 버전에 본문이 다른 충돌 행은 적재 전에 거절됐습니다. 그다음 성능을 봤습니다. 쓰기 100번 중 95번이 끝나는 시간(INSERT p95)은 285.5ms에서 86.2ms로, 중앙값은 157.0ms에서 78.6ms로 줄었고, 활성 part는 256개에서 2개가 됐습니다.

    반대 방향 결과도 그대로 기록했습니다. 큰 세션을 시간 조건과 함께 읽는 조회는 무파티션 쪽이 1,680행 대신 21,000행을 읽었습니다. sort key가 같으면 시간 범위 조회는 좋아지지 않는다는 예측과 맞는 결과였고, 뒤에서 backfill 순서와 날짜순 projection을 고민하게 된 출발점이 됐습니다. 로컬 결과로는 클라우드의 실제 트래픽과 replica, 백그라운드 병합을 설명할 수 없어서, 이 단계에서는 채택을 보류하고 다음 단계로 넘겼습니다.

  2. 운영 입력을 mirroring한 Shadow 비교: 실제 트래픽에서도 같은 방향인지

    운영 수집 경로에서 queue 단계부터 갈라지는 비교 경로(Shadow)를 만들었습니다. 운영 queue 발행이 성공한 배치를 같은 메시지 그대로 Shadow queue에 넘기고, 운영과 같은 consumer 로직이 별도 ClickHouse 서비스의 무파티션 테이블 B에 적재합니다. A는 운영 테이블 그대로입니다. 운영 producer를 끄고 순서대로 다시 켜는 방법은 운영을 멈춰야 해서 쓰지 않았습니다. 시작 전에는 queue 왕복이 실제로 되는지와 queue backlog가 0인지만 확인하고, 24시간 기한으로 켰습니다. 켠 직후 30초 동안에도 행이 늘어나는지와 오류가 반복되지 않는지만 봤습니다.

    약 9시간 누적 구간에서 B가 A의 약 90%만큼 행을 받는 동안, INSERT p95는 A가 3,410ms, B가 134ms였습니다. 활성 part는 1,019개와 5개였고, 새 part 생성과 병합 횟수도 B 쪽이 크게 적었습니다. 양쪽 INSERT 예외는 0이었습니다. 따로 잡은 최근 30분 구간에서는 B가 오히려 약 22% 더 많은 행을 받았는데도 INSERT p95가 6,345ms와 144ms, 활성 part가 1,026개와 8개로 같은 방향이었습니다.

    원래는 24시간을 다 채우고, 클라우드에서 A와 B의 실행 순서를 바꿔 가며 5쌍을 더 돌릴 계획이었습니다. 그런데 두 구간에서 지연, CPU, part, 병합 모든 축이 회귀 없이 같은 방향이었고 예외도, 결과 불일치로 비교를 멈춘 일도 없었습니다. 남은 약 10시간의 관측이 이 방향을 뒤집을 가능성보다 실험을 이어 가는 비용과 배포 제약이 더 크다고 판단해, mirroring을 끄고 무파티션 채택을 확정했습니다. queue를 비운 뒤 실험용 queue와 worker, ClickHouse 서비스와 계정을 지우고 남은 것이 없는지 확인했습니다.

  3. 새 테이블 후보 교차 실행: 운영 화면 쿼리로 backfill 순서 고르기

    운영 서비스 안, 원본 테이블 옆에 무파티션 새 테이블을 두 벌 만들었습니다. 한 벌은 기존 hash 파티션 단위로 64번에 나눠 채웠고, 다른 한 벌은 이벤트 시각 7일 구간 17개를 오래된 것부터 채웠습니다. 목적은 운영 화면이 실제로 읽는 쿼리에서 새 테이블이 나빠지지 않는지 보고, 새 테이블을 어떤 순서로 채울지 정하는 것이었습니다. 대시보드와 모니터링 쿼리를 그대로 모아 테이블 이름만 바꿔 기존 테이블과 두 후보에 똑같이 실행했습니다. 쿼리마다 120초, 4GiB, 4스레드 상한을 걸고 쿼리 캐시를 껐습니다. 판정 규칙도 미리 정했습니다. 읽은 바이트가 기존 테이블의 0.7배 이하면 개선, 1.2배를 넘거나 실행 시간이 1.2배를 넘으면 회귀입니다.

    hash 순서로 채운 후보는 FINAL 메모리가 4~7배 낮았고, 기존 테이블에서 메모리 한도 4GiB를 넘겨 실패하던 전체 이력 FINAL 뷰 5종도 끝까지 돌았습니다. 하지만 최근 1시간 조회는 읽은 바이트가 72배, 최근 75분 조회는 31배로 늘어 규칙상 회귀였습니다. part마다 109일 전체 기간이 섞여, 시간 범위로 건너뛸 part가 사라졌기 때문입니다. 시간 순서로 채운 후보는 part의 시간 범위가 이어져 이 문제가 없었습니다. 트래픽이 적은 시점에 세 번씩 잰 중앙값으로, 요약 화면 7일 조회가 기존 9.2초에서 4.8초, 방문자 화면이 6.9초에서 4.0초였습니다. 대시보드 쿼리 8개 모두 기존과 같거나 빨라, 시간 순서 backfill을 전환 방식으로 골랐습니다.

실험 중에 발견한 것

  • 같은 버전, 다른 본문. 비교 직전 24시간 점검에서 같은 이벤트, 같은 버전인데 본문이 다른 행 묶음이 나왔습니다. 파티션을 바꾸면 병합 순서가 달라져 남는 행이 바뀔 수 있어서 성능 비교를 멈췄고, 이벤트 본문 61개 필드를 같은 이벤트의 기준으로 정한 뒤 다시 시작했습니다(T-01).
  • 같은 입력을 받지 않던 비교 경로. 처음 만든 Shadow는 운영 적재가 끝난 이벤트의 ID만 넘겨받아, 배치마다 운영 테이블을 SELECT FINAL로 다시 읽어 가공했습니다. 이 구조는 운영 DB에 부하를 주고, 서비스 사이의 읽기 지연과 FINAL 비용, 다른 가공 코드까지 B의 측정값에 섞습니다. 실제로 첫 활성화에서 읽기 지연 때문에 배치가 통째로 실패해, 처리에 실패한 메시지를 모으는 DLQ로 넘어갔습니다. 실험의 전제는 같은 입력의 A/B였기 때문에, 같은 이벤트 묶음을 queue 단계에서 둘로 갈라 같은 consumer 로직에 넣는 구조로 다시 설계했습니다. 같은 메시지 배열과 같은 본문 객체가 넘어가는지는 테스트로 확인했습니다.
  • 측정 도구의 실패와 시스템 상태를 나눠 보기. Shadow를 켜는 작업이 실패로 표시된 적이 있습니다. 트래픽 문제는 아니었습니다. 활성화를 확인하는 검증 스크립트가 읽기 전용 측정 계정에 쿼리 설정을 다시 지정하려다 거부된 설정 충돌이었고, 실제 배치는 모두 처리됐으며 예외는 0이었습니다. queue가 실험 전용이 아닌 DB를 가리키던 설정도 이때 찾아 실험 전용 DB로 고정했습니다.
  • 병합 중 측정 노이즈와 측정이 만든 부하. 새 테이블 후보를 처음 비교했을 때는 시간 순서 후보가 1.5~3.7배 느리게 나왔습니다. 병합이 한창일 때 잰 값이었고, 트래픽이 적은 시점에 다시 재자 결과가 뒤집혔습니다. 유일하게 느렸던 봇 요약 쿼리도 집계가 디스크로 spill되면서 생긴 흔들림이라 다시 재서 확인했습니다. 기존 테이블과 새 테이블을 같은 순간에 번갈아 읽는 측정 도구가 수집 INSERT p95를 11~22초까지 올린 일도 있었습니다. 그 자리에서 멈추고, 이후 큰 대조와 읽기 비교는 트래픽이 적은 시간에만 돌렸습니다. 부하가 높아 실행 시간이 엇갈릴 때는 읽은 행, 바이트, part 수처럼 덜 흔들리는 지표로 판단했습니다.

Blue/Green 무중단 전환

실험에서 얻은 이득은 주로 파티션 제거에서 나왔으므로, 운영 전환에서도 바꾸는 것을 파티션 하나로 줄였습니다(D-03). 기존 테이블은 그대로 두고, PARTITION BY 절만 뺀 같은 열 69개짜리 새 테이블을 같은 ClickHouse 서비스 안에 나란히 세웠습니다. 서비스를 통째로 새로 띄우거나 새 schema로 옮기면, 파생 집계를 만드는 materialized view(MV) 19개와 뷰를 모두 다시 써야 합니다. 테이블 단위로 하면 schema가 같아 MV와 조회 코드는 그대로 두고 이름만 바꿔 끼우면 됩니다. 이름을 맞바꾸는 EXCHANGE TABLES는 같은 문장을 다시 실행하면 원래대로 돌아옵니다. 교체와 rollback이 같은 한 문장이라는 점이 이 방식을 고른 가장 큰 이유였습니다.

준비 단계에서 staging으로 두 가지를 먼저 확인했습니다. EXCHANGE 뒤에도 MV가 이름을 따라 새 테이블에서 trigger되는지, 그리고 일반 RENAME은 MV 연결을 끊는지입니다. 이 동작은 공식 문서에 나와 있지 않아서 실제 동작으로 확인했고, 결과에 따라 RENAME은 쓰지 않고 EXCHANGE만 쓰기로 했습니다.

  1. 같은 schema로 복제

    새 테이블은 손으로 쓰지 않고, 운영 테이블 정의에서 PARTITION BY 절만 지워 만들었습니다. 엔진과 sort key, TTL 2년, skip index 4개, 열 69개가 기존 테이블과 같습니다. 전환 스크립트는 첫 단계에서 두 테이블의 열 이름 순서가 같은지 확인하고, 다르면 멈추게 했습니다. dual write에 쓸 MV는 열을 이름으로 맞추지만 SELECT *는 위치로 맞춰서, 순서가 한 칸만 어긋나도 backfill한 행만 조용히 틀어질 수 있었기 때문입니다. backfill 쿼리에도 SELECT * 대신 열 목록을 적었습니다.

  2. 원본을 건드리지 않고 backfill

    기존 테이블과 MV, 수집 worker는 그대로 둔 채 새 테이블을 채웠습니다. 순서는 실험 3단계에서 고른 대로 이벤트 시각 7일 구간 17개를 오래된 것부터 넣었고, 약 55분 걸렸습니다. 병합이 끝난 뒤 새 테이블의 part는 9개였고, part마다 시간 범위가 이어져 있었습니다.

  3. 논리 키로 대조

    처음에는 양쪽을 같은 수신 시각 cutoff로 걸러 비교했는데 결과가 어긋났습니다. 재전송된 행이 cutoff를 넘나들면, 병합이 한쪽에서만 옛 버전을 지우기 때문입니다. 그래서 기존 테이블을 기준으로 두고, cutoff 시점의 기존 테이블 키 집합과 키별 최신 버전을 임시 테이블에 snapshot으로 저장했습니다. 새 테이블을 그 키로 좁힌 뒤 빠진 키 수와, 키마다 본문 61개 열로 고른 최신 행의 hash를 비교했습니다. NULL이 섞여도 hash가 NULL이 되지 않게 열을 tuple로 묶어 hash했고, replica가 2대라 select_sequential_consistency=1로 같은 상태를 읽게 했습니다. 빠진 키 0, 본문 차이 0이었습니다. 열 69개 전체로 비교하면 소비 시각처럼 처리할 때마다 바뀌는 열에서만 차이가 났는데, 같은 이벤트인지 판단하는 기준에서 뺀 열이라 예상한 결과였습니다.

  4. staging 리허설

    운영과 같은 순서로 staging에서 전 과정을 먼저 돌렸습니다. staging은 운영과 같은 ClickHouse 서비스 안에 있어서, 부하가 아니라 절차와 권한을 확인하는 리허설로 썼습니다. 시험 이벤트가 전환 앞뒤 모두 양쪽에 빠짐없이 복사됐고, 교체 뒤 MV가 모두 다시 연결됐으며 FINAL 건수도 양쪽이 같았습니다.

  5. dual write와 교체

    운영에서는 기존 테이블에 들어오는 행을 새 테이블에도 복사하는 bridge MV를 붙여 ClickHouse 안에서 dual write를 시작했습니다. cutoff 이후 bridge를 붙이기 전까지 들어온 구간은 26초 만에 다시 채웠고, 이 구간도 빠진 키 0, 본문 차이 0이었습니다. 실시간으로 들어오는 행은 키 집합으로 대조했습니다. count()로 비교했을 때는 1행, 비교 구간 끝에 5초 여유를 두고 키를 비교했을 때는 4~9개 키가 달랐는데, 둘 다 병합 상태와 INSERT 도착 지연이 만든 착시였습니다. INSERT 도착이 p99 기준 약 10초까지 늦기 때문에, 구간 끝을 현재보다 60초 앞으로 두자 키가 모두 일치했습니다. 세 대조가 모두 맞은 뒤 EXCHANGE TABLES 한 문장으로 교체했습니다. 스크립트는 열 불일치, 대조 실패, 실시간 대조 불일치 중 하나라도 나오면 교체하지 않고 원본을 그대로 두게 짜 두었습니다.

  6. rollback 경로

    교체 뒤에는 bridge MV가 이름을 따라 방향을 바꿔, 새 원본이 된 테이블에서 옛 테이블로 복사합니다. 그동안 옛 테이블이 최신 상태로 남아 있어서, rollback은 같은 EXCHANGE를 한 번 더 실행하면 끝납니다. rollback 가능 기간은 late event가 p99 기준 4.3시간, 최대 24시간 늦게 도착하는 것을 보고 72시간으로 잡았습니다. EXCHANGE는 idempotent하지 않아 다시 실행하면 원래대로 되돌아갑니다. 그래서 배포 때마다 모든 변경을 다시 적용하는 schema migration에는 넣을 수 없었고, migration 밖에서 한 번만 실행한 뒤 migration에는 교체 뒤의 테이블 정의만 반영하는 규칙을 정했습니다.

  7. bridge를 일찍 걷고 옛 테이블 정리

    교체 직후에는 bridge 때문에 매 flush가 옛 테이블의 64개 파티션에도 기록되면서 INSERT p95가 10.4초로 오히려 나빠졌습니다. 대조가 모두 통과한 상태라 rollback할 가능성은 낮다고 보고, bridge를 계획보다 일찍 걷어냈습니다. 이때부터 rollback은 EXCHANGE를 다시 실행한 뒤, bridge를 걷은 이후 구간을 backfill하는 절차가 됩니다. 옛 테이블은 다른 이름으로 바꿔 남겨 두고 지켜봤습니다. 지우기 전 점검에서 INSERT 예외 0, p95 3.1초, 갱신 오류 0, 옛 테이블을 참조하는 의존성과 읽기 0을 확인한 뒤 지웠습니다. 지운 뒤 8시간 동안은 UNDROP으로 되살릴 수 있었습니다.

전환 뒤 결과

전환은 서비스를 멈추지 않고 끝났습니다. cutover 때 버퍼에 모여 있던 async INSERT 3건이 옛 테이블 식별자로 flush되다 실패했지만, queue가 약 61초 뒤 같은 배치를 다시 넣어 잃은 데이터는 없었습니다. 이 실패는 이후 교체 때도 나올 수 있는 예상된 알림으로 runbook에 적어 두었습니다. bridge를 걷은 뒤 13분 동안 INSERT 예외는 0이었습니다.

원본 이벤트 테이블의 파티션은 64개에서 1개로, part는 454개에서 11개로 줄었습니다. 고객별 FINAL count 쿼리의 메모리는 731~826MB에서 141MB로, 24시간 FINAL count는 1,047~1,117MB에서 148MB로 줄었습니다. 트래픽이 적은 시점에 한 번 잰 요약 화면 7일 조회는 9.2초에서 2.1초가 됐습니다. 디스크 사용량은 11.46GiB와 11.29GiB로 거의 같았고, 14일 범위 조회도 기존 수준을 유지했습니다. sort key가 같아 구조로는 좋아질 수 없는 조회를 시간 순서 backfill로 지킨 결과입니다. 서버 평균 CPU와 동시 병합 수도 전날 평시보다 낮아졌습니다.

쓰기 지연은 비교 기준을 다시 잡아야 했습니다. 전환 당일 기존 테이블은 오전 실험과 backfill로 병합이 밀려 INSERT p95가 8,302ms로 평소보다 약 2배 나빴습니다. 이 값과 견주면 전환 뒤 3,823ms는 54% 개선처럼 보입니다. 그래서 전날 같은 시각의 평시 p95인 2,676~3,473ms와도 비교했고, 쓰기 지연은 평시와 같은 수준이라고 판단했습니다. Shadow의 B처럼 0.1초대까지 내려가지 않은 것은, 운영 테이블이 MV 19개를 INSERT와 함께 동기로 처리하고 남은 지연이 주로 여기서 나왔기 때문입니다.

회귀도 하나 있었습니다. 파티션이 하나로 합쳐지면서 큰 part끼리 병합하게 되자, 5분마다 FINAL로 도는 모니터링 쿼리의 최고 메모리가 약 10% 늘어 255MB 상한에서 14번 중 4번 실패했습니다. 같은 날 상한을 512MiB로 올리고 읽기 상한 4GiB를 함께 걸었고, 이후 최고 270MiB에서 메모리 초과 없이 돌았습니다.

같은 절차는 그 뒤에도 그대로 썼습니다. 이어서 원본 신호 테이블을 같은 방식으로 월 파티션으로 바꿨습니다. 이때는 backfill 중 INSERT p95가 15초를 넘거나 메모리가 11GiB 이상이면 backfill을 자동으로 멈추게 했고, 옛 테이블은 사흘 동안 INSERT 예외 0을 확인한 뒤 지웠습니다. 마지막으로 sort key를 (고객, 세션, 이벤트)로 바꿀 때도 같은 EXCHANGE 방식을 썼습니다. sort key와 projection의 효과도 같은 실험 틀로 쟀습니다. 운영 데이터를 읽는 분석 환경에서 바꾸기 전과 후의 테이블을 캐시를 끈 채 6회씩 번갈아 실행했고, 반환 결과의 hash가 같은 표본만 비교에 넣었습니다(D-04, D-05).

04설계 결정

해결 과정에서 고른 것과 버린 것을 결정마다 정리했습니다.

D-01

hash 파티션을 없애고 무파티션으로

고민
초기 설계는 (고객, 이벤트 ID)를 hash해 파티션 64개로 나눴습니다. 같은 이벤트가 다시 전송돼 중복으로 들어와도 같은 파티션에 모아, 병합 때 하나로 합치려는 의도였습니다. 그런데 hash 입력에 행마다 다른 이벤트 ID가 들어 있어서, 어떤 조회도 읽을 파티션을 미리 고르지 못했습니다. 4행을 돌려주는 조회가 그 수십만 배의 행을 읽었고, 세션 하나도 50개 넘는 파티션에 흩어져 있었습니다.
선택지
① 월 단위로 파티션을 나누는 방법, ② hash 파티션은 그대로 두고 index만 고치는 방법, ③ 파티션을 아예 두지 않는 방법(무파티션)을 비교했습니다.
결정과 이유
③을 골랐습니다. 파티션을 건너뛰려면 조회 조건의 값만으로 파티션 값을 계산할 수 있어야 합니다. 파티션 식에 그 열이 들어 있는 것만으로는 부족합니다. 월 파티션은 이벤트 시각으로 달을 정하는데, 이 시각은 재전송마다 달라질 수 있습니다. 그래서 late event로 들어온 재전송이 다른 달 파티션에 들어가 원래 행과 합쳐지지 않았고, 로컬에서 대조해 보니 합쳐지지 않은 행 2개가 남았습니다. index만 고치는 방법은 part가 많아서 생기는 비용을 그대로 남겼습니다. 무파티션은 같은 키의 행이 늘 같은 파티션에 모인다는 원래 조건도 그대로 지킵니다.
대가
월 파티션이었다면 할 수 있던 두 가지를 포기했습니다. 한 달치 데이터를 part째 통째로 지우는 방법과, 조회할 때 해당하지 않는 달을 통째로 건너뛰는 방법입니다. 기간을 정해 읽는 조회는 sort key와 projection이 맡게 했습니다(D-05).
D-02

효과는 변수 하나만 바꿔 같은 입력으로 비교

고민
운영 원본을 바로 바꾸면 수집과 복구가 함께 위험해집니다. 처음 만든 비교 경로는 운영 적재 결과를 다시 읽어 가공했습니다. 그래서 두 쪽이 같은 입력을 받았다고 말할 수 없었습니다.
선택지
① 운영에 적재된 결과를 다시 읽어 비교용 테이블에 적재하는 방법과, ② 파티션 설정만 다른 두 테이블에 같은 입력을 로컬에서 재생하고, 운영 입력은 운영 queue에 들어간 배치를 복사해 받는 mirror queue로 따로 받는 방법을 비교했습니다.
결정과 이유
②를 골랐습니다. 성능을 비교하려면 입력과 처리가 같고, 저장 구조 하나만 달라야 합니다. sort key와 엔진은 그대로 두었습니다. 함께 바꾸면 어느 쪽의 효과인지 나눌 수 없습니다. 비교 경로는 운영 경로에서 떼어 놓았습니다. 비교가 실패해도 운영 결과는 바뀌지 않습니다. 변인을 맞춘 방법은 표 1에 정리했습니다.
대가
비교에 쓴 두 클라우드 서비스는 replica 수가 서로 달랐습니다. 그래서 파티션 하나만 바꿔서 몇 배 좋아졌는지는 주장하지 않았습니다. 비교 직전에는 같은 버전인데 내용이 다른 행이 나와, 같은 이벤트의 기준부터 다시 정했습니다(T-01).
D-03

큰 이관 대신 테이블 교체 한 번

고민
처음 계획은 큰 이관이었습니다. 새 schema를 만들고, 기존 테이블과 새 테이블에 함께 쓰는 dual write를 하면서 과거 데이터를 채우고, MV까지 다시 쓰는 계획이었습니다. 그런데 비교해 보니 얻는 이득의 대부분은 파티션을 없애는 데서 나왔습니다.
선택지
① 새 schema로 전면 이관하는 방법과, ② 파티션 설정만 뺀 같은 schema의 테이블을 채운 뒤 EXCHANGE TABLES 한 문장으로 맞바꾸는 방법을 비교했습니다.
결정과 이유
②를 골랐습니다. 바꿀 것이 파티션 하나라면 운영 전환도 그 하나만 바꾸는 쪽이 위험이 가장 작습니다. schema가 같아 MV와 조회 코드는 그대로 두고 테이블 이름만 맞바꿨습니다. 같은 문장을 한 번 더 실행하면 원래대로 돌아갑니다. rollback 경로가 처음부터 있었습니다.
대가
dual write를 하는 동안 쓰기가 오히려 느려져서, dual write를 계획보다 일찍 걷었습니다. 또 이벤트 본문과, 소비 시각처럼 처리 과정에서 붙는 정보가 한 행에 섞여 있는 문제(T-01)는 운영 원본에 그대로 남았습니다.
D-04

sort key는 조회 속도보다 dedup 기준으로

고민
제품의 기본 단위는 세션인데 sort key는 (고객, 이벤트)였습니다. 세션 하나를 읽으려면 넓은 범위를 다시 읽어야 했습니다. 더 큰 문제도 있었습니다. 이 테이블은 병합할 때 같은 키의 행을 하나만 남기는 ReplacingMergeTree를 씁니다. 여기서 sort key는 어떤 행을 같은 행으로 보고 합칠지 정하는 기준입니다. 그래서 서로 다른 세션에서 온 이벤트라도 이벤트 ID가 같으면 하나로 합쳐져, 실제 행동이 사라질 수 있었습니다.
선택지
① 지금의 (고객, 이벤트)를 유지하는 방법, ② 시각을 앞에 두고 정렬하는 방법, ③ 탭까지 키에 넣는 방법, ④ (고객, 세션, 이벤트)로 바꾸는 방법을 비교했습니다.
결정과 이유
키를 바꾸기 전에 데이터의 계층 관계부터 정했습니다. 고객 아래에 방문자, 방문자 아래에 세션, 세션 아래에 탭, 탭 아래에 이벤트가 오는 관계입니다. 이것부터 정한 이유는, 탭이 세션보다 오래 열려 있어서 탭 하나가 부모 세션을 둘 갖는 경우가 재현됐기 때문입니다. 부모가 바뀔 수 있는 값을 키에 넣으면 같은 이벤트의 재전송이 서로 다른 행으로 갈라집니다. 이 계층을 기준으로 ④를 골랐습니다. 시각은 재전송마다 달라질 수 있어 키로 쓰지 않았습니다. 탭은 키가 아니라 속성으로 두었습니다. 수집 SDK가 붙이는 식별자부터 수집, 저장, 조회까지 모두 같은 키를 쓰도록 한 번에 맞췄습니다.
대가
그 대신 날짜를 기준으로 읽는 조회가 약 4.5배 느려졌습니다. 같은 비교 실험에서 서버 실행 시간으로 잰 값입니다. 이렇게 느려진 부분은 sort key를 되돌리지 않고 projection으로 메웠습니다(D-05).
D-05

다른 읽기 방식은 sort key 대신 projection으로

고민
sort key를 세션 기준으로 바꾸자, 날짜로 읽는 요약 화면은 하루만 조회해도 훨씬 많은 원본 행을 읽었습니다. 데이터가 쌓일수록 같은 요청이 계속 비싸지는 구조였습니다.
선택지
① sort key를 날짜 우선으로 되돌리는 방법, ② 정렬 순서를 따라 집계하게 하는 optimize_aggregation_in_order 설정만 켜는 방법, ③ sort key는 그대로 두고 날짜순 projection을 더하는 방법을 비교했습니다.
결정과 이유
③을 골랐습니다. 테이블의 sort key는 하나뿐이고, 그 자리는 이미 어떤 행을 같은 행으로 합칠지 정하는 dedup 기준이 차지했습니다. 결과를 정하는 키를 조회 속도 때문에 바꿀 수는 없습니다. 설정만 켜는 방법은 메모리를 약 60% 줄였지만 읽은 행은 그대로였습니다. 그래서 같은 데이터를 다른 순서로 한 벌 더 두는 projection이 기간 조회를 맡게 했습니다. 읽는 양이 쌓인 데이터가 아니라 요청한 기간에 비례하게 하려는 선택입니다. 원본 신호 테이블은 같은 원리로 반대 결론을 냈습니다. 지우는 단위와 읽는 단위가 모두 시간이라 월 파티션을 두었습니다.
대가
같은 데이터를 한 벌 더 두는 만큼 저장량이 약 32% 늘었습니다. 로컬에서 잰 값입니다. 데이터를 지운 뒤에는 projection을 다시 만들어야 readiness check를 통과하는 운영 절차도 생겼습니다. 그 대신 메모리 한도 4GiB를 넘겨 실패하던, 데이터가 가장 많은 고객의 90일 요약 조회가 약 1.9초에 끝났습니다. 운영에 적용하기 전에 같은 구성으로 잰 값입니다.

05결과

  • 원본 이벤트 테이블에서 파티션을 없애자, 디스크에 따로 저장된 데이터 조각(part)이 454개에서 11개로 줄었습니다. 같은 키의 행을 합쳐 읽는 대표 FINAL 집계 쿼리의 메모리 사용량도 약 80% 줄었습니다. 둘 다 전환 직후 운영 환경에서 관측한 값입니다.
  • 원본 신호 테이블의 쓰기 시간이 약 1.2초에서 0.2초로 줄었습니다. 쓰기 100번 중 95번이 끝나는 시간(INSERT p95)을 기준으로 한 값입니다. 테이블을 교체할 때, 같은 13시간 동안의 운영 쓰기를 놓고 비교했습니다.
  • 세션 하나의 행동을 읽는 FINAL 조회는 읽는 행이 99.9% 줄었습니다. sort key를 (고객, 세션, 이벤트)로 바꾼 뒤, 운영 데이터를 읽는 분석 환경에서 잰 값입니다. 바꾸기 전과 후의 조회 결과가 같은 표본만 비교에 넣었습니다.
  • 요약 화면에서 하루치를 조회할 때 읽는 행이 약 99% 줄었습니다. 날짜순 projection을 끈 상태와 켠 상태를 비교했고, 비교한 지표 4개의 값은 양쪽이 같았습니다.
  • 유입 채널 화면에서 7일치를 조회할 때 읽는 행이 약 80% 줄었습니다. 운영 환경에서 같은 고객의 조회를 3번 실행해 비교한 값입니다.
  • AI 유입 화면의 집계 쿼리는 평균 2.4초에서 7ms로 줄었습니다. 전에는 모두 실패하던 일별 조회도 평균 9ms에 끝났습니다. 15분마다 갱신되는 조회용 테이블로 바꾼 직후, 운영 환경에서 각각 5번씩 실행해 본 짧은 관측입니다.

속도를 재기 전에 두 구조의 결과가 같은지부터 확인해야 합니다. 요청 때 하던 계산을 미리 해 두면, 그 비용이 어디서 생기는지도 함께 재야 합니다.

06트러블슈팅

T-01

비교 직전에 나온 같은 버전, 다른 내용

문제
무파티션 비교를 시작하기 직전에 24시간 분량의 데이터를 점검했습니다. 같은 이벤트이고 버전 값도 같은데 내용이 서로 다른 행 묶음이 30개 넘게 나왔습니다. 버전은 ReplacingMergeTree가 같은 키의 행 중 어느 것을 남길지 정할 때 보는 값입니다.
원인
그중 31개 묶음에서 sort key에 들어 있지 않은 필드 65개를 하나씩 비교했습니다. 값이 다른 필드는 queue에서 이벤트를 꺼내 처리한 시각인 소비 시각 하나뿐이었습니다. retry할 때마다 바뀌는 값이 이벤트 본문에 섞여 있었던 것입니다. ReplacingMergeTree는 버전까지 같은 행이 여럿이면, 병합 순서에 따라 어느 행이 남을지가 달라집니다. 파티션을 바꾸면 part 구성이 바뀌므로, 같은 데이터인데도 화면에 나오는 숫자가 바뀔 수 있었습니다.
해결
비교를 멈추고, 이벤트 본문의 61개 필드를 같은 이벤트인지 판단하는 기준으로 정했습니다. 그리고 버전은 같은데 본문이 다른 행이 들어오면 적재하기 전에 거절하는 검사를 비교용 입력에 추가했습니다.
결과
로컬에서 파티션 설정만 다른 두 테이블에 같은 입력 약 3만 행을 같은 순서로 재생했습니다. 따로 계산한 기대값과 맞춰 보니 어긋난 값이 하나도 없었습니다.
