Blue/Green 무중단 인프라 이관: Cloud Run과 관리형 ClickHouse에서 GKE로

기존 환경을 그대로 두고 GKE에 새 환경을 나란히 세웠습니다. rollback 경로가 실제로 작동하는지 먼저 확인한 뒤에 API 트래픽과 ClickHouse 읽기를 새 환경으로 옮겼습니다. 되돌릴 수 없는 관리형 ClickHouse 해지는 맨 마지막에 했습니다.

01상황과 역할

API와 인증(Zitadel), 권한(OpenFGA) 서비스는 Cloud Run에서 돌았고, 이벤트 저장소로는 관리형 ClickHouse를 썼습니다. 관리형 ClickHouse 레플리카의 CPU 사용량을 약 한 달 동안 보니 p99가 상한인 4 vCPU의 99%였습니다. 바쁜 시간에는 CPU를 거의 상한까지 쓰고 있었다는 뜻입니다. 백업으로 데이터를 실제로 복원해 보는 복구 리허설은 한 번도 해 본 적이 없었습니다.

GCP 크레딧을 활용하고 인프라를 GKE 하나로 모으기 위해 ClickHouse도 GKE로 옮기기로 했습니다. 저는 이관 설계부터 관리형 서비스 해지까지 이끌었고, ClickHouse 이관은 혼자 맡았습니다. 장애가 나면 kubectl과 ClickHouse의 system 테이블을 직접 보며 원인을 추적했습니다.

두 시스템 모두 운영 트래픽을 받고 있었습니다. 특히 ClickHouse는 stateful 시스템이라, 한 번에 바꾸면 문제가 생겼을 때 되돌리기 어렵습니다. 그래서 기존 환경을 남겨 둔 채 새 환경을 옆에 세우는 Blue/Green 방식으로 설계했습니다.

02해결 과정

기존 환경은 Cloud Run의 API, 인증, 권한 서비스와 관리형 ClickHouse로 이뤄져 있습니다. 새 환경은 GKE에 같은 서비스를 띄우고 ClickHouse는 관리형 대신 직접 운영하는 클러스터로 뒀습니다. 이 클러스터는 레플리카 사이의 replication log를 관리하는 Keeper 3대와 데이터를 담는 레플리카 2대로 이뤄져 있고, 이들을 한 리전 안의 서로 다른 존 3곳에 나눠 놓았습니다.

기존 환경과 새 환경 사이에는 전환 스위치를 두 개 뒀습니다. API 트래픽은 로드밸런서가 두 환경에 요청을 나눠 보내는 backend 가중치로 옮기고, ClickHouse 읽기는 어느 쪽에서 읽을지 정하는 설정값 하나로 옮깁니다. 두 스위치 모두 rollback 절차를 먼저 확인한 뒤에 새 환경 쪽으로 넘겼습니다. 관리형 서비스 해지처럼 되돌릴 수 없는 단계는 맨 마지막에 뒀습니다.

ClickHouse는 stateful 시스템이라, 쓰기 성공 조건과 노드 하나가 빠졌을 때의 동작을 따로 그렸습니다.

  1. rollback 경로부터 확인한 API 전환

    Terraform으로 관리하는 외부 로드밸런서의 backend 가중치를 바꿔 트래픽을 옮겼습니다. 위험이 작은 API를 먼저 옮기고, 스테이징과 운영이 함께 쓰는 인증 서버는 마지막에 옮겼습니다. 인증 서버는 먼저 요청의 5%만 새 환경으로 보냈다가 다시 모두 기존 환경으로 되돌려 rollback이 실제로 되는지 확인했고, 그 뒤에 요청 전부를 새 환경으로 옮겼습니다. 기존 환경으로 되돌렸을 때와 새 환경으로 전부 옮겼을 때 각각 요청 12건을 보냈고, 12건 모두 정상으로 응답했습니다. 이 방식을 고른 이유는 아래 설계 결정 D-01에 적었습니다.

    기존 환경과 새 환경을 나란히 띄우면서 두 환경이 같은 PostgreSQL을 함께 쓴다는 점이 문제가 됐습니다. 전환 당일 새벽, Cloud Run의 스테이징 API를 다시 띄우자 권한 서비스 OpenFGA가 503을 돌려줬습니다. 스테이징 PostgreSQL은 동시 연결을 25개까지만 받는데, 그 25개가 이미 모두 쓰이고 있었습니다. 5% 전환을 멈추고, 아직 트래픽을 받지 않던 새 환경 쪽 Pod를 모두 내려 그쪽이 잡고 있던 연결을 돌려받았습니다. DB를 재시작해 max_connections를 올리는 대신, 서비스별 connection pool 크기를 API 4개, OpenFGA 2개, Zitadel 2개로 나눠 정했습니다. 쓰이는 연결이 15개로 내려온 것을 확인하고 같은 날 오후에 5%를 보냈습니다.

    요청 전부를 새 환경으로 옮긴 뒤에도 응답이 정상인 것을 확인하고, 더는 쓰지 않는 Cloud Run 서비스 6개를 정리했습니다.

  2. 새 환경을 Git으로 배포하는 GitOps 전환

    운영 상태를 Git에 선언해 두고, Argo CD가 Git에 적힌 대로 배포하게 바꿨습니다. 먼저 운영 중인 리소스 60여 개를 지금 모습 그대로 Git으로 가져왔습니다. 그다음 Kubernetes server-side diff로 Git의 내용과 실제 운영 상태를 비교해 diff가 0인 것을 확인한 뒤에 배포를 Argo CD에 맡겼습니다. 매니페스트를 새로 쓰지 않고 가져온 이유는 아래 설계 결정 D-02에 적었습니다.

    스테이징과 운영은 같은 Git 저장소와 Argo CD로 배포합니다. CI가 새 이미지를 빌드하면 Kargo가 Git에 적힌 이미지 버전을 새 버전으로 바꾸고, Argo CD가 이 변경을 클러스터에 반영합니다. 스테이징은 auto sync로 Argo CD가 Git과 실제 상태의 차이를 계속 맞추게 했습니다. 누군가 클러스터를 직접 고치면 Git 상태로 되돌리는 selfHeal은 켰고, Git에서 빠진 리소스를 클러스터에서도 지우는 prune은 꺼서 리소스가 실수로 지워지지 않게 했습니다. 운영은 Argo CD에서 diff를 확인한 뒤 수동으로 sync합니다.

    Secret은 GCP Secret Manager에 두고 External Secrets Operator로 클러스터에 동기화했습니다. DB schema migration은 Argo CD가 앱을 반영하기 직전 단계인 PreSync hook에서 돌게 옮겼습니다. CI 계정은 클러스터를 읽기만 할 수 있게 바꿨습니다. 쓰기 권한을 거둔 뒤 클러스터 audit log를 조회해 보니, CI가 클러스터를 바꾼 기록은 한 건도 없었습니다. 같은 쿼리를 권한을 거두기 전 기간에 돌리면 3건이 나왔으므로, 0건이 쿼리를 잘못 짜서 나온 결과가 아니라는 것도 확인했습니다.

    운영 API를 Argo CD로 처음 반영하며 Pod를 교체하는 동안, 외부 헬스체크가 503 응답을 한 번 받았습니다. 원인과 수정은 아래 트러블슈팅 T-01에 적었습니다.

  3. 존 하나가 빠져도 Keeper와 데이터가 남는 새 환경의 ClickHouse 구성

    Keeper 3대를 존 a, b, c에 한 대씩 뒀습니다. ClickHouse 레플리카 2대는 서로 다른 존에 뒀습니다. 처음 적용했을 때 Pod가 한 존에 몰려서, topology spread constraint를 필수 조건으로 바꾸고 minDomains를 3으로 둬 Pod가 반드시 3개 존에 나뉘어 놓이게 했습니다. 쓰기는 insert_quorum=2로 설정해, 두 레플리카가 모두 데이터를 받아야 성공으로 처리되게 했습니다. 이렇게 고른 이유는 아래 설계 결정 D-03에 적었습니다. 레플리카를 하나 내려 본 시험은 Kafka + Flink 스트림 처리 아키텍처 재설계와 무중단 전환 페이지에 적었습니다.

    리소스 크기는 실제 사용량을 기준으로 잡았습니다. 정해진 주기마다 결과를 다시 계산하는 Refreshable MV는 새 환경으로 옮기지 않았기 때문에, CPU는 그 부하를 뺀 사용량의 p95를 구하고 그 약 4배인 약 7 vCPU를 배정했습니다. 메모리는 과거 최대 사용량의 약 1.7배인 24 GiB로 잡았습니다.

    ClickHouse를 설치하고 관리하는 operator에는 ClickHouse namespace 안의 권한만 줬습니다. cluster-wide 권한을 주면 operator가 클러스터의 모든 Secret을 읽을 수 있기 때문입니다. 띄워 보니 users.xml에서 권한을 따로 정하지 않은 사용자가 모든 권한을 갖고 있어서, 기본 설정에 REVOKE ALL을 넣었습니다.

  4. 읽기를 옮기기 전에 끝낸 복구 리허설

    각 레플리카 Pod에 clickhouse-backup sidecar 컨테이너를 붙여, 레플리카마다 매일 GCS로 백업을 올립니다. 복구 리허설은 스테이징에서 먼저 했습니다. 첫 시도는 설정 문제로 ClickHouse가 오류 코드 36을 내며 실패했습니다. 설정을 고쳐 다시 돌렸고, 복구한 데이터의 테이블별 행 수와 hash가 원본과 같았습니다. 운영에서도 같은 크기의 데이터로 한 번 더 했습니다.

  5. retry해도 중복되지 않는 idempotent backfill

    원본을 읽어 바로 넣는 INSERT SELECT 쿼리 한 번으로 전체를 옮기면, 중간에 실패했을 때 어디까지 들어갔는지 알 수 없습니다. 그래서 과거 데이터 전체를 테이블별, 고객별, 날짜별로 잘게 나눈 청크 단위로 옮겼습니다.

    청크마다 dedup 토큰인 insert_deduplication_token을 붙였습니다. ClickHouse의 복제 테이블 엔진인 ReplicatedMergeTree는 이미 받은 토큰으로 다시 들어온 데이터 블록은 쓰지 않습니다. 그래서 실패한 청크를 같은 토큰으로 retry하면, 이미 들어간 블록은 건너뛰고 빠진 부분만 들어갑니다. 넣은 뒤에는 새 환경에서 그 청크를 다시 읽어 원본과 맞춰 봤고, 맞은 청크만 완료로 기록했습니다.

    복사하는 동안 INSERT 쿼리가 메모리 한도 4 GiB를 넘어 계속 실패했습니다. 처음에는 한 번에 넣는 블록이 커서 그렇다고 보고 블록을 쪼갰지만 효과가 없었습니다. 그래서 ClickHouse가 내부 동작을 기록하는 system.trace_log에서 메모리를 할당한 call stack을 모아 봤습니다. 그 결과 INSERT 하나가 쓰기 스레드 4개로 동시에 돌고 있었습니다. 쓰기 스레드 수(max_insert_threads)를 1로 줄이고, 서버가 들어온 데이터를 다시 묶어 쓰는 블록의 크기(min_insert_block_size_bytes)를 64 MiB로 낮췄습니다. 그러자 같은 청크를 넣을 때 쓰는 메모리가 약 0.6 GiB로 줄었습니다. 실패한 청크를 retry하기 전에는, part가 만들어지고 지워진 기록이 남는 system.part_log를 보고 실패한 쿼리가 남긴 데이터가 있는지 먼저 확인했습니다.

  6. 읽기 전환, 그리고 마지막에 둔 해지

    새 환경은 운영으로 들어오는 데이터를 기존 환경과 똑같이 함께 받는 mirroring 상태였습니다. 처음 계획했던 7일 동안의 관찰과 추가 복구 리허설은 건너뛰었고, 그 이유는 아래 설계 결정 D-04에 적었습니다. 대신 세 가지를 확인했습니다. 옮긴 청크가 모두 검증을 통과했는지, 최근 24시간의 고유 이벤트 수가 두 환경에서 같은지, 적재 이력이 Kafka consumer offset과 맞는지 봤습니다.

    해지 직전에 두 환경의 데이터를 대조해 보니, 이벤트 테이블 하나에서만 새 환경 쪽이 0.5% 이하로 조금 더 많았습니다. 같은 이벤트가 다시 전송됐을 때 두 환경의 dedup 방식이 달라서 생긴 차이로 판단하고 진행했습니다.

    읽기 경로는 설정값 하나로 새 환경으로 옮겼습니다. rollback은 같은 값을 되돌리고 재시작하면 됩니다. 이어서 기존 환경으로 데이터를 넣던 적재를 멈췄습니다. 그리고 따로 보관해 둔 과거 광고 데이터를 새 환경에 넣고, 고유 키가 원본과 맞는 것을 확인했습니다. 되돌릴 수 없는 관리형 서비스 해지는 이 모든 단계를 마친 뒤 맨 마지막에 했습니다.

03설계 결정

해결 과정의 각 단계에서 고른 방법과 그 대가입니다. 네 결정은 같은 원칙을 따릅니다. rollback 경로를 먼저 확인하고, 되돌릴 수 없는 작업은 맨 뒤로 미룹니다.

D-01

로드밸런서 가중치로 옮기고, rollback부터 실행해 보기

고민
API, 인증, 권한 서버를 Cloud Run에서 GKE로 옮겨야 했습니다. 인증 서버는 스테이징과 운영이 함께 쓰는, 로그인 토큰을 발급하는 서버였습니다. 한 번 잘못 넘기면 두 환경의 로그인이 함께 깨집니다.
선택지
두 방법을 비교했습니다. ① DNS 레코드를 바꿔 한 번에 넘기는 방법과, ② 기존 로드밸런서에 새 환경을 backend로 하나 더 붙이고 가중치를 조금씩 옮기는 방법입니다.
결정과 이유
②를 골랐습니다. DNS는 캐시가 남아 있어 되돌려도 바로 반영되지 않고, 트래픽을 비율로 나눠 보낼 수도 없습니다. 먼저 새 환경의 가중치를 0으로 둬 실제 트래픽은 보내지 않은 채, 새 환경의 서비스가 모두 정상인지 봤습니다. 인증 서버는 맨 마지막에 요청의 5%만 새 환경으로 보낸 뒤 기존 환경으로 한 번 되돌렸습니다. 한 번도 실행해 보지 않은 rollback은 실제로 될지 알 수 없다고 생각했습니다. 그래서 위험이 가장 작은 5% 시점에 rollback부터 실행해 봤습니다.
대가
전환이 반나절 늦어졌습니다. 대신 기존 환경과 새 환경이 함께 떠 있을 때만 드러나는 DB 연결 부족 문제를, 요청 전부를 새 환경으로 옮기기 전에 찾았습니다.
D-02

운영 중인 리소스를 Git으로 가져오고, 필드마다 관리 주체를 하나로 두기

고민
기존 배포 도구는 API를 GKE로 옮긴 뒤 한 번도 성공하지 못했습니다. 운영 클러스터를 바꾼 작업의 약 90%는 사람이 직접 한 것이었습니다. CI, 사람, 로컬 도구가 같은 리소스를 번갈아 고쳤습니다. 운영에 무엇이 떠 있는지 Git만 보고는 설명할 수 없었습니다.
선택지
두 방법을 비교했습니다. ① 배포 설정 파일(매니페스트)을 새로 써서 운영을 덮어쓰는 방법과, ② 지금 떠 있는 상태를 그대로 Git으로 가져와 운영과 다른 곳이 없는 것을 확인한 뒤 Argo CD에 넘기는 방법입니다.
결정과 이유
②를 골랐습니다. 덮어쓰면 그 순간 운영이 바뀝니다. 지금 상태를 먼저 가져오면 넘기는 일 자체는 아무것도 바꾸지 않습니다. 그 뒤의 변경은 모두 Git을 거쳐서만 들어옵니다. 같은 필드를 두 주체가 바꾸면 어느 쪽 값이 맞는지 정할 수 없습니다. 그래서 필드마다 바꾸는 주체(field manager)를 하나로 정했고, CI의 클러스터 쓰기 권한은 회수했습니다.
대가
Kubernetes의 server-side apply는 필드마다 어느 주체가 관리하는지 기록하고, 다른 주체가 관리하는 필드는 지우지 않습니다. 그래서 예전에 다른 주체가 넣어 둔 필드가 남아 있어도 비교 결과는 차이가 없는 것으로 나올 수 있었습니다. 필드별 관리 주체 기록(managedFields)을 세 번 확인해 이렇게 남은 필드를 찾아냈습니다.
D-03

직접 운영하는 ClickHouse는 존을 나눠 두고, 두 레플리카에 모두 쓰고, 복구 리허설을 통과한 뒤에 넘기기

고민
관리형에서 직접 운영으로 오면 벤더가 맡던 가용성과 백업을 직접 맡게 됩니다. 처음 적용했을 때 Keeper 3대가 한 존에 몰렸습니다. 복구 리허설은 한 번도 해 본 적이 없었습니다.
선택지
쓰기를 언제 성공으로 볼지는 ① 레플리카 하나만 받아도 성공으로 보는 방법과 ② 두 레플리카가 모두 받아야 성공으로 보는 방법 사이에서 골라야 했습니다.
읽기를 언제 옮길지는 ③ 백업만 갖춰 두고 옮기는 방법과 ④ 복구 리허설에 성공한 뒤에 옮기는 방법 사이에서 골라야 했습니다.
결정과 이유
②와 ④를 골랐습니다. replication log를 관리하는 Keeper는 3대 중 2대가 살아 있어야 쓰기를 받습니다. 존마다 1대씩 두면 존 하나가 빠져도 1대만 잃고 2대가 남습니다. 두 레플리카가 모두 받아야 성공으로 보면 한 대가 빠졌을 때 쓰기가 멈춥니다. 하지만 쓰기가 멈추는 쪽이 레플리카끼리 데이터가 서로 달라지는 쪽보다 복구하기 쉽습니다. 멈춘 동안 들어온 데이터는 ClickHouse 앞단의 Kafka에 쌓여 있습니다. 또 레플리카 수와 쓰기 성공에 필요한 레플리카 수(quorum)가 맞지 않으면, Kafka에서 ClickHouse로 데이터를 넣는 적재 consumer가 아예 시작하지 않게 했습니다. 직접 운영에서는 백업이 있는 것과 복구되는 것이 다른 문제입니다. 그래서 스테이징과 운영에서 복구 리허설을 통과한 뒤에 읽기를 옮겼습니다.
대가
레플리카 한 대가 빠지거나 레플리카를 rolling restart하는 동안에는 데이터 적재가 멈춥니다. 또 복구 리허설은 1.95 GiB 데이터로만 했기 때문에, 전체 데이터를 복구하는 데 얼마나 걸릴지는 말할 수 없습니다.
D-04

되돌릴 수 있는 단계는 한 번에 옮기고, 되돌릴 수 없는 단계는 맨 끝에 하나씩 하기

고민
처음 계획은 두 경로를 함께 켜고 7일 동안 지켜본 뒤 기존 경로를 지우는 것이었습니다. 관찰을 늘리면 관리형 서비스 비용이 약 한 달 치 더 나갑니다. 일정과 비용 때문에 그만큼 기다릴 수 없었습니다.
선택지
두 방법을 비교했습니다. ① 고객 단위 canary로 새 환경 비율을 조금씩 올리며 7일 동안 지켜보는 방법과, ② 단계마다 되돌릴 수 있는지 따져서 되돌릴 수 있는 단계는 한 번에 켜고, 되돌릴 수 없는 단계는 미리 정한 조건을 채운 뒤에 하나씩 진행하는 방법입니다.
결정과 이유
②를 골랐습니다. mirroring과 읽기 전환은 설정값 하나로 되돌릴 수 있어 한 번에 옮겼습니다. 기존 환경으로 넣던 적재를 멈추는 일, 관리형 서비스 해지, credential 폐기는 되돌릴 수 없어서 맨 끝에 뒀습니다. 해지하기 전에는 새 환경에 없고 다시 계산해 만들 수도 없는 데이터만 골라 따로 보관했습니다. 보관한 데이터는 청크마다 원본과 맞춰 봤습니다. 7일 동안 지켜보며 얻으려던 증거는, 매일 두 환경의 데이터를 대조하고 해지 직전에 전 기간 데이터를 한 번 더 대조하는 것으로 대신했습니다.
대가
7일 동안의 관찰, canary 전환, 추가 복구 리허설을 모두 건너뛰었습니다. 그래서 서비스가 한 번도 멈추지 않았다거나 잃은 데이터가 하나도 없다고는 말할 수 없습니다. 또 기존 환경으로의 적재를 끈 뒤에는 기존 환경으로 돌아갈 길이 없습니다.

04결과

  • 인증 서버를 옮길 때 rollback 경로가 실제로 작동하는지 먼저 확인했습니다. 요청의 5%를 새 환경으로 보낸 뒤 다시 기존 환경으로 되돌렸고, 그다음 요청 전부를 새 환경으로 옮겼습니다. 되돌렸을 때와 전부 옮겼을 때 각각 요청 12건을 보냈고, 모두 정상으로 응답했습니다.
  • 이전에는 백업으로 데이터를 되살리는 복구 리허설을 한 번도 해 본 적이 없었는데, 이번에 스테이징과 운영에서 한 번씩, 모두 두 번 성공했습니다. 1.95 GiB 데이터를 복구하는 데 스테이징은 약 2분, 운영은 약 30초가 걸렸습니다.
  • 운영 상태를 Git에 선언하고 Argo CD가 그대로 반영하는 GitOps로 배포 방식을 바꿨습니다. 전환 뒤 확인했을 때 Argo CD로 배포하는 앱 25개 모두 Git과 실제 상태 사이에 차이가 없었습니다. CI의 쓰기 권한을 거둔 뒤에는 CI가 클러스터를 직접 바꾼 기록이 한 건도 없었습니다.
  • 새 Pod로 교체하는 도중 503 오류가 한 번 나던 문제를 고친 뒤, 밖에서 1초 간격으로 헬스체크를 보내 확인했습니다. 스테이징에서 교체를 두 번 하는 동안 보낸 300여 회와 운영에 반영하는 동안 보낸 100회가 모두 정상 응답(200)이었습니다.
  • 과거 데이터를 모두 새 환경으로 옮기고 읽기도 새 환경으로 바꾼 뒤에 관리형 ClickHouse를 해지했습니다. 더는 쓰지 않는 Cloud Run 서비스 6개도 정리했습니다.

stateful 시스템을 옮길 때는 rollback 경로와 복구 시간을 먼저 확인한 뒤에 트래픽을 옮겨야 합니다. 되돌릴 수 없는 단계는 가장 뒤에 둬야 합니다. 검증 단계를 줄일 때는 무엇을 건너뛰었고 무엇으로 대신 확인했는지 함께 남겨야 합니다.

05트러블슈팅

T-01

새 Pod로 교체하는 중 한 번 나온 503 오류

문제
운영 API를 Argo CD로 처음 반영하며 Pod를 새로 교체하는 rollout 동안, /health를 호출하는 외부 헬스체크가 503 응답을 한 번 받았습니다. 컨테이너 이미지는 그대로이고 설정만 바뀐 rollout이었습니다. 보름 전 스테이징에서도 503을 한 번 본 적이 있습니다. 그때도 아래 원인에 적은 것과 같은 readiness gate 사유를 봤지만, 옛 Pod가 종료되는 쪽만 고쳤습니다. 종료하기 전에 60초를 기다리게 하는 preStop 설정과 90초의 termination grace period를 넣은 것입니다. 새 Pod가 트래픽을 받기 시작하는 쪽을 놓친 것이었습니다.
원인
로드밸런서는 5초 간격으로 보내는 헬스체크를 새 Pod가 2번 연속 통과해야 그 Pod로 트래픽을 보냅니다. 그런데 GKE가 매니페스트와 상관없이 Pod에 자동으로 넣는 NEG readiness gate는 이 헬스체크 통과보다 먼저 통과했습니다. Kubernetes는 이 조건이 통과하면 새 Pod가 준비됐다고 보고 옛 Pod를 내립니다. 운영의 새 Pod에도 헬스체크 없이 통과했다는 뜻의 사유 LoadBalancerNegWithoutHealthCheck가 남아 있었습니다. API Pod가 1개뿐이어서, 새 Pod가 트래픽을 받기 시작하기 전에 옛 Pod가 먼저 빠졌습니다.
해결
옛 Pod의 종료 대기를 더 늘리는 대신, 새 Pod가 트래픽을 받기 시작하기 전까지 생기는 빈틈을 메우기로 했습니다. 먼저 API Pod를 2개로 늘려도 되는지 코드로 확인했습니다. 프로세스 안에서 혼자 도는 스케줄러나, 여러 개 중 하나를 대표로 뽑는 leader election 로직이 없었습니다. 같은 데이터를 동시에 고치는 충돌은 PostgreSQL advisory lock이 막고 있었고, 세션은 Redis가 맡고 있었습니다. 그래서 세 가지를 Git에 적고 스테이징에 먼저 반영했습니다. 새 Pod가 준비된 뒤 30초가 지나야 사용 가능으로 치는 minReadySeconds 30초, Pod 2개, 그리고 한꺼번에 내려가는 Pod 수를 제한하는 PodDisruptionBudget(PDB)입니다. 30초는 5초 간격 헬스체크를 두 번 연속 통과하는 시간에, 전파가 늦어질 때를 대비한 여유를 더한 값입니다. Pod가 두 배가 되면 DB 연결도 그만큼 더 쓰므로, DB 연결에 여유가 있는지도 확인했습니다. 운영에는 Argo CD에서 Deployment와 PDB 두 리소스만 골라 반영했습니다.
결과
스테이징에서 rollout을 두 번 하는 동안 밖에서 1초 간격으로 헬스체크를 300여 회 보냈고, 모두 정상 응답(200)을 받았습니다. 이때 뜬 새 Pod 4개 중 2개에서는 readiness gate가 헬스체크 통과보다 먼저 통과하는 일이 다시 있었습니다. 하지만 30초 동안은 새 Pod를 사용 가능으로 치지 않으므로, 그 사이 옛 Pod가 먼저 빠지지 않았습니다. 운영에 반영하는 동안 보낸 헬스체크 100회도 모두 200이었습니다. 503을 처음 발견한 때부터 운영에 수정을 반영하기까지 약 46분이 걸렸습니다.
