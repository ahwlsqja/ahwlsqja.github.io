Blue/Green 설계와 안전한 전환: Cloud Run과 관리형 ClickHouse를 GKE로 이관

기존 환경(Blue)을 그대로 두고 GKE에 새 환경(Green)을 나란히 세웠습니다. 되돌리는 길을 먼저 확인한 뒤에 트래픽과 읽기를 Green으로 옮겼습니다. 되돌릴 수 없는 관리형 ClickHouse 해지는 맨 마지막에 했습니다.

01상황과 역할

API와 인증(Zitadel), 권한(OpenFGA) 서비스는 Cloud Run에서 돌았습니다. 이벤트 저장소는 관리형 ClickHouse를 썼습니다. 약 한 달 동안 잰 저장소 레플리카의 CPU p99는 상한 4 vCPU의 99%였습니다. 복구 리허설은 한 번도 해 본 적이 없었습니다.

ClickHouse를 GKE로 옮기는 것은 회사가 GCP 크레딧 활용과 인프라 단일화를 이유로 정했습니다. 저는 이관 설계부터 관리형 서비스 해지까지 이끌었고, ClickHouse 이관은 혼자 맡았습니다. 장애는 kubectl과 ClickHouse system 테이블로 직접 추적했습니다.

두 시스템 모두 운영 중이었습니다. 특히 저장소는 상태를 가진 시스템이라, 한 번에 바꾸면 문제가 생겼을 때 되돌리기 어렵습니다. 그래서 기존 환경을 남겨 둔 채 새 환경을 옆에 세우는 Blue/Green 방식으로 설계했습니다.

02해결 과정

Blue는 기존 환경입니다. Cloud Run의 API, 인증, 권한 서비스와 관리형 ClickHouse가 여기에 있습니다. Green은 새 환경입니다. GKE의 같은 서비스와 직접 운영하는 ClickHouse(Keeper 3대, 레플리카 2대, 3개 존)를 뒀습니다.

Blue와 Green 사이에는 스위치를 두 개 뒀습니다. API 트래픽은 로드밸런서 가중치로, ClickHouse 읽기는 설정값 하나로 옮깁니다. 두 스위치 모두 되돌리는 방법을 먼저 정하고 앞으로 옮겼습니다. 관리형 서비스 해지처럼 되돌릴 수 없는 단계는 맨 마지막에 뒀습니다.

  1. 롤백 경로부터 증명한 API 전환

    Terraform으로 관리하는 외부 로드밸런서의 가중치를 바꿔 옮겼습니다. 위험이 작은 API를 먼저 옮기고, 두 환경이 함께 쓰는 인증 서버는 마지막에 옮겼습니다. 인증 서버는 Green 5%, Blue로 롤백, Green 100% 순서로 옮겼습니다. 롤백과 100% 전환 때 각각 요청 12건을 보냈고 모두 정상 응답이었습니다. 이 방식을 고른 이유는 아래 설계 결정 D-01에 적었습니다.

    Blue와 Green을 나란히 띄우니 둘이 같은 PostgreSQL을 함께 쓴다는 점이 문제가 됐습니다. 전환 당일 새벽, Cloud Run의 스테이징 API를 다시 띄우자 OpenFGA가 503을 냈습니다. 스테이징 DB(연결 한도 25)에 남은 연결 슬롯이 없었습니다. 5% 전환을 멈추고, 트래픽이 없는 Green 쪽 Pod를 모두 내려 연결을 돌려받았습니다. DB를 재시작해 연결 한도를 올리는 대신, 서비스별 연결 풀을 API 4, OpenFGA 2, Zitadel 2로 나눴습니다. 연결 사용이 15로 내려온 것을 보고 같은 날 오후에 5%를 보냈습니다.

    100% 전환 뒤 응답이 정상인 것을 확인하고 Cloud Run 서비스 6개를 정리했습니다.

  2. Green을 Git으로 배포하는 GitOps 전환

    운영 상태를 Git에 선언하고 Argo CD로 배포하게 바꿨습니다. 운영 중인 리소스 60여 개를 Git으로 그대로 가져왔습니다. server-side diff로 차이가 0인 것을 본 뒤에 Argo CD에 맡겼습니다. 새로 쓰지 않고 가져온 이유는 아래 설계 결정 D-02에 적었습니다.

    스테이징과 운영은 같은 Git 저장소와 Argo CD로 배포합니다. 스테이징은 Argo CD가 Git과의 차이를 계속 맞추게 했습니다. Git에서 빠진 리소스는 지우지 않도록 selfHeal은 켜고 prune은 껐습니다. 새 이미지가 빌드되면 Kargo가 Git의 이미지 버전을 바꾸고, Argo CD가 이를 반영합니다. 운영은 Argo CD에서 차이를 확인한 뒤 직접 동기화했습니다.

    시크릿은 GCP Secret Manager에 두고 External Secrets Operator로 받게 했습니다. DB 마이그레이션은 Argo CD의 PreSync 단계로 옮겼습니다. CI 계정은 읽기 전용으로 바꿨습니다. 권한을 회수한 뒤 감사 로그에서 CI가 클러스터를 바꾼 기록은 0건이었습니다. 같은 조회로 회수 전 구간에서는 3건이 잡혀, 조회 자체가 맞는지도 확인했습니다.

    운영 API를 Argo CD로 처음 반영한 롤아웃에서 외부 헬스체크에 503이 한 번 찍혔습니다. 원인과 수정은 아래 트러블슈팅 T-01에 적었습니다.

  3. Green의 ClickHouse: 존 하나가 빠져도 남는 구성

    Keeper 3대를 존 a, b, c에 한 대씩 뒀습니다. ClickHouse 레플리카 2대는 서로 다른 존에 뒀습니다. 처음 적용했을 때 Pod가 한 존에 몰려서, 존 분산 조건(minDomains 3)을 필수로 바꿨습니다. 쓰기는 insert_quorum=2로 두 레플리카가 모두 받아야 성공하게 했습니다. 이렇게 고른 이유는 아래 설계 결정 D-03에 적었습니다. 레플리카를 하나 내려 본 시험은 V3 실시간 아키텍처 페이지에 적었습니다.

    Green에는 갱신 뷰(Refreshable MV)를 옮기지 않았습니다. 그래서 CPU는 그 부하를 뺀 실측 p95의 약 4배인 약 7 vCPU로 잡았습니다. 메모리는 과거 최대 사용량의 약 1.7배인 24 GiB로 잡았습니다.

    operator에는 해당 namespace 안의 권한만 줬습니다. 클러스터 전체 권한을 주면 모든 Secret을 읽을 수 있기 때문입니다. 띄워 보니 users.xml에서 권한을 따로 주지 않은 사용자가 전체 권한을 갖고 있었습니다. 그래서 REVOKE ALL을 기본으로 넣었습니다.

  4. 읽기를 옮기기 전에 끝낸 복구 리허설

    백업은 clickhouse-backup 사이드카로 매일 GCS에 받습니다. 복구 리허설은 스테이징에서 먼저 했습니다. 첫 시도는 설정 문제(Code 36)로 실패했습니다. 설정을 고쳐 다시 돌렸고, 테이블별 행 수와 해시가 원본과 같았습니다. 운영에서도 같은 크기로 한 번 더 했습니다.

  5. 다시 돌려도 중복되지 않는 과거 데이터 이관

    INSERT SELECT 한 번으로 옮기면 중간에 실패했을 때 어디까지 들어갔는지 알 수 없습니다. 그래서 과거 데이터 전체를 테이블, 고객, 날짜별 청크로 나눠 옮겼습니다.

    청크마다 insert_deduplication_token을 붙였습니다. ReplicatedMergeTree는 같은 토큰으로 들어온 블록을 다시 쓰지 않습니다. 그래서 실패한 청크를 같은 토큰으로 다시 돌리면 이미 들어간 블록은 건너뜁니다. Green에서 다시 읽어 원본과 맞춰 본 청크만 완료로 기록했습니다.

    복사 중에는 INSERT가 메모리 한도 4 GiB에 계속 걸렸습니다. 처음에는 블록이 크다고 보고 쪼갰지만 효과가 없었습니다. system.trace_log로 메모리 할당 스택을 모아 보니, INSERT 하나가 쓰기 스레드 4개로 동시에 돌고 있었습니다. max_insert_threads를 1로 줄이고, 서버가 다시 묶는 블록 크기(min_insert_block_size_bytes)를 64 MiB로 낮췄습니다. 같은 청크의 메모리가 약 0.6 GiB로 내려갔습니다. 다시 돌리기 전에는 실패한 쿼리가 남긴 데이터가 있는지 system.part_log로 먼저 확인했습니다.

  6. 읽기 전환, 그리고 마지막에 둔 해지

    Green은 10월 7일부터 운영 미러링으로 Blue와 같은 데이터를 함께 받고 있었습니다. 7일 관찰과 추가 복구 리허설은 건너뛰었습니다. 그 이유는 아래 설계 결정 D-04에 적었습니다. 대신 모든 청크의 검증, 24시간 고유 이벤트 수, 적재 이력과 Kafka 오프셋이 서로 맞는지 확인했습니다.

    해지 직전 대조에서는 이벤트 테이블 하나만 Green 쪽이 조금(0.5% 이하) 많았습니다. 재전송과 중복 제거 방식의 차이로 보고 진행했습니다.

    읽기 경로는 설정값 하나로 Green으로 옮겼습니다. 되돌릴 때는 같은 값을 되돌리고 재시작하면 됩니다. 이어서 Blue 쪽 적재를 멈췄고, 과거 광고 데이터 보관본을 Green에 넣어 고유 키가 맞는 것을 확인했습니다. 되돌릴 수 없는 관리형 서비스 해지는 이 모든 단계를 마친 뒤 맨 마지막에 했습니다.

03설계 결정

해결 과정의 단계마다 고른 길과 그 대가입니다. 네 결정에는 같은 기준이 깔려 있습니다. 되돌리는 길을 먼저 확인하고, 되돌릴 수 없는 일은 맨 뒤로 미룹니다.

D-01

로드밸런서 가중치로 옮기고, 되돌리는 길부터 써 보기

고민
API, 인증, 권한 서버를 Cloud Run에서 GKE로 옮겨야 했습니다. 인증 서버는 스테이징과 운영이 함께 쓰는 발급자였습니다. 한 번 잘못 넘기면 두 환경의 로그인이 함께 깨집니다.
선택지
① DNS를 바꿔 한 번에 넘기기 ② 로드밸런서에 Green 백엔드를 붙이고 가중치로 옮기기
결정과 이유
②를 골랐습니다. DNS는 캐시 때문에 되돌리기가 느리고 비율을 나눌 수 없습니다. 가중치 0에서 Green이 모두 정상인지 먼저 봤습니다. 인증 서버는 맨 마지막에 5%만 보낸 뒤 Blue로 한 번 되돌렸습니다. 한 번도 써 보지 않은 롤백은 롤백이라고 할 수 없습니다. 그래서 위험이 가장 작은 5% 시점에 되돌리기부터 써 봤습니다.
대가
전환이 반나절 늦어졌습니다. 대신 Blue와 Green이 함께 떠 있을 때만 보이는 DB 연결 부족을 100% 전환 전에 찾았습니다.
D-02

운영 중인 리소스를 Git으로 가져오고, 한 필드는 한 주체만 바꾸기

고민
기존 배포 도구는 9월 18일 이후 한 번도 성공하지 못했습니다. 운영 클러스터를 바꾼 작업의 약 90%는 사람이 직접 한 것이었습니다. CI, 사람, 로컬 도구가 같은 리소스를 번갈아 고쳤습니다. 운영에 무엇이 떠 있는지 Git만 보고는 설명할 수 없었습니다.
선택지
① 매니페스트를 새로 써서 덮어쓰기 ② 지금 떠 있는 상태를 그대로 Git으로 가져와 차이 0을 본 뒤 Argo CD에 넘기기
결정과 이유
②를 골랐습니다. 덮어쓰면 그 순간 운영이 바뀝니다. 지금 상태를 먼저 가져오면 넘기는 일 자체는 아무것도 바꾸지 않습니다. 그 뒤의 변경은 모두 Git 한 길로만 들어옵니다. 같은 필드를 두 주체가 쓰면 어느 쪽이 맞는지 정할 수 없습니다. 그래서 필드마다 바꾸는 주체를 하나로 정했고, CI의 클러스터 쓰기 권한은 회수했습니다.
대가
server-side apply는 다른 주체가 가진 필드를 지우지 않습니다. 그래서 남은 필드가 있어도 차이 0으로 보일 수 있었습니다. managedFields를 세 번 확인해 남은 필드를 찾아냈습니다.
D-03

직접 운영하는 ClickHouse: 존 분산, 두 레플리카 쓰기, 복구 리허설을 전환 조건으로

고민
관리형에서 직접 운영으로 오면 벤더가 맡던 가용성과 백업을 직접 맡게 됩니다. 처음 적용했을 때 Keeper 3대가 한 존에 몰렸습니다. 복구 리허설은 한 번도 해 본 적이 없었습니다.
선택지
쓰기: ① 레플리카 하나만 받아도 성공 ② 두 레플리카가 모두 받아야 성공
전환 조건: ③ 백업만 두고 전환 ④ 복구 리허설에 성공해야 읽기 전환
결정과 이유
②와 ④를 골랐습니다. Keeper는 3대 중 2대가 살아 있어야 쓰기를 받습니다. 존마다 1대씩 두면 존 하나가 빠져도 1대만 잃습니다. 쓰기가 멈추는 쪽이 레플리카끼리 데이터가 갈라지는 쪽보다 복구하기 쉽습니다. 멈춘 동안 밀린 데이터는 앞단 Kafka가 들고 있습니다. 레플리카 수와 쓰기 정족수가 다르면 적재기가 아예 뜨지 않게 했습니다. 직접 운영에서는 백업이 있는 것과 복구되는 것이 다른 문제입니다. 그래서 스테이징과 운영에서 복구 리허설을 통과한 뒤에 읽기를 옮겼습니다.
대가
레플리카 한 대가 빠지거나 순서대로 재시작하는 동안에는 적재가 멈춥니다. 리허설은 1.95 GiB 데이터로 했습니다. 그래서 전체 데이터의 복구 시간은 말할 수 없습니다.
D-04

전환 순서: 되돌릴 수 있는 단계는 한 번에, 되돌릴 수 없는 단계는 맨 끝에 하나씩

고민
처음 계획은 두 경로를 함께 켜고 7일 동안 지켜본 뒤 기존 경로를 지우는 것이었습니다. 관찰을 늘리면 관리형 서비스 비용이 약 한 달 치 더 나갑니다. 일정과 비용 때문에 그만큼 기다릴 수 없었습니다.
선택지
① 고객 단위로 비율을 조금씩 올리며 7일 관찰 ② 단계마다 되돌릴 수 있는지 따져, 되돌릴 수 있는 단계는 한 번에 켜고 되돌릴 수 없는 단계는 조건을 채운 뒤 하나씩
결정과 이유
②를 골랐습니다. 미러링과 읽기 전환은 설정값 하나로 되돌릴 수 있어 한 번에 옮겼습니다. 기존 적재 중단, 관리형 서비스 해지, 자격증명 폐기는 맨 끝에 뒀습니다. 해지 전에는 Green에 없고 다시 계산할 수 없는 데이터만 골라 따로 보관했습니다. 보관본은 청크마다 원본과 맞춰 봤습니다. 7일 관찰로 얻으려던 증거는 매일 대조와 해지 직전 전 기간 대조로 대신했습니다.
대가
관찰 기간, 단계적 비율 증가, 추가 리허설을 건너뛰었습니다. 그래서 무중단 전환이나 유실 0이라고는 말할 수 없습니다. 기존 적재를 끈 뒤에는 돌아갈 길이 없습니다.

04결과

  • 롤백 경로 확인(인증 서버): Green 5% → Blue 롤백 → Green 100%, 롤백과 100% 전환 때 각 12건 모두 정상 응답
  • 복구 리허설 0회 → 2회 성공 (1.95 GiB 기준 스테이징 약 2분, 운영 약 30초)
  • GitOps: 앱 25개 모두 Git과 차이 0 (10월 2일), CI가 클러스터를 직접 바꾼 기록 0건
  • 롤아웃 503 수정 뒤: 1초 간격 헬스체크가 스테이징 롤아웃 2번 동안 300여 회, 운영 반영 구간 100회 모두 200
  • 과거 데이터 전체 이관과 읽기 전환 뒤 관리형 ClickHouse 해지, Cloud Run 서비스 6개 정리

상태를 가진 시스템을 옮길 때는 되돌리는 길과 복구 시간을 먼저 확인한 뒤에 트래픽을 옮겨야 합니다. 되돌릴 수 없는 단계는 가장 뒤에 둬야 합니다. 검증 단계를 줄일 때는 무엇을 건너뛰었고 무엇으로 대신 확인했는지 함께 남겨야 합니다.

05트러블슈팅

T-01

롤아웃 중 한 번 찍힌 503

문제
9월 29일 운영 API를 Argo CD로 처음 반영한 롤아웃에서 외부 /health에 503이 한 번 찍혔습니다. 이미지는 그대로이고 설정만 바뀐 롤아웃이었습니다. 보름 전 스테이징에서도 503을 한 번 봤습니다. 그때도 같은 사유를 봤지만 종료 쪽만 고쳤습니다(preStop 60초, 종료 유예 90초). 새 Pod가 트래픽을 받기 시작하는 쪽을 놓친 것이었습니다.
원인
로드밸런서는 5초 간격 헬스체크를 2번 연속 통과해야 새 Pod로 트래픽을 보냅니다. 그런데 GKE가 매니페스트와 상관없이 자동으로 넣는 NEG readiness gate는 그보다 먼저 통과했습니다. 운영 새 Pod에도 사유 LoadBalancerNegWithoutHealthCheck가 남아 있었습니다. 레플리카가 1개뿐이라, 새 Pod가 트래픽을 받기 전에 옛 Pod가 빠졌습니다.
해결
종료 쪽 대기를 더 늘리는 대신, 새 Pod가 트래픽을 받기 시작하는 쪽의 공백을 메우기로 했습니다. 레플리카를 늘려도 되는지 코드로 먼저 확인했습니다. 프로세스 안에서 도는 스케줄러나 리더 선출이 없었고, 쓰기 경합은 PostgreSQL advisory lock이, 세션은 Redis가 맡고 있었습니다. minReadySeconds 30초, 레플리카 2개, PodDisruptionBudget(PDB)을 Git에 선언하고 스테이징에 먼저 반영했습니다. 30초는 헬스체크 간격 5초 × 연속 2번에 전파 여유를 더한 값입니다. Pod가 두 배가 되므로 DB 연결 여유도 확인했습니다. 운영에는 Deployment와 PDB만 골라 동기화했습니다.
결과
스테이징 롤아웃 2번 동안 외부 헬스체크를 1초 간격으로 300여 회 보냈고 모두 200이었습니다. 새 Pod 4개 중 2개에서 readiness gate가 먼저 통과하는 일이 다시 나왔지만, minReadySeconds 동안 새 Pod가 사용 가능으로 잡히지 않아 옛 Pod가 먼저 빠지지 않았습니다. 운영 반영 구간의 100회도 모두 200이었습니다. 탐지부터 운영 반영까지 약 46분이 걸렸습니다.
