인프라 이전: GKE, GitOps, ClickHouse 자체 운영

Cloud Run에 있던 API와 인증 서비스, 관리형 ClickHouse를 GKE로 옮기고 배포를 GitOps로 바꿨습니다. 과거 데이터 약 1.3억 행을 청크 2,600여 개로 나눠 모두 검증한 뒤 관리형 서비스를 해지했습니다.

01상황과 역할

API와 인증(Zitadel), 권한(OpenFGA) 서비스는 Cloud Run에서 돌았습니다. 이벤트 저장소는 관리형 ClickHouse를 썼습니다. 약 한 달 동안 잰 저장소 레플리카의 CPU p99는 상한 4 vCPU의 99%였습니다. 복구 리허설은 한 번도 해 본 적이 없었습니다.

ClickHouse를 GKE로 옮기는 것은 회사가 GCP 크레딧 활용과 인프라 단일화를 이유로 정했습니다. 이전 설계부터 관리형 서비스 해지까지 이끌었고, 1인 담당이었습니다. 장애는 kubectl과 ClickHouse system 테이블로 직접 추적했습니다.

02해결 과정

  1. 롤백부터 확인한 트래픽 전환

    롤백이 되는지 먼저 확인하고 트래픽을 옮겼습니다. Terraform으로 관리하는 외부 로드밸런서의 가중치를 바꿔 GKE로 5%, Cloud Run으로 롤백, GKE로 100% 순서로 옮겼습니다. 롤백과 100% 전환 때 각각 요청 12건을 보냈고 모두 정상 응답이었습니다.

    전환 당일 새벽에는 Cloud Run의 스테이징 API를 다시 띄우자 OpenFGA가 503을 냈습니다. PostgreSQL에 남은 연결 슬롯이 없었습니다. Cloud Run과 GKE의 서비스가 같은 스테이징 DB(연결 한도 25)에 동시에 붙어 있었기 때문입니다. 5% 전환을 멈추고, 트래픽이 없는 GKE 쪽 Pod를 모두 내려 연결을 돌려받았습니다. DB를 재시작해 연결 한도를 올리는 대신, 서비스별 연결 풀을 API 4, OpenFGA 2, Zitadel 2로 나눴습니다. 연결 사용이 15로 내려온 것을 보고 같은 날 오후에 5%를 보냈습니다.

  2. 운영 중인 리소스를 그대로 넘긴 GitOps 전환

    GKE로 옮긴 뒤 9월 말에 배포 경로를 조사했습니다. 기존 배포 도구는 9월 18일 이후 한 번도 성공하지 못했습니다. 운영 클러스터를 바꾼 작업의 약 90%는 사람이 직접 한 것이었습니다.

    배포 도구를 고쳐 쓰는 대신, 운영 상태를 Git에 선언하고 Argo CD로 배포하게 바꿨습니다. 운영 중인 리소스 60여 개를 Git으로 그대로 가져왔습니다. managedFields를 확인하고 server-side diff로 차이가 0인 것을 본 뒤에 Argo CD에 맡겼습니다.

    스테이징은 Argo CD가 Git과의 차이를 계속 맞추게 했습니다. Git에서 빠진 리소스는 지우지 않도록 selfHeal은 켜고 prune은 껐습니다. 새 이미지가 빌드되면 Kargo가 Git의 이미지 버전을 바꾸고, Argo CD가 이를 반영합니다. 운영은 Argo CD에서 차이를 확인한 뒤 직접 동기화했습니다.

    시크릿은 GCP Secret Manager에 두고 External Secrets Operator로 받게 했습니다. DB 마이그레이션은 Argo CD의 PreSync 단계로 옮겼습니다. CI 계정은 읽기 전용으로 바꿨습니다. 권한을 회수한 뒤 감사 로그에서 CI가 클러스터를 바꾼 기록은 0건이었습니다. 같은 조회로 회수 전 구간에서는 3건이 잡혀, 조회 자체가 맞는지도 확인했습니다.

    운영 API를 Argo CD로 처음 반영한 롤아웃에서 외부 헬스체크에 503이 한 번 찍혔습니다. 원인과 수정은 아래 트러블슈팅 T-02에 적었습니다.

  3. 존 하나가 빠져도 데이터가 남는 ClickHouse 클러스터

    Keeper는 Raft로 동작해서 3대 중 2대가 살아 있어야 쓰기를 받습니다. 그래서 Keeper 3대를 존 a, b, c에 한 대씩 뒀습니다. ClickHouse 레플리카 2대는 서로 다른 존에 뒀습니다. 존 하나가 통째로 빠져도 Keeper 과반과 레플리카 하나가 남습니다. 처음 적용했을 때 Pod가 한 존에 몰려서, 존 분산 조건(minDomains 3)을 필수로 바꿨습니다.

    쓰기는 insert_quorum=2로 두 레플리카가 모두 받아야 성공하게 했습니다. 레플리카 하나가 빠지면 쓰기가 멈춥니다. 그동안 밀린 데이터는 앞단 Kafka가 들고 있습니다. 레플리카 하나에만 조용히 쓰이는 것보다 이쪽이 복구하기 쉽다고 판단했습니다. 레플리카를 하나 내려 본 시험은 실시간 스트림 파이프라인 페이지에 적었습니다.

    새 클러스터에는 갱신 뷰(Refreshable MV)를 옮기지 않았습니다. 그래서 CPU는 그 부하를 뺀 실측 p95의 약 4배인 6.8 vCPU로 잡았습니다. 메모리는 과거 최대 사용량의 약 1.7배인 24 GiB로 잡았습니다.

    operator에는 해당 namespace 안의 권한만 줬습니다. 클러스터 전체 권한을 주면 모든 Secret을 읽을 수 있기 때문입니다. 띄워 보니 users.xml에서 권한을 따로 주지 않은 사용자가 전체 권한을 갖고 있었습니다. 그래서 REVOKE ALL을 기본으로 넣었습니다.

    백업은 clickhouse-backup 사이드카로 매일 GCS에 받습니다. 복구 리허설은 스테이징에서 먼저 했습니다. 첫 시도는 설정 문제(Code 36)로 실패했습니다. 설정을 고쳐 다시 돌렸고, 테이블별 행 수와 해시가 원본과 같았습니다. 운영에서도 같은 크기로 한 번 더 했습니다.

  4. 다시 돌려도 중복되지 않는 과거 데이터 복사

    INSERT SELECT 한 번으로 옮기면 중간에 실패했을 때 어디까지 들어갔는지 알 수 없습니다. 그래서 테이블, 고객, 날짜별 청크로 나눠 옮겼습니다.

    청크마다 insert_deduplication_token을 붙였습니다. ReplicatedMergeTree는 같은 토큰으로 들어온 블록을 다시 쓰지 않습니다. 그래서 실패한 청크를 같은 토큰으로 다시 돌리면 이미 들어간 블록은 건너뜁니다. 다만 블록을 나누는 설정을 바꾼 뒤에는 이 동작에 기대지 않고, 실패한 쿼리가 남긴 데이터부터 확인했습니다(아래 트러블슈팅). 새 클러스터에서 다시 읽어 원본과 맞춰 본 청크만 완료로 기록했습니다.

    새 클러스터는 10월 7일부터 운영 미러링으로 같은 데이터를 함께 받고 있었습니다. 원래는 읽기를 옮기기 전에 7일 관찰과 추가 복구 리허설을 거칠 계획이었습니다. 비용을 생각해 이 단계를 건너뛰기로 제가 결정했습니다. 판단 근거는 모든 청크의 검증, 24시간 고유 이벤트 수 대조(차이 ±0.2% 안), 적재 이력과 Kafka 오프셋의 일치(12개 파티션)였습니다.

    해지 직전 대조에서는 이벤트 테이블 하나만 새 클러스터 쪽이 0.1~0.5% 많았습니다. 재전송과 중복 제거 방식의 차이로 보고 진행했습니다. 읽기 경로를 설정값 하나로 옮긴 뒤 관리형 서비스를 해지했습니다.

03결과

  • 과거 데이터 약 1.3억 행, 청크 2,600여 개 모두 검증 통과 (실패로 남은 청크 0)
  • 트래픽 전환: 롤백과 100% 전환 때 각 12건 모두 정상 응답
  • 롤아웃 503 수정 뒤: 1초 간격 헬스체크가 스테이징 롤아웃 2번 동안 315회, 운영 반영 구간 100회 모두 200
  • GitOps: 앱 25개 모두 Git과 차이 0 (10월 2일), CI가 클러스터를 직접 바꾼 기록 0건
  • 복구 리허설 0회 → 2회 성공 (1.95 GiB 기준 스테이징 약 2분, 운영 약 30초)
  • 관리형 ClickHouse 해지, Cloud Run 서비스 6개 정리

상태를 가진 시스템을 옮길 때는 복구 시간과 데이터 일치를 먼저 확인한 뒤에 트래픽을 옮겨야 합니다. 검증 단계를 줄일 때는 무엇을 건너뛰었고 무엇으로 대신 확인했는지 함께 남겨야 합니다.

04트러블슈팅

T-01

블록을 쪼갰는데도 4 GiB를 넘던 INSERT

문제
과거 데이터 복사가 메모리 한도 4 GiB(Code 241)에 여러 번 걸려 멈췄습니다. 처음에는 관리형 ClickHouse에서 읽는 쿼리가 걸렸습니다. 1,270행짜리 청크가 약 37 GiB를 읽고 있어서 정렬 키 조건을 먼저 걸었고, 읽는 양이 약 3 GiB로 줄었습니다. 그다음에는 큰 청크 하나가 새 클러스터 INSERT에서 같은 한도에 계속 걸렸습니다. 블록이 크다고 보고 16,384행으로 쪼갰지만 같은 오류가 났습니다. 이 판단은 틀렸습니다.
원인
system.trace_log에서 실패한 쿼리의 메모리 할당 스택을 모았습니다. INSERT 하나가 쓰기 스레드 4개로 동시에 돌고 있었습니다. 서버는 스레드마다 받은 데이터를 min_insert_block_size_bytes(기본 256 MiB)까지 다시 묶어 들고 있었습니다. 클라이언트가 보내는 블록 크기와는 상관이 없었습니다.
해결
max_insert_threads를 1로, min_insert_block_size_bytes를 64 MiB로 바꿨습니다. 다시 돌리기 전에는 실패한 쿼리가 남긴 데이터가 있는지 system.part_log로 먼저 확인했습니다. 블록을 나누는 설정이 바뀐 채 같은 토큰을 쓰면, 일부만 들어간 청크에서 블록이 잘못 걸러질 수 있기 때문입니다.
결과
같은 청크의 메모리가 4 GiB 초과에서 약 0.6 GiB로 내려갔습니다. 이 설정으로 남은 복사를 마쳤습니다. 처음에 잘못 짚은 원인은 작업 기록에서 고쳐 두었습니다.
T-02

롤아웃 중 한 번 찍힌 503

문제
9월 29일 운영 API를 Argo CD로 처음 반영한 롤아웃에서 외부 /health에 503이 한 번 찍혔습니다. 이미지는 그대로이고 설정만 바뀐 롤아웃이었습니다. 보름 전 스테이징에서도 503을 한 번 봤습니다. 그때도 같은 사유를 봤지만 종료 쪽만 고쳤습니다(preStop 60초, 종료 유예 90초). 새 Pod가 트래픽을 받기 시작하는 쪽을 놓친 것이었습니다.
원인
로드밸런서는 5초 간격 헬스체크를 2번 연속 통과해야 새 Pod로 트래픽을 보냅니다. 그런데 GKE가 매니페스트와 상관없이 자동으로 넣는 NEG readiness gate는 그보다 먼저 통과했습니다. 운영 새 Pod에도 사유 LoadBalancerNegWithoutHealthCheck가 남아 있었습니다. 레플리카가 1개뿐이라, 새 Pod가 트래픽을 받기 전에 옛 Pod가 빠졌습니다.
해결
레플리카를 늘려도 되는지 코드로 먼저 확인했습니다. 프로세스 안에서 도는 스케줄러나 리더 선출이 없었고, 쓰기 경합은 PostgreSQL advisory lock이, 세션은 Redis가 맡고 있었습니다. minReadySeconds 30초, 레플리카 2개, PodDisruptionBudget(PDB)을 Git에 선언하고 스테이징에 먼저 반영했습니다. 운영에는 Deployment와 PDB만 골라 동기화했습니다.
결과
스테이징 롤아웃 2번 동안 외부 헬스체크를 1초 간격으로 315회 보냈고 모두 200이었습니다. 새 Pod 4개 중 2개에서 readiness gate가 먼저 통과하는 일이 다시 나왔지만, minReadySeconds 동안 새 Pod가 사용 가능으로 잡히지 않아 옛 Pod가 먼저 빠지지 않았습니다. 운영 반영 구간의 100회도 모두 200이었습니다. 탐지부터 운영 반영까지 약 46분이 걸렸습니다.
