DAAS-Vader: Sui 컨트랙트 이벤트로 움직이는 Kubernetes

Sui 컨트랙트로 워커 스테이킹과 배포 요청을 받는 Kubernetes를 만들었습니다. 마스터가 체인 이벤트를 읽어 kubectl 명령으로 바꿔 실행합니다.

01상황과 역할

Sui 해커톤에서 누구나 자기 머신을 워커로 내놓는 Kubernetes 클러스터를 제안했습니다. Sui 생태계에서 Vercel 같은 배포 플랫폼이 되는 것을 목표로 잡았습니다.

먼저 정해야 할 것은 워커가 클러스터에 들어오는 조건이었습니다. 주인을 모르는 머신이 들어오면 남의 워크로드가 그 위에서 돕니다. 기본 K3s는 서버가 만든 join 토큰 하나로 워커를 받습니다. 이 토큰으로는 워커의 주인을 구분할 수 없습니다.

맡은 일
아이디어를 내고 팀을 이끌었습니다. 마스터, 워커 등록과 스케줄러 Move 컨트랙트, 이벤트 기반 배포, K3s agent의 join 수정을 직접 설계하고 개발했습니다.
팀원
웹 화면과 Walrus 연동, Docker 이미지 등록 컨트랙트는 팀원이 맡았습니다.

02해결 과정

1. 워커 등록과 배포 요청을 Move 컨트랙트로 받기

관리자가 토큰을 나눠 주는 방식 대신, 워커마다 Sui 지갑으로 SUI를 맡기고 등록하게 했습니다. 스테이크를 건 워커에는 지갑 주소가 붙어서, 어떤 워커가 누구 것인지 체인에서 확인할 수 있습니다.

배포 요청도 kubectl로 API 서버를 직접 부르는 대신 컨트랙트 호출로 받았습니다. 요청과 워커 배정 기록이 체인에 남기 때문입니다.

컨트랙트는 Worker Registry와 K8s Scheduler로 나눴습니다. Worker Registry는 최소 스테이크를 확인하고 워커를 등록합니다. 워커 활성화와 join 토큰 저장도 맡습니다. K8s Scheduler는 요청자의 활성 워커 중에서 작업이 적은 워커를 고르고, 쉬고 있는 워커를 먼저 씁니다. 고른 워커는 체인에 기록으로 남깁니다.

2. 마스터에서 체인 이벤트를 K3s 작업으로 바꾸기

마스터는 K3s v1.28.2 서버를 Alpine 컨테이너로 실행합니다. Sui Testnet 이벤트는 3초 간격으로 조회합니다(suix_queryEvents).

워커 등록 이벤트가 오면 마스터가 K3s 서버의 node-token을 읽습니다. 이 값을 그 워커의 join 토큰으로 컨트랙트에 기록합니다(set_join_token).

배포 요청 이벤트가 오면 요청을 kubectl 명령으로 바꿔 실행합니다. GET은 kubectl get, POST와 PUT은 kubectl apply, DELETE는 kubectl delete가 됩니다.

WebSocket 구독(suix_subscribeEvent) 코드도 작성했습니다. 데모는 연결을 유지하지 않아도 되는 폴링으로 돌렸습니다.

마스터는 Sui Nautilus의 보안 실행 환경(TEE) 안에서 돌리는 구상이었습니다. 데모에서는 일반 컨테이너로 대신했습니다.

3. K3s agent의 join 코드에 Seal 토큰 확인 넣기

워커가 들어올 때 스테이크를 확인하려고 K3s agent 코드를 고쳤습니다. K3s 전체를 복사해 따로 관리하지 않고, agent 쪽 패키지 소스만 가져와 go.mod의 replace로 연결했습니다.

Seal 토큰은 이 프로젝트에서 정한 형식으로, 지갑 주소와 서명, 챌린지를 담습니다. agent가 서버에 붙을 때 토큰을 검증하는 곳은 두 군데입니다. join을 다시 시도하는 반복문과 토큰을 읽는 함수입니다. 두 곳에 같은 규칙을 넣었습니다. 토큰이 Seal 형식이면 스테이크와 서명을 확인하고, 아니면 원래 K3s 토큰 검증으로 넘어갑니다.

해커톤 기간에는 체인 조회와 서명 검증을 모의 응답으로 두고, 토큰 종류에 따라 검증을 나누는 구조를 먼저 만들었습니다. 데모용 워커 컨테이너는 원본 K3s agent에 마스터가 발급한 join 토큰을 넘기도록 구성했습니다.

4. EC2 워커 설정 스크립트

EC2 워커 설정 스크립트에는 K3s 노드 통신에 쓰는 포트를 여는 방화벽 규칙을 넣었습니다. API 서버 6443, kubelet 10250, Flannel VXLAN 8472/udp, WireGuard 51820/udp입니다. 컨테이너 런타임은 워커 설정에서 containerd와 Docker 중 하나를 고르게 했습니다.

04트러블슈팅

T-01

Move 컨트랙트 빌드가 bridge 모듈 중복으로 실패한 문제

문제
sui move build가 Duplicate module found: 0x...b::bridge 오류로 멈췄습니다.
원인
Sui 프레임워크가 업데이트되면서 bridge 모듈이 시스템 패키지로 함께 들어왔습니다. 이 모듈이 Move.lock에 남은 이전 의존성과 겹쳤습니다.
해결
Move.lock을 지우고 sui move clean 뒤 다시 빌드했습니다. 이후 Move.toml에 Sui 프레임워크를 rev = "framework/testnet"으로 고정했습니다.
결과
빌드가 통과했습니다. 이후 Worker Registry와 K8s Scheduler를 담은 패키지를 Sui Testnet에 배포했습니다. Sui 프레임워크 버전은 배포할 네트워크에 맞춰 Move.toml에 고정해야 합니다.

05배운 점

K3s 소스를 직접 읽으며 agent가 토큰을 검증하고 서버에 붙는 순서를 코드로 이해했습니다. 이 구조를 다시 보며 두 가지를 배웠습니다. 첫째, 워커가 들어오는 조건은 워커가 아니라 서버가 확인해야 합니다. 원본 agent를 쓰는 워커는 워커 쪽 확인을 거치지 않기 때문입니다. 둘째, join 토큰을 공개 체인에 그대로 기록하면 안 됩니다. 체인에 올린 값은 누구나 읽을 수 있습니다.
