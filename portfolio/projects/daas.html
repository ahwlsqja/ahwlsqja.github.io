DAAS-Vader: SUI를 맡긴 컴퓨터를 Kubernetes 워커로 받는 서버리스 플랫폼

남는 컴퓨터를 가진 사람이 SUI를 맡기면, 그 컴퓨터를 Kubernetes 워커로 받는 플랫폼입니다. 개발자의 배포 요청은 Sui 컨트랙트로 받습니다. 이 구조를 해커톤 데모로 만들었고, 그중 워커 참여 경로, 마스터, 컨트랙트, 이벤트 처리를 직접 설계하고 개발했습니다.

01상황: 어떤 프로젝트이고 무엇을 해결하는가

DAAS-Vader는 Sui 해커톤에서 만든 탈중앙 서버리스 플랫폼입니다. 팀 README에 적은 목표는 "Sui의 Vercel"입니다.

이 서비스에는 두 종류의 사용자가 있습니다.

  • 개발자: 팀 문서는 Vercel 같은 중앙화 서비스의 문제로 높은 비용, 벤더 락인, 검열 가능성을 꼽았습니다. 개발자는 지갑을 연결하고 Docker 이미지를 올려 앱을 배포합니다.
  • 노드 제공자: 남는 컴퓨터 자원을 내놓고 보상을 받는 사람입니다. SUI를 맡기고 자기 컴퓨터를 워커로 등록합니다.

먼저 풀어야 할 기술 문제는 소유자를 알 수 없는 컴퓨터가 클러스터에 참여하는 것이었습니다. 기본 K3s는 서버가 만든 join 토큰 하나로 워커를 받습니다. 토큰만 있으면 누구나 참여할 수 있습니다. 워커의 소유자도 구분하지 못합니다.

이 문제를 블록체인으로 풀려고 했습니다. README는 이 방향을 "기존의 중앙화된 인증을 블록체인 스테이킹으로 바꾸는 것"으로 적었습니다.

  • 관리자가 주는 인증 대신 스테이킹을 워커 참여 조건으로 설계했습니다.
  • SUI를 맡긴 워커에는 지갑 주소가 붙습니다. 그래서 누구의 워커인지 체인에서 확인할 수 있습니다.
  • 배포 요청도 컨트랙트로 받아 체인에 기록을 남기게 했습니다.
  • 이미지는 DockerHub 대신 Walrus에 올리게 했습니다(팀원 담당).
해결하려는 문제
토큰만 있으면 누구나, 소유자도 알 수 없이 클러스터에 참여할 수 있습니다.
해결 방식
SUI 스테이킹을 워커 참여 조건으로 두고, 배포 요청은 컨트랙트로 받아 체인에 기록합니다.

02과제와 역할

팀 README에는 이미지 업로드, 워커 등록, 작업 실행 세 흐름을 그렸습니다. 4명 팀에서 아이디어를 내고 팀을 이끌었습니다. 직접 설계하고 개발한 부분은 다음과 같습니다.

  • SUI를 맡겨 워커를 등록하는 경로(컨트랙트, 마스터의 토큰 기록)와, join 때 스테이크를 확인하도록 고친 K3s agent
  • 마스터: K3s 서버 실행, Sui 이벤트 조회, 이벤트를 kubectl 명령으로 바꾸는 처리
  • Sui Move 컨트랙트 2개: Worker Registry, K8s Scheduler
  • 배포 문서와 EC2 워커 설정 스크립트

팀원이 맡은 부분은 웹 화면(Next.js), Walrus 업로드 연동, Docker 이미지 등록 컨트랙트, Mysten Seal을 쓴 암호화 모듈, 발표 자료입니다. 팀원 화면의 스테이킹 통계는 직접 만든 Worker Registry 컨트랙트를 읽습니다.

03해결 과정

1. 아키텍처

  • client, walrus, chain: task (팀원): 이미지를 Walrus에 blob으로 올립니다. 이미지 정보는 컨트랙트에 등록합니다.
  • chain: worker registry (직접 개발): 스테이크를 확인하고 워커를 등록합니다. 소유자별 워커 목록과 join 토큰을 보관합니다.
  • chain: kubernetes schedule (직접 개발): 배포 요청을 검사합니다. 그다음 요청자의 워커 중 하나를 고릅니다.
  • masternode (직접 개발): K3s 서버를 띄우고, 체인 이벤트를 받아 kubectl 명령으로 바꿉니다. Sui Nautilus의 보안 실행 환경(TEE)에 둘 구상이었습니다. 데모는 일반 컨테이너로 대신했습니다.
  • operator (워커 부분 직접 개발): 노드 제공자의 컴퓨터에서 K3s agent를 띄워 클러스터에 참여합니다. 그림의 select task는 팀원 화면입니다. run docker images to pods는 만들지 못했습니다.

2. 주요 흐름

흐름 1. 노드 제공자가 워커를 클러스터에 참여시키기

  1. 노드 제공자가 stake_and_register_worker를 호출하며 SUI를 맡깁니다.
  2. 컨트랙트가 최소 스테이크, 이름 중복, 주소당 워커 10개 이하를 확인합니다. 통과하면 등록 이벤트를 냅니다.
  3. 마스터가 이벤트를 받아 K3s join 토큰을 set_join_token으로 컨트랙트에 기록합니다.
  4. 노드 제공자가 activate_worker로 워커를 active로 바꿉니다.
  5. 워커가 join 토큰으로 k3s agent를 실행해 클러스터에 참여합니다.

1~4단계는 Sui Testnet 기록으로 확인했습니다. 5단계는 실행 로그가 남아 있지 않습니다. 데모 워커는 원본 K3s agent를 썼습니다. 토큰은 컨트랙트 대신 마스터 HTTP에서 받았습니다.

흐름 2. 배포 요청을 컨트랙트로 받아 처리하기

  1. 요청자가 submit_k8s_request로 배포 요청을 보냅니다. 요청에는 메서드, 리소스, 네임스페이스, 내용, 우선순위를 담습니다.
  2. 컨트랙트가 메서드 5종(GET, POST, PUT, PATCH, DELETE), 리소스 7종, 우선순위 1~10 범위를 확인합니다.
  3. 컨트랙트가 요청자 본인의 active 워커 중 하나를 고릅니다. 고른 워커의 작업 수는 1 올립니다.
  4. 마스터가 요청 이벤트를 받고, kubectl get nodes로 K3s가 준비됐는지 확인합니다.
  5. 마스터가 요청을 kubectl 명령으로 바꿔 실행합니다. 결과와 실행 시간은 로그에 남깁니다.

1~3단계는 Sui Testnet 기록으로 확인했습니다. 4단계에서는 K3s가 준비되지 않아 요청이 처리되지 않은 로그가 남아 있습니다. POST 요청은 내용을 kubectl에 넘기는 부분이 빠져 Pod 생성까지 가지 못했습니다.

흐름 3. 개발자가 이미지를 올리기 (팀원 부분)

  1. 개발자가 Docker 이미지 tar 파일을 올립니다. 화면이 파일을 Walrus에 저장하고 Blob ID를 받습니다.
  2. 이미지 정보를 컨트랙트에 등록하면 작업 풀에 올라갑니다. 노드 제공자는 작업 풀에서 작업을 고릅니다.

작업 풀에서 고른 작업을 배포로 잇는 부분은 화면 시연이었습니다. 그래서 흐름 3은 흐름 2와 이어지지 않았습니다.

3. 설계 고민과 결정

워커가 클러스터에 참여하는 조건

  • 고민: 개인 컴퓨터를 워커로 받으면 소유자를 알 수 없는 머신이 참여합니다.
  • 선택지: K3s 기본 토큰 하나를 나눠 주는 방법, 관리자가 워커마다 토큰을 주는 방법, 워커마다 SUI를 맡기게 하는 방법이 있었습니다.
  • 결정: 스테이킹을 골랐습니다. 첫째 방법은 워커 소유자를 구분하지 못합니다. 둘째 방법은 중앙 관리자가 다시 생깁니다.

요청 경로를 어디에 둘까

  • 고민: 처음에는 kubectl 요청을 게이트웨이가 받아 마스터로 넘겼습니다. 권한 검사는 마스터에서 일어났습니다. 그래서 사용자는 마스터를 믿어야 했습니다.
  • 선택지: 게이트웨이 구조, 쓰기 요청만 컨트랙트로 확인하는 구조, 모든 요청을 컨트랙트로 먼저 받는 구조를 차례로 검토했습니다.
  • 결정: 마지막 구조를 골랐습니다. 배포 요청은 sui client call로 시작하게 했습니다. 마스터는 이벤트를 실행만 하게 했습니다. 권한 검사를 컨트랙트에 두어, 사용자가 믿을 대상을 마스터에서 컨트랙트로 옮기려 했습니다. 대신 응답이 몇 초 늦어집니다. kubectl을 바로 쓰는 편의도 내려놓았습니다.

K3s를 어디까지 고칠까

  • 고민: join 과정에 스테이크 확인을 넣으려면 K3s 소스를 고쳐야 합니다.
  • 선택지: K3s 전체를 복사해 따로 관리하는 방법, 워커에 필요한 agent 쪽 코드만 가져오는 방법이 있었습니다.
  • 결정: 워커에 필요한 agent와 그 의존 패키지만 가져와 go.mod의 replace로 연결했습니다. 워커에 필요한 것은 agent뿐이었습니다.

새 토큰과 원래 K3s 토큰을 같이 둘까

  • 고민: 고친 agent가 원래 K3s 토큰을 못 쓰면 일반 워커로 하는 시험이 막힙니다.
  • 선택지: 새 토큰만 받는 방법, 두 형식을 모두 받는 방법이 있었습니다.
  • 결정: 두 형식을 모두 받게 했습니다. 토큰이 직접 정한 형식(SEAL 접두어, 지갑 주소, 서명, 챌린지)이면 스테이크와 서명을 확인하는 분기를 넣었습니다. 그 밖의 토큰은 원래 K3s 검증으로 넘깁니다. 같은 규칙을 join 재시도 경로와 토큰 읽기 경로 두 곳에 넣었습니다. 해커톤 기간에는 스테이크 조회와 서명 확인을 모의 응답으로 두었습니다. 이 분기는 기본 설정에서 꺼 두었습니다.

4. 구현 상세

마스터

  • Go로 만든 마스터는 K3s 관리, HTTP API, Sui 이벤트 처리 세 부분을 함께 띄웁니다.
  • K3s v1.28.2 서버를 Alpine 컨테이너 안에서 실행합니다. 쓰지 않는 Traefik과 servicelb는 껐습니다.
  • 이벤트는 suix_queryEvents로 3초마다 조회합니다. 패키지 ID와 이벤트 이름으로 거릅니다.
  • 요청 메서드는 kubectl 명령으로 바꿉니다. GET은 get, POST와 PUT은 apply, PATCH는 patch, DELETE는 delete입니다.
  • WebSocket 구독 코드도 만들었습니다. 데모는 폴링으로 돌렸습니다.

컨트랙트

  • Worker Registry는 워커를 두 표에 나눠 저장합니다. 하나는 노드 이름으로, 다른 하나는 소유자 주소로 찾습니다.
  • join 토큰 기록은 관리자 주소만 할 수 있게 막았습니다.
  • K8s Scheduler는 요청자 본인의 active 워커만 후보로 둡니다.
  • 점수는 작업이 없는 워커가 1000점, 작업이 있는 워커가 100 ÷ (작업 수 + 1)입니다. 그래서 작업이 없는 워커가 먼저 뽑힙니다.

워커

  • 워커 프로그램은 스테이킹 확인, K3s agent 실행, 30초 하트비트, 상태 API 순서로 동작합니다.
  • 컨테이너 런타임은 설정에서 containerd와 Docker 중 하나를 고릅니다.
  • EC2 설정 스크립트는 K3s 통신 포트 6443, 10250, 8472/udp, 51820/udp를 엽니다.

04트러블슈팅

T-01

Move 빌드가 bridge 모듈 중복으로 멈춘 문제

문제
sui move build가 Duplicate module found: ...::bridge 오류로 멈췄습니다.
원인
Sui 프레임워크가 업데이트되면서 bridge 모듈이 중복으로 들어왔습니다. Move.lock에 남은 이전 의존성과도 충돌했습니다.
해결
Move.lock을 지우고 다시 빌드하는 방법과 의존성 설정을 바꾸는 방법을 정리해 차례로 시도했습니다. 최종 Move.toml에는 Sui 프레임워크를 Testnet 버전(framework/testnet)으로 고정했습니다.
결과
빌드가 통과했고 패키지를 Sui Testnet에 배포했습니다.

05결과

  • Sui Suimming Hackathon 2025 University Track 수상 (2025.09)
  • Sui Testnet에 컨트랙트 패키지 2개 배포 (주 컨트랙트 2개 약 740줄, 시험용 모듈 2개)
  • Testnet SUI를 맡긴 워커 등록 6건, 활성화 5건, join 토큰 기록 1건, 스케줄러 배정 8건이 Sui Testnet에 남아 있습니다. 실행 결과 기록은 0건입니다.
  • 배정 기록에서 선택 규칙을 확인했습니다. 요청 3건이 작업이 없는 워커 3개에 하나씩 갔습니다. 네 번째 요청은 첫 워커로 돌아갔습니다.
  • 마스터가 Testnet 이벤트를 3초 폴링으로 받아 메서드, 리소스, 네임스페이스를 읽어 내는 것까지 로그로 확인했습니다. (데모, 로컬 Docker)

마치지 못한 것

  • 데모에서는 스테이킹이 참여 조건으로 강제되지 않았습니다. 마스터가 join 토큰을 인증 없이 내줬습니다. 데모 워커는 원본 K3s agent를 썼습니다.
  • 워커 쪽 스테이크와 서명 확인은 모의 응답입니다.
  • 컨트랙트 경로로 들어온 POST 요청은 Pod 생성까지 가지 못했습니다. 요청 내용을 kubectl에 넘기는 부분이 빠져 있었습니다.
  • K3s가 준비되기 전에 들어온 요청은 처리되지 않고 버려졌습니다. Testnet 이벤트로 한 시험에서 마스터가 요청을 받고도 "K3s is not ready" 로그만 남긴 기록이 있습니다. 요청을 담아 둘 대기열은 만들지 못했습니다.
  • 스케줄러는 요청자 본인의 워커만 고릅니다. 개발자의 앱을 다른 사람의 워커에 올리는 구조는 만들지 못했습니다.
  • 맡긴 SUI는 컨트랙트 안에 보관하지 않고 다른 주소로 보냈습니다. 그래서 돌려주거나 깎을 수 없었습니다.
  • join 토큰은 컨트랙트에 그대로 기록했습니다.
  • 고른 워커에 Pod 배치, 결과의 체인 기록, Walrus 이미지 실행, 보상과 슬래싱은 만들지 못했습니다.

06배운 점

워커의 참여 조건은 워커가 아니라 서버가 확인해야 합니다. join 토큰 같은 비밀 값은 공개 체인에 그대로 기록하면 안 됩니다. 맡긴 SUI는 컨트랙트 안에 보관해야 돌려주거나 깎을 수 있습니다.
