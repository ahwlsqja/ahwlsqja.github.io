실시간 스트림 파이프라인 (Kafka + Flink)

브라우저 행동 이벤트를 받는 수집 경로를 Go 수신 서버 → Kafka → Flink → Go 적재기 → ClickHouse 구조로 새로 설계하고 구현했습니다. 운영 트래픽을 새 경로에도 똑같이 복사해 보내(미러링) 두 경로의 결과를 대조한 뒤 주 경로로 전환했습니다.

01상황과 역할

2026년 9월 말, 사람 방문 세션 중 집계가 끝난 비율이 사흘 사이 약 60%에서 30%로 떨어졌습니다. 세션 집계는 ClickHouse 안의 Materialized View 체인(SQL 약 2만 줄)이 맡고 있었습니다. 그중 한 뷰는 처리 대기 목록에서 한 번에 고르는 후보 수에 상한이 있었습니다. 후보가 되지 못한 세션은 처리되지 않고 지나갔습니다.

관리형 ClickHouse를 정리하고 자체 운영 클러스터로 옮기는 일정도 잡혀 있었습니다. 새 클러스터로는 이 Materialized View 체인을 옮기지 않기로 했습니다. 그래서 세션 집계를 맡을 곳이 따로 필요했습니다.

SDK는 최대 7일까지 이벤트를 다시 보냅니다. 같은 이벤트가 여러 번, 며칠 늦게 와도 결과에는 한 번만 반영돼야 했습니다. 장애가 나면 원본부터 다시 계산할 수도 있어야 했습니다.

맡은 일
구조와 기술 선택, Flink 세션 집계 잡, Go 수신 서버와 적재기, 전환 절차의 설계와 구현
회사에서 정한 것
상태 처리를 스트림 엔진으로 옮긴다는 방향은 회사에서 먼저 정했습니다. 데이터 경로는 혼자 맡았습니다.
AI 에이전트
코드 작성과 대조, 원인 추적의 일부는 AI 코딩 에이전트와 함께 했습니다. 구조 설계와 전환 판단, 검증 기준은 직접 정했습니다.

02해결 과정

세션 집계의 중복은 Flink 세션 상태에서 지웁니다. 적재를 다시 시도해 생기는 중복은 적재 토큰이 막습니다.

1. Kafka와 Flink를 고른 이유

브라우저 재전송, 큐 재전달, Kafka 재소비는 모두 최소 한 번 전달(at-least-once)이라 중복이 반드시 생깁니다. 그래서 기준을 둘로 정했습니다. 세션 집계의 중복은 세션 상태 한 곳에서 지웁니다. 같은 입력을 다시 돌리면 같은 결과가 나와야 합니다.

  • Kafka는 버퍼로 쓰면서, 다시 계산할 때 읽을 원본 저장소로도 두었습니다. 원본은 30일 보관합니다. Cloudflare Queues만 쓰는 안은 메시지를 한 번 읽으면 사라져 다시 계산할 수 없어서 쓰지 않았습니다.
  • Flink는 Go 소비자가 세션을 직접 계산하는 안과 비교했습니다. Go 쪽은 비용이 쌌지만, 키 상태와 타이머, 체크포인트를 직접 다시 만들어야 했습니다. 기존 Materialized View 체인도 상태 처리를 직접 만들다 SQL 약 2만 줄로 커졌습니다. 같은 일을 되풀이한다고 보고 Go 안은 쓰지 않았습니다.
  • 집계가 반영되기까지 목표는 약 15분이었습니다. Flink를 고른 이유는 지연 시간이 아니라, 늦게 오거나 다시 오는 데이터를 다루는 기능이었습니다.

2. 트래픽 수용 설계

지금 트래픽은 크지 않습니다. 고객사 10곳에서 30일 동안 원본 이벤트 약 2,250만 건이 들어왔고(2026.08 측정), 평균으로는 초당 10건이 되지 않습니다. 그래서 처리량보다, 순간적으로 몰릴 때 버티는 방식과 나중에 바꾸기 어려운 값을 먼저 정했습니다.

  • Kafka는 사설망에 있어 Worker가 직접 붙을 수 없습니다. 그래서 사이에 Go 수신 서버를 두었습니다. 수신 서버는 모든 레코드가 acks=all로 확인된 뒤에만 200을 돌려줍니다. 1건이라도 실패하면 요청 전체를 실패로 봅니다.
  • 버퍼가 차면 기다리지 않고 바로 실패하는 TryProduce를 썼습니다. 버퍼가 가득 찼거나 약 1.2초 안에 끝내지 못하면 503을 돌려줍니다. Worker는 503을 받으면 요청을 예비 큐로 보냅니다.
  • 수신 서버는 CPU 60%를 기준으로 HPA가 2개에서 8개까지 늘립니다.
  • 파티션 키는 (고객사, 세션)으로 정했습니다. 고객사만 키로 쓰면 한 파티션에 트래픽이 몰립니다. 세션을 함께 넣어, 한 세션의 이벤트는 같은 파티션에서 순서를 지키고 부하는 고르게 나뉘게 했습니다.
  • 파티션 수를 나중에 바꾸면 같은 세션의 이벤트가 다른 파티션으로 가게 됩니다. 그래서 지금 트래픽의 100배를 가정해도 파티션 하나가 감당할 수 있다고 계산한 12개로 처음부터 정했습니다.

3. Flink 세션 집계와 멱등 적재

  • 세션 상태 안에 이미 받은 이벤트 ID를 7일 동안 보관합니다. SDK가 다시 보낼 수 있는 기간과 같습니다. 같은 이벤트가 다시 오면 버립니다. ID는 같은데 내용이 다르면 한쪽을 고르지 않고 따로 빼서 알림을 보냅니다.
  • 결과마다 버전을 붙였습니다. 재처리 회차, 반영한 이벤트 수, 결과 상태(진행 중, 마감, 삭제)를 이 순서로 비교해 큰 쪽이 최신입니다. 결과를 낸 횟수나 현재 시각은 쓰지 않습니다. 그래서 같은 입력을 다시 돌리면 같은 버전이 나옵니다.
  • RocksDB 증분 체크포인트를 60초마다 GCS에 남깁니다.
  • Go 적재기는 구간마다 다음 순서로 일합니다.
    1. 적재할 오프셋 구간을 이력 테이블에 적습니다.
    2. 데이터를 넣습니다.
    3. 완료를 적습니다.
    4. Kafka에 읽은 위치를 남깁니다.
  • 적재기가 중간에 죽으면 같은 구간을 같은 insert_deduplication_token으로 다시 넣습니다. 그래서 같은 구간을 두 번 넣어도 중복이 생기지 않습니다.
  • insert_quorum=2로 두 레플리카가 모두 받아야 성공으로 봅니다. 하나가 내려가면 쓰기가 멈춥니다. 밀린 메시지는 Kafka가 들고 있습니다. 그래서 쓰기가 멈추는 쪽이 두 레플리카 내용이 서로 달라지는 쪽보다 복구가 쉽다고 판단했습니다.

4. 전환

전환은 Worker 설정값 하나로 합니다. 이 값으로 미러링과 주 경로를 오갑니다. 순서는 스테이징 미러링, 운영 미러링, 주 경로였습니다. 운영 미러링 전에는 스테이징에서 레플리카 중단과 적재기 강제 종료를 일부러 일으켜 봤습니다. 비율을 조금씩 올리는 방식은 관리형 ClickHouse를 더 오래 유지하는 비용 때문에 생략했습니다. 대신 전량 미러링 대조 결과를 근거로 한 번에 옮겼습니다.

03결과

  • 운영 미러링 24시간 두 경로의 이벤트 키 차이 약 0.06% (고객사별 ±0.2% 안), 확인 뒤 주 경로 전환
  • 적재 이력의 오프셋과 Kafka에 남긴 읽은 위치가 12개 파티션 모두 일치, 약 1주 뒤 다시 대조해도 차이 0
  • 레플리카 1대 중단 동안 쓰기 거부, 유실 0. 복귀 약 2분 뒤 밀린 분량 처리 완료 (스테이징 장애 주입)
  • Flink 잡 약 8일 재시작 없이 운영, 적재기 오류 0 (10월 중순 기준)
  • 수신 → 원본 테이블 30여 초, 세션 집계까지 1분 남짓 (스테이징 합성 이벤트, 클러스터 재기동 직후 측정)

04트러블슈팅

T-01

실패 기록이 없는데 복사본 약 0.2%가 빠진 문제

문제
운영 미러링을 켠 첫날, 기존 경로에는 있고 새 경로에는 없는 이벤트가 키 기준 약 0.2% 나왔습니다. 실패 로그, 예비 큐, 실패 메시지 보관 큐(DLQ)에는 아무것도 없었습니다.
원인
크기 초과와 형식 오류를 먼저 의심했지만 둘 다 아니었습니다. 빠진 이벤트는 모두 페이지를 떠날 때 나가는 이벤트였습니다. 같은 시간대 Worker 호출의 약 4%는 클라이언트가 먼저 연결을 끊은 호출이었습니다. 코드는 기존 경로 전송을 await로 기다린 뒤에야 복사본 전송을 waitUntil에 걸었습니다. Cloudflare는 클라이언트가 먼저 끊으면 그때까지 waitUntil에 걸린 일만 이어서 처리합니다.
해결
기존 경로를 기다리기 전에 복사본 전송을 waitUntil에 거는 순서로 바꿨습니다. 끊김을 흉내 낸 단위 테스트로, 고치기 전에는 복사본 전송이 아예 걸리지 않는 것을 먼저 확인했습니다. 끊긴 뒤 실제로 전송되는지는 배포 뒤 키 대조로 확인했습니다.
결과
배포 뒤 키 대조에서 누락은 0이었습니다. 이미 빠진 이벤트는 기존 경로 원본에서 되살려 원본 테이블에 다시 넣었고, 대조에서 누락 0을 확인했습니다.

05배운 점

경로를 바꿀 때 건수만 비교하면 일부가 빠져도 알아채지 못합니다. 이벤트 키 집합과 오프셋처럼 서로 다른 기록이 맞는지를 전환 조건으로 걸어야 합니다.
