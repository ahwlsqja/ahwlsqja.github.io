광고 데이터 수집 파이프라인

Google Ads, Meta, 네이버 검색광고에서 노출, 클릭, 광고비를 수집해 사이트 방문 여정과 잇고, 실제 리드와 구매로 ROAS를 계산하는 파이프라인입니다. 플랫폼마다 다른 API는 capability를 선언하는 adapter로 감쌌습니다. 광고 플랫폼은 지난 날짜의 값을 나중에 고치기 때문에, 최근 14일을 자주 다시 읽는 수집과 정정 기간 전체를 하루 한 번 다시 읽는 수집을 나눠 돌립니다. 작업 상태는 PostgreSQL job ledger에 두고 Kafka로 at-least-once 전달하며, ClickHouse 적재는 몇 번 반복해도 결과가 같도록 idempotent하게 만들었습니다.

01상황과 역할

수파리드는 구매까지 오래 고민하는 고관여 업종 사이트의 방문, 리드, 구매를 수집하는 분석 플랫폼입니다. 이 파이프라인은 광고 플랫폼에서 노출, 클릭, 광고비를 가져와 사이트에서 관측한 방문 여정과 이어, 어떤 광고가 실제 문의와 구매로 이어졌는지 계산합니다. 연동한 광고 플랫폼은 Google Ads, Meta, 네이버 검색광고입니다.

광고 데이터를 가져오는 일은 API를 하루 한 번 부르는 일로 끝나지 않았습니다. 기술적으로 풀어야 할 문제는 다섯 가지였습니다.

  1. 광고 플랫폼은 지난 날짜의 성과를 나중에 고칩니다. 전환은 클릭한 날짜의 행에 뒤늦게 더해지고, 무효 클릭은 환불됩니다. Meta는 28일이 지나야 값이 더 바뀌지 않고, Google은 전환을 최대 90일 뒤까지 클릭한 날짜에 더하며 무효 트래픽을 당월 말까지 소급해 고칩니다. 그래서 수집은 지난 구간을 주기적으로 다시 읽어 덮어쓰는 일이 됩니다. 게다가 두 플랫폼 모두 지표가 전부 0인 행은 돌려주지 않아서, 다시 읽었을 때 사라진 행이 삭제된 것인지 그날 0인 것인지 응답만으로는 알 수 없습니다.
  2. 플랫폼마다 API 모양이 다릅니다. Google Ads는 GAQL로 기간을 조회해 stream으로 받고, Meta는 광고 계정 단위로 페이지를 넘기며 받습니다. 네이버 검색광고는 보고서를 비동기로 만들어 달라고 요청한 뒤, 완성되면 헤더 없는 TSV를 내려받아 열 위치로 해석하고, 요청마다 HMAC 서명을 붙여야 합니다.
  3. 호출 한도가 플랫폼마다 다른 곳에 걸립니다. Google은 Cloud project 하나에 rolling 24시간 operation quota가 걸려 모든 광고 계정이 이를 나눠 쓰고, 실패한 요청도 quota에서 빠집니다. Meta는 광고 계정마다 시간당 호출 한도와 score cap이 있어 병렬로 부르면 오류와 대기만 늘어납니다. 다시 읽는 구간을 넓히고 자주 돌릴수록 같은 quota로 수집할 수 있는 계정 수가 줄어듭니다.
  4. 광고비와 사이트 행동은 grain이 다릅니다. 광고비는 계정, 캠페인, 날짜 단위이고 리드와 구매는 이벤트 단위입니다. 광고비 한 행을 행동 세 건에 붙이면 광고비가 세 번 더해지는 fan-out이 생깁니다. 광고비 날짜는 광고 계정의 현지 날짜이고, 통화도 계정마다 다릅니다.
  5. 수집이 멈춰도 알 수 없었습니다. 오류는 로그에 남았지만 데이터가 실제로 들어왔는지를 보고 울리는 경보가 없었고, 프로세스는 정상인데 데이터만 진행되지 않는 경우도 있었습니다.

기존 구조에서는 이 문제들이 실제 증상으로 나타났습니다. 광고 수집은 사이트 이벤트를 받는 Cloudflare Worker 안의 모듈이었고, 공통 interface 없이 플랫폼 이름으로 곳곳에서 분기했습니다. 다시 읽는 구간이 사실상 2일이라 Meta가 28일까지 고치는 값 중 26일치를 놓치고 있었습니다. Google Ads API 버전이 종료되면서 성과 수집이 멈췄지만 경보가 없어 몇 주 동안 묻혔습니다. 광고비와 유입을 화면 표시용 채널 이름으로 JOIN하는 구조라, Meta 광고 유입이 전 기간 0으로 보였습니다. 채널 성과 화면은 요청마다 전체 이력을 다시 읽다가 ClickHouse 읽기 행 한도에 걸려 호출의 53.8%가 실패했습니다. 유료 유입의 42.5%를 차지하는 네이버 검색광고는 연동이 없어 광고비가 0으로 붙었습니다.

맡은 일
수집 스케줄과 quota 예산, adapter interface, PostgreSQL ledger와 Kafka 경로, GCS 원문 보관과 ClickHouse 적재 규칙, 조회용 snapshot, 여정 속 광고 attribution과 ROAS 계산 규칙을 설계하고, Go 서비스로 구현해 GKE에서 운영했습니다. Meta를 먼저 새 경로로 옮기고, Google Ads와 네이버 검색광고를 같은 구조에 붙였습니다.
범위 밖
브라우저 이벤트로 방문 세션과 진입 기록을 만드는 실시간 처리는 V3 실시간 아키텍처 페이지에 적었습니다.

02아키텍처

광고 수집은 사이트 이벤트 수집과 분리된 독립 Go 서비스입니다. 광고 플랫폼 API는 Meta가 약 90일마다, Google이 분기마다 버전을 바꾸는데, 광고 쪽을 고칠 때마다 사이트 이벤트 수집까지 다시 배포하지 않도록 서비스를 나눴습니다. 같은 바이너리가 GKE에서 역할별 workload로 뜹니다. 수집 일정을 만드는 Scheduler와 outbox 행을 Kafka로 내보내는 relay는 CronJob이고, 광고 API를 부르는 Collector와 ClickHouse에 적재하는 Loader는 상주하는 Kafka consumer Deployment입니다. 역할마다 service account와 DB role을 따로 두고, 기대한 role이 아니면 기동하지 않게 했습니다. 저장소는 세 곳입니다. 작업 상태와 진행 기록은 PostgreSQL job ledger, 광고 API 응답 원문은 GCS, 분석용 성과 데이터는 ClickHouse에 두고, Kafka는 그 사이에서 작업 참조만 나릅니다. 광고 API 응답 한 페이지가 화면에 닿기까지의 경로는 그림 1과 같습니다.

운영에서 수집된 Meta 성과가 화면에 보이기까지 2~7분이 걸리고, Kafka consumer lag은 평소 0~4 레코드입니다. 아래에서는 구성 요소마다 무엇을 하는지와 왜 그렇게 만들었는지를 적었습니다.

1. Adapter 계층과 capability 선언

광고 플랫폼(provider)마다 adapter를 하나씩 둡니다. adapter가 맡는 일은 인증, pagination, 비동기 보고서 polling, 오류 분류, 응답을 공통 형식으로 바꾸는 일까지입니다. 작업 상태, lease, ClickHouse 반영 확인처럼 상태를 바꾸는 일은 adapter 밖의 공통 파이프라인이 맡습니다. adapter는 DB에 접근하지 않고, 정해진 자격증명과 공통 형식의 데이터만 주고받습니다. 그래서 새 provider를 붙여도 기존 provider 코드를 건드리지 않습니다.

interface는 다섯 동작으로 나눴습니다.

  • plan은 수집 window를 플랫폼이 받는 요청 단위로 나눕니다. 외부 호출이 없는 순수 함수라 test가 쉽습니다.
  • estimateOperations는 호출하기 전에 그 요청이 quota를 얼마나 쓸지 계산합니다.
  • fetch는 결과를 성공과 실패 둘이 아니라 행, 데이터 없음, 보고서 제출됨, 보고서 무효, 보류의 다섯 가지로 돌려줍니다. 네이버 보고서가 아직 만들어지지 않은 상태는 실패가 아니라 정상 상태이기 때문입니다.
  • classify는 오류를 영구 실패, rate limit, 일시 오류, 형식 오류 순서로 가립니다. 가리는 순서는 공통이고, provider별 오류 코드표만 adapter가 넣습니다.
  • mapRows는 응답을 공통 grain의 행으로 바꿉니다.

인증은 method, path, timestamp를 받아 서명하는 interface로 열어 두었습니다. 토큰 하나로 끝나는 Google, Meta와 요청마다 서명하는 네이버를 같은 자리에서 받기 위해서입니다.

capability는 adapter가 "무엇을 할 수 있나"보다 "무엇을 믿어도 되나"를 선언하는 자리입니다. API version과 종료일, 조회 방식(기간 조회, 단일 날짜, 비동기 보고서), 응답 형식, 지표가 0인 행을 돌려주는지, 며칠 뒤 값이 고정되는지, 월말에 값이 동결되는지, 전환 집계 기간, quota 모델, 단위별 rate limit이 여기에 들어갑니다. 이 선언이 수집 window의 폭, 삭제를 판정할 수 있는 범위, 호출 예산 계산의 입력이 됩니다. 플랫폼 응답이 선언과 어긋나면, 예를 들어 API version 경고가 오거나 실제로 쓴 operation 수가 추정과 다르면 그 자체를 경보로 씁니다.

2. 수집 스케줄: 최근 window와 정정 window, quota 예산

수집 window를 두 종류로 나눴습니다. 최근 window는 최근 14일을 6시간마다 다시 읽어 화면을 최신으로 유지합니다. 정정 window는 플랫폼이 값을 고칠 수 있는 기간 전체를 하루 한 번 다시 읽으며, Meta는 30일, Google은 95일입니다. 클릭 하나하나의 기록을 주는 Google click view는 하루 단위로만 조회되고 90일만 보관되어서, 최근 2일을 하루 한 번 읽는 별도 작업으로 뺐습니다. 네이버 검색광고도 최근 14일과 정정 30일의 같은 구조를 씁니다.

같은 날짜를 여러 window가 겹쳐 읽는 것은 낭비가 아니라 소급 정정을 잡는 장치입니다. 비용을 좌우하는 것은 window의 폭보다 다시 읽는 빈도입니다. 데이터 정확성은 정정 window가 책임지고 최근 window는 freshness만 맡게 하면, 최근 window의 폭을 줄여도 정정 범위는 줄지 않습니다. window의 폭은 코드에 숫자로 박지 않고 adapter가 선언한 값 고정 일수, 월말 동결 여부, 전환 집계 기간에서 계산하며, Scheduler는 운영 범위를 벗어난 window를 거부합니다.

실행 식별자는 UTC 시 단위로 만들고, 플랫폼에 보내는 조회 날짜는 광고 계정의 현지 날짜(IANA time zone)로 따로 계산합니다. 식별자에 날짜만 넣으면 같은 날 두 번째 수집이 막히고, 날짜 경계는 계정마다 다르기 때문입니다. 최근 window와 정정 window 작업은 대기열에 함께 있을 수 있지만, 한 계정에서 동시에 실행되는 작업은 하나뿐입니다. PostgreSQL의 FOR UPDATE SKIP LOCKED와 실행 중인 계정에 거는 unique index로 이를 보장합니다. 겹치는 window를 두 작업이 동시에 쓰면 삭제 판정과 다시 읽기 확인이 서로를 깨기 때문입니다.

quota는 쓰고 나서 세지 않고 쓰기 전에 예약합니다. 호출 전에 estimateOperations로 비용을 계산하고, PostgreSQL에 둔 공용 카운터에서 예약했다가 호출이 끝나면 실제 사용량으로 정산합니다. 카운터는 rolling 24시간을 5분 bucket 288개로 나눠 셉니다. quota를 쓰는 프로세스가 여럿이라 원자적인 공유 카운터가 필요했습니다. 실패한 호출은 cursor를 옮기지 못한 채 quota만 쓰므로, quota가 바닥나면 곧바로 데이터 정확성이 떨어집니다. 그래서 예산이 모자라면 최근 window부터 범위를 줄이고 정정 window는 끝까지 지킵니다. 최근 window를 캠페인 level로만 받도록 줄일 때는 광고그룹과 광고 level이 하루 늦게 맞춰진다는 사실을 기록해 두어, 품질이 조용히 낮아지지 않게 했습니다. Google은 조회 구간을 7일씩 쪼개던 방식을 없애 계정당 하루 operation을 약 180에서 약 80으로 줄였습니다.

3. Job ledger와 Kafka: at-least-once 전달과 계정 단위 lease

응답 한 페이지가 화면에 닿기까지 광고 플랫폼 API, GCS, PostgreSQL, Kafka, ClickHouse 다섯 시스템을 지나고, 이들은 트랜잭션을 공유하지 않습니다. 그래서 무엇이 어디까지 끝났는지는 PostgreSQL ledger 한 곳에 두고, Kafka에는 전달만 맡겼습니다.

  • 작업 단위는 GET 한 번입니다. 계정을 한 번 수집하는 일은 목표 설정, 성과(캠페인, 광고그룹, 광고), 광고 설정, 소재, 이미지 순서로 이어지는 작업 chain으로 나뉘고, 다음 단계는 ledger가 고릅니다.
  • 계정마다 lease는 하나이고, lease를 잡을 때 다음 호출 가능 시각을 최소 60초 뒤로 둡니다. rate limit이 계정과 앱에 걸려 있어 병렬 호출은 오류와 대기만 늘리기 때문입니다. 프로세스가 죽어도 잃는 것은 한 페이지이고, 다시 시도하는 단위도 한 페이지입니다.
  • 발행은 transactional outbox를 거칩니다. 작업 상태를 확정하는 트랜잭션 안에서 outbox 행을 함께 쓰고, relay가 acks=all로 broker 확인을 받은 뒤에만 전달 완료로 바꿉니다.
  • 소비할 때는 offset 자동 확정을 끄고, ledger에 결과를 확정한 레코드까지만 연속 구간으로 offset을 올립니다.
  • 같은 명령이 다시 오거나 너무 일찍 오면, ledger에서 작업 상태와 시도 번호를 compare-and-set으로 비교해 이미 끝남, 아직 시각 전, 다른 작업 실행 중, 오래된 명령 가운데 하나로 가려냅니다. 이때는 광고 API를 부르지 않고 끝냅니다. 결과 행은 입력으로 만든 sha256 ID와 ON CONFLICT로 써서, 같은 일을 두 번 해도 결과가 같습니다.
  • Kafka 메시지에는 작업 참조만 싣습니다. 자격증명, 응답 원문, 플랫폼 이름도 넣지 않고 consumer가 ledger에서 찾아 씁니다. topic이 새어도 비밀은 새지 않습니다.

topic은 수집 명령 topic, 플랫폼마다 하나인 결과 topic, 역할별 처리 완료를 모으는 완료 topic의 세 종류입니다. message key는 (고객사, 광고 계정)이라 한 계정은 세 topic에서 늘 같은 partition에 놓이고, 계정 사이는 병렬로 처리됩니다. 계정 안의 순서는 Kafka가 아니라 ledger의 비교가 보장하고, partition 순서는 offset 확정에만 씁니다. 같은 결과 topic을 성과 consumer group과 소재 consumer group이 따로 읽어서, 이미지와 영상처럼 느리고 자주 실패하는 소재 처리가 광고비와 전환 같은 핵심 숫자를 붙잡지 않습니다. 소재가 실패하면 ledger에 retry를 예약해 따로 다시 시도하고, 이미 반영된 성과는 되돌리지 않습니다. 플랫폼을 붙일 때는 결과 topic 하나와 설정 목록만 늘고 consumer 코드는 그대로입니다.

클러스터는 GCP 관리형 Kafka 최소 구성으로 두고, topic마다 partition 3개, replication factor 3, min.insync.replicas 2, retention 7일로 정했습니다. 메시지가 수백 바이트짜리 참조라 용량보다 운영 단순함과 비용이 중요했고, 원본 기록은 PostgreSQL과 GCS에 있어 Kafka는 며칠 안에 전달하는 일만 하면 되기 때문입니다. 연결은 SASL_SSL과 OAUTHBEARER로 하고 토큰은 Workload Identity에서 받습니다. topic과 ACL은 Terraform으로 관리합니다. topic과 consumer group 이름은 설정이 아니라 코드가 조립하고, consumer는 구독할 topic 목록이 설정과 정확히 같을 때만 기동합니다.

4. 저장과 적재: 원문 보관, idempotent 적재, 0행과 삭제를 구분하는 규칙

응답 원문은 GCS에 먼저 고정해 둡니다. 원본 페이지 JSON, 공통 형식으로 바꾼 JSONL, manifest를 gzip으로 저장하고, 같은 이름의 객체가 이미 있으면 실패하는 create-only 조건부 쓰기를 씁니다. 쓴 뒤에는 다시 읽어 길이와 SHA-256을 확인하고, 그 다음에 checkpoint, 작업 성공, lease 해제, 다음 작업, 다음 outbox 행을 한 PostgreSQL 트랜잭션에 묶어 씁니다. 객체 이름은 작업, 기간, lease 시도로 만든 결정론적 이름이라, 늦게 깨어난 옛 작업이 새 결과를 덮어쓰지 못합니다. GET을 하기 전에는 GCS에 같은 응답이 있는지 먼저 찾아 다시 부르지 않습니다.

모든 페이지가 모이면 manifest를 닫습니다. manifest에는 요청한 범위와 실제로 끝낸 범위, capability version, level별 기대 행 수, 객체별 checksum이 들어갑니다. 요청한 범위를 다 받지 못한 수집은 manifest를 닫지 않으므로, 일부만 받은 결과가 적재되지 않고 이전 데이터가 그대로 남습니다. 같은 수집 결과가 같은 checksum으로 다시 오면 그대로 받고, 다른 checksum으로 오면 거부합니다.

Loader는 GCS 원문을 정규화해 ClickHouse 성과 테이블에 씁니다. 성과 테이블은 같은 key의 최신 version만 남기는 ReplacingMergeTree이고, grain은 고객사, 플랫폼, 광고 계정, level, 캠페인, 광고그룹, 광고, 날짜의 여덟 개 컬럼입니다. level은 그 행이 캠페인, 광고그룹, 광고 중 어느 단위의 성과인지를 뜻합니다. 날짜는 광고 계정의 현지 날짜이고, 금액은 micros 단위로 통화와 함께 보존하며, 통화가 다른 금액은 합치지 않습니다. CTR, CPC, ROAS 같은 파생 지표는 저장하지 않고 조회할 때 합계에서 계산합니다. 저장해 두면 정정이 올 때마다 파생값까지 다시 계산해야 하기 때문입니다.

적재 순서는 다음과 같습니다.

  1. 바뀔 (캠페인, 날짜) key를 ClickHouse에 쓰기 전에 ledger에 먼저 적습니다.
  2. ClickHouse에 씁니다. version 컬럼에는 lease를 잡을 때 받은 값을 써서, 늦게 도착한 옛 쓰기가 새 값을 이기지 못하게 합니다.
  3. FINAL로 다시 읽어 실제 반영을 확인합니다.
  4. 확인한 뒤에만 같은 PostgreSQL 트랜잭션에서 cursor를 옮기고, 바뀐 key를 snapshot 재계산 대상으로 넘깁니다.

ClickHouse에 append한 데이터는 PostgreSQL rollback으로 되돌릴 수 없어서, ClickHouse 쓰기를 ledger의 의도 기록과 다시 읽기 확인 사이에 끼웠습니다. 중간에 죽으면 같은 원문으로 같은 행을 다시 쓰고, ReplacingMergeTree가 같은 key를 하나로 접으므로 결과는 같습니다.

가장 까다로운 것은 0행과 삭제를 구분하는 규칙이었습니다. 다시 읽은 응답에 어떤 행이 없을 때, 그 행이 플랫폼에서 지워졌는지 그날 값이 0이라 생략됐는지 응답만으로는 알 수 없습니다. 실적 최대화(Performance Max) 캠페인은 광고그룹과 광고 level 조회가 원래 빈 응답이라, 빈 응답을 삭제로 읽으면 window를 넓히는 순간 정상 데이터가 통째로 지워집니다. 그래서 규칙을 이렇게 정했습니다.

  • 정정은 (고객사, 플랫폼, 광고 계정, level, 날짜 범위)로 정한 window 안에서만 합니다.
  • adapter가 "이 level, 이 기간은 빠짐없이 받았다"고 증명한 범위에서만 삭제 표시 행(tombstone, is_deleted)을 씁니다. 증명이 없으면 정정 자체를 하지 않습니다.
  • 0행 결과에는 "명시적으로 비었다"는 표시와 그 근거가 있어야 합니다. Google은 같은 실행에서 계정 정보를 조회해 계정 ID와 시간대가 맞고, 그 level의 모든 조회가 오류 없이 끝났을 때만 빈 결과로 받아들입니다.
  • 조회는 FINAL과 WHERE is_deleted = 0으로 하고 PREWHERE는 쓰지 않습니다. 이유는 트러블슈팅 T-02에 적었습니다.

5. 조회 계층: 대시보드용 snapshot

기존 채널 성과 화면은 요청마다 전체 이력을 FINAL로 읽고 방문 세션 데이터와 JOIN했습니다. 요청 간격이 cache TTL 60초보다 길어 query cache의 실효 hit rate는 0%였습니다. 메모리가 아니라 읽기 행 한도에 걸려 실패했으므로, cache보다 읽는 행 수를 줄여야 했습니다. 광고 쪽 FINAL은 6ms로 빨랐고, 비싼 쪽은 세션 JOIN이었습니다.

그래서 성과 테이블은 그대로 두고 조회용 snapshot을 따로 만들었습니다.

  1. 적재 단계가 ledger에 남긴 바뀐 key 가운데 ClickHouse 반영이 확인된 것만 재계산 대상이 됩니다.
  2. 5분마다 도는 publisher가 대상을 lease로 가져가 shadow table에 snapshot을 채웁니다. 광고비는 범위를 좁혀 FINAL로 읽고, 세션 쪽 집계를 미리 계산해 둡니다.
  3. EXCHANGE TABLES로 shadow table과 현재 table을 통째로 바꿉니다.
  4. 어느 수집 결과로 만든 snapshot인지 version 정보를 함께 기록하고, 다시 읽어 내용과 맞으면 완료로 표시합니다. 대시보드 API는 이 version 정보가 맞을 때만 새 snapshot을 읽습니다.

읽는 쪽은 옛 snapshot 전체나 새 snapshot 전체만 보고, 반쯤 바뀐 상태는 보지 않습니다. 교체 명령이 성공했다는 것과 화면이 새 snapshot을 읽는다는 것은 서로 다른 사실이라 둘을 따로 확인했습니다. snapshot이 준비되지 않았을 때는 옛 계산 방식으로 돌아가지 않고 오류를 돌려줍니다. 이 구조로 캠페인 조회 응답은 p95 291ms 이하가 됐습니다.

03여정 속 광고 attribution과 ROAS

광고 플랫폼이 보고하는 전환과 ROAS는 플랫폼마다 attribution 기간과 보고 시점이 다르고, 사이트에서 실제로 일어난 리드와 구매와는 다른 숫자입니다. 예를 들어 Meta는 사이트 전환을 클릭한 날이 아니라 전환이 일어난 날에 보고하므로, Meta가 주는 일별 ROAS는 그날 쓴 광고비가 만든 성과를 뜻하지 않습니다. 그래서 플랫폼이 보고한 값은 "플랫폼 보고"로 따로 보여 주고, 이 파이프라인의 ROAS는 사이트에서 관측한 리드와 구매로 직접 계산합니다.

1. 세션 안의 광고 진입을 후보로 두기

방문 세션은 같은 브라우저의 탭들이 함께 쓰는 장기 세션이고, 그 안에서 새 광고나 검색으로 들어올 때마다 진입(entry)을 따로 기록합니다. entry에는 UTM과 클릭 ID 같은 진입 정보가 남습니다. 기존 모델은 세션 하나에 광고 하나만 두어서, 10시에 광고 A로 들어와 10시 40분에 광고 B로 다시 들어오고 10시 45분에 문의하면 B가 사라졌습니다. 이벤트가 세션 단위로 한 번 접히면 뒤의 어떤 JOIN으로도 B를 되살릴 수 없습니다. 그래서 진입 기록은 모두 그대로 남기고, 어느 광고에 성과를 붙일지는 조회 시점에 판정하게 했습니다. 진입 기록이 모두 남아 있으므로 같은 데이터로 First, Last, Linear 같은 attribution 모델도 요청마다 바꿔 계산할 수 있습니다.

2. 행동 직전의 마지막 광고 진입 고르기

판정에는 순서가 있습니다.

  1. 리드 시각 이전, lookback window 30일 안에 관측된 광고 진입만 시간 조건으로 후보에 넣습니다. 직접 방문과 사이트 안 이동은 후보가 아닙니다.
  2. 후보 중 가장 늦은 하나를 고릅니다.
  3. 그 다음에야 고른 진입을 캠페인과 잇습니다.

캠페인 정보와 먼저 JOIN해 후보를 줄이면, 캠페인과 이어지지 않는 최신 진입이 먼저 빠지고 과거 진입이 저절로 뽑힙니다. 오래된 광고가 성과를 가져가는 셈입니다. 그래서 최신 진입이 캠페인과 이어지지 않으면 과거 광고로 물러나지 않고 "연결 안 됨"으로 남깁니다. 같은 시각의 후보가 둘이면 "동률", 후보가 없으면 "후보 없음"으로 둡니다. 직접 방문을 포함한 마지막 클릭 대신 광고 진입만 후보로 둔 것은, 직접 방문을 후보에 넣으면 광고 성과가 Direct로 흘러가기 때문입니다.

lookback window 30일은 90일치 운영 데이터로 측정해 정했습니다. 30일이 연결의 99.17%를 덮었고, 90일로 늘려도 0.8%p만 늘었으며, 7일로 줄이면 4.1%를 잃었습니다. 이 판정으로 기존 구현보다 광고 접점을 23% 더 찾았습니다.

3. 확인된 연결만 성과에 넣기

고른 진입을 캠페인과 잇는 근거는 두 가지만 씁니다.

  • Google은 클릭 ID를 받는 즉시 고객사 ID와 함께 SHA-256으로 hash한 key로 바꾸고, click view로 받은 클릭 ID의 hash와 맞춥니다. 원문 클릭 ID는 로그와 저장소에 남기지 않습니다. hash 식은 Go와 ClickHouse 조회에서 바이트 단위로 같게 맞추고 test로 고정했습니다.
  • Meta는 광고 설정에 선언된 URL 태그의 광고 ID, 캠페인 ID가 사이트에서 관측한 값과 같을 때만 잇습니다.

캠페인 이름으로 잇는 방식은 버렸습니다. UTM의 캠페인 이름과 플랫폼 캠페인 이름이 일치하는 비율은 0~17%였습니다. 이름은 양쪽에서 바뀌고 이력이 남지 않습니다. 반대로 URL에 넣은 광고 ID는 92.8~99.9%, 캠페인 ID는 99.97%가 플랫폼의 실제 ID와 맞았습니다. 추정 연결은 성과 숫자에 넣지 않고, 여정 화면에 이유와 함께 참고로만 보입니다. 추정으로 성과를 부풀리지 않기 위해서입니다.

4. 광고비와 성과를 따로 집계한 뒤 합치기

광고비의 grain은 계정, 캠페인, 날짜이고 리드와 구매는 이벤트입니다. 둘을 SQL 안에서 먼저 JOIN하면 광고비 한 행이 행동 수만큼 곱해집니다. 그래서 둘을 따로 집계한 뒤, Go로 만든 결합 API에서 같은 계정, 캠페인, 기간, 통화 key로 붙입니다.

  • ROAS의 분자와 분모에는 광고비가 연결된 행만 넣습니다. 광고비가 일부 기간만 있거나, 통화가 섞였거나, 시간대가 없거나, 광고비가 0이거나, 확인된 연결이 없으면 ROAS는 0도 무한대도 아닌 빈 값과 이유 코드로 냅니다.
  • 시간대는 고객사 리포트 시간대, 광고 계정 시간대 순서로 찾고, 둘 다 없으면 UTC로 대신하지 않고 "시간대 미설정"으로 보입니다.
  • 집계 층마다 합계가 맞는지, attribution credit의 합이 전체 건수와 같은지 검산하고, 어긋나면 숫자 대신 오류를 냅니다.

틀린 숫자보다 빈 칸이 낫다고 판단했습니다. 빈 칸에는 이유가 함께 떠서 무엇을 채워야 하는지 보입니다.

04설계 결정

아키텍처의 방향을 정한 판단 일곱 가지입니다. 고민, 선택지, 결정과 이유, 대가 순서로 적었습니다.

D-01

소급 정정을 받도록 최근 window와 정정 window 나누기

고민
광고 플랫폼은 지난 날짜 값을 나중에 고칩니다. Meta는 28일이 지나야 값이 고정되고, Google은 전환을 최대 90일까지 더하며 무효 트래픽을 당월 말까지 소급해 줄입니다. 정정을 모두 받으려면 긴 구간을 다시 읽어야 합니다. 그런데 Google quota는 Cloud project 하나의 rolling 24시간 operation 한도를 모든 계정이 나눠 쓰는 구조라, window를 넓히고 자주 돌릴수록 수집할 수 있는 계정 수가 줄어듭니다.
선택지
① 짧은 window 하나를 자주 다시 읽는 안
② 긴 window 하나를 하루 한 번 읽는 안
③ 최근 window는 자주, 플랫폼별 정정 기간 전체는 하루 한 번 읽고, click view는 따로 돌리는 안
결정과 이유
③을 골랐습니다. ①은 소급 정정을 놓치고, ②는 최근 데이터가 하루씩 늦습니다. 긴 window를 자주 돌리면 quota가 먼저 바닥납니다. 같은 날짜를 여러 window가 겹쳐 읽는 것은 정정을 잡는 장치이고, 비용은 window의 폭보다 다시 읽는 빈도가 결정한다고 봤습니다. 데이터 정확성을 정정 window가 책임지게 하면 최근 window의 폭을 실측에 맞춰 줄여도 정정 범위는 줄지 않습니다. click view는 하루 단위로만 조회되고 90일만 보관돼서, 지표 window에 묶으면 계정당 하루 operation이 크게 늘어 계정 몇 개 만에 한도에 닿습니다. 둘을 하나로 묶으면 한쪽의 누락을 다른 쪽의 성공으로 잘못 표시하게 되는 문제도 있어서, click view는 최근 2일만 하루 한 번 읽는 작업으로 뺐습니다.
대가
오래된 날짜의 정정은 최대 하루 늦게 화면에 반영됩니다. 계정이 늘면 API 등급을 올려야 합니다. 같은 날짜를 여러 번 다시 쓰므로 ClickHouse 쓰기가 늘어나, 병합이 따라잡는지 따로 측정해야 했습니다.
D-02

정정과 삭제를 조회 시점이 아니라 쓰기 시점에 판정하기

고민
성과 테이블은 같은 key의 최신 행이 이기는 ReplacingMergeTree입니다. 정정 window에서 다시 읽었을 때 사라진 행은 지워야 하는데, Google과 Meta 모두 지표가 전부 0인 행은 돌려주지 않아 응답에 없는 행이 삭제인지 그날 0인지 알 수 없습니다. 실적 최대화 캠페인의 하위 단위는 원래 빈 응답이라, 빈 응답을 삭제로 읽으면 window를 넓히는 순간 정상 데이터가 통째로 지워집니다.
선택지
① 조회할 때마다 중복과 삭제를 걸러 내는 안
② ALTER DELETE로 정정하는 안
③ 빈 응답이면 window 전체를 삭제 표시하는 안
④ 빠짐없이 받았다고 증명한 범위에서만 적재 단계가 삭제 표시를 만들고, 다시 읽어 확인한 뒤에만 cursor를 옮기는 안
결정과 이유
④를 골랐습니다. ①은 모든 화면과 API가 같은 규칙을 반복해야 하고, 조회할 때마다 전체 이력을 FINAL로 읽게 됩니다. ②는 무거운 mutation이고 정정 범위를 증명하지 못합니다. ③은 실적 최대화 캠페인처럼 원래 빈 응답인 단위를 지웁니다. window를 넓히는 순간 삭제 표시가 처음으로 쓰이기 시작하므로, 이 규칙은 window를 넓히기 전에 먼저 있어야 했습니다. ReplacingMergeTree는 최신 값이 이기는 구조라 이전 상태로 되돌릴 수 없고, 잘못 쓴 삭제는 플랫폼이 다시 값을 주는 기간 안에서만 복구됩니다. 그래서 쓰기 전에 증거를 요구하는 쪽을 택했습니다.
대가
실행마다 의도 기록과 다시 읽기가 붙어 지연과 PostgreSQL 트랜잭션이 늘었습니다. 응답이 일부만 오면 그 범위는 진전이 없습니다. Google은 빈 결과를 증명하려고 계정 정보 조회가 한 번씩 늘었습니다.
D-03

capability를 선언하는 adapter interface

고민
플랫폼마다 깨지는 지점이 달랐습니다. 네이버 검색광고는 보고서가 아직 없는 상태가 정상이고, 요청마다 HMAC 서명을 하고, 헤더 없는 TSV를 열 위치로 읽어야 합니다. 예전 구현은 이 보고서의 13번째와 14번째 열을 조회수와 전환수로 잘못 읽은 적이 있었습니다. Google은 project 전체가 quota를 나눠 쓰고, Meta는 계정별 호출 한도가 있습니다. 기존 코드는 플랫폼 이름으로 곳곳에서 분기했고, 새 플랫폼은 코드 test가 모두 통과해도 DB 제약 조건에서 연결이 거부됐습니다.
선택지
① 플랫폼 이름 분기를 유지하는 안
② 조회 메서드만 있는 얇은 interface
③ 무엇을 믿어도 되는지까지 선언하는 capability 기반 interface
결정과 이유
③을 골랐습니다. ①은 플랫폼이 늘수록 분기가 퍼집니다. ②는 결과를 성공과 실패 둘로만 나눠, 보고서가 아직 없다는 정상 상태와 비동기 job을 표현하지 못합니다. 토큰 문자열 하나로 인증하는 interface로는 요청마다 서명하는 HMAC도 받을 수 없습니다. capability에 0행 반환 여부, 값이 고정되는 날, 월말 동결, quota 모델을 담자, 그 선언이 수집 window, 삭제 판정, 호출 예산 계산의 입력이 됐습니다. adapter는 인증, 페이지, 오류 분류, 공통 형식 변환까지만 맡기고 상태를 바꾸는 일은 공통 파이프라인에 두어, 새 provider가 기존 provider 코드를 건드리지 않게 했습니다. 운영 중인 Meta 동작을 흔들지 않으려고, 처리 로직의 공통화는 같은 형태가 세 provider에서 반복된 뒤에 하기로 했습니다.
대가
capability 선언을 계속 실제와 맞게 유지해야 합니다. 새 provider는 adapter, topic, 정규화, DB 제약 조건까지 여러 층을 함께 바꿔야 해서 checklist와 test로 묶었습니다. 공통화하기 전까지는 일부 확정 로직이 provider마다 중복됐습니다.
D-04

작업 상태의 기준을 Kafka가 아니라 PostgreSQL ledger에 두기

고민
응답 한 페이지가 화면에 닿기까지 광고 플랫폼 API, GCS, PostgreSQL, Kafka, ClickHouse를 지나고, 이 다섯은 트랜잭션을 공유하지 않습니다. 그러면서도 "60초 뒤에 다시", "이 계정은 한 번에 하나만", "여러 사실을 함께 확정" 같은 요구가 있었습니다.
선택지
① Kafka log를 source of truth로 두는 안
② CDC(Debezium, Datastream) 복제본으로 상태를 나르는 안
③ 작업 상태는 PostgreSQL ledger에 두고 transactional outbox로 발행하며, 메시지에는 참조만 담는 안
결정과 이유
③을 골랐습니다. offset은 어디까지 읽었는지만 알려 주고, 어떤 작업이 몇 번째 시도인지, 언제 다시 해도 되는지는 알려 주지 않습니다. Kafka의 배타 단위는 partition이라 계정 단위 배타도 표현할 수 없습니다. CDC 복제본은 lease를 판정하는 기준이 될 수 없고, PostgreSQL logical replication은 DDL과 sequence를 복제하지 않아 schema 변경도 따로 배포해야 합니다. snapshot과 WAL 보존 같은 운영 부담도 생깁니다. outbox는 작업 상태와 발행 의도를 한 트랜잭션에 묶어 주고, CDC 없이도 동작합니다. exactly-once를 쫓는 대신 at-least-once 전달에 결정론적 ID와 ON CONFLICT를 더해 idempotent하게 수렴시켰습니다. 지연 재시도도 Kafka 기능을 기대하지 않고 ledger에 예약한 뒤 relay가 보냅니다.
대가
한 페이지에 PostgreSQL 트랜잭션이 여러 번 들어가 전체 지연이 늘었습니다. 외부 광고 API까지 exactly-once가 되는 것은 아니어서, 중복과 순서 뒤바뀜은 consumer의 idempotent 처리와 version 비교로 따로 막아야 합니다. 처리를 마친 outbox 행을 얼마나 보관할지도 따로 정해야 했습니다.
D-05

광고 API 응답 원문을 GCS에 고정하기

고민
정규화 규칙이 바뀌거나 ClickHouse 적재가 실패하면 결과를 다시 만들어야 합니다. 그때마다 광고 API를 다시 부르면 quota를 쓰고, 그사이 플랫폼 값이 바뀌어 서로 다른 시점의 응답이 섞입니다. 플랫폼 데이터 보관 기간과 click view 90일 보관 제한 때문에 다시 받는 것도 늘 가능하지는 않았습니다.
선택지
① 응답을 바로 ClickHouse에 적재하는 안
② 원문은 메모리에서만 다루고 ClickHouse를 원본으로 두는 안
③ 원문을 GCS에 create-only로 고정하고 manifest로 묶는 안
결정과 이유
③을 골랐습니다. ①과 ②는 다시 처리할 입력이 남지 않고, 어느 응답으로 만든 결과인지 증명할 수 없습니다. GCS 객체 이름은 작업, 기간, lease 시도로 만든 결정론적 이름이라 늦게 깨어난 옛 작업이 새 결과를 덮어쓰지 못합니다. 다시 처리할 때는 광고 API를 부르지 않고 같은 원문에서 다시 만들어, 같은 입력이면 같은 결과가 나옵니다. Meta는 응답에 새 필드를 계속 추가하는데, 원문 필드를 고정 목록으로 검사하던 방식은 이 정상적인 필드 때문에 소재 수집을 반복해서 거절했습니다. 그래서 원문 단계에서는 자격증명이 섞이지 않았는지만 검사하고, ID와 날짜와 수치 검사는 정규화 단계로 넘겼습니다. 보안 검사와 값 검사의 경계를 나눈 것입니다.
대가
저장 비용이 들고, 고객사 사이 중복 제거는 하지 않습니다. 대신 한 고객사의 삭제가 다른 고객사 데이터로 번지지 않습니다. GCS 쓰기와 확인이 lease 시간을 씁니다. Google 95일 정정 window는 응답 42개, 응답당 최대 32MiB까지 메모리에 올라올 수 있어서, 원문까지 함께 받는 조회를 일반 조회와 다른 interface로 나눠 필요한 경로에서만 쓰게 했습니다.
D-06

조회용 snapshot을 성과 테이블과 분리하기

고민
채널 성과 화면이 요청마다 전체 이력을 FINAL로 읽고 방문 세션 데이터와 JOIN하다가 읽기 행 한도에 걸려, 호출의 53.8%가 실패했습니다. 정정은 계속 들어오므로 화면이 매번 전체 이력을 읽는 구조로는 버틸 수 없었습니다.
선택지
① incremental Materialized View로 미리 집계하는 안
② AggregatingMergeTree로 집계 상태를 저장하는 안
③ 요청마다 FINAL로 읽고 cache로 버티는 안
④ 주기적으로 전체를 다시 계산하는 안
⑤ 바뀐 key만 다시 계산해 snapshot을 통째로 교체하는 안
결정과 이유
⑤를 골랐습니다. incremental Materialized View는 INSERT된 블록만 보고 계산해서, JOIN 오른쪽 테이블이 바뀌거나 지난 날짜가 정정돼도 다시 계산하지 않고 정정 행을 중복으로 더합니다. AggregatingMergeTree는 세션 합계가 두 번 더해질 수 있고, anyLast(is_deleted)는 블록 안 순서에 따라 결과가 달라져 삭제 판정에 쓰면 조용히 틀립니다. cache는 실효 hit rate가 0%였고, 전체 재계산은 정정과 상관없이 비용이 듭니다. 미리 계산해 두는 대상은 광고 쪽이 아니라 세션 쪽 집계로 정했습니다. 광고비는 범위를 좁힌 FINAL로 충분히 빨랐고, 비싼 것은 세션 JOIN이었기 때문입니다. 바뀐 key는 ClickHouse에 쓰기 전에 ledger에 먼저 적어, 중간에 멈춰도 다시 계산할 대상이 사라지지 않게 했습니다. 조회 p95가 200ms를 넘거나 읽는 행 수 p95가 50만을 넘으면 사전 집계 구조를 다시 검토한다는 기준도 숫자로 정해 두었습니다.
대가
테이블 쌍을 유지해야 하고, publisher 주기 5분만큼 반영이 늦습니다. snapshot이 준비되지 않으면 옛 방식으로 돌아가지 않고 오류를 돌려주므로, 준비가 늦어지면 화면이 비어 보일 수 있습니다.
D-07

마지막 광고 진입에 확인된 연결로만 붙이고, 광고비는 따로 집계하기

고민
기존 모델은 세션 하나에 광고 하나만 두어 같은 방문 안의 두 번째 광고 진입이 사라졌고, 캠페인 이름 매칭은 실측 0~17%라 쓸 수 없었습니다. 광고비는 계정, 캠페인, 날짜 단위이고 행동은 이벤트 단위라, 먼저 붙이면 광고비가 행동 수만큼 곱해집니다. 플랫폼이 보고한 전환과 사이트에서 관측한 리드는 이름만 같은 다른 숫자입니다.
선택지
① 플랫폼이 보고한 전환과 ROAS를 그대로 쓰는 안
② 세션의 첫 랜딩이나 직접 방문을 포함한 마지막 클릭에 붙이고, SQL 안에서 광고비와 JOIN하는 안
③ 광고 진입만 후보로 둔 마지막 접점에 확인된 연결로만 붙이고, 광고비와 행동은 따로 집계해 API에서 합치는 안
결정과 이유
③을 골랐습니다. ①은 플랫폼마다 attribution 기간과 보고 시점이 달라 사이트 구매와 맞지 않습니다. ②의 첫 랜딩은 나중 진입을 잃고, 직접 방문을 포함한 마지막 클릭은 광고 성과를 Direct로 흘려보냅니다. SQL 안 JOIN은 grain이 달라 반드시 중복이 생깁니다. 진입 기록을 모두 남기고 판정을 조회 시점에 하면, 나중에 다른 attribution 모델을 얹어도 과거 데이터를 다시 만들 필요가 없습니다. 확인된 연결만 성과에 넣어 추정으로 숫자를 부풀리지 않게 했고, 빈 값과 이유 코드로 0과 모름을 구분했습니다.
대가
URL에 ID 매크로를 넣지 않은 캠페인은 연결이 0으로 보여 설정 안내가 필요합니다. 광고비 연결이 일부만 있으면 값이 비어 보입니다. 광고 계정의 날짜와 고객사 리포트 날짜가 다른 날은 둘을 나란히 보여 주고, 일별 통합 ROAS는 만들지 않았습니다. 세션이 며칠씩 이어지므로 세션 수를 방문 수로 읽지 않는 규칙도 필요해졌습니다.

05결과

  • Meta 30일과 Google 95일을 매일 다시 읽게 되어, 다시 읽는 구간이 사실상 2일이라 놓치던 Meta 소급 정정 26일치를 받게 됐습니다.
  • 호출의 53.8%가 읽기 행 한도로 실패하던 채널 성과 화면을 조회용 snapshot으로 옮겼습니다. 캠페인 조회 응답은 p95 291ms 이하이고, 수집된 Meta 성과가 화면에 보이기까지 2~7분이 걸립니다.
  • Google 조회 구간을 7일씩 쪼개던 방식을 없애 계정당 하루 operation을 약 180에서 약 80으로 줄였고, 같은 API 등급에서 받을 수 있는 계정 수가 두 배 남짓 늘었습니다.
  • Kafka consumer lag은 평소 0~4 레코드로 병목이 아니었습니다. 같은 명령이 다시 와도 ledger에서 판정해 광고 API를 다시 부르지 않습니다.
  • 행동 직전의 마지막 광고 진입을 고르는 규칙으로 기존 구현보다 광고 접점을 23% 더 찾았고, 캠페인 연결은 이름 대신 URL에 넣은 ID로 92.8~99.9%를 이었습니다.
  • Google Ads와 네이버 검색광고를 Meta 수집 경로의 단계와 topic을 바꾸지 않고 붙였습니다. Google은 API를 REST로 직접 조회한 결과와 adapter 결과 18건을 비교해 query ID, 행 수, 정규화 값까지 모두 일치하는 것을 확인한 뒤 새 경로로 전환했습니다. 네이버 검색광고는 전날 보고서가 새벽 2시 17분에서 4시 17분 사이에 열리는 것을 측정해 4시 30분 이후에만 요청하게 했고, 비용을 VAT 제외 금액으로 통일해 플랫폼 간 ROAS가 약 9% 어긋나는 것을 막았습니다.

06트러블슈팅

T-01

프로세스는 모두 정상인데 한 계정의 데이터만 4시간 넘게 멈춘 문제

문제
한 Meta 계정의 새 성과 작업이 약 4시간 22분 동안 발행되지 않았습니다. consumer는 모두 Ready였고, relay도 정상 종료했으며, Kafka offset도 계속 올라갔습니다. 프로세스 지표로는 이상이 없어서, 데이터를 직접 조회해 보고서야 발견했습니다.
원인
같은 계정의 영상 원본 조회가 잘못된 경로로 HTTP 400을 반복했고, 그 작업은 미래 시각에 다시 시도하도록 예약돼 있었습니다. ledger에서 실행할 작업을 골라 내보내는 dispatcher는 계정마다 실행 중인 작업이 하나여야 한다는 규칙을 지키는데, 이 규칙이 실행 중인 작업이 아니라 아직 끝나지 않은 모든 명령을 세고 있었습니다. 그래서 미래 시각의 retry 하나가 계정 전체를 막았습니다. 막고 있던 것은 Kafka가 아니라 PostgreSQL에서 작업을 고르는 조건이라, broker나 consumer를 늘려도 풀리지 않는 문제였습니다. endpoint 검사도 URL path의 마지막 segment만 봐서 잘못된 경로를 거르지 못했습니다.
해결
계정 단위 배타 조건을 "실행 중인 작업은 하나"와 "처리 중인 명령은 하나" 두 가지로 나누고, 예약 시각이 아직 오지 않은 대기 명령은 배타 조건에서 뺐습니다. 실행 중이거나 시각이 된 명령은 계속 막고, 계정 lease와 60초 간격도 그대로 두었습니다. endpoint는 전체 path로 검사하게 고쳤습니다.
결과
수정이 반영되고 1분 안에 핵심 데이터가, 10분 안에 캠페인 성과와 실패하던 영상이 복구됐습니다. 이 일 뒤로 감시 기준을 Pod 상태나 offset이 아니라 데이터 진행으로 바꿨습니다. 실행할 작업이 있는데 5분 동안 진행이 없으면 긴급, 계정의 핵심 데이터가 정해진 수집 시각부터 6시간 안에 끝나지 않으면 주의로 경보합니다.
T-02

FINAL과 PREWHERE를 함께 쓰면 지운 행이 살아나는 문제

문제
성과 테이블은 is_deleted 컬럼이 있는 ReplacingMergeTree라, 조회는 FINAL로 같은 key의 최신 행을 고른 뒤 삭제 표시를 걸러야 합니다. 조회 규칙을 정하면서 로컬 ClickHouse 두 버전에서 정정 시나리오를 재현해 보니, FINAL과 PREWHERE is_deleted = 0을 함께 쓰면 삭제 표시 124개 중 120개가 새어 클릭이 1.27% 많게 나왔습니다.
원인
PREWHERE 조건은 FINAL이 같은 key의 행을 하나로 접기 전에 적용됩니다. 최신 행이 삭제 표시인 key에서 PREWHERE가 그 삭제 표시 행을 먼저 버리면, FINAL은 남아 있는 옛 행을 최신으로 고릅니다. 지운 행이 다시 살아나는 셈입니다.
해결
FINAL 뒤에 WHERE is_deleted = 0으로 거르고 PREWHERE는 쓰지 않는 규칙을 모든 조회 view에 적용했습니다. PREWHERE가 꼭 필요한 곳은 apply_prewhere_after_final = 1을 함께 켭니다.
결과
두 버전 모두에서 같은 누출이 재현되는 것을 확인하고 규칙으로 막았습니다. 같은 실험에서 FINAL로 읽는 행 수가 물리 행 수와 같다는 것도 확인해, 조회 비용을 물리 행 수로 예측할 수 있게 됐습니다. 병합이 켜져 있으면 같은 날짜를 반복해 다시 써도 마지막 쓰기 뒤 약 20초 안에 물리 행과 고유 행이 1.11 대 1로 수렴했습니다.

07배운 점

  • 광고 숫자는 가져온 순간 끝나지 않고, 언제까지 바뀔 수 있는지가 데이터의 일부였습니다. 플랫폼이 무엇을 보장하는지 adapter가 먼저 선언하게 하자, 수집 window, 삭제 판정, quota 예산을 모두 그 선언에서 계산할 수 있었습니다.
  • 트랜잭션을 공유하지 않는 시스템을 잇는 파이프라인에서는 단계마다 증거를 따로 남겨야 했습니다. 광고 API의 HTTP 200, Kafka offset 확정, ClickHouse INSERT 성공은 모두 다른 사실이고, 다시 읽어 확인한 뒤에만 다음 단계로 넘어가게 해야 수집 완료를 잘못 표시하지 않습니다.
  • 사고는 오류보다 조용한 0으로 더 자주 왔습니다. 빈 결과, 연결 안 됨, 시간대 미설정을 0과 다른 상태로 끝까지 실어 나르고, 프로세스 상태가 아니라 데이터가 실제로 진행되는지를 감시해야 했습니다.
