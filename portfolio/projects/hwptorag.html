HWPtoRAG (글목): HWP 표를 살려 AI가 읽게 하는 엔진

한글(HWP) 문서를 PDF로 바꾸지 않고 파일 안의 레코드를 직접 읽어, 표 구조를 살린 Markdown, JSON, 그리고 AI 검색에 넣기 좋게 문서를 조각으로 나눈 RAG-JSON으로 바꾸는 엔진과 변환 서비스입니다. 엔진, 변환 서버, API, 평가 도구를 직접 설계하고 개발했습니다.

01상황과 역할

HWPtoRAG(글목)는 한글(HWP) 문서를 AI가 바로 읽을 수 있는 형태로 바꾸는 엔진과 변환 서비스입니다. RAG는 문서를 검색해 AI 답변의 근거로 붙이는 방식입니다. 공공, 법률, 학술 분야에는 HWP로 작성된 문서가 많습니다. 그런데 Unstructured.io, Azure Document Intelligence 같은 AI 문서 처리 도구는 HWP를 받지 않습니다. 그래서 HWP 문서를 RAG에 넣으려면 대개 PDF나 이미지로 바꾼 뒤 다시 읽어야 했습니다. 이 중간 변환을 없애는 것이 목표였습니다.

웹에서 파일을 끌어다 놓으면 Markdown, JSON, Plain Text, RAG-JSON, CSV, HTML 중 고른 형식으로 바꿔 줬습니다. 로그인하지 않아도 하루 5번, 파일 하나에 100MB까지 쓸 수 있게 했습니다. 개발자용으로 Python 패키지와 REST API도 만들었습니다.

대상 사용자는 넷입니다.

  • 학위 논문을 Markdown으로 옮기려는 대학원생과 연구자
  • 판결문과 계약서를 구조화하려는 리걸테크
  • RAG 파이프라인에 HWP를 넣으려는 AI 스타트업
  • 행정 문서를 디지털로 옮기려는 공공기관

해결하려던 문제

  1. PDF나 이미지로 바꾸면 여러 칸을 합친 병합 셀이 풀리고, 어느 값이 어느 header 아래에 있는지도 알 수 없게 됩니다.
  2. 법률 문서는 당사자, 금액, 기간이 표 안에 들어 있습니다. 표가 깨지면 검색과 요약이 틀립니다.
  3. RAG를 만들 때 많이 쓰는 LangChain 라이브러리에는 HWP를 읽어 들이는 공개 document loader가 있었습니다. 하지만 이 loader는 pyhwp라는 라이브러리로 글자만 뽑아내서 표 구조가 사라졌습니다.
  4. 법무 쪽 사용자는 문서를 외부 서버로 보내기 어렵습니다.

왜 바이너리를 직접 읽었나

HWP 5.0 파일 안에는 표 셀마다 행과 열 좌표, 병합 크기가 이미 저장돼 있습니다. 이 값을 읽으면 표 모양을 추론할 필요가 없습니다. 반대로 AI 모델로 표 모양을 추론하려면 GPU나 외부 API가 필요합니다. 문서를 외부로 보내기 어려워 인터넷과 분리된 air-gapped 환경에서 써야 하는 사용자에게는 맞지 않는 방식이었습니다. 그래서 CPU만으로 동작하는 엔진을 직접 만들기로 했습니다.

과제와 역할

  • 2026년 2월에 세운 첫 목표는 HWP를 직접 읽는 엔진과 웹 변환기를 만들고, 개발자용 API와 Python 패키지까지 내는 것이었습니다.
  • 2026년 3월부터 5월까지의 두 번째 목표는 같은 엔진 위에 법률 문서에서 당사자, 금액, 기간을 찾아내는 기능을 더하고, 이것으로 창업아이디어경진대회에 나가는 것이었습니다.
맡은 일
대표를 맡아 개발 전체를 이끌었습니다. Rust 엔진, 변환 서버, 개발자용 SaaS API, Python에서 엔진을 바로 부를 수 있게 하는 Python 바인딩, 평가 도구를 직접 설계하고 개발했습니다. 웹 화면에서는 출력 형식 선택, 변환 이력, 여러 파일을 한 번에 바꾸는 batch 변환, 변환 서버와의 연동을 맡았습니다.
팀원 (사업)
사업계획, 수익 모델, 시장 조사, 발표 일부를 맡았습니다.
팀원 (UX, 프런트엔드)
웹 화면의 첫 버전을 만들었습니다. 첫 화면, 업로드와 변환 화면, 파일 검사와 조각 단위 업로드, 요금 화면, Google 로그인이 여기에 들어갑니다. 협업 편집 화면 일부도 맡았습니다. 변환 결과의 검수용 표본을 한글 프로그램에서 연 원본과 하나씩 맞춰 보는 일도 맡았습니다.
자문 교수
검증 방법과 보안에 대해 자문했고, 특허를 함께 발명했습니다.
기반 코드
HWP 5.0과 HWPX를 읽어 들이는 부분은 MIT/Apache-2.0 라이선스로 공개된 Rust 라이브러리 hwpers를 기반으로 했습니다. 그 위에서 파일 속 레코드를 계층대로 묶는 레코드 트리, 셀 좌표로 표를 다시 세우는 표 복원, 결과를 각 형식으로 써 내는 writer를 직접 만들었습니다.

02해결 과정

1. 아키텍처

  • 웹 변환기 (Next.js, Vercel): 파일 확장자와, 파일 앞부분에 적힌 형식 표시인 magic number를 검사합니다. 검사를 통과하면 파일을 5MB 조각으로 나눠 변환 서버로 직접 올립니다. 초기 화면과 업로드 코드는 팀원이 만들었습니다.
  • 변환 서버 (NestJS, Docker, Railway): 올라온 조각을 하나의 파일로 이어 붙이고, Rust 엔진을 CLI로 실행합니다. 하루 사용 횟수 제한과 오래된 결과 삭제도 이 서버가 맡습니다.
  • 저장소 (Supabase): 변환이 어디까지 진행됐는지는 PostgreSQL 데이터베이스에 기록하고, 로그인은 Google 계정으로 받습니다. 크기가 큰 결과와 문서에서 뽑아낸 이미지는 Supabase Storage에 둡니다.
  • SaaS API (FastAPI): 개발자가 요청 한 번으로 RAG 준비를 끝낼 수 있게 한 API입니다. 문서를 읽고, 검색하기 좋은 크기의 청크로 나누고, 각 청크를 embedding vector로 바꾼 뒤 vector DB에 저장합니다. 벡터 DB는 Qdrant, Pinecone, Weaviate, Milvus 중에서 고를 수 있습니다.
  • 엔진 (Rust): 들어온 파일이 한글 문서의 세 가지 저장 형식인 HWP 5.0, HWPX, HWPML 중 무엇인지 가려낸 뒤, 표를 복원해 공통 구조인 IR(intermediate representation)로 만듭니다. 이 IR을 JSON, Markdown, Plain Text, RAG-JSON, CSV, HTML, HWPX의 7가지 형식으로 써 낼 수 있습니다.
  • Python 바인딩 (PyO3): Rust 엔진을 Python 코드에서 바로 부를 수 있게 이어 주는 부분입니다. SaaS API와 LangChain용 HWP loader가 이것을 거쳐 엔진을 직접 호출합니다.
  • 평가 도구: 변환한 표가 얼마나 정확한지 재는 metric인 TEDS-S와 Table F1을 계산하고, 사람이 원본과 맞춰 볼 검수용 표본을 뽑습니다. TEDS-S는 표 구조가, Table F1은 셀이 기준 표와 얼마나 같은지 재는 값입니다.

2. 주요 흐름

흐름 1. 웹에서 HWP 한 건을 바꿀 때

  1. 브라우저가 확장자와 magic number를 확인합니다. 100MB를 넘으면 막습니다.
  2. 업로드 세션을 열고 파일을 5MB 조각으로 보냅니다.
  3. 서버는 빠진 조각이 있으면 그 조각 번호를 돌려줘 다시 보내게 합니다. 조각이 다 모이면 파일 전체를 메모리에 한꺼번에 올리지 않고, stream으로 차례로 읽어 가며 이어 붙입니다.
  4. 엔진은 동시에 3개까지만 돌기 때문에, queue에서 slot이 나기를 기다린 뒤 Rust 엔진을 실행합니다. 한 건이 60초를 넘기면 중단합니다.
  5. 결과가 1MB보다 작으면 데이터베이스에, 그보다 크면 Supabase Storage에 저장합니다.
  6. 화면은 상태를 조회해 결과를 보여 줍니다. 1시간이 지난 결과는 매시간 도는 cleanup job이 지웁니다.

흐름 2. 엔진 안에서 표를 복원할 때

  1. HWP 파일의 본문은 작은 레코드들이 줄지어 저장된 구조입니다. 각 레코드에 적힌 level 값(계층 깊이)을 보고 부모와 자식으로 묶어 트리를 만듭니다.
  2. 표를 만나면 셀마다 앞에 붙은 cell header에서 그 셀의 행, 열, 병합 크기를 읽습니다.
  3. 읽은 좌표에 셀을 놓고, 다른 셀과 합쳐져 가려진 칸은 병합으로 표시합니다. 그래도 채워지지 않은 칸은 파일에 없는 누락 칸으로 둡니다.
  4. 첫 행이 header인지는 굵기, 배경색, header 단어 같은 6개 signal의 점수로 정합니다.
  5. 표마다 유형을 붙입니다. 유형은 데이터를 담은 데이터 표, 항목 이름과 값이 짝을 이루는 key-value 표, 내용을 배치하려고 쓴 layout 표의 세 가지입니다. 이 판정이 얼마나 확실한지를 나타내는 신뢰도도 함께 붙입니다.
  6. 표 안의 표는 같은 과정을 반복합니다. 깊이는 5단계까지입니다.

흐름 3. API로 벡터 DB까지 넣을 때

  1. vector DB 안에서 데이터를 담을 collection의 이름이 올바른지 먼저 검사합니다. 임베딩처럼 오래 걸리는 처리를 다 하고 나서 이름 때문에 실패하지 않게 하려는 것입니다.
  2. HWP 파일은 Python 바인딩을 거쳐 Rust 엔진으로 읽고, DOCX와 PDF는 기존 Python 라이브러리로 읽습니다.
  3. 표가 든 청크는 크기 제한을 넘어도 자르지 않습니다.
  4. 임베딩을 마치면 사용자가 고른 벡터 DB에 넣고, 각 단계에 걸린 시간을 응답에 담아 돌려줍니다.

3. 설계 고민과 결정

셀 위치를 어떻게 정할 것인가

  • 고민: 셀이 나오는 순서와 열 수로 위치를 계산하면 병합 셀에서 한 칸씩 밀립니다.
  • 선택지: 셀이 나오는 순서로 위치를 계산하는 방법과, 파일에 저장된 좌표를 그대로 읽는 방법이 있었습니다.
  • 결정: 좌표를 그대로 읽었습니다. 값이 이미 파일에 있는데 따로 계산할 이유가 없었습니다. 이렇게 하면 표의 모든 칸이 내용이 있는 칸, 빈칸, 병합으로 가려진 칸, 파일에 없는 누락 칸 중 하나로 분명하게 정해집니다.

어떤 형식을 기본 출력으로 둘 것인가

  • 고민: LLM은 Markdown을 잘 읽지만, Markdown 표는 병합 셀을 표현하지 못합니다.
  • 선택지: 모든 출력을 Markdown 하나로 통일하는 방법과, JSON을 기본으로 두고 Markdown을 보조로 쓰는 방법이 있었습니다.
  • 결정: JSON을 기본으로 삼아 header, 행, 병합 정보를 모두 담았습니다. Markdown으로 낼 때는 표 밑에 어느 칸이 합쳐졌는지를 주석으로 적었습니다.

RAG 청크를 어디서 자를 것인가

  • 고민: RAG에 넣으려면 문서를 검색용 조각(청크)으로 나눠야 합니다. 그런데 글자 수로 자르면 표의 header와 값이 서로 다른 청크로 갈립니다.
  • 선택지: 정해진 글자 수마다 자르는 방법과, 제목이나 표 같은 문서 구조를 기준으로 자르는 방법이 있었습니다.
  • 결정: 표는 자르지 않고 한 청크에 통째로 두었습니다. 청크마다 그 내용이 어느 제목 아래에 있는지 보여 주는 제목 경로를 붙였습니다. 출력은 한 줄에 청크 하나씩 적는 JSONL 형식으로 썼습니다. 결과 전체를 하나의 문자열로 만들지 않고 줄 단위로 쓰고 읽을 수 있게 했습니다.

웹 서버와 엔진을 어떻게 이을 것인가

  • 고민: Rust 엔진을 Node 서버 안에 직접 넣는 native addon 방식은 빌드가 까다롭습니다. 엔진을 별도 서버로 띄우면 서버를 하나 더 운영하는 비용이 듭니다.
  • 선택지: native addon으로 넣는 방법, 엔진을 별도 서비스로 띄우는 방법, 변환 서버가 엔진을 CLI로 실행하는 방법의 세 가지가 있었습니다.
  • 결정: 변환 서버가 변환 요청마다 엔진을 CLI로 실행하는 방식을 골랐습니다. 큰 파일이 몰리면 메모리가 넘칠 수 있어 concurrency를 3개로 제한했습니다. 한 건당 60초 제한도 걸었습니다.

법률 문서의 의미를 무엇으로 붙일 것인가 (2026.05)

  • 고민: 당사자와 금액을 LLM으로 뽑으면 hallucination 위험과 외부 API 비용이 생깁니다.
  • 선택지: LLM에게 뽑게 하는 방법과, 미리 정해 둔 규칙으로 뽑는 방법이 있었습니다.
  • 결정: 규칙으로 만들었습니다. 규칙이 내린 분류의 신뢰도가 threshold보다 낮으면, 세부 분류 대신 한 단계 넓은 상위 분류를 붙이게 했습니다.

4. 구현 상세

Rust 엔진과 CLI

  • 변환 서버가 오류를 처리할 수 있도록 CLI가 실패 원인을 JSON으로 출력하게 했습니다.
  • 결과가 클 때는 전체를 메모리에 모아 두지 않고, 64KB buffer에 모아 가며 파일에 바로 썼습니다.
  • 수식은 HWP 수식 문법을 따로 해석했습니다.

배포와 Python 연결

  • 다른 라이브러리 없이 혼자 실행되는 Rust 엔진 static binary와 NestJS 변환 서버를 Docker 이미지 하나에 함께 넣었습니다. 컨테이너는 root가 아닌 non-root 사용자로 실행했습니다.
  • 서버를 올린 Railway가 새 버전을 배포할 때 /api/health로 health check를 해 서버가 정상으로 떴는지 확인하게 했습니다. 서버 프로세스가 비정상으로 꺼지면 최대 5번까지 자동으로 다시 띄우게 했습니다.
  • Python에서 엔진을 부를 때 파일을 디스크에 저장해 경로를 넘길 필요 없이, 메모리에 있는 파일 내용을 그대로 넘길 수 있게 했습니다.

평가 도구

  • 국가법령정보센터에 올라온 법령 별표와 서식 HWP 파일을 모으는 crawler를 만들었습니다. 같은 파일은 dedup하고, 개인정보로 보이는 패턴도 걸러 냈습니다.
  • 표가 있는 파일 28,851개를 표 크기와 병합 셀이 얼마나 많은지에 따라 여러 stratum으로 나눴습니다. 그리고 stratum마다 골라 사람이 검수할 표본 186건을 뽑았습니다.
  • 검수자는 한글 프로그램에서 원본을 열어 변환 결과와 비교하고, 완전히 같음(Perfect), 작은 차이(Minor), 일부만 맞음(Partial), 실패(Fail)의 네 단계 중 하나로 판정하게 했습니다.

03결과

  • 2026년 5월 상명대학교 2026학년도 창업아이디어경진대회에서 최우수상을 공동 수상했습니다.
  • 2026년 3월, 표 구조를 보존하는 중간 표현 생성 방법을 자문 교수와 함께 특허 출원했습니다.
  • 웹 변환기(hwptorag.site)와 변환 서버를 배포해 누구나 쓸 수 있게 공개했습니다. 2026년 10월 현재 변환 서버는 중단된 상태입니다.
  • 엔진은 한글 문서의 세 가지 저장 형식인 HWP 5.0, HWPX, HWPML을 읽고, 7가지 형식으로 결과를 낼 수 있었습니다. 웹에서는 그중 6가지를 고를 수 있었습니다.
  • 2026년 3월에 법령 별표와 서식 HWP 파일 38,652건을 엔진에 넣어 직접 돌려 봤습니다. 읽지 못하고 실패한 파일은 한 건도 없었고, 이 파일들에 든 표는 약 33,000개였습니다.
  • 같은 달 팀원이 검수용 표본 중 60건을 한글 프로그램에서 연 원본과 하나씩 비교했습니다. 그중 56건은 변환 결과가 원본과 완전히 일치했습니다.
  • 2026년 5월에는 같은 엔진 위에, M&A 계약서에서 당사자, 금액, 기간을 찾아내는 법률 문서 처리 기능을 더했습니다.

04트러블슈팅

T-01

실제 HWP 파일에서 표가 잡히지 않았습니다

문제
기반 라이브러리(hwpers)로 직접 만든 테스트 파일에서는 표가 제대로 잡혔습니다. 그런데 실제로 쓰이는 HWP 파일을 넣으면 표와 문단이 통째로 빠졌습니다.
원인
레코드 종류를 나타내는 태그 번호가 기반 라이브러리(hwpers)와 공식 명세에서 달랐습니다. 실제 파일은 공식 명세를 따랐습니다. 테스트 파일은 같은 라이브러리로 만들어서 테스트에서는 문제가 드러나지 않았습니다. 또 엔진은 표 관련 레코드가 층층이 안쪽으로 겹쳐 들어가 있다고 가정했는데, 실제 파일에서는 같은 계층 깊이(level)에 나란히 놓여 있었습니다.
해결
실제 파일에 적힌 공식 명세의 태그 번호를, 라이브러리가 쓰는 번호로 바꿔서 읽게 했습니다. 표 레코드가 나란히 놓인 경우에는 cell header가 나올 때마다 새 셀이 시작된 것으로 보고 트리를 다시 세웠습니다.
결과
같은 문제가 다시 생기지 않도록, 라이브러리로 만든 파일이 아닌 실제 HWP 파일을 넣어 변환 전체를 확인하는 integration test를 추가했습니다.
남긴 규칙
라이브러리 상수와 그 라이브러리로 만든 테스트 파일은 공식 명세와 실제 파일로 다시 확인해야 합니다.
T-02

"정확도 100%"가 실제 정확도가 아니었습니다

문제
처음 만든 평가 보고서에서, 표의 첫 행이 header인지 맞힌 정확도인 header F1이 100%로 나왔습니다. 파일 38,652건 전부를 평가한 표 구조 점수 TEDS-S도 만점인 1.0이었습니다.
원인
header F1은 header가 없는 문서로 잰 값이어서, 엔진이 header를 제대로 찾는지는 보여 주지 못했습니다. 전체 파일 평가 점수는 한글 원본과 비교한 것이 아니라 엔진이 낸 결과끼리 비교한 값이었습니다. 엔진이 같은 결과를 일관되게 내는지만 보여 줄 뿐, 결과가 원본과 같은지는 알 수 없었습니다.
해결
결과를 한글 원본과 직접 비교하려고 검수용 표본 186건을 뽑고 검수 도구를 만들었습니다.
결과
팀원이 이 도구로 표본 중 60건을 원본과 비교했고, 56건이 완전히 일치했습니다. 나머지 4건에서는 ①, ② 같은 숫자 특수문자가 한자로 깨지거나 띄어쓰기가 빠져 있었습니다. 숫자 특수문자 문제는 엔진을 고쳐 해결했고, 그 과정은 다음 사례(T-03)에 적었습니다.
남긴 규칙
metric은 무엇과 무엇을 비교한 값인지 먼저 확인해야 합니다.
T-03

숫자 특수문자 자리에 뜻 없는 한자가 나왔습니다

문제
①, ② 같은 숫자 특수문자 자리에 뜻 없는 한자(灳瑣)가 나왔습니다. 파일 안에서만 쓰는 내부 경로 문자열도 본문 글자에 섞여 나왔습니다. 팀원이 결과를 원본과 비교하는 검수 중에 찾았습니다.
원인
처음에는 직인 이미지 자리에 남은 글자로 보고, 평가 스크립트에서 HWP 전용 기호 코드와 함께 지웠습니다. 그런데 검수에서 숫자 특수문자 자리에 한자가 나온 것을 보고 엔진을 다시 봤습니다. HWP 문단 텍스트에는 글자 말고도 서식을 지정하는 control character가 섞여 있습니다. ①, ② 같은 원문자를 만드는 "글자 겹침" 같은 extended control character는 문단 텍스트에서 8칸을 차지합니다. 그런데 엔진의 control character 분류표는 이를 1칸짜리로 보고 읽었습니다. 그래서 남은 7칸에 든 control character의 이름 값이 글자로 해석돼 한자로 출력됐습니다.
해결
분류표를 고쳐 extended control character를 만나면 8칸을 통째로 건너뛰게 했습니다. 원문자 숫자는 제어 코드 안에 담긴 번호를 읽어 다시 만들었습니다. 파일 내부 경로나 control character만 있는 줄은 결과에서 걸러 냈습니다.
결과
같은 control character가 든 입력을 넣어 이 문제가 다시 생기지 않는지 확인하는 regression test를 엔진에 추가했습니다.
남긴 규칙
깨진 글자를 출력 뒤에서 지우기 전에, 엔진이 그 글자를 왜 만들었는지 먼저 확인해야 합니다.

05배운 점

라이브러리로 직접 만든 테스트 파일만 믿으면 안 된다는 것을, 실제 파일에서 표가 통째로 빠지는 일로 알았습니다. 같은 이름의 metric도 무엇과 비교했는지에 따라 뜻이 다릅니다. 그래서 내부 일관성 값과 원본 대조 값을 나눠 적었습니다.
