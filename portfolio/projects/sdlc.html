01상황과 역할

수파리드는 적은 인원이 수집 SDK, 데이터 파이프라인, API, 인프라를 함께 바꾸는 팀이었습니다. 여러 에이전트에게 일을 나눠 맡기면서 변경 여러 개가 동시에 진행됐습니다.

에이전트는 대화가 바뀌면 이전 결정을 모릅니다. 그래서 같은 조사를 반복하거나, 이미 바뀐 규칙으로 작업하는 일이 생겼습니다. 구현한 에이전트가 테스트까지 맡으면 자기 코드에 맞춰 테스트를 고칠 수 있었습니다. 배포 쪽에서는 staging에서 확인한 것과 운영에 배포되는 것이 같다고 보장할 수 없었습니다. 배포마다 빌드 결과와 스키마 상태가 달라질 수 있었기 때문입니다.

여러 에이전트가 한 저장소를 동시에 바꾸는 구조에는 분산 시스템과 비슷한 문제가 있었습니다. 상태를 어디에 둘지, 누가 무엇을 바꿀지 정해야 했습니다. 한 참여자가 틀렸을 때 어떻게 멈출지도 정해야 했습니다.

맡은 일
이 체계 전체의 설계, 구축, 운영을 맡았습니다. 작업을 나누고 통과 여부를 판단하는 일, 운영 검증까지 했습니다.

02해결 과정

1. 설계 문서는 저장소에, 진행 상황은 Linear에 두기

정보를 유지되는 기간에 따라 나눴습니다. 오래 유지되는 것은 저장소 문서로 두었습니다. 설계 원칙, 데이터 계약, 스키마와 인프라 구성, 운영 규칙입니다. 도메인마다 해당 문서로 가는 색인도 두었습니다. 자주 바뀌는 것은 Linear 작업 항목에 두었습니다. 목표, 범위, 확정한 결정, 막힌 것, 검증 결과, 남은 일과 담당입니다.

지금 어떻게 동작하는지는 문서보다 코드, 설정, 테스트, 운영 기록으로 확인합니다. 문서에는 설계 의도와 그 자료로 가는 링크를 둡니다.

사람과 에이전트는 같은 순서로 작업을 시작합니다.

  1. Linear 작업 항목에서 목적, 완료 조건, 최신 결정을 읽습니다.
  2. 연결된 저장소 문서와 색인에서 관련 계약과 제약을 찾습니다.
  3. 코드, 설정, 테스트에서 실제 상태를 확인합니다.
  4. 정한 범위 안에서 조사나 구현을 하고 검증합니다.
  5. 결과, 검증 범위, 남은 위험, 다음 담당을 작업 항목에 남깁니다.

실패와 보류도 같은 자리에 남겼습니다. 다음 사람이나 에이전트는 이전 대화를 몰라도 작업 항목에서 이어받습니다.

작업 항목에는 사람 책임자와 실행하는 에이전트를 따로 적게 했습니다. 사람의 결정을 기다리는 작업은 바로 실행할 수 있는 작업과 구분했습니다. 에이전트가 작업 항목을 저장하기 전에는 분류, 책임자, 바로 시작할 수 있는지가 정해진 형식대로 적혔는지 자동 형식 검사(lint)로 확인합니다. 이 검사는 에이전트가 도구를 호출하기 직전에 자동으로 실행되는 hook에 걸었습니다. 검사기가 없으면 저장을 막습니다.

2. 역할을 나누고, 완료 보고는 검증의 입력으로만 쓰기

큰 목표를 여러 에이전트에 그대로 보내면 구현이 겹치거나, 서로 다른 가정으로 코드를 만듭니다. 그래서 목표와 데이터 불변 조건을 먼저 정했습니다. 그다음 작업을 조사, 설계, 구현, 검토, 독립 QA로 나눠 각각 다른 에이전트에게 맡겼습니다. 검토와 QA는 구현하지 않은 에이전트가 맡았습니다. 서로 의존하지 않는 부분만 병렬로 돌렸습니다.

에이전트에게 일을 맡길 때는 목표, 시작할 코드 버전, 수정할 수 있는 파일, 금지 범위, 수행할 검증을 함께 넘겼습니다. 구현 에이전트는 각자 별도 작업 폴더에서 일합니다. 한 파일의 주 작성자는 하나만 둡니다. 공용 의존성, 실행 진입점, 마이그레이션처럼 충돌하기 쉬운 파일은 통합 단계에서 순서대로 반영했습니다.

구현 에이전트의 완료 보고는 통과로 보지 않았습니다. 검토 에이전트와 QA 에이전트가 확인할 입력으로만 썼습니다. QA 에이전트는 제품 코드를 고치지 않고 판정만 합니다. 결함이 나오면 해당 부분의 수정 작업으로 되돌립니다. 수정한 버전에서 다시 검증합니다.

검토 규칙에도 같은 원칙을 두었습니다. 검토와 반영 판정에는 변경 전부터 반영돼 있던 규칙을 씁니다. 그래서 검토 규칙을 고치는 변경도 기존 규칙으로 검사받습니다. AI 검토 결과는 어떤 코드 버전을 검토했는지와 함께 확인했습니다. 코드가 바뀌면 이전 승인을 그대로 쓰지 않았습니다.

사람이 판단하는 지점도 정했습니다. 큰 설계 결정, 첫 통합, 비용이나 범위가 바뀔 때, 최종 반영 전입니다. 파괴적 스키마 변경, 새 데이터 수집, 개인정보와 과금, 장애 대응, 검사 규칙 변경은 항상 사람이 판단합니다.

버린 대안은 AI가 만든 변경을 조건만 맞으면 자동으로 반영하는 방식입니다. 자동 반영은 의존성 업데이트 봇에만 열었습니다. AI가 구현한 변경은 자동 검사와 AI 검토를 거친 뒤 사람이 최종 반영합니다. 기능을 빨리 만드는 일과 변경 권한을 넓히는 일은 따로 결정했습니다.

3. staging에서 검증한 이미지를 운영에 그대로 쓰는 배포 경로

코드에 반영하는 것과 운영에 배포하는 것은 다른 질문입니다. 검사가 통과해도 staging에서 동작한다는 뜻은 아닙니다. staging에서 동작해도 운영에 같은 이미지가 배포된다는 뜻은 아닙니다.

그래서 배포를 네 단계로 나눴습니다.

  1. 검사: 정적 분석, 타입 검사, 단위 테스트를 돌리고, 약속한 데이터 형식(데이터 계약)을 지키는지 보는 계약 테스트도 돌립니다.
  2. 배포 묶음 생성: 반영된 코드로 한 번만 빌드합니다. 배포 묶음에는 코드 버전, 이미지 내용으로 만든 hash인 이미지 digest, 스키마와 인프라 변경 계획, 테스트 결과를 함께 담습니다.
  3. staging 검증: 배포 순서를 줄 세우는 deploy queue 하나가 staging을 한 번에 하나씩만 바꿉니다. 배포 묶음을 적용하고 E2E 테스트(실제 사용 흐름을 처음부터 끝까지 돌리는 테스트)를 돌립니다.
  4. 운영 promotion: staging에서 검증한 이미지를 다시 빌드하지 않고, 같은 digest 그대로 운영에 배포합니다.

deploy queue에서는 아직 시작하지 않은 오래된 묶음만 새 묶음으로 대체합니다. 실행 중이거나 실패한 묶음의 기록은 지우지 않습니다. 판정에 필요한 근거가 없으면 통과로 보지 않고 보류합니다.

스키마와 인프라 변경에는 따로 점검을 두었습니다.

  • ClickHouse 마이그레이션은 배포마다 옛 마이그레이션 전체를 다시 돌리고 있었습니다. 마이그레이션 관리 도구인 Atlas로 바꿔 아직 적용되지 않은 것만 실행하게 했습니다. staging에서 적용해 보고, 한 번 더 실행해도 아무것도 바뀌지 않는 idempotent 상태인지까지 확인했습니다. 마이그레이션이 일부만 적용된 상태가 되면 실행을 멈춥니다. 이때 이미 적용된 것을 rollback하지 않고, 다음 마이그레이션을 새로 만들어 고칩니다.
  • 앱을 배포하기 전에, ClickHouse가 테이블과 컬럼 목록을 보여 주는 system.tables와 system.columns, 그리고 PostgreSQL 스키마 버전이 코드가 기대하는 상태와 맞는지 확인합니다. 맞지 않으면 배포를 멈춥니다.
  • Terraform이 관리하는 인프라 상태 기록(state)은 범위를 정해 두고, 그 범위 안에서만 변경을 적용합니다. 리소스를 삭제하거나 교체하는 내용이 들어간 변경 계획은 따로 살펴 통과 여부를 정합니다.
  • 마이그레이션의 DB 접속은 Cloud SQL IAM 인증으로 바꿔 비밀번호를 쓰지 않게 했습니다.

버린 대안은 두 가지입니다.

  • 변경마다 staging에 따로 배포하는 방식입니다. 늦게 끝난 검증이 다른 변경이 덮어쓴 staging을 통과할 수 있습니다. 그러면 어느 변경의 성공인지 알 수 없습니다.
  • 운영 배포 때 이미지를 다시 빌드하거나 태그를 다시 조회하는 방식입니다. staging에서 검증한 것과 다른 결과가 운영에 배포될 수 있습니다.

4. 시크릿과 에이전트 권한의 범위 정하기

시크릿 관리 도구인 Infisical을 도입해 시크릿 경로를 환경과 서비스별로 나눴습니다.

  • 2026년 6월 Infisical로 옮기면서, GCP Secret Manager에 있던 시크릿 약 40개를 실제로 누가 쓰는지 조사했습니다. 쓰는 곳이 확인된 값은 Infisical로 옮기거나 기존 값과 대조했습니다. 이 과정에서 운영 경로에 staging 계정이 들어 있던 설정 오류를 찾아 바로잡았습니다.
  • GitHub Actions는 저장해 둔 토큰을 쓰는 대신, 실행할 때마다 신원을 확인받는 OIDC 방식으로 인증하게 바꿨습니다. 인증한 뒤 Infisical에서 배포에 필요한 값만 받습니다.
  • 에이전트가 배포 명령을 직접 실행하면 hook에서 막습니다.

버린 대안은 Infisical이 기본으로 제공하는 GCP 동기화를 그대로 쓰는 방식입니다. 이 기능이 이름을 바꾸는 규칙이 기존 GCP 시크릿 이름과 맞지 않았습니다. 그래서 Infisical의 환경, 폴더, 키 이름 조합을 GCP 쪽 대상 시크릿에 하나씩 직접 연결하는 매핑을 만들었습니다. 동기화해도 되는 키만 적은 허용 목록과, 실제로 바꾸기 전에 무엇이 바뀔지 미리 보여 주는 dry-run도 함께 두었습니다.

03설계 결정

위 체계를 만들며 내린 결정 다섯 가지입니다. 고민, 선택지, 결정과 이유, 대가 순서로 적었습니다.

D-01

기준 문서는 저장소에, 작업 맥락은 Linear에

고민
에이전트는 대화가 길어지면 새 대화로 바뀝니다. 처음에는 다음 대화에 긴 인계 요약을 넘겼습니다. 요약을 거칠 때마다 이전 대화의 추측이 사실처럼 굳었습니다. 설계 계획서도 쓴 시점에 멈춰 있었습니다. 표본으로 본 설계 문서는 10개 중 9개꼴로 코드와 어긋나 있었습니다.
선택지
① 인계 요약을 더 꼼꼼하게 쓰기 ② 작업 항목마다 설계 정보를 복사해 두기 ③ 정보를 바뀌는 주기에 따라 나누고, 작업 항목에는 링크만 두기
결정과 이유
③을 골랐습니다. 추측이 굳는 것은 요약을 거듭하며 정보가 조금씩 빠지기 때문입니다. 요약 대신 원래 자료로 가는 링크를 주면 다음 작업자는 매번 원래 자료에서 다시 읽습니다. 복사본은 원문이 바뀌면 낡은 채 남습니다. 설계 계획서는 쓴 시점의 기록으로만 읽게 했습니다.
대가
외부 작업 관리 도구 하나에 기대게 됩니다. 링크만 보고는 단순히 관련된 일인지, 먼저 끝내야 하는 일인지가 흐려질 수 있습니다. 링크를 따라가는 시간도 듭니다.
D-02

완료 보고는 검증의 입력으로만 쓰고, 끝까지 이어진 한 건을 완료로 보기

고민
보고가 많아질수록 확인하지 않은 것이 완료로 적혔습니다. 하위 작업 하나가 끝나자 상위 작업이 자동으로 완료 처리된 적이 있습니다. 결과가 0행, 즉 한 건도 나오지 않았는데 이를 정상으로 보고 성공 처리한 작업도 있었습니다.
선택지
① 완료 표시와 자동 검사 통과를 완료로 보기 ② 보고 형식을 정하고, 완료 판정은 따로 확인한 증거로 하기
결정과 이유
②를 골랐습니다. 보고에는 실행한 검증과 실행하지 않은 검증을 빈칸 없이 적게 했습니다. 완료 표시는 목표 상태를 대신 보여 주는 지표일 뿐이라, 이 표시 자체를 목표로 삼으면 실제 상태와 벌어집니다. 그래서 배포 경로를 바꾸는 작업에서는 무엇을 완료로 볼지 정했습니다. 새 이미지 한 건이 빌드되고, promotion 단계를 거치고, 배포 변경이 Git에 기록되고, 실제로 서비스를 돌리는 컨테이너(Pod)에 반영된 뒤, 화면에서 조회되는 데까지 이어져야 완료로 봤습니다. 운영을 감시하는 작업에서도 확인하지 못한 값을 정상이나 0으로 바꿔 적지 않게 했습니다.
대가
보고를 쓰는 데 시간이 더 듭니다. 작업 상태가 실제보다 늦게 바뀝니다.
D-03

검증 강도는 되돌릴 수 있는가에 맞추기

고민
되돌릴 수 있는 내부 시험에서도 에이전트가 빡빡한 사전 검증을 요구했습니다. 이미 끝난 backfill을 다시 하려 한 적도 있습니다. 이런 일이 병목이 됐습니다. 반대로 운영 변경을 가볍게 넘기면 데이터가 조용히 틀어집니다.
선택지
① 모든 변경을 똑같이 엄격하게 보기 ② 모든 변경을 똑같이 가볍게 보기 ③ 되돌릴 수 있는 정도에 맞춰 검증 강도를 다르게 하기
결정과 이유
③을 골랐습니다. 사람이 판단할 수 있는 시간은 한정돼 있습니다. 그래서 되돌릴 수 없는 지점에 판단을 모았습니다. 내부 시험과 비교 측정은 동작하는지만 확인합니다. 되돌릴 수 없는 운영 변경은 엄격하게 봅니다. 급한 병목을 우회로 푼 뒤의 후속 설계는 작은 결정이라도 멈추고 사람에게 묻게 했습니다.
대가
어디까지 가볍게 보고 어디부터 엄격하게 볼지 매번 판단해야 합니다.
D-04

되돌릴 수 없는 스키마 변경만 막고, backfill은 배포에서 떼어 내기

고민
배포 전 점검 하나가 너무 많은 일을 했습니다. 스키마 변경, 대기, backfill, Materialized View(MV) 중지와 재개, 판정을 한 번에 했습니다. 그 뒤 마이그레이션 도구가 같은 변경을 다시 적용했습니다. cutover 때 가장 느린 단계가 전체를 막았습니다.
선택지
① 배포 전 점검을 더 강하게 만들기 ② 스키마 적용, 짧은 동작 확인, backfill을 세 단계로 나누기
결정과 이유
2026년 8월에 ②를 골랐습니다. 스키마 변경은 되돌릴 수 없고 한 번만 적용돼야 합니다. backfill은 몇 번이고 다시 할 수 있습니다. 성격이 다른 일을 한 조건에 묶으면 가장 느린 일이 전체 속도를 정합니다. 그래서 스키마 적용과 짧은 동작 확인만 배포를 막게 했습니다. backfill은 배포와 따로 뒤에서 돌게 했습니다. 스키마를 바꾸는 도구도 Atlas 하나로 모았습니다. 배포 전 점검은 정상 데이터를 안전하게 처리할 수 있는지만 확인합니다. 운영 데이터에 결함이 하나도 없는지까지 묻지 않습니다.
대가
과거 데이터가 덜 채워진 채로 운영하는 기간이 생깁니다. 그 기간은 0건처럼 보이지 않게 따로 표시해야 합니다. 떼어 낸 backfill 작업도 따로 관리해야 합니다.
D-05

에이전트도 시크릿을 쓰는 주체로 보고, 값은 주입만 하기

고민
에이전트에게 코드 작성, 배포, 조회를 맡겼습니다. 에이전트는 셸과 배포 도구를 씁니다. 시크릿 값이 로그에 찍히거나, 로컬 명령이 검증된 배포 경로를 건너뛸 수 있었습니다.
선택지
① 에이전트가 필요한 값을 직접 조회하기 ② 정해진 실행 스크립트로만 조회하고, 값은 실행할 프로세스에 주입만 하기
결정과 이유
②를 골랐습니다. 에이전트에게도 사람처럼 신원을 주고, 신원마다 볼 수 있는 범위를 정했습니다. 실행 스크립트는 등록된 범위의 키만 꺼냅니다. 값을 보는 일과 쓰는 일을 나누면 값이 대화 기록에 남지 않습니다. Infisical에서 값을 받아 명령을 실행하다 실패해도, 예전 저장소인 GCP Secret Manager의 값으로 바꿔 자동으로 retry하지 않습니다. 실패로 보여도 명령이 이미 실행됐을 수 있어서, 다시 실행하면 같은 명령이 두 번 실행될 수 있기 때문입니다.
대가
권한을 바꿀 때마다 범위와 시간을 좁힌 임시 권한 절차를 거쳐서 느립니다.

04결과

  • 2026년 4월부터 9월까지 팀의 개발 방식에서, AI가 구현한 변경도 자동 검사와 검토를 거친 뒤 사람이 최종 반영했습니다. 조건만 맞으면 자동으로 반영하는 것은 의존성 업데이트 봇에만 허용했습니다.
  • 구현을 맡지 않은 QA 에이전트가 운영에 닿기 전 로컬 검증 단계에서 결함 두 가지를 재현해 수정 작업으로 되돌렸습니다. 하나는 아래 트러블슈팅에서 다룬, Kafka에서 처리하지 못한 메시지를 건너뛰던 결함입니다. 다른 하나는 파일 경로를 검사할 때 파일 이름만 같으면 틀린 경로도 통과시키던 결함입니다.
  • 2026년 6월 말부터 9월 중순까지 쓴 배포 경로에서는, deploy queue를 거쳐 운영에 올릴 때 이미지를 다시 빌드하지 않았습니다. staging에서 검증한 것과 digest가 같은 이미지를 그대로 운영에 배포했습니다.
  • 통과 여부를 판단할 근거가 모자란 배포 묶음은 통과로 보지 않고, 운영에 올리기 전에 보류했습니다. 배포 묶음은 한 번 빌드한 이미지와 스키마 변경 계획, 테스트 결과를 함께 담은 단위입니다.
  • ClickHouse 마이그레이션은 배포마다 옛 마이그레이션 전체를 다시 돌리고 있었습니다. 2026년 7월에 아직 적용되지 않은 것만 실행하는 방식으로 바꿨고, 한 번 더 실행해도 아무것도 바뀌지 않는 idempotent 실행임을 확인했습니다.
  • GitHub Actions의 인증을 저장해 둔 토큰에서 OIDC 방식으로 바꿨습니다. 2026년 7월 운영 환경에서 실제로 OIDC로 인증하는 경로를 거쳐 배포 전 점검 6개를 돌렸고, 6개 모두 통과했습니다.

05트러블슈팅

T-01

QA 에이전트가 재현한 Kafka 메시지 건너뜀

문제
비동기 전달 기능의 Kafka consumer(메시지를 읽는 쪽)를 작업으로 나눠 구현 에이전트에게 맡겼습니다. 구현 작업의 테스트 일부는 통과한 상태였습니다. 그 뒤 QA를 맡은 별도 에이전트가 처리하지 못한 메시지를 건너뛰는 반례를 재현했습니다. offset(읽은 위치) 10을 처리하지 못한 채 다음 poll(메시지를 가져오는 호출)에서 11을 처리하는 경우입니다. 이때 다음에 읽을 위치가 offset 12로 확정될 수 있었습니다. 그러면 offset 10의 메시지는 다시 읽히지 않습니다.
원인
처리하지 못한 레코드가 poll 한 번을 처리하는 함수 안에만 있었습니다. 다음 poll에서는 그 기록이 사라졌습니다. poll을 한 번만 호출하는 테스트로는 이 결함이 보이지 않습니다. 같은 검증에서 처리하지 못한 건수가 누적되지 않고 덮어써지는 결함도 찾았습니다.
해결
수정 방향을 정해 구현 에이전트에게 다시 맡겼습니다. 처리하지 못한 레코드는 다음 poll까지 보존합니다. 보존한 레코드는 새 메시지보다 먼저 다시 처리합니다. offset은 앞에서부터 끊김 없이 처리된 지점까지만 확정합니다. 보존 개수에는 상한을 둡니다. 재검증은 관련 파일 4개와 반례 테스트로 좁혔습니다. 이미 통과한 큰 DB 테스트 묶음을 반복하는 대신 바뀐 부분을 다시 보게 했습니다. 수정한 버전에서 같은 반례, 보존 상한, partition rebalance 시점을 QA 에이전트가 다시 확인하게 했습니다.
결과
운영에 닿기 전, 로컬 검증 단계에서 메시지 건너뜀 결함을 잡았습니다. 실제 Kafka broker에 연결해 운영에서 확인하는 일은 별도 완료 조건으로 두고 따로 확인했습니다. 같은 기능의 Kafka 인프라 작업은 코드가 반영되자 작업 관리 도구에서 자동으로 완료 처리된 적이 있었습니다. 실제 broker 접근 권한, 메시지 송수신, 지연, DLQ(처리에 실패한 메시지를 따로 모으는 queue) 확인 결과가 없어 완료 처리를 되돌렸고, 이 결과를 채운 뒤 완료로 닫았습니다.

06배운 점

완료 판정은 구현자의 보고와 떼어, 따로 확인한 증거로 해야 합니다.

배포 경로도 같은 기준으로 봤습니다. 직접 만든 deploy queue는 9월 중순 이후 실제 배포에 성공하지 못했습니다. 10월에 배포 경로를 Git에 적힌 배포 설정을 기준으로 배포하는 GitOps 방식으로 옮겼고, 도구로는 Argo CD와 Kargo를 씁니다. 지금은 새 이미지가 Kargo의 promotion 단계를 거친 뒤 Argo CD가 이를 적용하는 경로로, staging 배포와 운영 promotion을 모두 운영합니다.

여러 에이전트가 함께 일하는 구조는 개인 오픈소스에서 이어서 다뤘습니다. oh-my-factory는 사람이 목표, 설계 결정, 증거를 승인하고 에이전트는 격리된 환경에서 일하도록 설계한 도구입니다. 목표를 정의하고 측정하는 기능, 작업 항목 관리, 격리된 환경에서 구현하고 판정하는 단계를 만들었습니다. hash chain ledger도 만들었습니다. ledger는 기록을 이어 붙일 때마다 앞 기록의 hash를 함께 남기는 장부라서, 누가 중간 기록을 고치면 알아챌 수 있습니다.
