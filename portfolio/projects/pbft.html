PBFT 합의 엔진과 Go P2P 라이브러리

BFT 합의가 코드에서 어떻게 돌아가는지 확인하려고 만든 학습용 구현입니다. PBFT 합의 엔진은 Cosmos SDK 0.53이 쓰는 ABCI 2.0 인터페이스에 맞췄습니다. 노드 사이 연결을 맡는 P2P 라이브러리는 TCP부터 따로 만들었습니다.

기간
2025.11 – 2025.12
소속
개인 학습 프로젝트, 1인 (대회와 수상 없음)

논문 정리, 설계, 구현, 테스트, 문서 전부 1인 담당

공개 저장소의 학습 구현 (운영 환경에 띄운 적 없음)

01상황: 어떤 프로젝트이고 무엇을 해결하는가

블록체인 노드 안에서 합의와 연결을 맡는 부분을 만들어 본 학습 프로젝트입니다. 세 갈래로 나뉩니다.

  • consensus-study 조직: PBFT 논문 정리, 코드 읽기 노트, PBFT 엔진 구현을 모았습니다.
  • LockFree-p2p-go: 노드끼리 연결하고 메시지를 퍼뜨리는 Go 라이브러리입니다.
  • BFTcd: 같은 시기에 쓴 설계 제안서입니다. 구현은 없습니다.

조직 소개 글에 적은 목표는 PBFT, HotStuff 같은 합의 논문을 읽고 그림으로 정리한 뒤, 작게 구현해 Cosmos SDK에 붙여 돌려 보는 것입니다. PBFT 저장소의 통합 가이드에는 CometBFT 대신 PBFT를 Cosmos SDK 앱의 합의 엔진으로 쓰는 것을 목표로 적었습니다.

해결하려는 문제
합의 엔진을 설정하고 쓰기만 해서는 노드 사이에 메시지가 어떤 순서로 오가는지 알 수 없었습니다. 외부 사용자의 문제가 아니라 제 학습 문제였습니다.
해결 방식
PBFT 3단계와 리더 교체를 직접 구현해 ABCI 2.0 앱에 붙이고, gRPC가 감추는 연결 계층(핸드셰이크, 피어 탐색, 중복 필터)을 TCP부터 만들었습니다.
고른 이유
Cosmos SDK는 합의 엔진과 앱이 ABCI라는 인터페이스로 나뉩니다. 그래서 엔진만 바꿔 끼우는 실험을 할 수 있습니다.

시기 순서는 이렇습니다. 2025년 10월에 Besu 네트워크의 합의를 Clique에서 QBFT로 바꿨습니다. 11월 중순에는 Ignite로 만든 Cosmos SDK 로컬 체인에서 밸리데이터 생성, 위임, jail과 unjail을 명령으로 실습했습니다. PBFT 논문 정리는 11월 말에 시작했습니다.

4노드 테스트가 확인하는 동작은 이렇습니다. 트랜잭션 하나를 넣으면 네 노드가 PBFT 3단계로 합의해 블록을 확정합니다. 그 뒤 네 노드의 앱에서 같은 값이 조회됩니다. 리더가 멈췄을 때 다음 리더로 넘어가는 코드도 작성했습니다. 다만 여러 노드를 띄운 테스트로는 확인하지 않았습니다.

02과제와 역할

스스로 정한 목표는 세 가지입니다.

  1. PBFT 3단계와 리더 교체(view change)를 구현하고, ABCI 2.0 메서드에 맞춰 앱과 연결합니다.
  2. 4노드에서 트랜잭션 하나가 네 노드 모두에 같은 상태로 반영되는지 테스트로 확인합니다.
  3. gRPC가 감추는 연결 계층(핸드셰이크, 피어 탐색, 중복 필터)을 TCP부터 만듭니다.
직접 설계하고 개발
논문 정리, 합의 엔진, 앱 연결 어댑터, 멤풀, gRPC 전송, 메트릭, P2P 라이브러리, 테스트, 문서 전부. 1인 프로젝트라 팀원이 맡은 부분은 없습니다.
범위
테스트 코드를 작성한 범위까지이며, 운영 환경에 띄운 적은 없습니다.

03해결 과정

1. 아키텍처

PBFT 저장소에는 그림 파일이 없어 아래 애니메이션 다이어그램으로 대신합니다. PBFT 노드는 다음 요소로 이루어집니다.

  • 합의 엔진(코드 이름 EngineV2): 합의 메시지와 요청을 채널로 받아 단계별 처리 함수로 보냅니다.
  • 상태 로그: 시퀀스 번호마다 단계와 투표를 기록합니다. 마지막 체크포인트 다음 번호부터 200개 범위의 메시지만 받고, 범위 밖 메시지는 버립니다.
  • view change 관리자: 리더 교체 투표(VIEW-CHANGE)를 모으고 새 view를 만듭니다.
  • 앱 연결 어댑터: 엔진과 앱 사이를 잇습니다. 외부 앱에 gRPC로 붙는 것, 같은 프로세스의 테스트 앱을 부르는 것, 앱 없이 합의만 도는 것 3가지입니다.
  • 멤풀과 트랜잭션 전파 모듈(reactor): 트랜잭션을 모으고 다른 노드 멤풀로 보냅니다.
  • gRPC 전송: 합의 메시지와 트랜잭션을 주고받고, 상태 동기화 요청에 블록을 내어 주는 RPC 8개입니다.
  • 저장소: 블록과 체크포인트를 파일에 쓰고 다시 읽는 코드를 만들고 저장소 단독 테스트를 붙였습니다. 노드 시작 경로에는 아직 연결하지 않았습니다.
  • 메트릭: /metrics로 Prometheus 메트릭 11종을 내보냅니다. 포트는 CometBFT 배치(26656, 26658, 26660)와 맞췄습니다.

P2P 라이브러리는 PBFT 엔진과 별개입니다. 두 코드는 서로 연결하지 않았고, PBFT는 gRPC로 통신합니다. P2P 라이브러리는 다음 모듈로 나뉩니다.

  • TCP 연결(transport)
  • 13바이트 헤더 프레이밍(protocol)
  • 최대 50개 피어 관리(PeerManager)
  • seed와 gossip 피어 탐색(discovery)
  • 중복 필터가 있는 메시지 전파(BroadcastManager)
  • 멤풀

2. 주요 흐름

흐름 1. 트랜잭션 하나가 블록이 되기까지 (4노드, 장애 허용 1, 정족수 3)

  1. 클라이언트가 트랜잭션을 넣습니다. 멤풀이 크기, 중복, 최소 가스 가격, 발신자 nonce를 검사합니다.
  2. 전파 모듈이 트랜잭션을 다른 노드 멤풀로 보냅니다.
  3. 리더가 멤풀에서 최대 500개를 꺼내 앱의 PrepareProposal에 넘깁니다. 앱이 돌려준 목록으로 블록을 만듭니다.
  4. 리더가 PRE-PREPARE를 보냅니다. 각 노드는 보낸 노드가 현재 리더인지 확인합니다. 이어서 ProcessProposal로 앱 검증을 받고 PREPARE를 보냅니다.
  5. PREPARE가 3개 모이면 COMMIT을 보냅니다. COMMIT이 3개 모이면 FinalizeBlock과 Commit으로 블록을 실행합니다.
  6. 멤풀에서 확정된 트랜잭션을 지웁니다. 100블록마다 체크포인트를 만들고 오래된 상태를 지웁니다.

흐름 2. 리더가 멈췄을 때 (코드에 적은 흐름입니다. 여러 노드를 띄운 테스트로는 확인하지 않았습니다)

  1. 각 노드는 PRE-PREPARE를 받을 때마다 10초 타이머를 다시 맞춥니다.
  2. 시간이 지나면 VIEW-CHANGE를 보냅니다. 여기에 자기 체크포인트와 Prepared 증명(PRE-PREPARE와 PREPARE 정족수를 묶은 것)을 싣습니다. 타이머는 두 배로 다시 겁니다.
  3. VIEW-CHANGE가 3개 모이면 새 리더가 될 노드만 NEW-VIEW를 만듭니다. 마지막 체크포인트 뒤로 Prepared까지 간 시퀀스는 PRE-PREPARE를 다시 만들어 NEW-VIEW에 싣습니다.
  4. 다른 노드는 NEW-VIEW를 보낸 노드가 맞는 리더인지, 투표가 정족수인지 확인합니다. 확인을 통과하면 새 view로 넘어갑니다.

흐름 3. P2P 메시지 전파

  1. 연결할 때 핸드셰이크를 주고받습니다. 상대 Nonce가 내 것과 같으면 자기 자신에게 연결한 것이므로 끊습니다.
  2. 메시지를 받으면 xxhash로 해시를 계산합니다.
  3. 처음 본 메시지일 때만 다시 보냅니다. 보낸 피어를 빼고 무작위 7개 피어에 보냅니다.
  4. 본 메시지 기록은 10분 뒤 지웁니다.

3. 설계 고민과 결정

앱을 어떻게 부를 것인가

  • 고민: 처음 만든 엔진은 자체 인터페이스로 앱을 직접 호출했습니다. Cosmos SDK 앱은 ABCI 2.0으로만 통신합니다. 그래서 이 구조로는 실제 앱에 붙일 수 없었습니다.
  • 선택지: 엔진 안에 앱 유무 분기를 넣는 방식, 앱 연결을 인터페이스 뒤로 숨기는 방식.
  • 결정: ABCI 2.0 메서드를 기준으로 엔진을 다시 만들었습니다. 앱 연결은 어댑터 3가지로 나눴습니다. 분기 방식은 테스트와 실제 연결이 서로 다른 코드를 타게 되어 고르지 않았습니다.

트랜잭션 순서는 누가 정할 것인가

  • 고민: 멤풀에 가스 가격 순 정렬이 있었습니다. 엔진이 이 순서대로 블록을 채울 수도 있었습니다.
  • 결정: 엔진은 도착 순서로 꺼내 넘기기만 합니다. 정렬과 거르기는 앱의 PrepareProposal이 하게 했습니다. 잔액과 nonce 같은 상태를 가진 쪽이 앱이기 때문입니다.

빈 블록을 만들 것인가

  • 고민: CometBFT는 트랜잭션이 없어도 일정 간격으로 빈 블록을 냅니다.
  • 결정: 꺼낼 트랜잭션이 없으면 올린 시퀀스 번호를 되돌리고 제안하지 않게 했습니다.
  • 남은 점: 이 때문에 리더가 살아 있어도 view change 타이머가 돌 수 있습니다. 아직 해결하지 않았습니다.

lock-free 자료구조를 쓸 것인가

  • 고민: lock-free가 늘 빠르다고 보지 않았습니다. 큐, 해시맵, 우선순위 큐를 lock-free와 mutex 두 버전으로 만들어 비교했습니다.
  • 측정 결과 (Windows 10, Ryzen 5 3500 로컬 측정)
    • 큐와 우선순위 큐: mutex 쪽이 빨랐습니다. lock-free 큐는 넣을 때마다 힙 할당이 생겼습니다.
    • 해시맵(읽기 75%): lock-free 쪽이 약 2배 빨랐습니다. lock-free 쪽은 직접 만든 Split-Ordered List입니다.
    • 중복 필터: sync.Map과 RWMutex 맵을 따로 비교했습니다. 읽기만 할 때는 sync.Map이 빨랐습니다(RWMutex 27.79 ns, sync.Map 7.74 ns). 쓰기가 많을 때는 RWMutex가 빨랐습니다.
  • 결정: 중복 필터를 RWMutex 맵에서 sync.Map으로 바꿨습니다. 처음부터 sync.Map을 쓴 피어 관리와 mutex와 heap을 쓴 멤풀은 결과와 맞아 그대로 뒀습니다.

중복 필터 해시를 무엇으로 할 것인가

  • 고민: 같은 메시지가 여러 피어에서 들어오므로 받을 때마다 해시를 계산합니다. 이 해시는 위변조 방지가 아니라 중복 판별용입니다.
  • 결정: SHA256 문자열 대신 xxhash 정수를 키로 썼습니다. 해시 계산이 398.9 ns에서 41.24 ns로 줄었습니다. 지금 코드가 쓰는 방식 기준이고, 버퍼를 미리 준비한 직접 호출은 23.22 ns였습니다.

4. 구현 상세

정족수와 단계 전이

  • 정족수는 2*((n-1)/3)+1입니다. 4노드면 3입니다.
  • 리더는 view % 검증자 수번째 검증자입니다. 검증자를 차례로 돌아가는 방식이라 리더가 바뀌는 순서를 예측할 수 있습니다.
  • 투표는 노드 ID를 키로 저장합니다. 같은 표가 두 번 세지지 않습니다.
  • 블록을 실행하기 전에 실행 여부 표시를 먼저 확인합니다. 같은 블록을 두 번 실행하지 않습니다.

메트릭 11종

  • 블록 높이, 현재 view, view change 횟수, 메시지 타입별 송수신 수, 합의와 실행 시간, TPS를 기록합니다.
  • 합의가 멈추면 높이가 서고 view change 횟수가 오르도록 계측했습니다. 메시지 타입별 수신 수로 멈춘 단계를 좁힐 수 있게 했습니다.
  • 엔드포인트와 계측 코드까지 만들었습니다.

P2P 프레이밍과 핸드셰이크

  • 헤더는 Magic 4바이트, Type 1바이트, Length 4바이트, CRC32 4바이트입니다.
  • Magic이 다르면 거절합니다. 길이가 10MB를 넘으면 본문을 읽기 전에 거절합니다.
  • 핸드셰이크에는 전체 주소 대신 리스닝 포트만 보냅니다. IP는 연결에서 알 수 있습니다. 연결에 쓰인 포트는 임시 포트라 다시 연결할 때 쓸 수 없습니다.

5. 같은 시기에 쓴 설계 제안서: BFTcd

PBFT와 P2P를 구현하던 2025년 12월 중순에 설계 제안서를 썼습니다. 코드는 없고 문서와 그림만 있습니다.

제안서가 짚은 문제는 은행 컨소시엄 인프라의 계층 불일치입니다. 블록체인 계층은 BFT 합의를 씁니다. 블록체인 노드를 배포하는 Kubernetes는 상태를 etcd에 둡니다. etcd는 Raft를 쓰고, Raft는 노드가 멈추는 경우만 가정합니다(CFT). 제안서에는 한 은행의 etcd 노드가 잘못된 배포 정보를 보내도 Raft로는 걸러낼 수 없다고 적었습니다.

  • 결정: Kubernetes를 고치지 않도록 etcd API는 두고 합의 층만 HotStuff2로 바꾸자고 제안했습니다.
  • 이유: PBFT는 메시지 수가 노드 수의 제곱으로 늘어납니다. 같은 달에 쓴 비교 글에서 세어 보니, 100노드면 PBFT의 PREPARE와 COMMIT만 19,800개였습니다.
  • 제약: Go로 된 HotStuff2 구현이 없어 Rust 구현을 옮겨야 한다고 적었습니다.

04트러블슈팅

T-01

4노드에서 자기 표가 집계에서 빠지던 문제

문제
4노드 테스트를 붙이며 집계 코드를 다시 보니, 리더가 아닌 노드는 PREPARE를 2개까지만 모을 수 있었습니다. 정족수는 3입니다.
원인
브로드캐스트는 자기 자신에게 보내지 않습니다. 그래서 자기 투표가 집계에서 빠졌습니다. 리더는 PREPARE를 보내지 않으므로 다른 노드 둘의 표만 남았습니다.
해결
PREPARE와 COMMIT을 보낼 때 자기 표를 상태에 먼저 넣게 했습니다. 리더는 PRE-PREPARE를 보낼 때 자기 PREPARE를 넣습니다.
결과
정족수 2f+1에는 자기 표가 들어갑니다. 자기에게 보내지 않는 브로드캐스트를 쓰면, 보낼 때 자기 표를 먼저 집계에 넣어야 합니다.
T-02

가십 전파의 데이터 경쟁

문제
전파 대상을 섞는 난수 생성기 하나를 여러 고루틴이 같이 썼습니다. 같은 날 전파 경로를 손보며 넣은 코드였습니다.
원인
Go의 rand.Rand는 동시 사용에 안전하지 않습니다. 여러 피어의 메시지를 동시에 다시 보내면 같은 생성기를 동시에 건드립니다.
해결
호출마다 지역 난수 생성기를 쓰게 했습니다. 같은 때 본 메시지 기록 전체를 훑던 정리 함수를 없애고 10분 만료 정리에 맡겼습니다.
결과
여러 고루틴이 같이 쓰던 난수 생성기를 없앴습니다. 호출마다 지역 생성기를 쓰는 방식은 전역 rand.Shuffle보다 빨랐습니다(84.71 ns에서 55.78 ns).

05결과

  • 수상과 배포는 없습니다. 공개 저장소의 학습 구현입니다.
  • PBFT 4노드 시나리오 테스트를 작성했습니다. localhost gRPC로 4노드를 띄우고 한 노드에 트랜잭션을 넣습니다. 그 뒤 10초 안에 네 노드가 같은 값을 돌려주는지 봅니다.
  • PBFT 통합 테스트 10개와 단위 테스트 11개를 작성했습니다.
  • P2P 라이브러리에는 테스트 25개와 벤치마크 41개를 작성했습니다.
  • P2P 해시 계산과 중복 확인 구간이 418.0 ns에서 167.6 ns로 줄었습니다. 메시지당 할당은 160 B에서 32 B가 됐습니다(SHA256과 RWMutex 맵에서 xxhash와 sync.Map으로 교체, 로컬 마이크로벤치마크, 전파와 네트워크 왕복 미포함).

남은 범위

  • 메시지 서명 검증을 합의 경로에 연결하지 않았습니다.
  • 실제 Cosmos SDK 앱이 아니라 프로세스 안의 키-값 앱으로 테스트했습니다.
  • 리더 교체(view change)는 단위 테스트로만 확인했습니다. 리더를 멈추는 다중 노드 테스트는 없습니다.
  • 블록 저장과 재시작 복구 코드를 노드에 연결하지 않았습니다.
  • 상태 동기화는 블록을 내어 주는 쪽만 있습니다. 다른 노드에 요청하는 쪽은 없습니다.
  • P2P 라이브러리와 PBFT 엔진은 연결하지 않았습니다.

06배운 점

"2f+1개를 모은다"는 문장에 자기 표가 들어간다는 것을 4노드 테스트를 붙이며 알았습니다.

lock-free 큐는 mutex 큐보다 느렸습니다. lock-free 쪽이 빨랐던 것은 읽기가 대부분인 해시맵뿐이었습니다. 자료구조는 읽기와 쓰기 비율을 재고 고릅니다.

블록 높이, view, view change 횟수 같은 지표가 엔진의 어떤 상태에서 나오는지 코드로 확인했습니다. 그래서 높이가 멈췄을 때 볼 순서가 생겼습니다. view change 횟수를 먼저 보고, 메시지 타입별 수신 수로 멈춘 단계를 좁히는 순서입니다.
