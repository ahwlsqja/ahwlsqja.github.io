CDP 방문자 신원과 데이터 모델 설계와 개발

브라우저 이벤트를 세션, 방문자, 사람 단위로 묶는 신원 모델을 설계했습니다. 그 모델에 맞춰 브라우저 SDK의 세션, ClickHouse 저장 구조, 신원 계산 배치를 개발했습니다.

01상황과 역할

B2B 서비스처럼 구매까지 몇 주가 걸리는 업종이 있습니다. 이런 업종의 방문자는 광고로 들어와 여러 번 다시 오고, 탭을 여러 개 열고, 마지막에 문의를 남깁니다. 이 흐름을 광고부터 문의까지 이어 보여 주려면 먼저 "이 이벤트는 누구의 것인가"를 정해야 했습니다.

기존 방식은 핑거프린트 값을 그대로 방문자 ID로 썼습니다. 광고 차단기가 핑거프린트 스크립트를 막으면 그 브라우저는 식별에서 통째로 빠졌습니다.

세션도 자주 끊겼습니다. 처음에는 30분 동안 움직임이 없으면 세션이 끊겼습니다. 점심을 먹고 돌아온 사람은 새 직접 유입으로 잡혔습니다. 동료가 탭이 열려 있는 동안만 유지되는 세션(탭 세션)으로 바꾼 뒤에는 탭마다 세션이 따로 생겼습니다. 탭 세션의 수명은 중앙값이 3분도 되지 않았습니다.

맡은 일
이벤트, 세션, 방문자의 의미를 정하고, 그 정의에 맞춰 브라우저 SDK의 세션, ClickHouse 저장 구조, 신원 계산 배치를 설계하고 구현했습니다.
동료
탭 세션의 첫 구현, 고객사별 세션 설정, 화면을 맡았습니다. 사람 단위 연결의 큰 방향도 동료가 정했습니다.
AI 에이전트
조사와 코드 작성에 AI 코딩 에이전트를 함께 썼습니다. 방향 결정과 운영 데이터 검증은 직접 했습니다.

02해결 과정

1. 신호가 끊기는 시점에 맞춰 층 나누기

탭 세션은 탭을 닫으면 끝납니다. 브라우저 저장소에 둔 ID는 Safari가 저장소를 지우면 끝납니다. 운영 데이터로 확인해 보니, iOS Safari에서 같은 핑거프린트로 돌아온 방문 중 브라우저 저장소가 비어 있던 비율은 3~7일 만에 온 경우 약 24%, 7~14일 만에 온 경우 약 49%였습니다. 데스크톱은 같은 구간에서 10% 안팎이었습니다.

그래서 신원을 이벤트 → 공유 세션 → 브라우저 묶음 → 방문자 → 사람의 다섯 층으로 나누어 설계했습니다. 공유 세션은 같은 고객사 사이트에서 같은 브라우저의 모든 탭이 함께 쓰는 세션입니다. 층마다 쓸 수 있는 근거를 따로 정했습니다.

  • 브라우저 묶음은 같은 브라우저에서 나온 것이 확실한 세션들을 모은 단위입니다. 같은 공유 세션, 같은 탭에서 30분 안에 이어진 세션, 서명된 1회용 토큰으로 넘긴 도메인 이동만 근거로 씁니다.
  • 핑거프린트는 ID로 쓰지 않습니다. 저장소가 지워져 끊긴 브라우저 묶음을 한 단계만 잇는 데 씁니다. A와 B, B와 C가 이어져도 A와 C는 잇지 않습니다.
  • 사람은 문의 연락처나 주문처럼 확정된 값이 있을 때만 붙입니다.

버린 대안은 두 가지입니다.

  • PostHog처럼 식별하는 순간 이벤트마다 사람 ID를 기록해 두는 방식입니다. 소스 코드를 읽어 보니 잘못 합친 결과를 되돌리기 어려웠습니다. 핑거프린트는 틀릴 수 있는 단서입니다. 그래서 원본은 그대로 두고, 버전마다 처음부터 다시 계산하는 쪽을 택했습니다.
  • 연결을 끝까지 따라가 묶는 방식입니다. 한 고객사의 30일 데이터에서 핑거프린트 470개가 한 덩어리로 이어졌습니다. 너무 많은 핑거프린트에 걸린 값은 연결에 쓰지 않고, 각 핑거프린트를 중심 하나에만 붙이는 별 모양으로 제한했습니다. 이 규칙으로 운영 데이터를 시뮬레이션하자 가장 큰 덩어리가 핑거프린트 7개로 줄었습니다. 별 모양으로 제한해서 더 잃는 연결은 약 3%였습니다.

2. 세션과 유입 나누기

공유 세션은 탭을 새로 열거나 시간이 지나도 바꾸지 않습니다. 새 광고나 검색으로 들어오면 세션은 그대로 두고 유입만 하나 더 남깁니다.

SDK는 IndexedDB에 고객사별로 세션을 둡니다. 기존 세션 조회와 새 세션 생성은 readwrite 트랜잭션 하나로 처리합니다. 그래서 탭 여러 개가 동시에 열려도 세션은 하나만 생깁니다.

SDK는 세션을 시작하는 이벤트를 브라우저에 보관해 둡니다. 수집 서버가 큐에 받은 (세션, 이벤트) 쌍을 202 응답에 담아 돌려줘야 보관한 이벤트를 지웁니다. HTTP 응답이 성공이라는 것과 큐에 실제로 들어갔다는 것은 다르기 때문입니다.

3. 같은 이벤트가 한 행으로 모이도록 키 바꾸기

원본 이벤트 테이블은 ReplacingMergeTree(ingested_at)이고, 정렬 키는 (고객, 이벤트)였습니다. 이 엔진은 병합할 때 정렬 키가 같은 행을 하나만 남깁니다. 그래서 다른 세션에서 같은 event_id가 오면 서로 덮어쓸 수 있었습니다.

정렬 키를 (고객, 세션, 이벤트)로 바꿨습니다. 운영 테이블 7개는 새 키로 복사한 뒤 교체했고, 연결된 파생 집계 19개는 그대로 유지했습니다.

4. 신원 계산을 다시 돌릴 수 있는 배치로 옮기기

처음에는 Flink 안에서 세션을 실시간으로 잇는 안을 냈습니다. 그런데 신원은 여러 날의 세션을 함께 봐야 합니다. 규칙이 바뀌면 전체 이력을 다시 계산해야 합니다. 그래서 신원 계산은 Flink 밖에서 원본을 읽는 배치에 두기로 했습니다.

Flink 쪽은 신원 계산에 쓸 기록을 별도 토픽으로 내보내도록 메시지 형식을 정했습니다. 이 기록에는 핑거프린트 같은 식별 값을 싣지 않고, 어느 세션에 어떤 신호가 몇 번 왔는지만 담습니다.

그 첫 단계로, 지금 쓰는 세션 신원 규칙을 하루 한 번 버전 단위로 미리 계산하는 Go 배치를 만들었습니다. 화면을 그릴 때마다 원본을 읽으면, 큰 고객사는 조회 한 번에 약 3.8GiB를 읽어 요청 한도 2GiB를 넘었기 때문입니다. 지금 규칙은 세션 안의 첫 핑거프린트 성공값을 방문자로 보고, 없으면 캐시에 남은 방문자 값, 그것도 없으면 세션 ID를 씁니다.

적재가 끝나면 행 수를 다시 읽어 보낸 수와 맞춥니다. 직전 버전보다 1% 넘게 줄지 않았을 때만 완료 표시를 남깁니다. 읽는 쪽은 완료 표시가 있는 최신 버전만 봅니다. 그래서 실패한 실행은 화면에 닿지 않습니다.

브라우저 묶음과 방문자 계산은 결과를 버전마다 따로 두도록 설계했습니다. 화면은 포인터가 가리키는 버전만 읽습니다. 잘못 묶은 것이 드러나면 포인터만 직전 버전으로 돌리는 구조입니다.

03결과

  • 핑거프린트 하나에 세션이 2개 이상 붙은 비율 약 27% → 약 3% (공유 세션 도입 전후, 같은 길이 5.5일 구간 비교, 운영)
  • 공유 세션의 약 40%가 유입 2개 이상, 약 26%가 탭 2개 이상을 한 세션에 담음 (같은 기간, 운영)
  • 운영 테이블 7개를 온라인 복사 후 새 키 테이블로 교체, 연결된 파생 집계 19개 유지 (2026.09, 운영)
  • 교체 뒤 다시 적재한 고객과 세션 조합을 새 키로 대조, 복사 누락 0
  • 신원 계산 배치의 계산식이 기존 조회 결과와 대상 고객사 전체 이력에서 100% 일치, 대상 중 가장 큰 고객사 1회 계산 약 3초 (운영 데이터 읽기 전용 측정)

규칙을 비교하기 전에 입력이 온전한지부터 확인해야 합니다. 이 작업에서는 수집 결함이 규칙 차이보다 10배 넘게 컸습니다.

04트러블슈팅

T-01

첫 페이지가 공유 세션에 들어가지 않던 문제

문제
9월 20일과 22일에 걸쳐 운영 중인 모든 고객사에 공유 세션을 켰습니다. 일주일 뒤 확인해 보니 첫 페이지의 약 65%가 공유 세션으로 이어지지 않았습니다. 광고 클릭과 문의가 서로 다른 세션에 남아, 광고 전환이 직접 유입처럼 보일 수 있었습니다. 세션 수도 고객사에 따라 약 7~23% 부풀었습니다.
원인
SDK는 페이지를 열 때 브라우저에 캐시된 고객사 설정을 보고 세션 방식을 고릅니다. 이 캐시는 24시간 동안 유효합니다. 처음 온 방문은 캐시가 없고, 마지막 방문 뒤 하루가 지난 재방문은 캐시가 만료돼 있었습니다. 이런 방문은 첫 페이지를 탭 세션으로 시작했고, 새로 받은 설정은 둘째 페이지부터 적용됐습니다. 켜기만 하면 첫 페이지부터 공유 세션이 될 거라고 봤는데, 그 예상이 틀렸습니다.
해결
처음에는 설정을 최대 2초 기다리는 안을 설계했습니다. 하지만 기다리는 동안 페이지를 떠나는 방문은 여전히 놓쳤습니다. 공유 세션은 새로 모으는 정보 없이 브라우저에 난수 ID 하나를 두는 일입니다. 그래서 고객사별로 원격에서 끄는 기능을 포기하고, 배포하는 SDK에서 공유 세션을 항상 켜기로 했습니다. 실제 배포 파일로 Chrome에서 네 경우를 재현해 확인했습니다. 광고를 눌러 처음 들어온 페이지, 새 탭, 설정이 늦게 도착한 경우, 꺼짐 설정이 캐시에 남은 경우입니다. 이전 SDK는 롤백용으로 남기고 10월 2일 운영에 배포했습니다. 이미 갈라진 과거 세션은 원본을 고치지 않습니다. 같은 탭에서 30분 안에 이어진 두 세션을 같은 브라우저 묶음으로 보는 규칙을 신원 설계에 넣었습니다.
결과
같은 측정에서 신원 규칙끼리의 방문자 수 차이는 2% 이내였습니다. 수집과 적재 결함이 만든 차이는 지표에 따라 20~80%였습니다. 세션 집계는 원본 세션의 약 20%를 빠뜨렸고, 새로 생긴 공유 세션의 약 80% 앞에는 같은 탭의 탭 세션이 붙어 있었습니다. 입력 쪽 오차가 규칙 차이보다 10배 이상 컸습니다. 그래서 새 신원 규칙을 기존 규칙과 나란히 돌려 비교하는 일은, 첫 페이지 수정과 집계 누락 해결이 끝난 뒤 시작하도록 순서를 바꿨습니다.
