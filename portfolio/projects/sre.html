Professional수파리드운영 중

장애 탐지, 1차 진단, 심각도 판정을 자동화한 SRE 에이전트

수파리드의 데이터 수집 파이프라인을 5분마다 점검해 이상 신호를 incident로 묶고, AI가 근거를 붙인 1차 진단을 남기고, 심각도를 P0, P1, P2로 판정해 등급에 맞는 방식으로 알리는 서비스를 혼자 설계하고 운영합니다. 사람을 24시간 호출하는 등급은 P0 하나뿐이고, 그 호출은 기존 paging 경로가 맡으며, 복구는 사람이 직접 실행합니다.

01한 줄 요약

파이프라인이 조용히 멈추는 것을 5분 안에 알아채고, 사람을 깨울 일과 아닌 일을 코드로 가려내는 SRE 서비스를 만들어 운영하고 있습니다.

수파리드는 사이트에서 발생하는 이벤트를 Kafka와 Flink로 처리해 ClickHouse에 쌓습니다. 이 서비스는 그 경로의 지표를 5분마다 읽어 이상 신호를 incident 하나로 묶고, AI가 근거를 붙여 1차 진단을 남깁니다. 그다음 심각도 등급에 따라 사람에게 전달하는 방식을 달리합니다. 사람이 판단할 장애는 드물기 때문에 반복해서 지표를 보는 일과 1차 진단은 서비스가 하고, 사람은 결정만 합니다.

  • 1사람을 24시간 호출하는 등급, P0 하나
  • 1상태를 두는 곳, incident 원장 한 곳
  • 0서비스가 스스로 실행하는 복구, 꺼 둠
  • 5분지표를 읽는 주기
맡은 일
혼자 맡은 프로젝트이고, 사내 서비스로 제가 직접 운영하고 있습니다. 알림 등급 정책, 저장 구조, AI의 권한 범위를 설계했습니다. 구축, 배포, rollback, 운영 투입 판단도 제가 했습니다.

02왜 만들었나

새 실시간 파이프라인은 HTTP 응답과 Pod 상태가 모두 정상인 채로 데이터가 중간에서 멈출 수 있어서, 기존 경보로는 장애가 보이지 않았습니다.

수신 서버는 Kafka가 기록을 확인한 뒤에야 HTTP 200을 돌려줍니다. 그래서 그 뒤에 있는 Flink가 멈추거나 ClickHouse 적재가 밀려도 수신 서버는 계속 200을 응답하고, Pod도 Ready 상태를 유지합니다. 장애는 응답 뒤의 단계에 숨고, Flink checkpoint가 앞으로 나가는지, INSERT가 얼마나 오래 걸리는지, partition lag이 쌓이는지를 직접 읽어야 보입니다.

반대쪽 문제도 있었습니다. 기존 방식은 dead letter queue에 메시지가 한 건만 들어와도 사람을 깨웠습니다. 신호는 많고 사람이 판단할 장애는 드문데 호출이 잦으면, 정말 급한 호출의 무게가 떨어집니다.

그래서 세 가지를 요구사항으로 잡았습니다.

  1. 응답 뒤의 단계를 직접 읽는다

    HTTP 상태나 Pod 상태가 아니라 처리가 실제로 진행되는지를 나타내는 지표를 읽습니다.

  2. 사람을 부르는 기준을 등급으로 나눈다

    무엇이 사람을 깨울 일인지 미리 정의하고, 그 기준이 모델이나 신호의 판단에 흔들리지 않게 합니다.

  3. 1차 진단은 서비스가 한다

    사람이 열었을 때 이미 근거가 붙은 가설이 있게 하되, 복구까지 자동으로 하지는 않습니다.

03전체 구조와 흐름

서비스는 지표를 읽는 관측 Job, 상태를 보관하는 incident 원장, 진단과 알림을 맡는 부분으로 나뉘고, 상태는 원장 한 곳에만 둡니다.

구성 요소

  • 관측 Job. Cloud Scheduler가 5분마다 Cloud Run Job을 실행합니다. Job은 Managed Prometheus에서 고정된 PromQL 28개를 Google OIDC로 인증해 읽고, 질의문의 해시를 대조해 정해진 질의만 실행되게 합니다. ClickHouse는 직접 질의하지 않습니다. 감시 질의가 감시 대상에 부하를 주지 않게 하려는 선택입니다.
  • 수신 Worker와 incident 원장. Cloudflare Worker가 서명과 본문 크기를 확인하고, 조직마다 하나인 Durable Object에 신호를 넘깁니다. 이 Durable Object가 SQLite로 신호, incident, 근거, 작업, 알림 outbox, 모델 비용 예산을 함께 기록하는 원장입니다.
  • 작업 Queue와 AI 진단. 진단 작업은 Queue로 at-least-once 전달됩니다. 먼저 한 모델이 근거를 읽고 원인 가설을 만들고, 두 번째 모델이 그 가설을 정해진 형식으로 다시 검토해 판정합니다. 가설이 검토 없이 굳지 않게 하려는 구성입니다.
  • 알림과 기록. Slack에는 멘션 없는 스레드와 평일 17시 요약을 보내고, 추적이 필요한 것은 Linear에 기록합니다.

데이터 흐름

지표가 원장에 들어오면 신호 중복 제거, incident 갱신, 진단 작업 생성, 알림 outbox 기록이 한 트랜잭션 안에서 끝납니다. 알림은 이 outbox에서 꺼내 보내므로 incident는 기록됐는데 알림은 사라지는 경우가 생기지 않습니다.

이 구조를 고른 이유

상태를 한 곳에 두고 싶었습니다. 조직마다 Durable Object를 하나 두면 한 조직의 모든 쓰기가 하나의 스레드에서 순서대로 처리되어 동시성 문제가 사라집니다. 처음 비교한 다른 안은 Cloudflare D1, Workflows, Agents SDK를 조합하는 것이었는데, 세 실행 계층마다 retry와 상태 규칙이 따로 있어 장애 시 어느 계층이 진실인지 따져야 했습니다. 그래서 하나의 원장에 SQLite 트랜잭션으로 쓰는 쪽을 골랐습니다.

04P0, P1, P2 체계

사람을 24시간 호출하는 등급은 P0 하나뿐이고, 등급은 신호나 AI가 아니라 서버의 규칙으로 정해집니다. 규칙이 보는 축은 두 가지로, 고객 영향이 확인됐는지와 손실을 되돌릴 수 있는지입니다.

표 1. 등급별 정의, 전달 방식, 그렇게 정한 이유
등급정의누구에게, 언제기준과 이유
P0개인정보, credential, 고객 간 데이터 노출. 확인된 데이터 유실. 고객 영향이 확인된 핵심 수집 중단. 근거가 있는 임박한 비가역 손실.on-call 담당자를 24시간 호출합니다. 호출은 기존 paging 경로가 하고, 이 서비스는 incident 채널에 복사본만 남깁니다.정말 급한 일에만 사람을 깨웁니다. 호출 경로를 새로 만들지 않고 기존 경로를 그대로 두어, 같은 일로 두 번 울리는 것을 막았습니다.
P1고객 영향 가능성이 있는 문제, 행 단위 데이터 품질 문제, 회복 가능한 적체.멘션 없는 Slack 스레드에 남깁니다. 사람의 결정이 필요하면 업무시간 09시부터 18시 KST에 결정 카드를 보냅니다.영향이 아직 확인되지 않았거나, 영향이 있어도 원본이 남아 있어 되돌릴 수 있습니다. 밤에 깨울 이유가 없어서 결정은 업무시간으로 돌립니다.
P2기본 등급. 추세, 용량, 준비 상태, 관측 공백.평일 17시 KST 요약 1건에 최대 20개 항목까지 모아 보냅니다.모르는 것과 관측 공백은 사람을 깨울 근거가 아니라 점검 목록입니다.

P0를 좁게 정의한 방식

P0는 조건을 가장 엄격하게 두었습니다. 핵심 수집 중단은 입력 중단, 완료 중단, 관측자 정상, 이렇게 세 가지 확인 자료가 같은 시간 창에서 5분 이상 중단을 덮을 때만 P0가 됩니다. 관측자가 정상이라는 확인을 함께 요구하는 이유는, 관측 자체가 죽어서 값이 없는 상황을 파이프라인 장애로 오해하지 않기 위해서입니다. 핵심 수집이 멈추면 모든 고객의 데이터가 함께 빠지므로 이를 고객 영향이 확인된 것으로 봅니다. 데이터 유실은 유실이 확인됐을 때만, 고객 간 노출은 위반이 확인됐을 때만 P0입니다. 값을 모르는 상태나 지표 공백만으로는 P0가 되지 않습니다.

P1과 P0를 가르는 기준

같은 적체도 되돌릴 수 있는지에 따라 등급이 달라집니다. 회복 가능한 적체는 원본이 Kafka에 30일 동안 남아 있어서 아침에 처리해도 잃는 것이 없으므로 P1입니다. 되돌릴 수 없게 된다는 근거가 있으면 임박한 비가역 손실이어서 P0입니다. 고객 영향이 확인됐는지, 손실을 되돌릴 수 있는지, 그리고 되돌릴 수 없게 되기까지 시간이 얼마나 남았는지를 보고 등급을 정합니다.

등급, 전달, 실행 권한을 따로 둔 이유

기존 방식은 "심각하다"와 "지금 사람을 깨운다"와 "자동으로 고친다"가 한 판단에 섞여 있었습니다. dead letter queue에 한 건만 쌓여도 사람이 깨는 것이 그 결과였습니다. 그래서 심각도 등급, 누구에게 언제 전달할지, 어떤 조치를 실행할 권한이 있는지를 서로 다른 규칙으로 나눴습니다. 이렇게 하면 등급을 올려 달라는 압력이 실행 권한으로 번지지 않습니다.

아래 그림은 같은 규칙을 판정 순서로 그린 것입니다. 위에서 아래로 내려가며 먼저 걸리는 등급이 확정됩니다.

예시, 가상의 P1 스레드 문구

적재 단계 정체가 의심됩니다.

최근 15분 동안 INSERT 경과 시간이 계속 늘고 있습니다. 지금까지의 판단은 기술적 가설이며, 고객 영향은 확인되지 않았습니다. 근거는 저장된 수집 자료 3건입니다.

사람이 할 일은 없습니다. 5분 뒤 자동으로 다시 평가하고, 결정이 필요해지면 업무시간에 알립니다.

05incident 생애주기

incident는 감지, 묶기, 재평가, 해소, 기록의 다섯 단계를 거치고, 사람이 개입하는 지점은 코드로 제한했습니다. 그림 3은 같은 흐름을 상태 이름으로 그린 것입니다.

  1. 감지

    5분마다 읽은 자료를 판정에 쓰려면 5분 안에 들어온 자료여야 하고, 질의 창이 완전해야 합니다. 조건을 채우지 못하면 판정을 보류합니다.

  2. 묶기

    환경, 서비스, 증상 묶음, 영향 범위가 같은 신호는 새 incident를 만들지 않고 기존 incident를 갱신합니다. 같은 원인으로 알림이 여러 번 울리는 것을 막기 위해서입니다.

  3. 재평가

    incident는 한 번 정한 등급에 고정되지 않습니다. 시간이 지나면 같은 자료로 등급을 다시 계산합니다. 재평가 간격과 기한은 P0가 60초와 5분, P1이 5분과 1시간, P2가 15분과 6시간입니다. 재발은 15분 쿨다운이 지난 뒤에만 기존 incident에 새 조사 기회를 만듭니다. 같은 incident의 조사는 3회까지로 제한됩니다.

  4. 해소

    P0는 사람이 해소해야 닫힙니다. 그 밖의 등급은 회복이 검증되어야 닫힙니다. 기술 조건이 풀린 것과 고객이 회복한 것은 따로 보며, 회복이 검증되지 않은 상태에서 서비스가 스스로 해소하지 않습니다.

  5. 기록

    모든 단계는 원장에 남고, 사람이 읽을 형태로 Slack 스레드, Linear, 일일 요약에 나갑니다. 결정을 기다리는 incident에는 누구의 책임 범위인지와 기한을 함께 보여 줍니다.

06AI 진단과 사람 판단

AI는 저장된 근거를 읽고 가설을 세우고 조치를 제안하는 데까지 하고, 복구 실행과 책임은 사람이 집니다.

표 2. AI와 사람의 역할 경계
단계AI가 하는 일사람이 하는 일
조사저장된 수집 자료와 승인된 런북 목록만 읽고 원인 가설을 만듭니다. 빈 결과 확인이나 재조회 같은 일상 조사는 사람에게 묻지 않고 직접 처리합니다.가설을 읽고 맞는지 판단합니다.
검토두 번째 모델이 가설을 정해진 형식으로 다시 검토해 판정을 내립니다.판정이 어긋나 보이면 결정 카드에서 바로잡습니다.
등급등급을 제안할 수 있지만 확정하지 못합니다.정책 규칙을 설계하고 바꿉니다. 서버는 이 규칙으로 등급을 다시 계산합니다.
복구복구 방법을 제안합니다. secret과 실행 권한은 받지 않습니다.제안을 승인하고 외부에서 직접 실행합니다. 승인은 기록만 만들고 서비스가 실행하지 않습니다.

AI가 한 말을 어떻게 믿을 수 있게 했나

AI가 낸 주장은 입력으로 준 수집 자료의 ID를 인용해야 하고, 한 주장에 최대 8개까지만 인용할 수 있습니다. 존재하지 않는 근거를 만들어 인용하면 검증에서 걸립니다. 입력으로 들어온 수집 자료는 믿을 수 없는 관측 데이터로 취급해서, 그 안에 지시문이 섞여 있어도 따르지 않습니다.

한도와 비용

한 incident에서 모델 조사는 3회까지, 모델 호출은 한 번에 60초까지, 하루 모델 비용에는 상한을 두었습니다. 모델을 부르기 전에 그 호출이 쓸 수 있는 최대 비용을 예산에서 먼저 떼어 둡니다. 하루 한도 안에서 호출 가능한 횟수가 정해져 있어서, 오류가 반복되어도 비용이 한도를 넘지 못합니다.

복구 실행기를 꺼 둔 이유

복구 실행기는 구현해 두었지만 정책으로 꺼 두었습니다. 모델 두 개가 같은 의견을 내거나 사람이 Slack에서 확인 응답을 누르는 것은 실행 권한이 아니라고 정의했습니다. 진단이 틀렸을 때 피해가 비가역적일 수 있는 조치를 서비스가 스스로 하게 하지 않고, 사람이 판단한 뒤 외부에서 실행하게 했습니다. 대가는 복구가 사람의 속도에 묶인다는 점입니다. 아직 서비스가 스스로 고치게 만들 만큼 진단의 신뢰를 쌓지 못했다고 판단했습니다.

07false positive 줄이기

오탐은 임계값을 조이기 전에, 판정에 쓰는 자료를 믿을 수 있는지부터 검사해서 줄였습니다.

감지기가 보는 조건은 간단합니다. 어려운 부분은 오래되었거나 불완전한 자료로 정상을 장애로 읽는 것입니다. 그래서 판정 앞에 자료 검사를 두었습니다.

표 3. 오탐을 막는 장치와 막으려는 상황
장치막으려는 오탐
자료 신선도 5분5분보다 오래된 자료로 지금의 상태를 판정하는 일.

P0의 세 가지 확인한 지표의 일시적 이상이 곧바로 호출로 이어지는 일.

수집 시각 jitter 보정수집 주기의 경계에서 시각이 조금씩 흔들려 같은 상태가 반복 알림되는 일.

모든 감지 결과는 "기술 가설"로 표시합니다. 고객 영향, 데이터 유실, SLO 위반은 별도로 확인되기 전까지 미확인으로 둡니다. 감지기가 본 것과 사람이 알아야 할 것을 구분해서, 확인하지 못한 것을 사실처럼 말하지 않게 했습니다.

ClickHouse 알림 정책의 임계값은 알림 채널에 연결하지 않은 상태에서 실제 지표와 대조해 정했습니다. 시간대별 트래픽에 맞춰 움직이는 기준선은 쓰지 않고, 고정 조건과 자료 검사로 판정합니다.

08신뢰성 장치

알림 서비스가 거짓말을 하거나 침묵하면 신뢰를 잃기 때문에, 서비스가 죽는 경우와 같은 알림이 반복되는 경우를 먼저 설계했습니다.

R-01

감시자는 감시 대상 밖에 둔다

문제
감시 서비스가 파이프라인과 같은 클러스터에 있으면, 클러스터가 죽을 때 서비스도 함께 죽어 아무도 모릅니다.
선택지
① 서비스가 자기 heartbeat를 스스로 확인합니다.
② 클러스터 밖의 Cloud Monitoring이 heartbeat를 확인합니다.
결정과 이유
②를 골랐습니다. 파이프라인의 heartbeat는 클러스터 밖에서 확인하고, 이 경보는 서비스를 거치지 않고 Slack으로 바로 나갑니다. 감시자 자신이 죽은 경우만을 위한 유일한 예외입니다. 서비스 안에도 5분마다 도는 watchdog을 따로 두었습니다.
대가
경보 경로가 하나 더 생깁니다. 그래서 이 경로는 긴급 경보에만 허용하고, 주의 경보는 서비스의 등급 규칙을 거치게 했습니다.
R-02

알림은 기록과 같은 트랜잭션에 넣는다

문제
incident는 저장됐는데 알림 전송이 실패하면, 사람은 모르고 서비스는 보냈다고 믿습니다.
결정과 이유
incident 갱신과 알림 outbox 기록을 한 트랜잭션에 묶고, alarm으로 깨어나는 relay가 outbox를 읽어 보냅니다. 기록이 있으면 전송 대상도 반드시 있습니다.
대가
전송이 at-least-once가 되어 같은 알림이 다시 나갈 수 있어서, R-04의 중복 방지가 필요해집니다.
R-03

늦게 끝난 AI 응답은 버린다

문제
Queue는 같은 작업을 두 번 줄 수 있고, 모델 호출은 오래 걸립니다. 먼저 시작한 낡은 호출이 나중에 끝나 새 결과를 덮을 수 있습니다.
결정과 이유
작업을 받을 때 늘어나는 fencing token을 주고, 결과를 반영할 때 token과 상태 version을 다시 확인합니다. 어긋나면 버립니다. 쓰기 충돌은 최대 3번까지 다시 시도합니다.
대가
버려진 호출만큼 모델 비용이 헛듭니다. 그래서 비용은 호출 전에 예약합니다.
R-04

중복 알림을 막는다

문제
외부 호출이 timeout 나면 보냈는지 못 보냈는지 알 수 없습니다. 다시 보내면 중복이 되고 안 보내면 누락입니다.
결정과 이유
Slack과 Linear 호출이 timeout 나면 다시 보내지 않고, 먼저 읽어서 전송 여부를 확인합니다. 확인 전까지는 알 수 없음 상태로 둡니다. 같은 incident에서 이미 보낸 알림이나 요약 항목이 있는지 보고, Slack 확인 응답도 중복에 안전하게 처리합니다. 진행 알림은 처음 읽은 상태를 기준으로 저장해 과거 사건을 다시 알리지 않습니다.
대가
확인 전까지 상태가 잠시 불확실합니다. 누락과 중복 가운데 더 나쁜 쪽을 피하려고 이 불확실함을 받아들였습니다.

입구에서도 막습니다

수신하는 본문은 64KB까지만 받고, 거부된 요청의 기록은 최근 50건만 남겨 원장이 비정상 입력으로 불어나지 않게 했습니다.

09운영 상태와 배운 점

서비스는 production 한 곳에서 운영 중이고, 자연 발생한 incident로 진단부터 기록까지 이어지는 것을 확인했습니다.

지금 상태

  • production 한 곳에서 5분마다 PromQL 28개를 읽고 있습니다. 값이 비어 있는 질의는 0이 아니라 값 없음으로 기록합니다.
  • 10월 10일에 수신 오류 감지기가 자연 발생한 P2 incident를 잡았습니다. 이 incident가 두 모델을 거쳐 Linear 기록까지 통과했고, P2 항목이 Linear에 실제로 기록됐습니다.
  • 자동 복구는 꺼 두었고, 고객 영향이 확인되는 P0가 실제로 발생한 적은 아직 없습니다. P0 조건은 테스트로 검증했습니다.
  • ClickHouse 쪽 알림 정책은 코드로 선언했고, 알림 채널에는 연결하지 않은 채 지표와 대조해 임계값을 정했습니다. 채널에 바로 연결하면 P0만 사람을 부른다는 규칙을 건너뛰는 두 번째 통로가 생기기 때문입니다.

운영하면서 고친 것

  • 모델 호출 실패. 첫 자연 incident에서 진단 모델이 60초 제한에 두 번 걸렸고, 두 번째 모델의 요청이 보내기 전 검증 단계에서 거부되었으며, 사람에게 묻지 않아도 될 질문이 한 번 나갔습니다. 요청 검증 결함을 고치고, 빈 결과나 재조회 같은 일상 조사는 AI가 직접 처리하고 사람에게 묻지 않도록 지침에 명시했습니다.
  • 재평가와 기억. 한 번 정한 판단이 굳지 않도록 alarm으로 깨어나 등급을 다시 평가하는 장치를 넣었습니다. 사건 사이에 이어지는 기억은 성공한 조사만 신뢰하고, 지난 가설은 "과거"로 표시해 지금의 사실처럼 읽히지 않게 했습니다.
  • 배포 직후 수신 거부. 한 번의 배포 뒤 수신 요청 일부가 거부되어 rollback했고, 수신 경로가 과거 진행 기록을 다시 읽던 join 조회를 없앴습니다. 거부의 정확한 본문은 과거 로그가 남지 않아 확정하지 못했습니다.
  • 읽기 쉬운 요약. 일일 요약은 사람이 한눈에 읽을 수 있게 다시 정리했고, 결정 대기 항목에는 책임 범위와 기한을 붙였습니다.

배운 점

  1. 배포 성공은 다음 주기에 모든 지표를 받았는지로 판단합니다.

    프로세스가 떴는지는 성공의 증거가 되지 못했습니다. 다음 5분 주기에 28개를 모두 받았는지를 봐야 합니다.

  2. 빈 지표는 0이 아닙니다.

    없는 값을 0으로 채우면 정상으로도 정지로도 읽힙니다. 값 없음이라는 상태를 따로 두어야 오탐도 누락도 줄어듭니다.

  3. 사람을 부르는 기준은 모델이 아닌 코드에 둡니다.

    모델은 가설과 근거를 만드는 데 쓰고, 누구를 깨울지는 사람이 설계한 규칙으로 정해집니다. 그래야 모델이 바뀌어도 호출 기준이 변하지 않습니다.

  4. 경보 통로는 늘리기보다 하나로 모읍니다.

    예외는 감시자 자신이 죽은 경우 하나뿐입니다. 통로가 둘이면 등급 규칙을 거치지 않는 경로가 생기고, 사람은 어느 쪽을 믿을지 판단해야 합니다.

10관련 링크

서비스 저장소는 비공개라 링크하지 않습니다.

  • Decklog ↗ 짧게 실행되고 끝나는 SRE 에이전트들이 incident 맥락을 이어받는 구조를 다룬 연구 노트입니다.
