월드랜드 GPU 노드 플랫폼

GPU 머신을 키 파일 하나와 명령 한 줄로 Kubernetes 워커에 붙이는 노드 SDK와 중개 서버(Hub)를 만들었습니다. Hub는 결제가 확인된 렌탈에만 GPU Pod를 만듭니다.

기간
2026.01 – 2026.02
소속
리버벤스(월드랜드), 계약직 인턴

상태
Kind 클러스터에서 렌탈 전체 흐름으로 검증, 정산 컨트랙트는 Sepolia 테스트넷 배포

01상황과 역할

월드랜드 체인 위에서 GPU를 빌려주고 쓴 시간만큼 정산하는 렌탈 플랫폼이었습니다. GPU를 빌려주는 쪽을 프로바이더, 빌려 쓰는 쪽을 렌터라고 불렀습니다. Hub는 둘 사이에서 머신 등록과 렌탈, 결제 확인을 맡는 중개 서버입니다.

합류 무렵에는 월드랜드 노드 클라이언트(geth 포크, ECCPoW 합의)의 합의와 난이도 조정, 제네시스 코드를 읽었습니다. 로컬에 프라이빗 체인을 띄워 계정을 만들고 거래를 보내 보며 구조를 익혔습니다.

프로바이더 머신마다 containerd와 kubeadm 설치 상태가 달랐습니다. 그래서 GPU 머신 한 대를 붙일 때마다 사람이 손으로 맞춰야 했습니다. Hub는 여러 프로바이더 클러스터에서 노드마다 남은 GPU를 알아야 했습니다. 결제가 확인되기 전에 GPU를 내주면 돌려받을 방법이 없었습니다. 렌탈이 없는 시간에는 같은 GPU로 월드랜드 마이닝 노드를 돌려야 했습니다.

맡은 일
Hub 백엔드를 맡아 개발했고, 노드 SDK와 렌탈 정산 컨트랙트도 맡았습니다. 같은 기간에 프로바이더와 렌터용 웹 화면도 만들었습니다. NFT 마켓플레이스와 Faucet 컨트랙트는 월드랜드 메인넷에 배포했습니다.
팀원
노드 SDK의 첫 버전과 kubeadm 컨트롤 플레인 구축 가이드, 마이닝 노드 컨테이너 이미지는 팀원이 만들었습니다.

02해결 과정

1. 실행 경로를 Kubernetes 하나로 정리

머신을 Kubernetes 워커로 붙이는 경로를 먼저 만들었습니다. 그 뒤 개인 프로바이더를 받으려고, Hub가 mTLS로 프로바이더 머신의 Docker를 원격 실행하는 경로를 추가했습니다. 이렇게 실행 경로가 두 갈래로 나뉘었습니다.

이 구조에는 보정 로직이 계속 붙었습니다. 이미지 pull이 늦어 응답이 끊기면 SSH 접속 정보를 대신 채우는 처리, Hub가 재시작한 뒤 SSH 정보를 되살리는 처리가 그 예입니다. 스케줄링과 Pod 수명주기는 Kubernetes에 맡기는 편이 낫다고 판단했습니다. 그래서 Docker 경로를 지우고 Kubernetes 경로 하나만 남겼습니다.

2. 지갑 인증부터 kubeadm join까지 명령 한 줄로

노드 SDK는 두 모드로 나눴습니다.

  • node master는 Hub와 연결을 유지하는 노드 데몬입니다. 지갑 서명 로그인(SIWE)으로 서명을 보내면, Hub의 CA가 지갑 주소를 인증서 이름(CN)에 넣은 인증서를 발급합니다. 그 뒤로는 mTLS로 30초마다 생존 신호(heartbeat)를 보내고, 여기에 NVML로 읽은 GPU 지표를 담습니다. 연결이 끊기면 5초에서 60초까지 간격을 늘리며 다시 붙습니다.
  • node worker는 GPU 머신을 클러스터에 붙이는 설치기입니다.

설치기는 아래 명령 한 줄로 시작합니다. -master-wallet에는 붙을 클러스터를 등록한 프로바이더의 지갑 주소를 넣습니다.

설치기 실행sh
./node worker -hub-http <Hub 주소> -private-key-file <키 파일> -master-wallet <지갑 주소>
  1. 구성요소 6개(nvidia-smi, containerd, kubeadm, kubelet, kubectl, nvidia-ctk)를 점검합니다. NVIDIA 드라이버를 뺀 나머지 중 빠진 것은 Ubuntu와 Debian에서 바로 설치합니다.
  2. containerd에 NVIDIA 런타임을 기본값으로 설정합니다.
  3. 지갑 서명으로 인증한 뒤 Hub에 join 토큰을 요청합니다.
  4. Hub는 kube-system에 만료 24시간짜리 bootstrap token Secret을 생성하고 kubeadm join 명령을 돌려줍니다.
  5. 설치기는 받은 명령이 kubeadm join으로 시작할 때만 실행합니다.
  6. 붙은 뒤에는 NVML로 읽은 GPU 종류와 VRAM을 노드 어노테이션으로 남깁니다.

kubeadm 동작을 읽으면서 두 가지를 반영했습니다.

  • 새 노드는 처음에 API 서버를 믿을 근거가 없습니다. 그래서 kubeadm join은 --discovery-token-ca-cert-hash로 CA를 고정합니다. 이 해시는 CA 인증서의 공개키 필드(SubjectPublicKeyInfo)만으로 계산합니다. Hub도 이 필드로 해시를 계산해 join 명령에 넣었습니다.
  • kubeadm reset은 CNI 설정과 인터페이스를 지우지 않습니다. 그래서 다시 붙는 머신에서 flannel이 cni0 already has an IP address different from ... 오류로 멈췄습니다. 설치기가 reset 뒤에 /etc/cni/net.d, /var/lib/cni 디렉터리와 cni0, flannel.1 인터페이스까지 지우게 했습니다.

3. 클러스터 상태에서 다시 세우는 GPU 용량

Hub는 여러 프로바이더 클러스터를 함께 다룹니다. 클러스터마다 worldland.io/gpu-rental=true 라벨이 붙은 렌탈 Pod만 Informer로 지켜봤습니다.

노드마다 가용 GPU는 전체 GPU에서 실행 중인 렌탈 Pod가 쓰는 수를 빼서 계산했습니다. 이 값은 Hub 메모리에 둡니다. Hub가 재시작하면 준비 상태인 노드와 실행 중인 렌탈 Pod를 다시 읽어 이 값을 세웁니다.

DB는 읽기용 사본으로 두었습니다. 2분마다 전체를 맞추고, 할당이나 반납 때는 그 노드만 바로 맞춥니다. DB를 기준으로 두면 재시작 뒤 클러스터와 어긋날 수 있어서, 클러스터 상태에서 다시 세우는 쪽을 택했습니다.

렌터 지갑마다 Namespace와 ResourceQuota, NetworkPolicy를 만들어 렌터끼리 자원과 네트워크를 나눴습니다.

마이닝은 실행 경로를 따라 바뀌었습니다. Docker 경로를 쓰던 때에는 노드 데몬이 유휴 GPU에서 마이닝 노드 컨테이너를 띄웠습니다. 렌탈이 들어오면 멈추고, 끝나면 다시 띄웠습니다. Kubernetes 경로로 옮긴 뒤에는 Hub가 프로바이더 요청에 따라 worldland-mining Namespace에 마이닝 Pod를 배포하고 지웁니다. 마이닝에 쓰는 GPU는 프로바이더 단위 GPU pool로 따로 셌습니다.

4. 결제가 확인된 렌탈에만 Pod 생성

Solidity로 작성한 렌탈 컨트랙트는 block.timestamp 기준 사용 시간에 초당 가격을 곱해 비용을 정합니다. 재진입은 OpenZeppelin ReentrancyGuard로 막았습니다.

Hub의 이벤트 리스너는 WebSocket RPC 여러 개를 차례로 시도해 연결합니다. 연결이 끊겼다 돌아오면 마지막 체크포인트부터 1,000블록씩 다시 읽습니다. 블록이 뒤집혀(reorg) 사라질 수 있는 이벤트로 Pod를 만들지 않도록, 이벤트는 15블록이 더 쌓인 뒤에 처리합니다. 같은 이벤트가 두 번 와도 처리 기록에 남긴 tx hash로 걸러냅니다.

Hub는 tx receipt로 세 가지를 확인합니다. 거래가 블록에 들어갔는지, 실패하지 않았는지, 호출한 함수와 렌터, 프로바이더가 맞는지입니다. 셋을 모두 통과한 렌탈에만 렌터 Namespace에 GPU Pod를 만듭니다.

03결과

  • 프로바이더 온보딩: 구성요소 설치부터 클러스터에 붙이기까지 사람이 단계별로 하던 설정 → 키 파일 하나와 명령 1줄 (NVIDIA 드라이버 설치 뒤)
  • Hub 재시작 뒤 노드 복구: 노드를 손으로 다시 시작 → 자동 재연결 (5초에서 60초 간격)
  • 실행 경로: 2개 → 1개 (Docker 원격 실행 모듈 파일 8개, 약 1,400줄 삭제)
  • 테스트: Hub 약 350개(Kind 클러스터에서 예치부터 Pod 회수까지 도는 테스트 포함), 컨트랙트 약 40개
  • 노드 SDK의 인증서 자동 발급과 GPU 자동 감지가 월드랜드 공식 GitHub 저장소에 반영

04트러블슈팅

T-01

같은 지갑의 두 번째 머신이 클러스터에 붙지 않는 문제

문제
같은 지갑으로 GPU 머신 2대를 올리면 첫 대만 join 명령을 받았습니다. 두 번째 머신은 join 명령을 받지 못했습니다.
원인
Hub는 join 명령을 보낸 노드를 'join 대기'로 기록하고, 기록이 있으면 명령을 다시 보내지 않았습니다. 이 기록의 키가 지갑 주소였습니다. 한 시간쯤 전에 노드가 등록할 때 보내는 식별자는 GPU UUID(없으면 /etc/machine-id)로 바꿨지만, Hub가 연결을 구분하는 값은 지갑 주소로 남아 있었습니다.
해결
지갑 하나 아래에 머신이 여러 대 있을 수 있어서, Hub가 지갑 주소만으로는 머신을 가려낼 수 없었습니다. 당시 노드 데몬에는 이미 클러스터에 붙어 있으면 건너뛰는 확인이 있었습니다. 그래서 Hub는 접속한 모든 노드에 join 명령을 보내게 했습니다. 남은 join 대기 기록에는 2분 만료를 넣었습니다.
결과
같은 지갑으로 올린 머신이 모두 join 명령을 받았습니다.

05배운 점

노드 식별자는 머신 단위로 정해야 합니다. 머신을 붙이는 절차도 두 번 실행해서 결과가 같아야 합니다.

RPC를 바꿔 붙는 기준은 연결 여부만으로는 부족합니다. 블록 높이를 따라잡았는지까지 봐야 합니다.

마이닝 Pod도 GPU를 요청하는데, 가용 GPU는 렌탈 Pod만 세서 계산했습니다. 같은 노드에서 마이닝이 돌면 가용량이 실제보다 크게 잡히는 구조였습니다. 용량은 그 자원을 요청하는 워크로드를 모두 세서 계산해야 합니다.
