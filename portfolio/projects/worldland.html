월드랜드 GPU 렌탈 마켓

월드랜드 체인 위에 RunPod, Akash Network 같은 GPU 렌탈 마켓을 만드는 프로젝트였습니다. 저는 공급자 GPU 머신을 명령 한 줄로 붙이는 노드 SDK와, 결제가 확인된 렌탈에만 GPU를 내주는 중개 서버(Hub)를 만들었습니다.

01상황

월드랜드는 무엇인가

월드랜드는 리버밴스가 만든 EVM 호환 블록체인입니다. 리버밴스는 GIST 교원 창업 기업이고, 2023년 8월에 메인넷을 열었습니다. 합의는 오류 정정 부호를 쓰는 작업증명(ECCPoW)입니다. 메인넷(Seoul)의 체인 ID는 103입니다.

무엇을 위한 프로젝트인가

월드랜드는 스스로를 '탈중앙 AI를 위한 웹3 클라우드'라고 소개합니다. 그 중심이 GPU 렌탈 마켓입니다.

  • 공급자는 GPU 머신을 올리고 가격을 정합니다.
  • 사용자는 토큰을 예치하고, SSH로 접속하는 GPU 컨테이너를 빌립니다.
  • 렌탈이 끝나면 쓴 시간만큼 체인 위에서 정산되어 공급자에게 갑니다.
  • 렌탈이 없는 시간에는 같은 GPU로 월드랜드를 채굴합니다.

회사가 풀려던 문제

마켓이 돌아가려면 공급자가 모이고, 사용자가 믿고 돈을 내야 했습니다.

  • 공급자 머신마다 드라이버와 kubeadm 설치 상태가 달랐습니다. 한 대씩 손으로 맞춰야 했습니다.
  • 대금이 확인되기 전에 GPU를 내주면 돌려받을 방법이 없었습니다.
  • 공급자마다 클러스터가 따로 있었습니다. 남은 GPU를 한곳에서 볼 수 없었습니다.
  • 렌탈이 없는 시간에는 GPU가 놀았고, 공급자 수익도 끊겼습니다.

02과제와 역할

비즈니스 요구는 다섯 가지였습니다.

비즈니스 요구제가 만든 것
공급자가 머신을 쉽게 붙인다공급자 머신에 까는 노드 SDK입니다. Hub와 연결을 유지하는 노드 데몬과, 머신을 Kubernetes 클러스터에 합류(join)시키는 설치기로 나뉩니다.
대금이 확인된 렌탈에만 GPU를 내준다체인에서 결제를 확인한 뒤에만 GPU 컨테이너(Pod)를 만드는 흐름과, 렌탈 종료를 체인에서 받아 GPU를 돌려받는 이벤트 리스너입니다.
쓴 만큼만 정산하고 남은 돈은 돌려준다예치, 정산, 출금을 처리하는 렌탈 정산 컨트랙트입니다.
여러 클러스터의 GPU를 한곳에서 본다여러 클러스터의 노드와 렌탈 Pod를 지켜보면서, 지금 빌려줄 수 있는 GPU 수를 세는 기능입니다.
렌탈이 없을 때는 채굴로 수익을 잇는다렌탈이 없는 GPU에 채굴 프로그램을 띄우고 내리는 기능입니다. 채굴에 쓰는 GPU는 공급자별로 따로 셉니다.
맡은 일
Hub 백엔드와 노드 SDK, 렌탈 정산 컨트랙트를 맡았습니다. 같은 기간에 웹 화면을 만들고, NFT 마켓과 Faucet 컨트랙트를 월드랜드 메인넷에 배포했습니다.
팀원
노드 SDK 첫 원형, kubeadm 컨트롤 플레인 구축 가이드, 마이닝 노드 이미지는 팀원이 만들었습니다.

03해결 과정

0. 전체 구조: Akash와 비교한 뼈대

설계 전에 Akash Network의 노드와 공급자 코드를 분석해 비교했습니다. 공급자가 자기 Kubernetes 클러스터와 공급자 데몬을 운영하는 뼈대는 같습니다. Akash는 공급자 입찰, 임대 계약(리스), 맡겨 둔 대금의 정산(에스크로)을 모두 체인 위에서 처리합니다. 월드랜드는 체인 위에 예치와 정산만 두고, 사용자와 GPU를 짝짓는 일과 Pod를 만들고 지우는 일은 Hub가 맡았습니다.

1. 공급자가 머신을 쉽게 붙인다

요구
머신을 붙이기 어려우면 공급자가 들어오지 않습니다.
설계
공급자 지갑 하나를 신원으로 삼고, 노드 SDK를 두 역할로 나눴습니다.
  • node master는 클러스터를 가진 공급자의 노드 데몬입니다. 지갑 서명 로그인(SIWE)을 거치면, Hub 안의 인증서 발급 기관(Hub CA)이 지갑 주소를 기준으로 인증서를 내줍니다. 그다음 클러스터를 등록합니다. 그 뒤로는 양쪽이 서로 인증서를 확인하는 암호화 연결(mTLS)로 30초마다 살아 있다는 신호를 보내고, 연결이 끊기면 다시 붙습니다.
  • node worker는 GPU 머신을 그 클러스터에 붙이는 설치기입니다.
구현
설치기 하나로 머신 점검부터 클러스터 합류(join)까지 끝냅니다.

설치기는 명령 한 줄로 시작합니다.

설치기 실행sh
./node worker -hub-http <Hub 주소> -private-key-file <키 파일> -master-wallet <지갑 주소>
  1. 구성요소 6개(nvidia-smi, containerd, kubeadm, kubelet, kubectl, nvidia-ctk)를 점검합니다. 드라이버 말고 빠진 것은 바로 설치합니다.
  2. containerd에 NVIDIA 런타임을 기본값으로 설정합니다.
  3. 지갑 서명으로 인증하고, Hub에 클러스터 합류용 토큰(join 토큰)을 요청합니다.
  4. Hub가 24시간짜리 토큰으로 kubeadm join 명령을 만들어 돌려줍니다.
  5. 설치기는 Hub에서 받은 명령이 kubeadm join으로 시작할 때만 실행합니다.
  6. NVIDIA 관리 라이브러리(NVML)로 GPU 종류와 VRAM 용량을 읽어 노드 정보에 표시합니다.

Hub는 클러스터 CA 공개키의 해시를 join 명령에 넣었습니다. 새 노드는 이 값으로 자기가 붙으려는 API 서버가 맞는지 확인합니다. 설치기는 kubeadm reset을 해도 남는 컨테이너 네트워크 설정(CNI)과 네트워크 인터페이스도 지웁니다. 이것이 남아 있으면, 클러스터에서 빠졌다가 다시 붙는 머신에서 네트워크 플러그인인 flannel이 멈췄습니다.

2. 대금이 확인된 렌탈에만 GPU를 내준다

요구
대금 없이 GPU가 나가면 돌려받을 방법이 없습니다.
설계
결제 확인 뒤에만 Pod를 만드는 순서를 Hub 한곳에 고정했습니다.
구현
예치금을 확인하고, 렌탈 시작 거래를 확인한 뒤 Pod를 만들고, 렌탈이 끝나면 Pod를 거둬들이는 과정을 이 순서대로 묶었습니다.
  • 렌탈 요청이 오면 사용자가 컨트랙트에 넣어 둔 예치금을 봅니다. 1시간 요금보다 적으면 요청을 받지 않습니다.
  • 렌탈 시작 거래는 체인이 남긴 처리 결과인 영수증(receipt)을 읽어 확인합니다. 거래가 성공했는지, 어떤 컨트랙트 함수를 불렀는지, 사용자와 공급자가 누구인지를 봅니다.
  • 확인을 통과하면 사용자 지갑마다 따로 둔 격리 공간(Namespace)에 GPU Pod를 만들고 SSH 접속 정보를 줍니다. Namespace마다 쓸 수 있는 자원의 상한(ResourceQuota)과 네트워크 접근 규칙(NetworkPolicy)을 걸었습니다.
  • 공급자 머신에서 아무 이미지나 돌지 않게, 이미지는 미리 정한 목록에서만 고릅니다.
  • 체인에서 렌탈 종료 이벤트가 오면 Pod를 지워 GPU를 돌려받습니다. 이벤트 리스너는 체인 접속 주소(RPC) 여러 개를 하나씩 시도해 붙습니다. 연결이 끊겼다 돌아오면 마지막으로 읽은 지점(체크포인트)부터 다시 읽습니다.

3. 쓴 만큼만 정산하고 남은 돈은 돌려준다

요구
사용자는 쓴 시간만큼만 내고, 공급자는 그만큼을 확실히 받아야 합니다.
설계
돈은 컨트랙트가 맡습니다. 사용자가 미리 예치하고, 렌탈이 끝나면 쓴 만큼만 공급자 몫으로 옮깁니다.
구현
Solidity로 예치, 정산, 출금을 만들었습니다.
  • 비용은 사용 시간에 초당 가격을 곱해 정합니다. 사용 시간은 블록에 기록된 시각으로 잽니다.
  • 남은 예치금은 사용자가 언제든 출금합니다.
  • 함수가 끝나기 전에 같은 함수를 다시 불러 돈을 여러 번 빼 가는 재진입 공격은 OpenZeppelin의 ReentrancyGuard로 막았습니다.
  • 렌탈을 연장할 때는 Hub가 지금까지 쓴 금액에 연장할 시간의 요금을 더해, 그 합이 예치금 안에 드는지 확인합니다.

4. 여러 클러스터의 GPU를 한곳에서 본다

요구
사용자에게는 지금 빌릴 수 있는 GPU만 보여야 하는데, GPU는 클러스터마다 흩어져 있었습니다.
설계
클러스터 상태를 기준으로 삼았습니다. DB는 재시작 뒤 클러스터와 어긋날 수 있어 화면용 읽기 사본으로만 두었습니다.
구현
클러스터마다 렌탈 Pod를 지켜보고, 가용 GPU는 Hub 메모리에서 셉니다.
  • 공급자가 등록한 클러스터 접속 설정 파일(kubeconfig)로 클러스터마다 클라이언트를 만듭니다. 그리고 Kubernetes의 변경 알림 기능(Informer)으로 렌탈 Pod의 변화만 받아 봅니다.
  • 가용 GPU는 노드의 전체 GPU 수에서 렌탈 Pod가 쓰는 수를 뺀 값입니다. 이 값은 DB가 아니라 Hub 메모리에 둡니다.
  • Hub가 재시작하면 클러스터에서 노드와 렌탈 Pod를 다시 읽어 이 값을 처음부터 계산합니다.
  • DB의 값은 2분마다 클러스터 기준으로 다시 맞춥니다. GPU를 빌려주거나 돌려받을 때는 해당 노드의 값만 그 자리에서 바로 맞춥니다.

5. 렌탈이 없을 때는 채굴로 수익을 잇는다

요구
GPU가 놀면 공급자 수익이 끊깁니다.
구현
렌탈을 실행하는 방식이 Docker에서 Kubernetes로 바뀌면서, 마이닝 기능도 방식에 맞춰 두 번 만들었습니다.
  • Docker로 렌탈을 돌리던 때는 노드 데몬이 유휴 GPU에서 마이닝 노드 컨테이너를 띄웠습니다. 렌탈이 오면 멈추고, 끝나면 다시 띄웠습니다.
  • Kubernetes로 옮긴 뒤에는 Hub가 공급자 요청으로 마이닝 Pod를 배포하고 지웁니다. 마이닝 GPU는 공급자별로 따로 셌습니다.

6. 설계 고민: 실행 경로를 Kubernetes 하나로

클러스터가 없는 개인 공급자를 받으려고, Hub가 공급자 머신의 Docker를 원격 실행하는 경로를 더했습니다. 그러자 이미지 pull 지연과 Hub 재시작에 대비한 보정 로직이 계속 붙었습니다. 보정을 쌓는 대신 스케줄링과 Pod 수명주기를 Kubernetes에 맡기기로 했습니다. 설치기로 개인 머신도 워커 노드로 붙일 수 있었기 때문입니다. Docker 원격 실행 코드 약 1,400줄을 지웠습니다.

04트러블슈팅

T-01

같은 지갑의 두 번째 머신이 붙지 않는 문제

문제
같은 지갑으로 올린 GPU 머신 2대 중 첫 대만 join 명령을 받았습니다.
원인
Hub가 'join 대기' 기록을 머신이 아니라 지갑 주소 단위로 남겼습니다. 그래서 두 번째 머신도 이미 대기 중인 것으로 보고 건너뛰었습니다.
해결
노드 데몬은 이미 클러스터에 붙은 머신이면 join 명령을 받아도 건너뜁니다. 그래서 Hub가 접속한 모든 노드에 join 명령을 보내도록 바꿨습니다. 남아 있던 대기 기록은 2분이 지나면 만료되게 했습니다.
결과
같은 지갑으로 올린 머신이 모두 join 명령을 받았습니다.
T-02

한 사람이 빌리면 노드가 마켓에서 사라지는 문제

문제
한 노드의 GPU를 여러 사용자가 나눠 빌리게 바꿨는데, 한 사람이 빌리면 GPU가 남아 있어도 그 노드가 마켓 목록에서 사라졌습니다.
원인
목록 조회에 '렌탈 중인 노드는 뺀다'는 예전 조건이 남아 있었습니다.
해결
조건을 '가용 GPU가 1개 이상'으로 바꿨습니다. GPU를 빌려주거나 돌려받을 때는 그 노드의 가용 GPU 수를 DB에 바로 반영했습니다.
결과
여러 사용자가 한 노드를 나눠 빌릴 수 있게 됐습니다.

05결과와 임팩트

  • 전에는 공급자가 GPU 머신을 마켓에 붙이려면 구성요소 설치, 컨테이너 런타임 설정, 합류 토큰 발급, 클러스터 합류(join) 같은 6단계를 사람이 직접 해야 했습니다. 이제는 NVIDIA 드라이버만 깔려 있으면 설치기 명령 한 줄로 이 과정이 끝납니다.
  • 노드 SDK에 넣은 지갑 서명 로그인, 연결용 인증서 자동 발급, NVML을 이용한 GPU 자동 감지 기능이 월드랜드 공식 GitHub 저장소에 반영됐습니다.
  • Hub는 체인에서 결제를 확인하기 전에는 GPU Pod를 만들지 않습니다. 로컬 테스트용 클러스터(Kind)에서 사용자가 예치하는 단계부터 렌탈이 끝나 Pod를 거둬들이는 단계까지 전체 흐름을 자동 테스트로 확인했습니다.
  • 렌탈 정산 컨트랙트는 Sepolia 테스트넷에 배포했고, 컨트랙트 테스트는 약 40개입니다.
  • 전에는 Hub가 재시작하면 공급자 쪽 노드를 사람이 다시 시작해야 했습니다. 이제는 연결이 끊기면 노드 데몬이 스스로 Hub에 다시 연결합니다.
  • 렌탈 컨테이너를 실행하는 경로를 Docker 원격 실행과 Kubernetes 두 가지에서 Kubernetes 하나로 줄였습니다. Hub 백엔드 테스트는 약 350개입니다.

06배운 점

돈과 자원이 함께 움직이는 시스템에서는 결제를 확인한 뒤에 자원을 내주는 순서를 한곳에서 지켜야 합니다.

노드를 구분하는 기준은 지갑이 아니라 머신이어야 합니다. 같은 지갑으로 여러 머신을 올릴 수 있기 때문입니다. 머신을 붙이는 절차도 같은 머신에 두 번 실행해서 결과가 같아야 합니다.

빌려줄 수 있는 GPU 수를 셀 때는 그 GPU를 쓰는 작업을 모두 빼야 합니다. 마이닝 Pod도 GPU를 쓰는데, 가용 GPU를 계산할 때는 렌탈 Pod만 뺐습니다.

여러 체인 접속 주소(RPC) 가운데 어디에 붙을지는 연결이 되는지만 보고 정하면 안 됩니다. 그 노드가 최신 블록까지 따라왔는지, 즉 블록 높이를 보고 정해야 합니다.
