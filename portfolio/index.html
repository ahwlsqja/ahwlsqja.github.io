대표 사례

사례 12026.09 ~ 10운영 반영단독 담당

관리형 ClickHouse를 GKE 자체 운영 클러스터로 옮기고 해지까지

문제

관리형 레플리카의 CPU p99가 상한 4 vCPU에 붙어 있었고 복구 리허설은 한 번도 없었습니다. 회사는 GCP 단일화를 이유로 10월 말 이전을 정했습니다.

한 일

  • Altinity operator를 namespace 권한으로만 깔고 Keeper 3대를 존 a, b, c에 하나씩 띄웠습니다. Autopilot이 safe-to-evict: false 파드를 한 존에 몰아 넣는 것을 잡아 minDomains를 필수로 바꿨고, Keeper Ready 뒤에 ClickHouse를 올리는 순서로 크래시루프를 없앴습니다.
  • grants를 주지 않은 users.xml 사용자가 전체 권한을 갖는 것을 26.8에서 실측해 REVOKE ALL을 넣고, 읽기 계정의 max_execution_time=0 우회는 constraints min으로 막았습니다.
  • staging에서 3,300만 행 복구 리허설(105초, 표별 해시 일치)을 하고, 레플리카 1대를 0으로 내려 insert_quorum=2가 쓰기를 Code 285로 거부하며 유실 0인 것을 봤습니다.
  • 과거 데이터를 (표, 고객, 일) 청크와 dedup 토큰으로 옮기고, 고객사별 24시간 이벤트 수와 Kafka 커밋 위치 12개 파티션을 대조한 뒤 읽기 경로를 설정값 하나로 넘겼습니다.

결과

  • 과거 데이터 prod청크 2,640개 → 1.3억 행, 실패 0
  • 24시간 대조고객사 10곳 → 모두 ±0.2% 안
  • 복구 리허설 staging3,300만 행 → 105초, 표별 해시 일치
  • 해지10월 16일 관리형 서비스 해지

판단과 대가

7일 관찰은 비용 때문에 생략했습니다. 대신 바깥 기준 두 개(기존 쪽 이벤트 수, Kafka 커밋 위치)를 맞춰 본 뒤 해지했고, 직전 대조에서 새 쪽이 0.1~0.5% 많은 차이는 재전송 중복으로 보고 감수했습니다.

배운 점

레플리카를 직접 내려 봐야 나머지가 무엇을 보장하는지 안다고 생각합니다. 노드도 한 대를 빼 보는 것부터 하겠습니다.

사례 22026.09.29staging 검증운영 반영

롤아웃 중 503 한 건: Ready가 트래픽보다 먼저 왔다

문제

Argo CD로 처음 운영을 동기화한 롤아웃에서 외부 /health에 503이 한 번 찍혔습니다. 보름 전 같은 증상에 종료 쪽(preStop 60초)만 막았는데 다시 났습니다.

한 일

  • 새 Pod의 status.conditions에서 NEG 준비 게이트가 LoadBalancerNegWithoutHealthCheck 사유로 LB 헬스체크(5초 × 2회)보다 먼저 True가 된 것을 찾았습니다. replica가 1개라 그 틈에 옛 Pod가 빠지며 정상 endpoint가 0이 됐습니다.
  • minReadySeconds 30, replica 2, PDB minAvailable 1을 걸었습니다. 늘리기 전에 코드에 리더 선출과 프로세스 내 스케줄러가 없는 것을 확인했습니다.
  • staging 롤아웃 2회 동안 외부 /health를 1초 간격으로 폴링하고, 운영은 argocd app sync --resource로 Deployment와 PDB만 넘겼습니다.

결과

  • staging1초 폴링 → 315회 연속 200
  • prod적용 구간 → 100회 연속 200
  • 걸린 시간탐지 → 운영 반영 46분

배운 점

Pod가 Ready인 시점과 트래픽을 받는 시점은 다릅니다. 노드라면 HTTP 200 대신 참조 노드 대비 head lag로 readiness를 걸어야 한다고 생각합니다(beacon은 동기화 중 206, CometBFT는 뒤처져도 200).

사례 3리버벤스, 2026.01 ~ 02공식 org 반영

GPU 머신을 Kubernetes 노드로 붙이는 Go 노드 데몬과 Hub

문제

프로바이더 머신마다 드라이버, containerd, kubeadm 상태가 달라 사람이 붙여야 했고, Hub를 재배포하면 노드가 끊겼습니다.

한 일

  • 노드 데몬. SIWE 인증 → Hub CA의 90일 mTLS 인증서 → 30초 heartbeat, 끊기면 5초에서 60초까지 백오프 재접속, NVML로 GPU 자동 감지.
  • V3 설치기. nvidia-smi, containerd, nvidia-ctk 점검 → kubeadm reset -f와 cni0 잔재 정리 → kubeadm join → kubelet 재시작.
  • Hub. client-go Informer로 여러 클러스터의 Pod를 감시하고, 지갑마다 Namespace, ResourceQuota, NetworkPolicy로 격리하며, 온체인 receipt가 확인된 렌탈만 GPU Pod로 띄웠습니다.
  • 같은 지갑의 두 번째 노드가 pending에 묶이던 문제, GPU 한 장 대여에 노드 전체가 마켓에서 사라지던 쿼리, 초당 단가 1,000배 오류를 커밋마다 원인을 적어 고쳤습니다.

결과

  • 구조일주일 동안 V2 → V3 → V4, Docker 경로 제거, Kubernetes 전용
  • Hub 테스트356개 (Kind e2e 포함)
  • 노드 SDK월드랜드 공식 GitHub org에 반영

배운 점

이벤트 리스너는 끊긴 RPC를 다음 주소로 넘겼지만 뒤처진 노드는 거르지 못했습니다. 다음에 붙일 것은 RPC 간 블록 높이 비교라고 생각합니다.

05

왜 노딧, 그리고 90일

  • 노딧 Wallet Node 글은 노드의 가용성과 동기화 상태를 보고 요청을 보낸다고 씁니다. 503 한 건에서 붙든 "언제 트래픽을 받아도 되는가"가 노드에서는 head lag 문제라고 생각해 이 일을 하고 싶습니다.
  • 공고는 노드 업그레이드와 하드포크를 무중단으로 넘기는 구조를 업무로 적습니다. 저는 되돌릴 수 없는 관리형 해지를 복구 리허설과 이벤트 수 대조로 넘겼고, Besu 합의를 바꿀 때는 체인 초기화와 EVM 버전 차이를 직접 겪었습니다.
  • 채용 설명회가 꼽은 과제는 데이터를 끊김 없이 수집하고 정합성을 지키는 것입니다. 1.3억 행 이관과 ID 3,907개 대조가 같은 종류의 일입니다.
