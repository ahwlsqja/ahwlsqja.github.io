1 · 만들고2026.04 – 10운영 중

제품 데이터 파이프라인 0→1

TypeScript · Go · Cloudflare Workers와 Queues · ClickHouse · Kafka · Flink

한 줄브라우저 SDK → 수집 게이트웨이 → 큐 → 원본 → 현재 상태 → 서빙 테이블을 처음부터 만들었고, 10월에는 같은 원칙으로 Kafka 경로를 설계해 미러 대조 뒤 갈아탔습니다.

왜, 내 몫

사이트 행동과 광고 유입을 이어 보여 주는 B2B 분석 제품에 브라우저 이벤트를 모으는 경로가 없었습니다. 데이터 모델과 수집, 적재, 층 설계, 실패 경로를 주도했습니다(SDK 탭 수명 모델 선행 구현과 광고 연동 일부, 화면은 동료). 10월 경로는 동료가 요구사항을 썼고 저는 구조 결정과 장애 시험, 전환 판단을 맡았습니다.

파고든 원리

브라우저 재전송, Queue 재전달, Kafka 재소비는 모두 at-least-once라 같은 이벤트가 여러 번 올 수 있고, 저장소는 그걸 전제로 짜야 했습니다. 같은 이벤트가 두 번 INSERT되면 ReplacingMergeTree 원본은 언제일지 모르는 병합 때 1행으로 합쳐지지만, INSERT에 걸린 Materialized View는 블록마다 바로 +1을 더해 집계가 2로 남고 나중 병합으로도 돌아오지 않습니다. 그래서 원본은 다시 읽을 수 있게 두고, 정확한 값은 논리 키로 다시 읽는 층에서, 빠른 값은 미리 집계하는 층에서 내도록 나눠야 한다고 생각했습니다.

설계 결정

선택버린 대안이유
층 분리원본 → 현재 상태(논리 키 argMax) → 세션 Fact → 서빙을 다른 그레인으로조회마다 원본 FINAL, INSERT 시점 집계만 믿기중복 INSERT가 MV 집계에는 그대로 남아, 정확한 값은 다시 읽는 층에서 내야 함
실패분 붙잡기본 큐 재시도 → DLQ → 1회 재발행 → 소비자 없는 보관 큐, 보관이 성공한 뒤에만 ack—실패분을 잃지 않고, 적재 직전에 남는 R2 원본 기록을 복구 대조의 기준으로 씀
10월 경로Go 수신 서버 → Kafka(12 파티션) → Flink → Go 적재기. 적재기는 구간을 원장에 먼저 쓰고 두 레플리카가 모두 받아야 성공. 트래픽은 Worker 다이얼 off → mirror → primary기존 경로 유지세션 커버리지가 사흘 사이 약 60%에서 30%로 떨어지고, 그 경로가 기대던 관리형 ClickHouse 해지가 잡힘

앞뒤로 이어진 것

초기에 둔 64 해시 파티션과 (고객, 이벤트) 키가 데이터가 늘며 쓰기 병목과 다른 세션 이벤트가 합쳐질 위험으로 돌아와 2의 출발점이 됐고, 미러 대조는 3의 해지 근거로 쓰였습니다.

결과 관측 기록

  • 장애 구간 대조 운영이벤트 ID 약 3,900개 → 누락 0, 중복 0 (그 구간 한정)
  • 운영 미러 24시간고유 이벤트 차이 약 0.06% (고객사별 ±0.2% 안)
  • Kafka 커밋 위치적재 원장과 12/12 파티션 일치
  • 미러 첫날 사본약 0.2% 누락을 Worker의 waitUntil 등록 순서로 좁혀 고친 뒤 → 약 4천 건 누락 0

그 안의 장면 · 2026-06

큐가 비었다로 끝내지 않은 복구

저장소 인스턴스가 종료돼 적재가 약 4시간 멈추고 실패분이 보관 큐에 쌓였습니다. 보관 큐에 임시 consumer를 붙여 10건 canary 뒤 나머지를 본 큐로 다시 흘리고, 본 큐 전송이 성공한 뒤에만 ack했습니다. 큐가 비었다는 건 큐에 있던 것이 나갔다는 뜻일 뿐이라, 장애 구간의 R2 원본 ID와 저장소 ID를 양방향으로 대조했습니다.

노드 운영으로 가져갈 것

큐가 비었다는 신호와 원본이 모두 들어왔다는 사실 사이에는 틈이 있었습니다. 노드 재동기화도 동기화 완료 표시만 보고 끝내지 않고, 기준 노드와 같은 높이의 블록 해시를 맞춰 본 뒤 복구를 닫겠습니다.

2 · 파고들고2026.08 – 09운영 반영

ClickHouse 저장 구조를 MergeTree 동작부터 다시 짜기

ClickHouse(projection, refreshable MV) · EXPLAIN · query_log · part_log

한 줄해시 파티션이 INSERT를 여러 part로 쪼갤 뿐 pruning 이득이 없다는 것을 엔진 동작에서 짚고, 테이블과 화면마다 파티션, 정렬 키, 읽기 경로를 다시 정했습니다.

왜, 내 몫

데이터가 늘자 쓰기 지연과 병합 부담이 커지고 요약과 채널 화면이 읽기 한도에 걸려 실패했는데, 실행 시간만으로는 원인을 나눌 수 없었습니다. 원리 분석, 비교 실험, 운영 테이블 전환, 화면별 읽기 경로를 주도했습니다(채널 분류 기반은 동료와 함께).

파고든 원리

쓰기 쪽부터 따라갔습니다. MergeTree는 INSERT 한 번을 파티션 값마다 나눠 따로 part를 만들어, 64개 해시 파티션이면 배치 하나가 최대 64개 part가 됩니다. 병합은 파티션 경계를 넘지 않아 part가 쌓였고, FINAL은 그 part를 모두 펼쳐 합치느라 메모리를 썼습니다. 그 대가로 얻는다는 pruning은 실제 파티션 식과 EXPLAIN을 맞춰 보니 조건이 DDL의 해시 식과 정확히 같을 때만 1/64를 건너뛰었고, 식이 조금만 달라도 0%였습니다. 화면 필터(고객, 세션, 시각)는 그 해시 식을 쓰지 않아, 파티션은 이득 없이 쓰기 비용만 늘리고 있었습니다.

설계 결정

선택버린 대안이유
테이블마다 파티션을 반대로원본 이벤트는 무파티션, 원본 신호는 월 파티션과 (고객, 시각, 이벤트) 정렬64 해시 파티션 유지판본을 합치는 원본 이벤트는 part를 줄여야 했고, 원본 신호는 시간 범위 조회와 보존 정리가 핵심
정렬 키는 식별용, 읽기 경로는 따로원본은 (고객, 세션, 이벤트) 논리 키로 정렬, 날짜로 읽는 요약은 7개 열만 (고객, 시각) 순으로 둔 projection, AI 유입은 15분 주기 서빙 테이블원본을 시간순으로 되돌리기, 명시적 PREWHERE희소 기본 인덱스는 정렬 키 앞부분으로만 granule을 건너뜀. 원본 ORDER BY는 판본을 합치는 기준이라 조회 속도 때문에 바꾸면 정합성이 바뀜
온라인 교체새 테이블 → 실시간 브리지 → 차이분 백필 → 논리 키 대조 → EXCHANGE TABLES—논리 키 전환에서 운영 테이블 7개를 바꾸며 파생 집계 19개를 살렸고, 재발행 대조 누락 0

앞뒤로 이어진 것

정렬 키 원리는 3의 과거 데이터 복사에서 FINAL이 고객 전 기간을 병합하던 읽기를 고치는 데 그대로 쓰였습니다.

결과 관측 기록

  • 무파티션 전환 운영part 454 → 11, 대표 FINAL 집계 메모리 약 80% 감소 (낮은 부하 시점 관측)
  • 원본 신호 INSERT 운영p95 약 6배 단축, 저장량 약 1/4 (같은 13시간 관측, 정렬 압축 효과 포함)
  • 단일 세션 조회읽은 행 약 99.9% 감소 (전환 후 분석 서비스, 6회 교차 중앙값)
  • AI 유입 집계평균 약 2.4초 → 7ms 수준 (전환 직후 짧은 운영 관측)

그 안의 장면

비교 직전에 멈춘 이유

비교 직전 24시간 감사에서 같은 이벤트, 같은 판본인데 내용이 다른 묶음이 30개 넘게 나왔습니다. 다른 값은 소비 시각 하나였지만 같은 판본이면 병합 순서가 승자를 정해, 파티션을 바꾸는 순간 화면 숫자가 바뀔 수 있었습니다. 비교를 멈추고 이벤트 본체를 동일성 기준으로 고정한 뒤(이 기준이 뒤이은 논리 키 전환의 대조 기준이 됨) 파티션만 다른 두 테이블에 같은 입력을 재생해(로컬) 독립 기대값과 불일치 0을 확인했고, 느려지는 반례도 함께 남겼습니다.

노드 운영으로 가져갈 것

학부 때 Besu에서도 Clique period를 5로 바꿨는데 블록은 계속 15초마다 나왔습니다. 설정에 적힌 값과 엔진이 실제로 하는 일은 다를 수 있어서, 노드 튜닝도 옵션을 바꾼 뒤 클라이언트가 실제로 내놓는 지표로 효과를 확인하고 넘어가겠습니다.

3 · 옮기고2026.09 – 10운영 중운영 자동 승격은 진행 중

Cloud Run 서비스와 관리형 ClickHouse를 GKE로

GKE Autopilot · Terraform · Argo CD · Kargo · ClickHouse Keeper · Altinity Operator

한 줄API와 인증 서비스를 블루/그린으로 GKE에 옮기고 배포를 GitOps로 바꾼 뒤, Keeper 3대와 레플리카 2대의 자체 운영 ClickHouse로 약 1.3억 행을 옮겨 관리형 서비스를 해지했습니다.

왜, 내 몫

배포 대기열은 9월 중순 이후 성공이 없었고 운영 쓰기의 약 90%가 손작업이었으며, 관리형 ClickHouse는 CPU p99가 상한에 붙었는데 복구 리허설이 없었습니다. 회사가 인프라를 GCP로 모으기로 정했고, 저는 ClickHouse 이전의 유일한 담당이자 블루/그린과 GitOps 전환 리드로 kubectl과 system 테이블로 직접 디버깅하며 전환 시점을 판단했습니다.

파고든 원리

상태를 가진 것은 "떠 있다"보다 "같은 데이터로 되돌릴 수 있다"를 먼저 증명해야 한다고 생각했습니다. Keeper는 Raft 과반이 살아야 쓰기를 받아 3대를 존 a, b, c에 나눴습니다. ReplicatedMergeTree는 INSERT 블록의 해시(또는 dedup 토큰)를 Keeper에 남겨 같은 블록을 다시 쓰지 않으므로, 같은 청크를 다시 돌려도 한 번 넣은 것과 같습니다. 여기에 insert_quorum=2를 걸면 두 레플리카가 모두 받아야 성공으로 봐 사본이 어긋나지 않습니다. 레플리카 하나가 빠지면 쓰기가 멈추지만, 앞단 Kafka가 버퍼라 사본 하나만 조용히 남는 것보다 낫다고 판단했습니다.

설계 결정

선택버린 대안이유
트래픽가중치 5% → 기존 쪽 롤백 → 100%—되돌림부터 확인. 공개 전환 몇 시간 전 새벽 점검에서 기존 쪽과 새 쪽이 staging 공유 DB 연결 한도를 함께 잡아 권한 서비스가 뜨지 못하자, 서비스별 연결 예산을 나눈 뒤 그날 오후 진행

관측과 SRE 에이전트

한 줄5분마다 PromQL 28개를 읽어 감지 5종으로 사건을 만들고, AI가 저장된 근거에 묶인 1차 진단을 남긴 뒤 P1은 스레드, P2는 평일 17시 요약으로 보내는 사내 SRE 서비스를 올렸습니다. P0는 기존 독립 호출 경로에 두었고 복구는 모두 사람이 승인합니다.

왜, 내 몫

경로가 바뀌자 Pod Ready나 lag 하나로 정상이나 유실을 단정하는 오판이 생길 수 있었고, 신호는 많은데 사람이 판단할 장애는 드물었습니다(heartbeat 경보는 먼저 클러스터 밖으로 뺐습니다). 등급 정책, 원장과 권한 구조, 배포와 인수, 롤백 판단을 맡은 단독 프로젝트이고 사내에서 운영 중인 서비스입니다.

파고든 원리

Durable Object 하나는 요청을 한 번에 하나씩 처리하고, 내장 SQLite 트랜잭션은 그 안에서 원자적입니다. 그래서 조직별 DO를 사건 원장으로 두면 락 없이 "중복 제거 → 사건 갱신 → 작업 → 보낼 의도"를 한 번에 기록할 수 있지만, 요청 하나가 무거워지면 뒤 요청이 모두 기다립니다. Queue는 최소 한 번 전달이라 트랜잭션에는 보낼 의도(outbox)만 남기고, 소비자는 작업마다 매긴 번호로 중복 전달과 늦게 끝난 모델 응답을 걸러 냅니다. 빈 응답을 0으로 채우면 멈춘 경로가 조용한 경로처럼 보인다고 생각했습니다.

설계 결정

선택버린 대안이유
원장조직별 SQLite DO + Queue + alarm—사건 상태와 전송 의도를 한 트랜잭션으로 묶기 위해

왜, 내 몫

월드랜드 체인 위 GPU 렌탈 마켓인데 머신마다 설치 상태가 달라 한 대 붙이는 데 사람 손이 계속 들어갔고, 렌탈이 없을 때는 같은 GPU에서 월드랜드 마이닝 노드를 돌려야 했습니다. Hub 백엔드(커밋 94개 중 93개)와 노드 SDK(월드랜드 공식 org에 커밋 12개), 렌탈 컨트랙트를 맡았습니다(SDK 원형과 컨트롤 플레인 구축, 마이닝 이미지는 팀원).

파고든 원리

새 노드는 처음에 API 서버를 믿을 근거가 없습니다. kubeadm join은 bootstrap token으로 서명된 cluster-info를 받아 그 안의 CA가 --discovery-token-ca-cert-hash와 맞는지 확인해 CA를 고정하고, 같은 토큰으로 kubelet 인증서를 받습니다(TLS bootstrap). 이 해시는 인증서 전체 대신 공개키 필드(SPKI)로 계산해 같은 키로 재발급된 CA에도 맞고, Hub도 그 필드로 계산하게 했습니다. 또 nvidia.com/gpu만으로는 마이닝에 묶인 GPU를 알 수 없어 마이닝분을 따로 빼야 했고, Hub가 재시작해도 클러스터 사실에서 다시 셀 수 있어야 한다고 생각했습니다.

선택버린 대안이유
