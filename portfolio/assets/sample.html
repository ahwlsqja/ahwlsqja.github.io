01상황과 역할

기존 경로는 세션 집계를 ClickHouse 안의 갱신 뷰와 Materialized View로 만들었습니다. 9월 말 사람 세션 커버리지가 사흘 사이 약 60%에서 30%로 떨어졌습니다.

관리형 ClickHouse 해지도 10월 말로 정해져 있었습니다. 새 클러스터에는 기존 뷰 체인을 옮기지 않기로 해서, 세션 집계를 맡을 곳이 따로 필요했습니다.

맡은 일
아키텍처 설계와 기술 선택, Flink 잡과 Go 수신 서버, Go 적재기 구현, 전환 판단
범위 밖
방문자 신원 계산은 별도 배치가 맡습니다.

02해결 과정

  1. Kafka를 버퍼이자 재처리 원천으로 두었습니다

    원본 토픽은 12 파티션에 30일 보존으로 잡았습니다. 파티션 키는 (고객사, 세션)입니다. 한 세션의 순서를 지키면서 부하를 고르게 나누기 위해서입니다.

    Cloudflare Queues만 쓰는 구조는 소비하면 메시지가 사라져 다시 읽을 수 없어서 쓰지 않았습니다.
  2. 세션 상태는 Flink가 들고 중복을 지웁니다

    SDK가 최대 7일까지 다시 보내므로 중복은 반드시 생깁니다. 세션 상태 안에 이벤트 ID를 7일 동안 두고 같은 이벤트는 버렸습니다.

    Go 소비자가 직접 세션을 계산하는 쪽은 더 쌌지만, 키 상태와 타이머, 체크포인트를 다시 만들어야 했습니다.
  3. 적재가 확인된 뒤에만 오프셋을 확정합니다

    적재 구간을 먼저 기록하고, 두 레플리카에 쓴 뒤, Kafka 오프셋을 확정했습니다. 같은 구간을 다시 넣어도 같은 토큰이라 중복으로 쌓이지 않습니다.

남은 일Flink 롤백 절차는 staging에서만 실행했습니다. 운영에서 실행한 적은 없습니다.

04트러블슈팅

T-01

미러링 첫날 사본이 약 0.2% 빠지는 문제

문제
기존 경로에는 있고 새 경로에는 없는 이벤트가 약 0.2% 나왔습니다. 실패 로그도 DLQ 기록도 없었습니다.
원인
빠진 이벤트는 모두 페이지를 떠날 때 나가는 이벤트였습니다. 클라이언트가 먼저 연결을 끊으면, 기존 경로를 기다린 뒤에 거는 waitUntil 줄까지 가지 못했습니다.
해결
사본 전송을 기존 경로를 기다리기 전에 waitUntil로 걸도록 순서를 바꿨습니다.
결과
배포 뒤 약 4천 건 대조에서 누락 0건이었습니다.
